# 7 系统架构 · 租户并发

## 目标

一致性由“事实如何成为事实”保证，而不是由“谁独占租户”保证。一个租户内：

- 读取不等待写入，也不等待后台工作；每次读取看到一个完整的已应用位置。
- 决定（授权、规则、拥有者 Decide）在不可变映像上计算，不持有车道。
- 车道只包住“验证基准位置 → 提交 → 应用 → 发布映像”，持有时间以毫秒计。
- 接受结果的格式、重放语义、幂等与隔离规则不变；历史字节不变。

本文是 [README §7.3](README.md#73-写入路径)、[§7.4](README.md#74-读取路径) 的并发规格；两处的步骤顺序不变，本文规定每一步在哪把锁里、看哪个位置。

## 规则

- C-R1 租户仍是唯一的提交序列：一个租户的接受结果按位置严格递增，同一时刻只有一个提交者。不引入对象锁、行锁、Actor、消息队列、分布式事务或工作流引擎。
- C-R2 车道只做提交：车道内只允许基准校验、`AppendAccepted`、从已提交字节应用、发布映像、隔离判定。网络、外部进程、构建、模型调用、全量扫描、`sleep`、等待其他锁都不得在车道内。
- C-R3 读取经映像：协调读取取最新已发布映像，不取车道。映像发布后不可变；任何读取不得触达映像之外的可变租户状态。
- C-R4 决定是暂定的：决定在映像的分叉上计算，带基准位置；只有在车道内基准等于已应用位置时才提交。基准落后即作废重算，不做部分合并。
- C-R5 有界进展：同一决定的乐观重算至多 2 次；仍冲突则在车道内决定一次（即今日行为）。任何路径都不会饿死，最坏情况不差于今日。
- C-R6 外部 I/O 两段化：先以接受结果预留（reserve / prepare），在车道外调用，再以接受结果结算（settle / consume）。决定本身只读预留与已准备的输入，不发起 I/O。
- C-R7 不以超时、重启、换进程或给锁加超时作为修复；慢操作按 C-R2 移出车道。
- C-R8 一个实现：读取映像就是现有记录投影的不可变发布，不新建“从 SQL 直接读”的第二条读取或授权路径；乐观校验在内核提交处实现一次，拥有者不写并发代码。
- C-R9 进程安全优先：Go 的映射并发读写会使整个宿主崩溃（影响所有租户）。任何移出车道的读取或决定，先证明它触达的状态在映像内或不可变，并在 `-race` 下通过 K13。

## 规格

### C1 三段

```
读取：  映像 N ──────────────► 结果（同一位置 N；SQL 视图校验 = N）
决定：  映像 N ─► 分叉 ─► Decide/授权/规则 ─► 待提交结果(basis=N)
提交：  [车道] applied==N ? 追加→应用→发布映像 N+1 : 冲突
后台：  预留(接受) ─► 车道外 I/O ─► 结算(接受)
```

### C2 车道

| 项 | 规格 |
|---|---|
| 实现 | `kernel.Lane` 是容量 1 的通道信号量，等待按到达顺序；`Hold(ctx, holder)` 在 `ctx` 结束时放弃排队并返回错误；`Lock()` 等价于不可取消的 `Hold`；释放未持有的车道直接 panic |
| 持有者标签 | 未指定时取调用函数名（如 `host.Tenant.submit`）；HTTP 协调读取用路由模式；后台工作用 `work`。标签只有代码位置与路由模式两类取值，不含 ID |
| 预算 | 单次持有超过 200 ms 记一条日志（tenant、holder、时长），并作为“最近一次慢持有”出现在健康读取中；不打断执行 |
| 调用方上下文 | HTTP 协调读取把请求 `ctx` 传给独立读取范围与 SQL；需要回退车道时，客户端断开即退出排队 |
| HTTP 响应 | `rt.recordRead` 在读取范围内写入缓冲，结束范围后才写网络；文件与媒体在读取范围内鉴权、经 `outsideLane` 在范围外流式传输 |
| 诊断 | 车道状态（持有者、持有时长、等待数）用原子值读取，不取车道；`/v1/health` 的观测存储探测与指标采集都不在车道内 |
| 车道内禁止 | C-R2 所列；违反由持有预算日志暴露，修正方式是移出车道，不是放宽预算 |

### C3 读取映像

映像是某个已应用位置 N 上、读取路径所需全部租户状态的不可变快照：

| 内容 | 来源 | 不可变方式 |
|---|---|---|
| 记录投影各类型的行与派生索引 | `kernel/records`（`Index[*Row]` 已是路径复制持久树） | 发布时取根；应用只生成新根 |
| 当前范围与 SQL 来源行的位置 | `records.Current()` | 映像记录 N；SQL 读取经 C4 校验 |
| 授权上下文：成员、团队、许可、标记索引、项目授权 | `services/security`、`host/markings.go` | 发布时冻结或改为持久结构 |
| 资源目录与工作状态 | `host/resource_directory.go` | 同上 |
| 拥有者命名读取所需的账本状态 | 各 `platform.Ledger` | 生产拥有者全部实现 `ReadForkApp`；未实现的测试或扩展拥有者回退车道 |
| 已应用位置、隔离标记、业务停止标记 | `Tenant` | 原子值 |

- 发布：车道内应用完成后，以原子指针替换“当前映像”。读取者 `Load` 一次，整次读取只用这一份。没有状态变化的持有不重复发布；状态变化以接受轮次、定义与记录代数、工作通知和 SQL 位置判定。
- 实时刷新：数据版本与通知在映像发布后推进；查询版本读取该映像的记录代数，不能提前读取活动投影。工作通知可即时发出，发布映像后再次唤醒，并把已发布工作版本纳入工作查询版本。
- 缓存：同一映像复用原有有界、互斥保护的元数据缓存与生效标记索引；标记缓存只用于未修改的映像记录，暂存决定仍按自己的记录代数重建。记录和定义代数未变时，新工作通知不重建标记图。按次读取拥有独立错误与 SQL 视图，不重复构造同一映像的目录。
- 映像内容清单写在一处（`host` 的映像构造函数），读取闭包只经它取状态；新增读取依赖必须先加进清单。
- 前提是读取范围按次持有：一次读取的 SQL 视图、读取错误和追踪上下文属于这次读取的值，经调用者传递，不再是租户级字段；在此之前任何两次读取都不能并发。
- `host/read_image.go` 是状态清单与唯一构造处：复用持久记录根、分叉拥有者状态与账本，复制控制、发布、授权、通知及运行前提；分叉的拥有者重新绑定该范围的 Host。`runtime.ReadScoped` 显式表明已有范围，不以租户中恰好打开了某个 SQL 视图来推断当前调用者持有范围。
- 会话、个人令牌列表、令牌的一次性密钥交付与连接器心跳使用原拥有者，由其自身互斥保护；它们是即时状态，不从已接受位置的映像复制或消费。Agent 的在途标记只在原拥有者领取与释放，映像只列出待执行轮次，不用复制的在途标记决定是否执行。索引同步、上传清理等派生状态修改由源拥有者执行，记录与授权仍从映像读取。
- 内存：持久结构共享未改动部分；旧映像随最后一个读取者释放。不得为发布深拷贝全量行。

### C4 读取一致性

SQL 来源行仍从 PostgreSQL 可重复读事务读取：

1. 取映像 N。
2. 开启只读可重复读事务，第一条语句读 `runtime_tenants.seq` 得到 S（固定该事务快照）。
3. S = N：一致，执行读取。
4. S > N：已有更新的提交尚未发布映像；关闭事务，等待映像 ≥ S 发布（上限 50 ms）后重试，至多 2 次；仍不一致则取车道读一次（今日行为）。
5. S < N：不可能出现在健康租户中；隔离租户（与今日 `StatePositionError` 同义）。

读取结束不再检查“内存应用位置 = SQL 位置”，因为读取不再持有车道；该检查移到车道内应用完成处（C5）。

### C5 决定与提交

| 步骤 | 位置 | 规格 |
|---|---|---|
| 准入 | 车道外 | 租户、主体、隔离、业务停止、模式、项目角色边界（`submit` 前半段） |
| 幂等预查 | 车道外，映像 N | 命中已提交答案直接返回；未命中继续（提交时再查一次） |
| 决定 | 车道外，映像 N 的分叉 | `newStagedDecisionOn(image.records.Fork())`；序列、通知、连接器状态取自映像；产出待提交结果与 `basis=N`；拒绝同样待提交 |
| 校验 | 车道内 | `applied == basis` 才继续；否则释放车道、按 C-R5 重算 |
| 提交 | 车道内 | `AppendAccepted` 不变（SQL 事务内的 `statePosition == seq-1` 检查保留为最后防线）；幂等在 SQL 中二次确认 |
| 应用与发布 | 车道内 | 从已提交字节应用；应用后断言 SQL 位置 = 内存位置，不一致即隔离；发布映像 N+1 |
| 事件与副作用 | 车道外 | 入队投递、自动化、外部副作用 |

- `host/optimistic_decision.go` 是前台提交与后台任务的共用实现：准备阶段在原接受边界产出原格式的待提交字节，不应用、不追加；基准有效时复用原提交和应用函数。早期拒绝与幂等命中也经过相同基准校验。发布与激活、环境晋级、分支合并、组合提交、集成与观测结算、模型预留与用量、Agent 步骤、Compute 领取与结算、连续 Flow 批次与清理确认均复用此处；各自在原接受边界捕获原格式字节，再调用原应用函数，不引入按信封种类分发的新写入网关。
- 内存模式没有 SQL 位置时，以接受轮次校验；定义、记录代数与系统投影一并校验；工作选择另校验调度代数，不让空作业的调度推进使业务动作反复作废。任务的配额与轮转、无变化作业的下次运行时间只在基准有效后更新；读取映像保留这些内存运行状态，不写成伪造历史。
- 校验粒度是整个租户位置：任何插入的提交都使待提交结果作废。这自然覆盖跨对象唯一性、库存汇总、权限撤销、包退役等约束，不需要拥有者声明读集合。
- 细粒度校验（对象版本、读集合）不在本规格内；只有在 C8 指标显示冲突重算成为瓶颈时，才另写规格，由内核统一记录读集合，拥有者不手写。
- C-R5 的车道回退仍建立独立的当前状态分叉并捕获待提交结果，再应用到源；不让嵌套读取重新获取同一车道。未实现 `ReadForkApp` 的测试或扩展拥有者保留旧串行执行。
- 决定必须确定且无副作用：同一映像、同一提交得到同一待提交字节。依赖外部结果的决定只读 C-R6 的预留或准备输入（现有 `preparedOperationInput`、模型预留即此模式）。

### C6 后台工作

- `Tenant.Round` 每个任务、每个作业在映像分叉上决定（`WorkLoop.Round(now, 1)`），提交各取一次车道，任务之间前台提交可以进入。冲突与回退复用 C5；无变化作业只推进内存调度时间，不追加空接受结果。
- `WorkLoop` 的配额、轮转与 `opsMu` 不变；轮转按任务推进。
- 投递、同步、构建、管道运行、智能体步骤：外部部分按 C-R6 在车道外执行；结果以接受结果回到 C5。
- 调度器按租户轮转不变；一个租户的长任务只延迟该租户的下一任务，不占用其他租户的车道。

| 路径 | 车道外 | 车道内 |
|---|---|---|
| 源、管道与投影 | 读取接受定义与输入、转换、凭据解析、网络与文件字节 | 校验基准并提交结果 |
| Dispatch、Confirmation、Observation | 扫描待办、准入、读取凭据、取证与规则求值；回读节奏由独立互斥保护 | 校验最新版本与权限基准、结算 |
| Agent 与模型 | `WithAgentRead` 只在回调内提供读取范围；提示词与工具读取在映像内，模型与知识取证在车道外 | 预留、步骤与用量的提交和应用 |
| 连续 Flow | 在独立读取范围中建立计划并完成帧/输入准备，范围结束后不得再用其 Caller；字节封存、读取、退役及重试等待均不取车道 | 将准备结果绑定到本次决定的拥有者账本，校验实例、源配置与权限后提交 |
| 知识索引 | 索引自己的同步锁串行化加载与更新；只在源记录代数已发布后领取 dirty，读取失败重新标脏；读取文档字节与嵌入不取车道 | 无索引构建 |
| 上传清理 | 扫描包含归档的附件与媒体版本引用；预留后删除字节，失败解除标记等待重试 | 验证扫描基准并标记待删除、推进运行代数 |

- 上传写入与删除按哈希互斥：写入期间不选作清理，待删除期间不接受重传或新引用；附件决定记录它检查过的哈希，提交时再次检查待删除标记。已引用与归档文件保留；删除成功后重新上传可正常引用。不为临时上传状态制造接受历史。
- `ApplicationRuntimeOf`、应用运行列表与诊断在宿主建立同一个读取范围；应用服务只消费传入上下文，不再持有或切换宿主车道。

### C7 启动、快照、隔离与重放

- 启动恢复、快照保存、维护操作仍可整段持有车道（holder 为 `startup`、`snapshot`、`admin:*`），需要等待恢复位置的读取按 C4 第 4 步回退；已有一致映像的读取继续使用原位置。这些路径不在前台请求热路径上。
- 重放只应用已接受映像（README R6），与本规格无关；K1 不变。
- 隔离判定集中在两处：车道内应用后位置断言（C5）与读取 S < N（C4）。

车道调用的剩余归属：C5 提交与有界回退；C4 未发布或不支持分叉的读取回退；本节的启动迁移、资源目录初始化、系统投影恢复、快照与重放；宿主管理的生命周期、支持与迁移接受；封存完成后的摘要登记与映像发布。候选、制品和跨环境发布元数据直接读取已发布映像；无映像时只在启动或隔离诊断中串行读取。隔离健康响应也先缓冲，释放车道后再写网络。普通工作台读取、授权扫描、批次准备、模型调用和对象存储字节不再以直接获取车道包住整个函数。

| 指标 | 类型 | 标签 |
|---|---|---|
| `platform.lane.wait` | 直方图（秒） | tenant、holder |
| `platform.lane.hold` | 直方图（秒） | tenant、holder |
| `platform.lane.waiters` | 当前值 | tenant |
| `platform.lane.held` | 当前值（秒），当前持有者已持有时长 | tenant |

## 现存差距

- 扩展：未实现 `ReadForkApp` 的测试或扩展拥有者仍使用串行读取与决定；生产拥有者已全部纳入映像。新增拥有者必须实现该契约后才能获得并发读取。
- 预算：200 ms 是诊断预算，不是强制超时。大定义集的应用与映像发布、启动恢复仍可能超过预算，持续记录持有者与时长；不通过放宽预算或取消提交掩盖耗时。
