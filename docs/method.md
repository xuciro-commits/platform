# 开发方法

## 目标

全部代码由 AI 代理编写，负责人只有一人。稀缺的是负责人的注意力和代理的上下文，不是写代码的速度；最常见的失败是膨胀：每次会话各加一层防御、一个新词、一条旁路，单看都合理，合起来没人看得懂。本文规定人与代理怎样分工、代理按什么原则作决定，使一批没人盯着的工作也让仓库变好。文档怎样存放见 [README](README.md)，一批的操作步骤见技能 `platform-batch`。

## 规则

- R1 负责人掌舵，代理执行。负责人决定意图、承重决定（[1-enterprise §1.10](1-enterprise.md)）和有持久代价的取舍，并在浏览器判断观感；顺序、设计、实现、验证由代理决定并负责（人的注意力只花在机器判断不了的事上）。
- R2 仓库是唯一记录。代理读不到的决定等于不存在：会话里定下的事，同一批写进规范或路线图。
- R3 诊断与施工分开。架构代理（主会话，最强的模型）找病灶、定方案、写工单、审阅结果；方案已定的施工派给实现代理（判断贵、施工便宜；施工占满主会话的上下文，判断就变差）。分工是判断，不是流程：哪一步派出去由架构代理按 [亲手做还是派出去](#亲手做还是派出去) 决定。
- R4 工单是分派的单位。工单写明目标、所实现的规范小节、范围内与范围外的文件、要删除的路径、完成标准（命令与期望结果）和汇报内容。实现代理发现方案行不通时停下汇报，不自行改设计。
- R5 最小完整改动。按顺序取第一个可行的：不需要存在就不写；仓库里已有就复用；标准库或平台已有就用；已批准的依赖；最后才是新代码。删除优先于新增。不为只有一个实现的东西写接口，不加没人设置的选项，不留兼容分支。省的是方案，不是改动本身：调用方、验收用例和规范一并改完。
- R6 防御只在信任边界。校验放在外部输入进入的地方：HTTP 入口、产品包导入、租户扩展与外部系统的返回、日志装载时的纪元校验。边界之内信任类型与不变量：不重复校验，不为不会出现的状态写分支，不吞掉错误换成默认值。不变量被破坏时在内核的唯一位置失败（[7-system §7.3](7-system/README.md)），不在各调用点分别兜底。判断方法：说不出哪个输入能走到这个分支，它就是该删的防御。
- R7 深模块。包对外的接口要小，背后的行为要多。用删除测试判断：删掉它，复杂度随之消失，说明它只是转手；复杂度散到各调用方，说明它有用。只有一个实现的接口不是接缝，有两个才是。测试只经模块的对外接口（因此只写内核不变量和黄金路径验收）。
- R8 约束进机器。同一条规则被违反两次，就改成钩子、棘轮或不变量（文字提醒到下一次会话就失效）。检查的报错写明怎样改。
- R9 熵只减不增。每批删除它替换的东西；形状基线只调低；每个里程碑结束做一次架构诊断（技能 `platform-diagnose`），结果是规范差距和路线图条目，不是报告。
- R10 验证才算完成。每张工单、每一批都有机器可判的完成标准（[7-system/verification](7-system/verification.md)）；汇报写明没有验证的部分。
- R11 上下文是预算。常驻内容极小，规范按“何时读”取用；大范围阅读派只读子代理，只带回结论；状态写在路线图里，不留在对话里。

## 规格

### 角色

| 角色 | 谁 | 做 | 不做 |
|---|---|---|---|
| 负责人 | 人 | 意图、承重决定、有持久代价的取舍、界面走查 | 排顺序、逐行审代码 |
| 架构代理 | 主会话 | 选批次、诊断、定方案、写工单、亲手做关键改动、审阅差异、收尾并提交 | 把判断派出去 |
| 实现代理 | `.claude/agents/implementer.md`，Sonnet，在本地检出工作 | 按工单施工，运行完成标准，如实汇报 | 改设计、改规范的规则、提交 |
| 只读子代理 | 内置的探查与评审 | 大范围查找；以全新上下文对照规范审阅大的差异 | 修改文件 |

不设更多固定角色（角色越多，交接越多；需要时由架构代理临时分派）。

### 亲手做还是派出去

| 架构代理亲手做 | 派给实现代理 |
|---|---|
| 改变内核语义、并发、存储格式或公开接口 | 方案已定的搬迁、改名、删除 |
| 要在两种设计之间取舍 | 文件范围能列全、完成标准是命令 |
| 规范的规则与规格 | 脚本、检查和验收用例 |
| 审阅实现代理的差异；内核路径逐行读 | 互不相交的文件集合可以并行 |
| 一两处就能改完的小事（写工单比动手慢） | |

### 何时问负责人

只在这些事上停下来问：改动承重决定；冻结或推进格式纪元；新依赖；增删工具应用或资源类型；删除用户可见的能力；两份规范冲突且两边都有理由。其余自行决定，在汇报里说明所作的选择。

### 自治阶梯

代理能独立做多少，取决于机器能判定多少。级别靠补齐前提来提高，不靠放松检查。

| 级 | 代理独立完成 | 负责人做 | 前提 |
|---|---|---|---|
| 1 值守批次 | 一批：读规范、实现、检查、提交、推送 | 给每批起头，走查界面 | `make check` 与提交钩子 |
| 2 连续批次 | 按路线图顺序连续完成多批，只在“何时问负责人”的事项上停 | 定里程碑，抽查结果，走查界面 | 形状棘轮；验收覆盖改动的任务路径；内核差异有全新上下文的评审 |
| 3 例行清理 | 定期扫描漂移与膨胀，自行开清理批次 | 看差距与基线的走向 | 2 级稳定；清理批次只删不增，由棘轮证明 |
| 4 平台构建平台 | 智能体在构建租户里经平台工具产出行业应用，不手写产品包 JSON | 验收应用 | 自举一级；智能体的工具覆盖 Ontology Manager、Workshop、Logic、DevOps 的编辑动作 |

第 4 级是 [1-enterprise §1.1](1-enterprise.md) 第三项下注的落点：写宿主代码的是编码代理，做行业应用的应当是平台里的智能体，两者走的是同一条接受路径。

## 现存差距

- 自治级别（规格“自治阶梯”，第 7 层）：处在 1 级。升到 2 级还缺：验收只跑在内存宿主（[7-system/verification 现存差距](7-system/verification.md#现存差距)）；内核差异的评审靠架构代理自觉，没有检查。
- 边界之内的防御（R6，第 7 层）：重复的幂等判断、散在各处的隔离调用、以类型断言探测能力，位置见 [7-system 现存差距](7-system/README.md#现存差距)。
- 例行清理（R9）：没有定期的诊断，靠负责人提起。
