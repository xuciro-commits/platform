# 测试

怎么通过应用测试平台，以及每个场景怎么走。年度目标与验收标准在 [Platform.md](Platform.md) §10.6，目标架构与路线分别在 §10.3、§10.5；本文规定怎样取得验收证据，不另列一套年度指标。下一阶段的设计决定见 [ADR-0031](ADR/0031-ai-application-platform.md)。环境（启动、地址、账号、接入外部系统要填什么）在 [deploy/local/README.md](../deploy/local/README.md)；账号按"一个人一份职责"分好了，测权限差别时换人登录，要同时看两个人就用一个普通窗口加一个无痕窗口。

固定工具链的证明检查入口是 `scripts/verify.sh formal`；规范、定理、向量与实现测试的对应及可信前提在 [K4 证明模型](../contract/lean/README.md)。它用于检查有界内核模型，不替代下方 UI 路线、恢复演练或负责人验收。

## 测的是什么

**应用是平台能力的探针**（Intent.md，AGENTS.md 规则 12）。探针可以是一条完整的 FDE 构建、交付和业务操作闭环：从接入客户数据、建立语义、组合页面与业务和 AI 逻辑，到测试发布、人员使用和后续升级。前端质量、客户自己构建应用和行业交付效率都是平台的被测能力，必须完整可用。制造、财务、酒店、请假是让这些能力在真实工作中接受检验的载体；行业细节增加到足以验证平台保证为止。

下方 C1–C35 和 S1–S6 记录现有能力及 UI 路径。表中的保证是验收要求，历史走通和已有自动测试不代表当前版本已重新通过，更不代表组合后的权限、规模或构建体验已完备。下一阶段的方法单独标为**待实现、待验收**；C25–C26 的已安装定义和页面路线通过浏览器自动测试，不代表客户构建器或视觉质量已验收。

发现问题时按顺序问两句：

1. **换一个应用，这个问题还会不会出现？** 会，就是平台的问题：记进 [WorkQueue.md](WorkQueue.md)，马上在平台里修（修的是表里"失败时修哪里"那一栏的主人），不在出问题的应用里打补丁。
2. **不会的话：要证明或推翻某个平台保证，是否必须有这层业务深度？** 不是，就记进工作队列"应用深度"那一项，这一轮不做（比如 SFC 数量怎么拆、生产成本怎么结转、赢单后怎么退房）。

另一类问题是**能力逃逸**（AGENTS.md 规则 11）：应用自己做了一份平台已经有、或者本该由平台拥有的能力（自己画表格和面板、自己管签名和审批、自己做时间线）。它往往不会让测试失败，却会让同一件事有两种行为。`scripts/escapes.sh` 列出已知的逃逸并阻止新增；测试中看到"这个应用的这块和别的应用长得不一样、做法不一样"，就是线索，记下来。

## 规则

1. **按能力测，由场景承载，证据对应保证。** 平台能力表是既有能力的主表：每项能力写明平台保证、在哪个场景的哪一步测、失败时修哪里。场景是一段业务，路上自然经过多项能力；场景里每一步开头的 `[C…]` 标出它测的能力。跨入口权限、客户扩展、第二行业复用等组合保证必须覆盖各自的路径，不能用单个页面走通代替。
2. **优先级**：P0 每轮都要走完，阻断发布；P1 能力做完或改动过时走；P2 暂缓，条件具备（外部系统、向量模型、采集器）再走。
3. **具体 UI 路径在界面上走通过，才记为已走通场景。** 待实现能力先在本文写验收方法与证据要求，明确标注未验收，落地后再补真实路径。演练脚本（`deploy/local/rehearse.sh`）和接口测试不能代替 UI 操作；浏览器自动测试也不能单独证明视觉质量和使用感受。
4. **每个应用先能自己干**（ADR-0025 D3）：涉及外部系统的步骤，都有一步说明不接外部系统时怎么走。
5. **失败也是场景的一部分**：被拒绝时写明看到的原因；超时、没人处理时，谁在哪里看到了什么。
6. 标【自动】的步骤已写成浏览器测试（`web/e2e`，Playwright），`scripts/verify.sh web` 和 CI 每次都会跑；其余靠人走。
7. 业务细节只写到能力需要的程度：步骤里出现的数量、工序、科目只是数据，不是被测对象。
