负责人判定现状「视觉是原型、交互反智、边界不清」，批准两条 change 并行推进，验收由负责人截图走查：

- 双线里程碑完成一批同步一批规范（sync-specs）；供暖交付（下节）中被重构直接修复的阻碍并入对应里程碑，不双线重复排。

## 2. 楼宇供暖与既有平台整理

围绕现有供暖应用的构建、发布、运行和维护任务修复实际阻碍与重复职责，不横向增加资产种类或新的工作台。

范围包括门禁；数据分发包括推送、看板报表与导出/API。系统上线、应用资产和缺口清单是同一次交付的三件产出。当前是开发阶段，平台工程先完成，真实使用不作为继续开发的前置条件。

`application.heating`、两份模拟配置和 Modbus 点表接入用于开发验证；客户实际上线、客户变更与第二城市记录保持未验证。规模优化先按确定的目标密度测量。

### MES 的保留范围

由未参与底层开发的 FDE 从空白项目构建、测试并升级：基础主数据、工艺与版本、生产计划/工单/拆批/派工、现场执行、异常与质量、生产追溯、资源约束、跨系统协同。设备能力匹配、返工限制与完工的关联变化由构建者声明，页面候选、服务端拒绝和 AI 共用原规则。平台开发者补底层能力，不能代替独立构建者的完成证据。

至少使用两套语义不同的工厂配置：装配场景要求多项设备能力；加工场景包含返工与外协确认。同一机制、同一组件，差异只在数据与配置。再做一次加字段、重命名和退役动作的模型升级，保留在途工单的原版本。

以下情况均不能算完成：

- MES 专用代码进入宿主、构建器或共享 UI，或把原 Go 行业规则搬到另一个客户代码包。
- 为通过任务而放宽约束、权限，或要求操作员输入服务端能够计算的数组下标等内部值。
- 构建业务时需要修改内核，或只在一个工厂配置成立。
- 原生实现与构建产物的接受、拒绝、记录变化或拒绝码不一致，却未明确判断是原实现错误还是构建能力缺失。

受阻时先复用已有能力；确属通用缺口则在本队列登记具体阻碍，在归属方补齐。需要新原语时，先证明它在第二种业务语义也成立，再修改契约与实现；不能在行业代码绕过后宣称完成。对照场景由原生实现和构建产物各做一遍，负责人实际操作并确认等价后才退出原实现；作者不能自行判定自己的实现等价。

分批生产协同继续保留：首批开工发送 start，每批良品/报废有独立 confirm 与稳定身份，上游分别保存累计、剩余、终结与入库事实，拒绝超量；答复丢失按本批键回读，不自动重发。沿原事务、Flow、Confirmation 与 `production.orders/2` 表达，不扩充原生行业执行器。旧整单 v1 只在仍有实际消费者时承担原责任；本次获准重建的原生测试数据不要求迁移。

## 队列规则

- 一次推进一块，块内按实际依赖迁移；已通过且未受影响的证据直接复用。
- 只有当前交付阻断、已确认回归或负责人明确的新目标才能入队。登记未来可能性不增加实施范围。
- 外部分支持续 Flow 候选不自动成为集成任务。
- 不在当前范围：XMI/UAF 实例导入、画布新形态、跨设备排布、更多连接器、行业交易/排产、插件市场、第二数据库、更多形式化证明。
- 旧 W0/W5 与 XXL/L 编号不恢复为另一套队列。
- 每次代码合入 main 后沿 AGENTS 的同步协议更新两台宿主，保留原数据卷。
