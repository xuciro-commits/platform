# 文档治理

本项目几乎全部代码由 AI 代理编写。文档的用途只有一个：让每一次会话在不读全仓的前提下做出与整体一致的决定。文档过多会污染上下文，过少会让每次会话各自发明规则；本文规定两者之间的平衡点。

## 1 原则

0. 规范领导代码。层级规范写的是目标设计，不迁就现有实现；代码与规范冲突时改代码，规范只在设计本身被推翻时修改。现有代码只用来衡量差距，写进“现存差距”。
1. 常驻层极小。每次会话都加载的只有 `AGENTS.md`（经 `CLAUDE.md` 导入）。其余一律按需：按路径触发的规则、按任务触发的技能、按“何时读”索引的层级规范。
2. 活文档只写目标状态与现存差距。不写背景故事、不写演进历史、不写“之前我们……”。历史只在 git。
3. 一个事实只在一处。其他地方链接，不复述。发现两处说法不一，以层级更低（更具体）的规范为准并立即合并。
4. 能执行的不写成文字。必须恒成立的规则交给钩子、生成器或验收用例；文字只写判断性的约束。
5. 同一变更同步更新。代码改变了某份规范描述的行为，同一提交更新该规范；提交前钩子按 `covers` 检查。
6. 只写代码推不出来的东西。目录结构、函数签名、字段列表能从代码读到的不抄进文档；文档写归属、边界、取舍、规则与理由。
7. 决定直接改规范。规则后用括注写一句“为什么”；需要时补一句“不采用 X，因为 Y”。被推翻的规则直接改写，不保留旧版。

## 2 文档类型

| 类型 | 位置 | 加载 | 写什么 | 不写什么 | 预算 |
|---|---|---|---|---|---|
| 宪章 | `AGENTS.md` | 每次 | 使命一句、文档索引、硬规则、命令、工作方式（几行，细节链接技能）、易错点 | 架构说明、目录导览 | ≤150 行 |
| 层级规范 | `docs/1-…7-*` | 按“何时读” | 该层的目标、规则、规格、差距 | 历史、实现细节复述 | 每文件 ≤400 行，超出按主题拆目录 |
| 路线图 | `docs/roadmap.md` | 每批开始与结束 | 终局、阶段、当前批次、待办、已知漂移 | 已完成批次的细节 | ≤250 行 |
| 术语表 | `docs/glossary.md` | 命名时 | 术语、中英文、定义、所属层 | 用法教程 | 一词一行 |
| 路径规则 | `.claude/rules/*.md` | 编辑匹配路径时 | 该区域必须遵守的短规则与要读的规范 | 流程步骤 | ≤60 行 |
| 技能 | `.claude/skills/*/SKILL.md` | 任务匹配时 | 可重复的操作流程与检查清单 | 规范本身（链接到规范） | ≤300 行 |
| 子代理 | `.claude/agents/*.md` | 委派时 | 角色、工具、模型、交付格式 | 项目规则（它们也加载 `AGENTS.md`） | ≤40 行 |
| 钩子 | `.claude/settings.json`、`.claude/hooks/` | 自动 | 确定性检查 | 判断性规则 | — |

不再建立的文档：ADR 目录、按变更归档的 spec、审计报告、评审报告、会议纪要、进度日志。它们是历史，历史在 git 与提交说明里。

## 3 层级规范

七个层级各有一份规范（或一个目录）。层级只是分工，不是流程：一次变更可能同时改几层，各层只写本层的事实。

| 层级 | 文件 | 回答的问题 |
|---|---|---|
| 1 企业架构 | `1-enterprise.md` | 平台为谁、终局是什么、业务/应用/数据/技术怎样组合、质量目标与约束 |
| 2 产品体系 | `2-product.md` | 有哪些产品、每项能力归谁、边界在哪、平台与行业应用如何分工 |
| 3 信息架构 | `3-information.md` | 导航、资源分类、页面层级、路由、命名、搜索 |
| 4 交互设计 | `4-interaction/` | 页面原型、布局、编辑与保存模型、模式规格、各工作台布局 |
| 5 用户体验 | `5-experience.md` | 角色与任务、任务路径、可发现性、效率、文案、评估方法 |
| 6 领域架构 | `6-domain/` | 资源内核、本体、数据、动作与函数、规则、安全、变更与交付 |
| 7 系统架构 | `7-system/` | 进程与包边界、写入与读取路径、运行机制、前端架构、验证 |

### 3.1 文件头

每份层级规范以 YAML 文件头开始：

```yaml
---
level: 4 交互设计
covers: [web/packages/ui/src/**]
read-when: 新建或修改页面、面板、表单、表格、弹窗
---
```

- `covers`：该规范描述的代码路径。提交前钩子据此提醒同步更新。
- `read-when`：何时必须读它。`AGENTS.md` 的索引与之一致。

### 3.2 正文结构

1. 目标：一段话，说明本层要达成什么。
2. 规则：编号条目，用“必须 / 不得 / 只”表述；每条可被检查。理由放在括注里。
3. 规格：表格、清单、示意。写到实现者不必猜的程度。
4. 现存差距：代码与目标不一致之处，每条链接路线图编号；差距消除后删除该条。差距大不是降低目标的理由。
5. 相关：链接到相邻规范的具体小节。

规则编号在一份文件内稳定；引用时带文件名，如 `4-interaction R7`、`6-domain/security R4`。交互模式编号为 M1–M22；路线图编号为阶段 P1–P5 与条目 P2.1 等；二者不混用。

## 4 变更流程

完整流程见技能 `platform-batch`。与文档相关的只有三点：

1. 找不到唯一归属时，先改 `2-product.md`。
2. 改变规则或规格的变更，同一提交改规范；只是消除差距的，不改规则，只删差距条目。
3. 批次结束时路线图反映真实状态：完成的条目删除，新发现的差距入表。

## 5 保鲜

- 提交前钩子：相对 HEAD 改动的代码命中某规范 `covers` 而该规范未改时，第一次提交被拦下并列出规范；确认无需修改后原样重试即可通过。
- 每个阶段结束做一次文档审计：删除过期条目，合并重复，检查预算；结果直接体现在文档变更里，不写审计报告。
- 路线图条目完成即删除，不保留“已完成”列表。

## 6 外部评审与记忆

- 外部评审是输入，不入库。逐条对照代码：采纳的写入规范或路线图，不采纳的在会话中说明理由。
- 项目知识（决定、约束、易错点、进度）只写进仓库。代理的私有记忆只存负责人的个人偏好。

## 7 角色分工

| 角色 | 承担 | 模型 |
|---|---|---|
| 负责人 | 方向、持久代价的决定、浏览器走查与观感判断 | — |
| 主代理 | 设计、规范、拆分批次、审查合并 | Opus |
| `implementer` | 按已设计的批次实现、检查、提交 | Sonnet |
| `reviewer` | 对照规范审查差异，只读 | Sonnet |
| Explore | 资料收集、代码定位，只读 | Haiku 或 Sonnet |

委派原则：资料收集与机械修改交给便宜的模型；需要取舍的设计留在主代理；独立审查用全新上下文的 `reviewer`。
