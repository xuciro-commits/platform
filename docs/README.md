# 文档

这个项目几乎全部由 AI 写成。文档只有一个用途：让每一次会话不读全仓，也能做出与整体一致的决定。
文档按问题分，每份都短；U 系列单列路线图，保留执行细节。

## 地图

| 想知道 | 读 |
|---|---|
| 项目为谁、凭什么赢、什么不做、哪些决定不能动 | [intent](intent.md) |
| 现在在哪、下一步做什么、什么先不碰 | [plan](plan.md) |
| U 系列后端收尾的细分工作与验收 | [roadmap](roadmap.md) |
| 系统由哪几块组成，写入、读取、发布各走哪条路 | [architecture](architecture.md) |
| 有哪些概念：资源、类型、对象、动作、权限、产品包 | [domain](domain.md) |
| Go 代码放在哪，守什么规矩 | [backend](backend.md) |
| 界面代码放在哪，新界面怎样做出来 | [frontend](frontend.md) |
| 用户看到什么结构，怎样操作，文字怎么写 | [ux](ux.md) |
| 界面该是什么观感，什么不许出现 | [design](design.md) |
| 一个东西该叫什么，中文怎么说 | [glossary](glossary.md) |

每次会话自动加载的只有仓库根的 `AGENTS.md`：硬规则、命令与易错点。其余按上表在需要时读，只读相关的一节。

## 文档的规矩

1. 只有地图里的文档。新内容写进已有的某一份；真要增加一份，先问负责人。
2. 规范写目标，代码与规范不一致时改代码；产品进度写在 plan，U 系列的进度和执行细节写在 roadmap。
3. 不写历史，不写“之前我们”。没做完的事写入对应规划，做完就删；历史在 git 里。
4. 一个事实只在一处，别处链接，不复述。
5. 只写代码里读不出来的东西：归属、边界、取舍、规则与理由。目录、函数签名、字段列表不抄进文档。
6. 冻结的东西不写文档。它的事实是代码与测试；解冻时再把规则写进来。
7. 写给会读但没时间的人：短句，常用词，一行一件事。
8. 代码改变了文档写着的行为，同一提交改文档。
9. 不入库的：评审报告、审计、会议纪要、进度日志、方案草稿和 U 系列以外的任务分解。外部评审逐条对照代码。

预算由 `make check` 核对：`docs/` 下只有地图中的文档；每份不超过 250 行，plan 不超过 150 行，`AGENTS.md` 不超过 120 行；
一行不超过 200 个字；没有“现存差距”一类的标题；文档与代理配置里提到的文档都存在。

## 谁决定什么

| 谁 | 决定 |
|---|---|
| 负责人 | 意图与承重决定；格式纪元；新依赖；删除用户看得见的能力；旗舰包与第一个客户；一个阶段过没过门槛；观感好不好 |
| 主会话 | 其余一切：顺序、设计、实现、验证、文档；并对结果负责 |

- 负责人不需要读代码。他看两样东西：plan 里的那一行，和浏览器里的界面。
- 主会话只在“只有负责人能决定”的事上停下来问；其余自己定，在汇报里说明所作的选择。

## 怎样干活

1. 一次一行。产品阶段从 plan 取，U 系列从 roadmap 取；做完、核对、提交、推送，再取下一行。
2. 先读后写。读这一行涉及的文档小节、实现与调用方；从根因解决；删掉被替换的旧路径。
3. 小事顺手修，大事进对应规划。路上发现的小缺陷在这一行里修掉；大的加成一行，不当场展开。
4. 核对了才算完。跑与改动对应的检查（命令在 `AGENTS.md`）；界面在浏览器里用真实数据看过。
   没跑的检查、没看的界面，汇报里照实说。
5. 汇报给人看，只说三件事：现在能做什么（附能点开的地址）、什么没做或没核对、要负责人决定什么。不贴过程。

## 分级执行

U 系列的切片和并行边界见 [roadmap](roadmap.md)，交付按本节执行。

学人的协同，学原理，不学形式。人靠信任与记忆协作；智能体没有信誉，也没有记忆，只能靠验收，和写进仓库的状态。
所以不设“规划、开发、测试”的岗位接力，不让代理之间开会，不养常设的团队。
留下的是人类协同里最硬的四样：写清楚的工单、单一的责任人、独立的验收、做不下去就停下上报。

| 级 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 负责人 | 人 | 意图、承重决定、阶段门槛、观感 | 读代码 |
| 主会话 | 最强的模型 | 设计契约与表现、拆工单、写验收、审差异、集成、提交 | 交得出去的体力活 |
| 执行者 | 代理 `builder`（中档模型），或负责人另开的便宜模型 | 一张工单：一个完整的切片，连同自测 | 设计、越界、提交 |
| 探查 | 只读代理（Claude Code 里是 `Explore`，最便宜的模型） | 找、盘点、对比，只带回结论 | 写任何文件 |
| 复核 | 代理 `critic`（强模型，干净的上下文） | 只看工单、差异与规则，挑错 | 看执行者的推理、改代码 |
| 验收 | 机器 | 检查、内核不变量、主干验收 | 看情面 |

分派像分级诊疗：按难度与风险交给够用的最低一级；疑难上转，方案定了再下转。

| 这件事 | 给谁 |
|---|---|
| 要判断：方案没定，或要动契约、表现、内核语义、文档 | 主会话自己做 |
| 已定：做什么、改哪里都清楚，有先例，验收能跑 | 执行者 |
| 定式：照一个例子填（入口声明、翻译、夹具、产品包里的资源） | 最便宜的执行者 |
| 只读：找文件、盘点用法、对比两处 | 探查 |
| 高风险：授权、内核、格式与纪元、删除与迁移、发布与安装 | 主会话做；或执行者做完，提交前过复核 |

纪律：

1. 工单是契约。写明目标、可改的文件、参照的例子、能跑的验收、不做什么。执行者没有别的上下文，工单要自己站得住。
2. 按上下文的边界拆，不按工种拆。一个执行者交付一个完整的切片；不搞“一个写、一个测、一个审”的接力。
3. 先有验收再派工。验收是能跑的命令或用例；说不出验收的事不派，主会话自己做。
4. 默认不拆。前后相依的步骤留在一个上下文里；交出去的活，要明显大于写工单与审差异的开销。
5. 拉绳。做不下去就停下，带着证据上报；同一条验收两次没过就上转一级。不绕过，不改检查，不扩大范围。
6. 一个集成者。只有主会话提交 `main`；执行者不提交。同时写的执行者至多两个，可改的文件互不相交；探查不限。
7. 状态只在仓库。plan、U 系列 roadmap 与提交记录当前状态；临时工单与汇报只存在于对话里。
8. 开工先看 `git status`：有来历不明的未提交改动，停下来告诉负责人，不接着写，不替别人提交，不整理。

执行者怎样做一张工单、主会话怎样写一张工单，在技能 `work-order`。

## 一行怎样算做完

- 负责人照 plan 那一行“做完你能看到”的描述，在浏览器里做得到。
- 检查通过；改到的行为有对应的文档改动；对应规划里这一行已经删掉。
- 没有留下第二条路：旧实现已删，没有兼容分支，没有开关，没有“以后再接上”的空壳。
- 已提交并推送。
