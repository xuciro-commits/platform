# 文档

这个项目几乎全部由 AI 写成。文档只有一个用途：让每一次会话不读全仓，也能做出与整体一致的决定。
文档按问题分，每份都短；当前阶段的细目见 [roadmap](roadmap.md)。

| 现在在哪、下一步做什么、什么先不碰 | [plan](plan.md) |

每次会话自动加载的只有仓库根的 `AGENTS.md`：硬规则、命令与易错点。其余按上表在需要时读，只读相关的一节。

## 文档的规矩

1. 只有地图里的文档。新内容写进已有的某一份；真要增加一份，先问负责人。
2. 规范写目标，代码与规范不一致时改代码；产品进度写在 plan，当前阶段的细目写在 roadmap。
3. 不写历史，不写“之前我们”。没做完的事写入对应规划，做完就删；历史在 git 里。
4. 一个事实只在一处，别处链接，不复述。
5. 只写代码里读不出来的东西：归属、边界、取舍、规则与理由。目录、函数签名、字段列表不抄进文档。
6. 冻结的东西不写文档。它的事实是代码与测试；解冻时再把规则写进来。
7. 写给会读但没时间的人：短句，常用词，一行一件事。
8. 代码改变了文档写着的行为，同一提交改文档。
9. 不入库的：评审报告、审计、会议纪要、进度日志、方案草稿；任务分解只写在 roadmap。外部评审逐条对照代码。

预算由 `make check` 核对：`docs/` 下只有地图中的文档；每份不超过 250 行，plan 不超过 150 行，`AGENTS.md` 不超过 120 行；
一行不超过 200 个字；没有“现存差距”一类的标题；文档与规则里提到的文档都存在。

## 谁决定什么

| 谁 | 决定 |
|---|---|
| 负责人 | 意图与承重决定；格式纪元；新依赖；删除用户看得见的能力；旗舰包与第一个客户；一个阶段过没过门槛；观感好不好 |
| Agent | 其余一切：顺序、设计、实现、验证与文档，并对结果负责 |

- 负责人不需要读代码。他看两样东西：plan 里的那一行，和浏览器里的界面。
- Agent 只在“只有负责人能决定”的事上停下来问；其余自己定，在汇报里说明所作的选择。

## 怎样干活

1. 一次一项。从 plan 当前的一行取，按 roadmap 的细目做；做完、核对、提交、推送 main，再取下一项。
2. 先读后写。读这一行涉及的文档小节、实现与调用方；从根因解决；删掉被替换的旧路径。
3. 小事顺手修，大事进对应规划。路上发现的小缺陷在这一行里修掉；大的加成一行，不当场展开。
4. 核对了才算完。按下节选择定点验收，界面在浏览器里用真实数据看过；核对提交对应的 CI。
   没跑的检查、没看的界面，汇报里照实说。
5. 汇报给人看，只说三件事：现在能做什么（附能点开的地址）、什么没做或没核对、要负责人决定什么。不贴过程。

## 三档验收

原则：保留测试覆盖，消除重复执行。日常按改动验收，远程检查集成，发版才跑全量；不把三档都绑到每次提交。

| 档位 | 入口 | 责任与边界 |
|---|---|---|
| Fast（本地开发） | `make fast`、相关定点用例 | Git 提交自动核对暂存空白和 Go 格式，另查提交信息；不编译、不跑全量 |
| CI（GitHub） | `make check`、`make test-runner`、`make check-frontend` | push main / PR 自动执行；后端编译、vet、边界、包、契约、文档、纪元、前端规范与构建 |
| Release（本地） | `make verify` | 先 `make test-pg`，再 `make trunk-pg`，各一次全量；不用内存全量重复验收 |

### 日常怎样选

- 后端行为改动：`make test RUN=K13`（换成受影响的不变量编号）；需要数据库行为时用 `make test-pg RUN=K13`。
- 前端行为改动：`make trunk SPEC=crm`（换成相关 spec，可通过 `TRUNK_ARGS='--grep ...'` 缩小）；按需运行类型检查。
- `make trunk-changed` 只执行明确映射的用例；影响过广返回非零并要求选择 SPEC，不自动跑全量。
- 纯文档或规约：`node scripts/check-docs.mjs`；不启动业务宿主。修改测试工具才按需运行 `make test-runner`。
- 已通过的相同检查不因准备提交而重跑；有新的相关改动才重验。CI 失败修原因，不降低断言或绕过检查。
- 格式化、提交信息与热更新不是业务验收；热更新构建不应触发回归测试。

### 发版怎样验

1. 在干净的候选提交上验收，记录 `git rev-parse HEAD`；确保该提交的 GitHub 轻量 CI 通过。
2. 本地具备 Docker、`platform-postgres:18-vector` 镜像、前端依赖与 Chrome；缺少环境先补齐，不改成内存全量代替。
3. 执行 `make verify`，固定全量参数，后端失败不启动浏览器。两套测试分别使用临时 PostgreSQL。
4. 核对 `.build/check/test-results.json` 与 `.build/trunk/playwright-results.json`：失败、跳过、未执行、零用例或不稳定通过均不能算全量通过。
5. 验收后候选提交或相关工作区字节变化，重新核对受影响的证据；不得把旧提交的报告冒充新提交的全量通过。
6. 同一提交的 CI 与本地验收均通过才打 Tag。GitHub Release 工作流只构建、签发和发布制品，不再运行重型测试。

这里的发版要求是工作规约：现有 Tag 工作流未自动绑定本地验收证据。Agent 在发版前核对，不将打 Tag 本身当成通过证明。

### 专项按需

| 命令 | 何时使用 |
|---|---|
| `make test-voice` | 明确需要语音模块竞态专项时；不进入固定流程 |
| `GATES="race" bash deploy/dev/kernel-gates.sh` | 并发、同步与共享状态变更 |
| `make verify-sql` | 写入、重启与恢复专项 |
| `make load-sql` | 容量、导入、延迟和吞吐专项 |
| `bash deploy/dev/kernel-gates.sh quick` | 仅定点 K1/K13；其他专项显式选 GATES |

不要把专项命令拼成日常默认全量。内存环境的 `make test`、`make trunk` 全量入口保留供明确需要时使用。

## 一行怎样算做完

- 负责人照 plan 那一行“做完你能看到”的描述，在浏览器里做得到。
- 定点验收与该提交的 CI 通过；改到的行为有对应的文档改动；对应规划里这一行已经删掉。
- 没有留下第二条路：旧实现已删，没有兼容分支，没有开关，没有“以后再接上”的空壳。
- 已提交并推送。
