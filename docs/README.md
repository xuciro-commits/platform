# 文档

这个项目几乎全部由 AI 写成。文档只有一个用途：让每一次会话不读全仓，也能做出与整体一致的决定。
文档按问题分，每份都短；当前阶段的细目见 [roadmap](roadmap.md)。

## 文档的规矩

1. 只有地图里的文档。新内容写进已有的某一份；真要增加一份，先问负责人。
2. 规范写目标，代码与规范不一致时改代码；产品进度写在 plan，当前阶段的细目写在 roadmap。
3. 不写历史，不写“之前我们”。没做完的事写入对应规划，做完就删；历史在 git 里。
4. 一个事实只在一处，别处链接，不复述。
5. 只写代码里读不出来的东西：归属、边界、取舍、规则与理由。目录、函数签名、字段列表不抄进文档。
6. 冻结的东西不写文档。它的事实是代码与测试；解冻时再把规则写进来。
7. 写给会读但没时间的人：短句，常用词，一行一件事。
8. 代码改变了文档写着的行为，同一提交改文档。
9. 不入库的：评审报告、审计、会议纪要、进度日志、方案草稿；任务分解只写在 roadmap。外部评审逐条对照代码。

预算由 `make check` 核对：`docs/` 下只有地图中的文档；每份不超过 250 行，plan 不超过 150 行，`AGENTS.md` 不超过 120 行；
一行不超过 200 个字；没有“现存差距”一类的标题；文档与规则里提到的文档都存在。

## 谁决定什么

| 谁 | 决定 |
|---|---|
| 负责人 | 意图与承重决定；格式纪元；新依赖；删除用户看得见的能力；旗舰包与第一个客户；一个阶段过没过门槛；观感好不好 |
| Agent | 其余一切：顺序、设计、实现、验证与文档，并对结果负责 |

- 负责人不需要读代码。他看两样东西：plan 里的那一行，和浏览器里的界面。
- Agent 只在“只有负责人能决定”的事上停下来问；其余自己定，在汇报里说明所作的选择。

## 怎样干活

1. 一次一项。从 plan 当前的一行取，按 roadmap 的细目做；做完、核对、提交、推送 main，再取下一项。
2. 先读后写。读这一行涉及的文档小节、实现与调用方；从根因解决；删掉被替换的旧路径。
3. 小事顺手修，大事进对应规划。路上发现的小缺陷在这一行里修掉；大的加成一行，不当场展开。
4. 核对了才算完。按下节选择定点验收，界面在浏览器里用真实数据看过；核对提交对应的 CI。
   没跑的检查、没看的界面，汇报里照实说。
5. 汇报给人看，只说三件事：现在能做什么（附能点开的地址）、什么没做或没核对、要负责人决定什么。不贴过程。

## 三档验收

原则：按规模设速度预算，按改动路由执行，跨层与跨阶段零重复。通用能力只在平台层测一次，产品包只测声明特有的流转，冻结功能不跑机械循环。

### 规模与速度预算

| 规模 | 单条预算 | 整批目标 | 适用对象与约束 |
|---|---|---|---|
| Small（秒级核心） | `<= 1s` | `< 10s` | `make test-fast`、`make test RUN=K…`：内核、表达式、授权与合成最小包不变量；禁用 250 国主数据或全量业务包夹具 |
| Medium（定点集成） | `<= 5s`（Go）/ `< 30s`（单 spec） | `< 45s` | `make test`（LPT 6 分片并行）与 `make trunk SPEC=…`（常驻 PG 池 + 按 spec 建独立场景库、动态端口） |
| Large（发版与重型专项） | `< 60s` | 按需 / 发版一次 | 千行批量回放、跨库备份恢复、`make verify`（常驻 PostgreSQL 池中的新建数据库全量）、`make load-sql`；日常开发与提交严禁触发 |

### 阶段分工

| 档位 | 入口 | 责任与边界 |
|---|---|---|
| Fast（本地开发与提交） | 定点 `RUN=` / `SPEC=`、提交自动 `make fast` | 开发只跑改到的定点用例；`pre-commit` 只查暂存空白、Go 格式与提交信息（`< 1s`），不编译、不跑测试 |
| CI（GitHub） | `make check`、`make test-runner`、`make test-fast`、`make check-frontend` | push main / PR 自动执行静态门禁、契约零漂移、秒级核心不变量与前端构建 |
| Release（本地发版） | `make verify` | 先 `make test-pg`，再 `make trunk`，各一次全量；不用内存全量重复验收 |

### 日常怎样选

- 后端行为改动：优先 `make test RUN=K13`（受影响编号，`< 5s`）或 `make test-fast`（`< 10s`）；涉及 SQL 方言或存储时跑 `make test-pg RUN=K13`。
- 前端行为改动：`make trunk SPEC=crm`（可通过 `TRUNK_ARGS='--grep ...'` 缩到单条）；自动分配空闲端口并只灌该 spec 所需租户，与运行中的开发环境互不干扰。
- `make trunk-changed` 按 `scripts/trunk-affected.mjs` 的受影响图只跑明确映射的 spec；影响过广返回非零并要求指定 `SPEC`，绝不自动跑全量。
- 跨层去重：不为单个内部函数写单元测试，严禁伪造旧路由或内存桩的自欺测试；界面前置状态优先经真实 `submit` 注入；若自动编号、分配或授权的行为本身依赖界面入口，必须先证明两种路径等价。
- 纯文档或规约：`node scripts/check-docs.mjs`；修改测试调度器才运行 `make test-runner`。已通过的相同检查不因准备提交而重跑。

### Trunk 场景与租户

租户是隔离边界，不是测试功能的计数器。以下四层定义在 `scripts/trunk-seeds.mjs`，每个 spec 必须归属一层；新增用例优先复用现有场景。
只有必须同时对比不同租户、不同安装状态或权限边界时才新增模板，禁止为单个功能另造租户。稳定英文 ID 用于存储与 API，中文 Name 注入现有租户 name 设置，用于登录后工作区展示；测试语言仍为 en，不能为改显示名改变语言断言。

| 层 | 命令 | 初始状态 |
|---|---|---|
| Runtime · 通用运行时 | `make trunk LAYER=runtime` | 星河科技（acceptance）；切换工作区时加一个空的对照租户 |
| Business · 业务组合 | `make trunk LAYER=business` | 复用星河科技，按需要加入 CRM、电话和协作权限场景 |
| Delivery · 包交付 | `make trunk LAYER=delivery` | 空租户、历史版本、已安装版本等互斥状态按需创建；真实安装、升级与恢复 |
| Security · 安全隔离 | `make trunk LAYER=security` | 浏览器验证授权 UI 与撤权后的实时行为；纯 API 隔离由 `make test-security-pg` 创建两个独立安全租户和一个非成员租户 |

日常 `make frontend-host` 只建星河科技一个租户；单 spec 不加载无关租户。
`builder` 不装 CRM；`crm` 只建启明商贸；`crm-records` 与 `package-extension` 才准备星河科技的 CRM。
交付拆为 `marketplace`（空企业）、`package-upgrade`（文件导入与 CRM 升级）、`party-upgrade`（主数据迁移）、`package-library`（目录）、`package-apps`（已安装应用）、`package-lifecycle`、`official` 等，互不加载无关业务数据。
前置状态从已按锁校验的远程制品字节导入，不为每个租户重复下载；真实 HTTPS 安装与市场自动依赖下载仍走产品接口，不以准备缓存替代传输验收。升级场景预置目标版本声明的真实依赖（如尚未发布的 call 从锁定源码构建），不跳过依赖检查。全量验收覆盖四层常规场景和独立 API 安全验收，不把演示、测试租户保留在开发或生产实例。
默认单 worker，当前有串行依赖的用例共享所属场景状态；不同执行批次的数据库、文件目录和宿主互不共享，尚不宣称每个用例或每个 worker 完全隔离。

测试池按 PostgreSQL 镜像 ID 创建专用本机容器（仅回环地址），不使用开发/生产数据库。
数据库名每次随机；运行结束删除运行库与恢复库，失败保留运行目录证据。
可复用场景的只读基准按宿主二进制、包输入清单、种子文件、场景、日期及池 ID 定键，同时复制数据库与文件字节。
交付、安全、电话及连接器专项从新库实际构建初始状态；全量发布不使用基准。
基准与运行目录均在忽略的 `.build/` 下。用 `make trunk-cache-clean` 删除当前工作树的基准，不删除运行库或常驻容器；异常中断遗留的锁需确认无活动进程后清理。

### Trunk 用例准入与精简

Trunk 是真实用户行为的最小验收集合，不是业务功能清单；用例数只作预算，不作删除指标。
新增或保留用例时逐项回答：

1. 验收哪项平台能力或真实交付链路？
2. 为什么必须由浏览器验证，而非内核或真实 HTTP API？
3. 是否已有后端不变量覆盖相同失败条件？
4. 是否已有 Trunk 验证相同的用户路径，能否合并断言？
5. 前置状态是否能通过真实提交准备，而不重复操作界面？
6. 是否必须新建租户，现有场景为什么不可复用？
7. 是 Platform 的能力，还是产品 Package 自己的业务规则？
8. 属于哪一层、何时运行，失败证据和成功条件是什么？

替代用例实测覆盖原有独立断言后才删除旧用例；不以改名、放宽断言或隐藏失败实现精简。
包自有规则优先由包库验收；未确认包库存在等价验收之前，保留平台当前覆盖。
路由注册与入口文件的一一对应由静态门禁检查，浏览器只抽取有行为风险的页面，不遍历全部页面标题。
模拟万行数据的窗口化测试仅验证前端渲染，不证明数据库容量；通过 `make trunk-special` 单独执行。

### 发版怎样验

1. 在干净的候选提交上验收，记录 `git rev-parse HEAD`；确保该提交的 GitHub 轻量 CI 通过。
2. 本地具备 Docker、`platform-postgres:18-vector` 镜像、前端依赖与 Chrome；缺少环境先补齐，不改成内存全量代替。
3. 执行 `make verify`，固定全量参数，后端失败不启动浏览器。后端不变量、HTTP 安全与浏览器验收使用专用常驻 PostgreSQL 池中的独立数据库；浏览器全量从真实初始状态执行，不复用基准。
4. 核对 HTTP 安全验收退出码，以及 `.build/check/test-results.json` 与 `.build/trunk/playwright-results.json`：失败、跳过、未执行、零用例或不稳定通过均不能算全量通过。
5. 验收后候选提交或相关工作区字节变化，重新核对受影响的证据；不得把旧提交的报告冒充新提交的全量通过。
6. 同一提交的 CI 与本地验收均通过才打 Tag。GitHub Release 工作流只构建、签发和发布制品，不再运行重型测试。

这里的发版要求是工作规约：现有 Tag 工作流未自动绑定本地验收证据。Agent 在发版前核对，不将打 Tag 本身当成通过证明。

### 专项按需

| 命令 | 何时使用 |
|---|---|
| `make test-voice` | 明确需要语音模块竞态专项时；不进入固定流程 |
| `GATES="race" bash deploy/dev/kernel-gates.sh` | 并发、同步与共享状态变更 |
| `make verify-sql` | 写入、重启与恢复专项 |
| `make load-sql` | 容量、导入、延迟和吞吐专项 |
| `make trunk-special` | 模拟大列表的浏览器窗口化专项，不进入常规 Trunk |
| `bash deploy/dev/kernel-gates.sh quick` | 仅定点 K1/K13；其他专项显式选 GATES |

不要把专项命令拼成日常默认全量。内存环境的 `make test` 保留供内核专项使用；浏览器不存在内存执行入口。

## 一行怎样算做完

- 负责人照 plan 那一行“做完你能看到”的描述，在浏览器里做得到。
- 定点验收与该提交的 CI 通过；改到的行为有对应的文档改动；对应规划里这一行已经删掉。
- 没有留下第二条路：旧实现已删，没有兼容分支，没有开关，没有“以后再接上”的空壳。
- 已提交并推送。
