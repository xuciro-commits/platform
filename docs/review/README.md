# 平台与 AI 评审｜对抗性收敛版

**复核日期：** 2026-10-05（America/Los_Angeles）　**代码基线：** `87b8307`　**范围：** 本目录此前 `01–09` 评审及当前 Intent、WorkQueue、ADR、关键运行时代码；仅整理评审文档，不修改源码、产品设计或执行队列。

> 这是收敛后的唯一入口。旧的九篇专题稿已合并为本索引与两份重点报告；不再把它们作为额外队列或设计规范。

## 执行结论

前一版 Review **发现了有价值的风险，但优先级和篇幅失衡**：把文档/Widget/Playwright 文件数量、多个架构视图、SAP/Palantir 对照写得过重；有些意见建议先停掉现有工作、重写架构文档或再建一套阶段门禁，收益证据不足，也与仓库已存在的 Intent、单一 WorkQueue、ADR-0038 和 `AGENTS.md` 的渐进式规则重复。该“暂停扩展并先做总体重构”的建议在本次对抗复核中**撤回**。

当前最重要的不是增加评审层数，而是对平台影响最高的三件事保持聚焦：

1. **权限与副作用：** 流程 Agent 的 `context`/`search` 可能以全租户宿主角色读取；在途模型调用被取消/暂停后，迟到工具意图可能仍被执行。两项均为高影响静态路径，尚未实测复现。
2. **数据与持久化保证：** accepted-result 已覆盖若干路径，但 ADR-0038 明确其余入口仍按旧输入/代码重放。不能把局部结果恢复说成全平台原子提交或“恰好一次”；这是已知边界，且当前 WorkQueue 已安排稳定交付、恢复和演进工作。
3. **用户价值与成本：** Intent 已明确平台服务 FDE/客户构建者、贯通构建到运营；当前 #141 主线也在推进 Studio 体验。真正缺的是关键业务旅程的可复验结果，而不是再写一份产品定义或以组件数推导路线。AI 成本/留存问题应在扩展模型自主权前处理，但不自动改写队列。

P1 表示“在扩大敏感或自主能力前要确认/验证”，**不等于已证实漏洞、要求停止当前无关批次，或自动授权重排 WorkQueue**。

## 三种对抗性复核视角

| 视角 | 对前版的挑战 | 收敛结果 |
|---|---|---|
| **层级/轻重** | 是否把小事写成大事、漏掉平台级问题？ | 75 个 Widget、57/127 等文件/测试计数、文档字节数均不能证明过度建设或业务风险，已移除。权限边界、持久结果范围、真实交付闭环优先。 |
| **实时性/证据** | 是否忽略更近的源文件/设计/方法？ | 当前基线仍是 `87b8307`；本轮重新核对 Intent、当前 WorkQueue、ADR-0029/0038 和对应代码。方法论参考更新到 2026 年 9 月 OpenAI Agents API、2026 年 3–4 月 Anthropic Agent harness/managed-agent 文章及 DORA 2026 ROI 页面。 |
| **收益/机会成本** | 建议是否比正在做的任务更有回报？ | 现有 WorkQueue 已分批推进 Studio、恢复/定位、最小升级、首个接入等。此前提出的总体停工、架构图工程和额外矩阵会新增协调成本，本轮不采纳。AI-first 是后续可验证方向，不应抢占当前已授权批次。 |

**评审能力限制：** 当前工具没有独立子智能体调度、模型选择或多模型投票接口，因此不能诚实声称已召集三个不同的顶级模型。以上三类复核由同一助手按独立检查表完成，并使用当前代码/文件和外部资料交叉核对；这不是多个模型的共识，也不替代安全团队或业务 owner 的独立审批。

## 最高优先级事项

| 顺序 | 影响面与证据状态 | 下一步建议 |
|---|---|---|
| **1** | 流程 Agent 的无 `OnBehalf` 读取调用可走 `Tenant.host()`；host 为每个 app 赋 `*`，空 scope 默认可为 tenant。与流程 Agent 应只读所属应用的代码注释/ADR 说法不一致。**路径静态确认、预期授权待定、未复现。** | Owner 决定允许的 app scope；用应用 A/B、受限字段、撤权、显式跨应用授权测试。 |
| **2** | 模型调用在租户锁外；取消/暂停后，返回路径未明显检查 run state/generation 后再提交工具结果。**竞态静态推断、未复现。** | 阻塞式模型测试取消/急停；在动作提交前加运行代次/状态围栏；迟到 usage 仍计量但不执行工具。 |
| **3** | 受限的 accepted-result 范围与旧 `Submit`/`Input`/异步路径并存。**ADR-0038 已明示的覆盖边界，不是本轮新发现的漏洞。** | 继续按 ADR-0038 与 WorkQueue 的持久化/恢复、升级批次推进；文案和宣传按具体入口描述保证。 |
| **4** | Chat 路由没有本地 body 上限；`maxTokens` 没有平台硬上限；Token/频次在调用后计量、缺 usage 记零；人员日 Token 默认 `0` 无上限。全局 HTTP body 限制未排除。 | 在扩大 Chat/Agent 使用前验证外层限制并明确请求/输出/并发/额度策略；不把美元上限描述为漏实现——ADR-0029 明确暂缓通用 USD hard cap。 |
| **5** | 完整模型请求/回答存储，`transcript-days <= 0` 会跳过清理；普通 Chat 转录可能无法通过当前 API 读回。字段可读不等于允许发往某个外部 provider。**代码路径确认，管理员语义/租户政策未验证。** | 明确零值、普通 Chat 留存、可读/删除与 provider 数据分类；要求 trace 标识真实用量未知。 |

## 前版结论的修正

- **产品意图不是空白。** `Intent.md` 已明确“面向 FDE 与客户构建者的 AI 业务应用平台”、构建→运行→演进路径和成功衡量方向。旧报告将其写成“两个产品身份未决”过强；更准确的是首要行业/业务任务及外部用户价值仍待验证。
- **开发流程不是缺少队列。** `AGENTS.md`、`WorkQueue.md`、ADR 与 Testing 已有分工、停止条件和选择性检查。当前主线有次序；需要按实际风险向 owner 升级，而不是另建 Review 队列、检查清单森林或能力矩阵。
- **文档/功能计数不是最高优先级证据。** Platform/ADR 的详细程度可能增加维护成本，但文档长度本身不是交付故障；共享 Widget/Playwright 数也不说明产品多余。只有死链、状态冲突、权限缺陷或任务受阻等可观察后果才应触发整理。
- **平台可靠性结论按现有保证缩小。** K1–K9 与 K4 有界证明是强项，但不证明所有宿主路径；反过来，也不应把“有不同日志路径”直接判断为数据丢失漏洞。路径适用范围看 ADR-0038 和真实故障证据。
- **不调整当前 WorkQueue。** 本报告不启动新的开发优先级，不要求现在重画所有图/改 ADR/加新 gate。若 P1 风险被复现，负责人与现队列做显式取舍。
