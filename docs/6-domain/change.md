# 6 领域架构 · 变更与交付

## 目标

定义从“一次编辑”到“安装在客户租户中的版本”的完整链路：每一步都有明确的权威、可审阅、可回滚，并且客户扩展不阻断升级。

## 规则

- R1 分支只覆盖定义（资源元数据），不覆盖实例数据；对象与数据集版本不随分支合并。
- R2 合并是一个接受结果；检查在分支的暂存世界中运行，与 main 隔离。
- R3 产品版本不可变、内容寻址；安装与升级只应用已接受的映像，不重跑规则、授权或外部调用。
- R4 升级不覆盖客户资源；不兼容变更在升级审阅中提前列出。
- R5 恢复只应用已接受映像；任何恢复不改写历史字节。

## 6.19 工作状态

- 每位构建者在每个分支上一个工作状态，包含其未保存到该分支的全部资源编辑；资源草稿与原始输入自动保存到该成员的私有记录，其他构建者与管理员均不能读取。
- 自动保存把编辑写入工作状态；“审阅并保存”把工作状态写入分支（main 上即生效）。
- 工作状态对其他人不可见；保存后才可见。
- 全局审阅汇总当前成员在所选分支的全部私有资源编辑，展示资源与字段差异，允许选择或放弃。保存请求由各资源编辑器产生，与个人工作状态一同保留，汇总不另做界面状态转换。main 上复用联合接受结果保存资源并清除对应私有状态；分支上经原有资源保存路径共享，随后进入提案审阅。原始输入有问题时先修正，不共享半成品输入。

## 6.20 分支与提案

- 分支：main 之外的一个命名定义空间；从 main 的某一版本分出，记录基线。
- 分支上的保存只写分支；分支可随时从 main 更新（三方合并，冲突需逐项选择）。
- 提案：请求把分支合并到 main；包含差异、自动检查结果、审阅者、讨论。
- 合并条件：自动检查通过 + 至少一位非作者的 Editor/Owner 批准（项目可配置）；合并后分支变为已合并、只读。
- 检查：类型检查、引用存在、提交条件可求值、破坏性变更的下游影响、业务测试计划。

## 6.21 产品与版本

- 产品：DevOps 拥有的 `build.product` 资源，位于一个项目，Contents 是该项目中可交付资源的有序集合；闭包外的依赖必须来自已声明的产品依赖。
- 候选：产品 Contents 在某一时刻的完整发布快照；保存候选仍经现有发布审阅（差异、检查、测试计划）。
- 版本：DevOps 拥有的 `build.productversion` 记录；不可变，带语义版本号，引用一个已保存候选并从其冻结字节计算 Contents 闭包。声明的依赖产品资源不复制进本产品；记录候选字节哈希、产品内容哈希、依赖产品的版本范围、所需的业务角色与标记。`platform.PackageDescriptor` 只作为版本的序列化格式，不是另一套产品模型。
- 激活：在产品所在的租户中把某个版本设为生效版本，回滚即激活上一个版本；其他租户使用版本只经安装（6.22）。

## 6.22 安装与升级

- 安装：只从产品版本目录选择版本。先解析满足全部依赖范围且兼容已安装产品的版本闭包，审阅明确列出顺序与精确版本；各产品分别经其原有接受结果安装，失败停在当前产品；把产品版本放入目标租户的一个受管项目；映射业务角色与标记到目标租户的角色与标记；安装审阅列出将创建的资源与所需权限。Marketplace 不建立通用包或第二套安装事实。
- 受管项目：产品定义只读，只能被升级替换；连接地址与凭据引用是租户环境配置，单独经配置动作写入；Check、Pull 与 Run 等运行操作保持可用；受管定义不使业务对象、数据集事务与媒体上传变为只读，已有数据版本仍不可变。
- 客户扩展：放在客户自己的项目中，可实现受管接口、为受管对象类型追加属性（扩展属性）、新增动作与模块、引用受管资源。
- 升级：计算新旧版本差异 → 检查每个客户扩展是否仍有效（引用存在、接口兼容）→ 升级审阅 → 一次接受结果切换。不兼容时阻止升级并说明需要先改哪个扩展；移除资源时列出仍引用它的客户资源，并在接受升级前执行同一检查，不能绕过审阅直接提交。
- 卸载：先列出移除资源与受影响的引用，再归档受管项目；客户资源、引用与业务数据保留，缺失引用不级联删除。

## 6.23 恢复与迁移

- 宿主重启：从快照恢复并重放之后的接受结果；结果逐字节一致。
- 迁移：记录格式的演进只经版本化的迁移，迁移本身是接受结果；不重写历史字节。
- 租户迁移与宿主升级在 Host Console 进行。

## 现存差距

- 产品的安装、升级与卸载均经审阅和单个接受结果写入受管项目；业务角色在准备页显式列出，安装不会隐式授权。当前产品没有专项标记声明，因此没有待映射项。
- 未发布客户草稿不在已安装资源的移除影响审阅内；它尚未成为已接受资源。
