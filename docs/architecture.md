# 架构

这份文档回答：系统由哪几块组成，一次写入、一次读取、一次发布各走哪条路，怎样知道它是对的。
概念的含义在 [domain](domain.md)，Go 代码的规矩在 [backend](backend.md)，界面在 [frontend](frontend.md)。

## 一页图

```
 浏览器 frontend/                       外部系统
    │  /v1 读取、提交                      │  同步、回写
    ▼                                      ▼
┌───────────────── 宿主：一个 Go 进程，服务多个租户 ─────────────────┐
│ host      HTTP 路由、身份接入、租户装配、后台调度                   │
│ services  资源 本体 对象 动作 函数 数据 自动化 应用 工作 交付        │
│           安全 AI —— 每个服务拥有自己的状态与自己的接受结果          │
│ kernel    车道、接受结果日志、读取映像、重放与快照                   │
│ platform  应用 SDK 的契约   capability 能力图   expr  规则语言       │
└────────────────────────────────────────────────────────────────────┘
    │ 日志与投影            │ 文件、数据集、制品        │ 租户函数
    ▼                       ▼                          ▼
 PostgreSQL            S3 兼容对象存储            隔离进程（WASM）
```

宿主之外的一切业务内容都是产品包：声明式、带版本、经同一条安装路径进入租户（D4）。平台里没有行业代码。

## 写入：只有一条路（D1）

```
POST /v1/submissions
 → 准入：租户、主体、隔离状态、项目角色边界
 → 定位拥有者：动作 → 服务
 → 决定：在读取映像的分叉上调用拥有者，得到编辑与意图
 → 内核接收：字段校验、模式版本、幂等键、期望修订、授权、领域规则
 → 封存接受结果（拒绝也封存）
 → 日志追加：一个 SQL 事务里写日志行、状态增量并推进位置
 → 从已提交的字节应用到记录存储，发布新的读取映像
 → 发布事件，入队副作用与自动化
```

- 拥有者只返回编辑与意图，从不直接写存储。应用只发生在提交之后，并且只从已提交的字节解码。
- 决定先在车道外准备。取得车道时，若原读取映像已过期且还有提交或后台工作排队，在车道内基于当前位置重做决定。
- 标准的创建、编辑、归档是内置的三种动作，与业务动作共用同一个执行器。
- 幂等只在两处判定：读取映像上的预检，与车道内的提交。其余步骤信任这两处。
- 副作用至少投递一次，以请求键幂等。外部调用分两段：先以接受结果预留，在车道外调用，再以接受结果结算。
- 应用结果与已提交字节不一致时隔离该租户：停止写入，只读，等待处理。别的错误是拒绝或运行失败，不隔离。
- 重放只应用已接受的映像，不重跑规则、授权或外部调用。

## 读取：也只有一条路

- 每次读取取一份已发布的读取映像，看到一个完整的已应用位置；读取不等待写入，也不等待后台工作。
- 命名读取 `GET /v1/{read}`：入口授权 → 拥有者读取 → 行与字段收窄。
- 单条记录 `GET /v1/records/{type}/{id}`：按主键读取对象与可见字段，动作可用性在同一 SQL 读视图内复用该行。
  关系、活动、文件、工作、历史、评论各是一个分区，经 `/sections/{section}` 分别读取、分别授权。
- 列表和单条记录的 `refs` 按字段与引用标识给出显示名；调用者须能读取来源字段、目标记录与显示字段。
- 列表加 `actions=1` 可读取每条返回记录的动作可用性，按记录标识索引。
- 单条记录的 `actions` 给出可披露动作、可用性和原因。预检与提交共用授权、生命周期和守卫；缺少参数时只预检能判定的条件。参数、修订与执行步骤在提交时判断。
- 声明的反向集合从 `GET /v1/record-sets/{type}/{id}/{name}` 读取。集合上限内返回每行及修订，`total` 与 `sums` 只用可读的行与字段。
- 对象发布的动作预检从同一读取映像统计影响，在私有决策里运行原发布校验，不提交结果。
- 对象集：编译成计划 → 能下推的条件下推到索引列 → 行策略与标记 → 字段视图。
- 授权只有一个决定函数（D5）。集合读取与单条读取走同一条决定路径。
- 变更流 `GET /v1/changes` 的 `changed` 信号携带已改类型与作用域，页面据此重取。注册 `watch` 的连接接收授权后的查询快照，租户内经确认结果一致的订阅共享已编码的查询结果。

## 发布与安装：一种交付物（D4）

```
项目里的资源草稿 → 保存到 main（或分支 → 提案 → 合并）
 → 产品：选定项目的内容与依赖
 → 候选：某一时刻内容的完整冻结
 → 产品版本：不可变、内容寻址、带语义版本号
 → 市场目录 → 安装到目标租户的受管项目 → 升级只替换受管部分
```

每种资源类型的校验、冻结、草稿闭包、安装与冻结映像读取由拥有它的服务实现；资源服务只做跨类型的编排。

- 草稿闭包接收调用者、草稿身份和成员，返回所需草稿、前后资产与引用；拒绝时保留已算出的引用。
- 冻结接收来源版本与候选资产：对象逐项处理并可传递处理后的资产，版本族批量处理并返回发布映像或安装计划。
- 安装映像先由所属资源解码身份，再校验并应用；同一资源族的多个类型或模式由一条登记分派。
- 联合候选先建立对象与声明上下文，再处理相互依赖的草稿；保留读取、冻结和拒绝顺序。
- 对象草稿生成对象、动作与默认页面；显式页面可以覆盖默认页面。保留代码对象跳过对象发布钩子。
- 评估集与测试计划共用 DevOps 持有的记录和版本族，由变体选择 AI 的评估集行为或 DevOps 的测试计划行为；DevOps 为样本集直接生成安装计划。
- 代码函数与决策表共用计算资源登记，按各自的发布模式解码和安装，并保留各自的版本历史。
- 宿主装配各服务及依赖。决定分叉复制各自状态并重新绑定钩子，模拟实例新建状态；执行分叉按资产顺序绑定选中的版本。

## 租户与并发

一个租户的接受结果按位置严格递增，同一时刻只有一个提交者。一致性靠“事实怎样成为事实”，不靠独占租户。

```
读取：  映像 N ──────────────► 结果（位置 N）
决定：  映像 N ─► 分叉 ─► 授权、规则、拥有者决定 ─► 待提交结果（基准 N）
提交：  [车道] 已应用位置 == N ？追加 → 应用 → 发布映像 N+1 ：作废重算
后台：  预留（接受）─► 车道外 I/O ─► 结算（接受）
```

车道只包住基准校验、追加、应用与发布映像，持有以毫秒计。规则见 [backend](backend.md)“并发”。

## 运行机制

| 机制 | 规则 |
|---|---|
| 租户隔离 | 权威状态在共享表里按租户列隔离 |
| 快照 | 每若干条接受结果与停机时保存；启动时从最新快照恢复，再重放其后的条目 |
| 后台工作 | 同步、构建、自动化、投递经工作队列；每项有运行记录，可重试 |
| 隔离计算 | 租户函数受控编译，在独立进程的 WASM 里执行，有内存、并发与模块大小上限 |
| AI 网关 | 预留额度 → 车道外调用供应商 → 结算；供应商与模型由租户管理员配置 |
| 身份 | 外部身份服务；开发与夹具用开发令牌 |
| 凭据 | 部署注入或受控加密托管；应用只保存引用 |

## 扩展：包贡献的四层

交付物只有包（D4）；区分的是包贡献哪一层。自下而上，上层只引用下层，不复制下层的数据。

| 层 | 是什么 | 归谁 |
|---|---|---|
| 组织 | 人、组织单元、岗位、内部地点、日历；账号登录为某人 | 平台（`services/security/organization`），不可卸载 |
| 主数据 | 外部当事人（客户组织、联系人）；参考数据：行政区划、计量单位 | 官方主数据包 `party`、`geo`、`uom` |
| 能力 | 带版本的能力契约（动作、读取、事件、计量、一致性测试）与它的实现；租户绑定用哪个实现 | 能力包 |
| 应用 | 一个业务场景的对象、动作、页面与流程；只给某个应用加东西的是扩展 | 应用包、扩展包 |

包的种类由 `pkg` 按内容推导，写进市场目录，作者不声明；一个包贡献几层时取最高层。
- 带能力契约或它的实现的是能力包；依赖某个应用包、只往它里面加东西的是扩展包；有应用根的是应用包；应用写 `surface: master-data` 或没有应用的是主数据包。
- 依赖只能向下：主数据包只依赖主数据包，能力包不依赖应用包，扩展包写明目标应用的版本范围。`pkg check` 指名拒绝反向依赖。

一样东西归哪里，按四问判断：
- 每个类型都该有的是平台特性（评论、附件、打印预览），由界面运行时给，不做成包。
- 多个应用共用的名词是主数据；应用选用、要能换供应商的是能力；只给某一个应用加东西的是扩展。

包只带声明，不带前端代码（D8）。应用包进应用轨；其余三种不进：主数据包的应用写 `surface: master-data`，出现在“管理 → 主数据”里（角色与设置菜单仍归这个应用），能力在“管理 → 能力”里绑定，
扩展出现在目标应用里。包往别人的界面放入口只经贡献位（[frontend](frontend.md)“包的界面落点”）。

- 账号与人不同：一个账号至多登录为一个人，一个人在一个租户里至多一个账号；智能体与系统账号没有人。授权沿人的组织关系求单元与岗位。
- 包给下层的名词加自己的字段，用附属对象：对象写 `extends`，必填引用字段 `base` 指向那个名词（组织里的人、地点、组织写 `extends: enterprise.element` 并给 `base` 定一个元素类型）。
  一个名词在一个附属对象里至多一条，`base` 建后不可改；读写只按附属对象自己的 `access` 判，所以别的包读不到。客户扩展用的是同一机制。
- 能力实现有四种形态：声明式（包里的对象与动作）、连接器（宿主经 HTTPS 调第三方）、沙箱代码（WASM）、受管服务。
  对使用方都一样：同一契约、同一授权、同一种运行记录；换实现不改应用。
- 受管服务是宿主之外的独立进程（码流、GPU、电话网关）：用一次性令牌换证书注册，宿主探活；调用走预留 → 车道外调用 → 结算，结果以接受结果写回，重放不重调。
- 绑定前对候选实现跑契约自带的一致性测试，通过才能绑定。发给实现方的数据按导出授权；连接器只能访问声明的出站地址。
- 应用作者声明 `uses` 并放入口，能力绑定了才出现；能力不自己往别的应用里加入口。
- 契约是构建应用里的独立资源，标识 `名字/主版本`；实现方只写映射，按契约核对。契约资源的绑定由租户显式选择，不随实现安装自动生效。
- 平台特性开箱就有、不经契约；同一件事要换供应商或要在服务端做的那部分才是能力。打印：预览、浏览器打印与条码是平台特性，
  单据模板是定义，服务端渲染 PDF 是能力 `document.render/1`。单据只绑一条记录及其明细与引用，不是报表设计器（[intent](intent.md)“不做”）。
- “能力”只指上面的契约与实现。宿主的运行装配（`capability.CapabilityModule`、`ResolveComposition`）只选部署用哪个存储与 owner 模块、
  定包的安装顺序，不承载租户的能力绑定；`Action.Capability` 是可整体停用的动作组，也不是能力。

## 智能体：工具由类型生成（D6）

声明一个类型，人得到界面，智能体得到工具。平台不跑智能体的长循环；智能体是调用者，从外面连进来，和人用同一批动作、同一个授权决定点。

| 口子 | 给谁 | 是什么 |
|---|---|---|
| 工具面 | 助手、外部 MCP 客户端、被委派的智能体 | 每个已发布动作是一个工具：参数取自动作输入，说明取标题与帮助，风险取动作的 `ask`；每个可读类型是一个对象集查询工具。随发布与安装出现，不手写 |
| 委派 | 长时、自主的工作 | 一种资源：什么发生了（对象集变化、状态、到期、计划）→ 交给哪个智能体 → 以谁的名义、能调哪些动作、什么时候告诉人 |
| 提问 | 需要人的地方 | 收件箱里带选项与推荐的事项；回答只算第一次，是一个新事件，叫醒原来的事项 |

- **智能体没有自己的权限。** 委派以委派人的授权运行，再与委派列出的动作取交集；委派人失去权限时暂停，同自动化。外部客户端以登录的成员运行。
- **文字是资料，委派才是指令。** 记录里别人写的文字（客户邮件、供应商备注）只进标明“资料”的上下文，不进提示词；
  交给谁、以谁的名义、能调哪些动作，只由已发布的委派决定。这挡不住所有提示注入，但把最坏的结果限在委派给的范围里。
- **先问。** 动作可声明 `ask`：删数据、对外发消息、花钱、改权限、不可冲正的过账这一类。智能体调用它时不执行，变成一个提问，
  成员批准后按原参数执行；没声明的动作在委派授权内直接执行。助手面前有人，每次写入都在对话里确认。
- **一轮一个回执。** 一轮的全部写入、提问、复查与通知写在回执里，一次接受生效，不留半轮。同一轮的令牌重交同样内容得同样结果，内容不同拒绝；
  回执写错只让智能体重写回执，不重做业务。
- **一轮不等人。** 要问人就结束这一轮；回答到了再开一轮，尽量接着原会话。等人时不占进程、不花额度，重启也不丢。
- **跳数。** 智能体或自动化的写入引起的新事件带跳数加一，超过 8 记下不派发并通知委派人，挡住自动化与智能体互相触发的回路。
- **每个 AI 写下的值都有来由。** 接受结果记委派与它的版本、触发事件、模型、用量与费用；记录页的活动里点开就是“为什么”。
- **身份只由宿主定。** 委派的令牌用部署的令牌密钥签，没有密钥的部署不接委派；调用者、批准人、跳数、触发事件与运行只由宿主写，客户端只能补充自己的名称、模型与用量。
- **用量。** 模型调用经 AI 网关预留后结算；委派可设每日额度，到额度停派并发一个提问。

接单与编排：

- 接单程序只往外连：领任务、交回执。任何能打印最后一条消息的命令行智能体都能接（Claude Code、Codex、Gemini CLI），不需要 SDK。
- 协议的形状照 [agent-autoloop](https://github.com/xuciro-commits/agent-autoloop)（任务、回执、提问、跳数、先问）。先直接接它：
  平台是它的事件来源与提问通道，智能体经工具面回调平台。宿主自建多租户接单，等第一个租户要托管委派时再做，协议不变。
- 宿主里唯一的循环是助手：一问一答，模型经网关，工具是同一个工具面。构建也是动作（`build.*`），智能体搭类型用的还是这个工具面，发布照常审阅。
- `services/ai` 保留模型配置与网关、检索、函数调用准备与评估集、`/mcp` 工具面及 `delegation`（委派与 `/autoloop` 接单协议）；宿主内运行智能体的 `services/ai/runtime` 已删除，不留两套。

## 版本与纪元（D7）

- `contract/proto` 是协议的唯一来源。Go 与 TypeScript 的类型由它和宿主类型生成（`make contract`），生成文件不手改。
- 每次提交带模式版本头；接受结果的格式带版本；存储格式只经版本化迁移演进，迁移本身是接受结果。
- 格式纪元在第一个客户租户装载之前冻结于 1（`store.FrozenEpoch`）；冻结之前的格式不读取。纪元之内历史字节逐字节保留，不改写。
- 此后格式变化只经版本化迁移：`FormatEpoch` 每加一，`kernel/store` 带一个 `migration_<n>_<n+1>.go` 与它的用例；重放与备份导入按步升级到当前纪元。`make check` 缺一项就指名拒。
- 错误带错误码与英文原因，原因字符串就是翻译键。
- 修订不符用 HTTP 409，保留 `ERROR_CODE_CONFLICT`，并给可读记录附 `reasonCode: stale_revision` 与 `currentRevision`，消息按成员语言返回。

| 形态 | 怎么起 | 说明 |

| 本地开发 | `make local` | 热更新，入口 `http://localhost:8495` |

| 无 Docker | `make lite` | 一个二进制，持久化运行 |
| 夹具宿主 | `make frontend-host` | 常驻 PostgreSQL 测试池中独立的演示数据库，仅星河科技租户 |

托管的 SaaS 与装进客户机房的私有部署是同一个二进制；区别只在谁运维、放几个租户。
租户文件（`-tenants`）里一个租户的 `settings` 是它的设置默认值：管理员没改过的设置取它，没写的取应用声明的默认。
