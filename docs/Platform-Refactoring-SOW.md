# Platform 平台架构治理与产品化重构项目

**Software Requirements Specification (SRS) & Statement of Work (SOW)**

**版本与效力：** v1.0，正式执行版，2026-10-10 生效。本文是本项目的需求、工作范围和验收基线，取代 v0.1。供应商及承接开发团队立即开展范围内的核查、设计、重构、迁移、清理、验证和交接，无需再次申请整体立项或逐项开工许可。

**委托原则：** 本文规定产品与架构结果；技术方案、代码组织和工程方法由供应商负责。既有正确能力凭证据验收并保留，实际缺口必须完成。阶段检查用于核实交付质量，不构成重新授权实施的前置。

**执行管理：** 执行顺序和停止条件统一进入 [WorkQueue](WorkQueue.md)，架构决策与现状分别归对应 ADR 和 Platform。供应商持续执行至本项目完成；仅涉及本文件范围外的扩项、额外费用、交付目标变更或削弱既有契约保证时，按 §7.4 办理变更，其他工作继续。

**现状证据基线：** 仓库 `95c3e1c0233493d85a9332a414f5e8689ceb0631`。§2 的结论来自宗旨、现行架构、工作队列、相关 ADR 和代码抽查，并运行了现有边界检查；这些基线证据不代替供应商应完成的实际运行与交付验收。后续实施按实际交付版本更新证据。

## 1. 委托目标

平台服务于 FDE、客户构建者和业务使用者，支持“连接数据与系统 → 建立业务语义 → 组织动作、流程与 AI → 构建应用界面 → 测试发布 → 运行、维护与演进”的完整过程。行业应用用于证明平台可用，并承载各自的业务语义。

本次重构的目标，是使平台成为**边界清楚、能力可组合、权威来源明确、交付与运行可控、维护成本可持续的产品**。供应商应围绕整个应用的建设和长期使用组织方案，并处理阻碍这些结果的结构性问题。

成功的表现包括：新团队能理解平台；构建者知道每项能力支持到哪里；同类能力有明确归属；应用可以按声明的范围组合、发布、升级和退出；业务操作在不同页面保持一致；运维人员能够解释故障、恢复任务并控制资源增长。

## 2. 高层审查结论

### 2.1 已有基础，应当保留

当前仓库已经具备语言中立的内核契约、应用公开 API、跨应用协议、共享 UI 与前端应用 API，以及构建、业务使用、治理运维的工作区结构。代码包描述、依赖预检、安装、升级、排空和退役已有实现；受控定义、联合候选、发布激活与部分恢复路径也已存在。[E1–E4]

共享表单输入和 Inspector 编辑最近已经做过一次平台化整合；AI 的模型接入、预算、运行与评测也有实际代码。这些能力应在现有归属上评估覆盖范围和产品效果，避免供应商重复建设。[E5、E8]

基线审查时运行的现有检查结果为：`boundaries` 通过，覆盖 6 个业务应用、2 个协议和 10 个平台应用包；`escapes` 通过，记录 6 个文件中的 7 项已知例外，没有新增例外。这证明已存在可执行的部分边界约束，不能据此推断整体低耦合、全部功能完成或生产就绪。[E10]

### 2.2 主要短板与风险

| 编号 | 证据与判断 | 对产品和维护的影响 | 应达到的结果 |
| --- | --- | --- | --- |
| F1 | **已确认：能力状态分散。** 已有实时能力目录和矩阵，但产品支持边界还需同时阅读 Platform、WorkQueue 和多份 ADR。部分状态摘要滞后于同文档或后继文档的实际实现说明。[E2、E6、E11] | 功能“存在”“局部实现”“可交付”“已被用户接受”容易混为一谈，供应商可能重复收费，也可能漏掉真正影响交付的缺口。 | 形成一套有唯一维护归属的产品能力与成熟度口径，并关联当前实现证据。 |
| F2 | **已确认：资产的交付生命周期覆盖不一致。** 页面、对象、Flow 等已进入联合候选；集成 Connection/Source/Dataset/Pipeline 记录尚不在候选封存与晋级范围。更广升级、客户扩展保留和部分恢复路径也仍有明确边界。[E3、E6] | 一个应用在当前环境可用，不等于其依赖可以完整迁移、升级和恢复。交付人员需要理解多套边界。 | 以完整应用为单位说明和控制依赖、环境差异、变更及恢复，明确各资产的支持范围。 |
| F3 | **已确认：扩展机制并存；风险在支持边界。** 原生应用依靠代码组合和前端包装配；租户通过受控定义扩展；包安装生命周期又承担另一类职责。[E4] | 如果“可插拔”未说明对象、阶段和限制，就会形成超过现有机制的承诺，或使每个客户采用不同扩展方式。 | 明确受支持的扩展模式、可选能力、兼容约束和退出责任。 |
| F4 | **需重点复核：跨功能协作仍集中在少数枢纽。** 宿主内部接口、定义安装/恢复和 Build 资源管理承担多个功能域的协作；业务应用公开边界则已存在。[E1、E7] | 集中协调本身合理，但局部变更可能牵动多个责任域。现有静态检查不足以判断实际变更影响和替换成本。 | 以典型变更的影响范围证明职责清晰、依赖受控；拆分或保留都需有证据。 |
| F5 | **已确认：通用平台能力与行业深度需要明确区分。** 企业模型、共享业务对象和行业应用都有实现；MES 工艺主数据仍有种子数据和行业语义边界，ERP/MES 深度也在延后范围。[E6、E9] | 容易把行业样例做深等同于平台进步，或因名称相近而重复建设组织、人员、地点、主数据等概念。 | 明确业务语义的权威归属、关系与可选性，让行业投入由真实交付需求驱动。 |
| F6 | **已确认：工程完成与使用效果仍有距离。** 共享输入能力已整合，部分画布与表单仍待负责人体验走查；AI 真实任务质量与更广运行体验也未整体验收。[E5、E8、E11] | 用户仍可能遇到跨页面不一致；接口、组件或机制存在不能单独证明产品可用。 | 验收覆盖真实角色的一段完整任务，并区分自动检查、实际行为和用户体验证据。 |
| F7 | **已确认的局部缺口，需限定推广范围：运行与数据生命周期未全部收口。** 持续 Flow 已接 PostgreSQL 输入，但完整处理链和部分制品生命周期仍未完成；集成运行冻结血缘、对账等也有未覆盖范围。[E3、E6] | 运行时间增长、异常中断和版本变更可能暴露维护负担；局部机制不能代表整个运行体系。 | 对承诺投入使用的能力，交付完整的运行、失败处置、恢复和保留边界。 |
| F8 | **治理风险：不同性质的尾项容易被统称为欠账。** 工作队列已区分主线和延后事项，但延后项仍包含必要依赖、触发式扩展和未来产品选择；已有减法清单，部分替代已完成，部分必须等待业务条件。[E6、E10] | 若把每个“尚未实现”都认作技术债，会持续增加功能、抽象和测试，迟迟无法收尾。 | 对尾项作完成、合并、取消或按条件保留的决定；必要交付缺口必须有明确终点。 |

本次证据不足以认定平台存在普遍的越权漏洞、所有大文件都需拆分，或所有多份数据都是多重权威。这些结论需要针对性的行为证据。供应商不得用未经验证的概括扩大报价范围。

## 3. 功能矩阵调整要求

下表划分产品责任域，用于讨论能力归属和交付范围；不规定菜单、目录、服务数量或部署形态。供应商可提出更简洁的划分，但必须解释覆盖关系与变化收益。

| 产品责任域 | 应保留的基础 | 顶层调整要求 | 本次范围原则 |
| --- | --- | --- | --- |
| 工作区与业务使用 | 共享 Shell、应用门户、角色投影、原生及构建应用入口 | 按用户任务组织入口、对象上下文、反馈与诊断，避免技术结构直接成为业务导航 | 对纳入交付的业务任务统一体验；不以重做全部界面为目标 |
| 业务语义与企业模型 | 对象、关系、动作、查询、企业模型和共享业务对象 | 清楚区分账号、人员、岗位、组织、地点、业务记录和模型元素；定义权威来源及关联责任 | 先消除职责歧义；完整行业模型或标准覆盖另行决策 |
| 数据连接与集成 | Connection、Source、Dataset、Pipeline、Matching、Writeback | 接入、转换、业务映射、回写及故障处置形成可交付能力，依赖与环境差异可管理 | 完成 §5.2 交付链必需部分；连接器数量不作重构目标 |
| 应用构建与共享交互 | Ontology、Workshop、共享表单、Inspector 和草稿机制 | 定义、输入约束、引用选项与编辑行为同源；业务输入和设计编辑有清晰责任 | 复用已完成的整合，治理实际覆盖缺口 |
| 业务执行与协作 | 动作、审批/任务、自动化、Flow、受控计算 | 各类执行能力职责清楚，可组合且可追踪；面向用户解释等待、失败、人工介入与版本 | 完成 §5.2 的任务链；持续 Flow 是其中一个子能力 |
| AI 与知识 | 模型治理、检索、函数、智能体、评测与预算 | 明确建议、读取和执行的边界，提供可核实的任务质量、权限、成本与人工接管能力 | 完成 §5.2 的真实 AI 任务；不扩建通用评测或模型市场 |
| 应用与扩展交付 | 原生包、受控定义、候选、环境、发布与迁移 | 对应用及其依赖给出一致的版本、兼容、升级、停用与历史保留承诺 | 属于本次核心结果；不要求所有资源拥有相同实现 |
| 治理与运行维护 | 身份授权、审计、Runs、Host Console、配额与恢复基础 | 区分租户治理、宿主管理和业务运营；故障处置与资源责任可定位 | 覆盖实际承诺的运行范围；不默认建设完整云管理产品 |
| 行业应用与业务包 | 酒店、制造及相关应用、跨应用协议、装配探针 | 行业规则留在适当业务归属；平台共性能力由平台提供；非必要模块可不装配 | 保留代表性验证应用；不以完整 ERP/MES 替代作为验收 |

内核契约、共享运行能力和共享 UI 是这些产品责任域共同使用的基础；产品功能域、技术依赖层、用户入口和部署单元需要分别说明，不能相互替代。工程治理贯穿上述各域：每项能力都必须能回答“给谁用、由谁维护、依据什么定义、依赖什么、支持到哪里、怎样验收和退出”。

## 4. SRS：正式需求

AR-01–AR-17 均为本项目必须逐项满足的要求，适用范围见 §5。已有实现满足的，提交证据并保留；不满足的，实施整改。供应商不得自行把必做项改为未来规划，也不得仅因存在一项要求就重新建设已满足要求的能力。

### AR-01 产品能力矩阵与归属

**要求：** 对全平台现行能力完成统一盘点，明确产品定位、用户、责任归属、公共契约、必要依赖和支持边界。区分基础能力、构建工具、业务运行、治理与行业扩展。识别重复职责、过度拆分和不合理合并，完成保留、整合、下沉、独立、退役或补全的处置。

**验收结果：** 每项职责有唯一负责方，多能力可以按契约组合。矩阵分别列出“支持状态、重构处置、验收证据”，避免把“需要重构”误作“不可用”。任何现有能力均有去向；新团队可以据此判断应用依赖和交付边界。

### AR-02 产品术语与概念模型

**要求：** 消除核心概念中的同名异义、同义异名和没有必要的历史概念。区分产品功能域、技术依赖层、用户入口和部署单元；账号、人员、岗位、组织、地点、模型元素和业务记录之间的关系明确。

**验收结果：** 术语在用户界面、公开契约和现行文档中一致。新开发者能理解各概念及关系，无需先了解历史演变；已有身份和历史数据的含义得到保留，不以改名掩盖语义变化。

### AR-03 架构分层与职责边界

**要求：** 审查内核、宿主、应用 API、平台应用、共享前端、构建工具与行业应用的实际依赖。各层责任有限且明确，跨域协作走受支持的边界。通用基础不承载行业特例，消除无必要的循环依赖、私有状态访问和契约旁路。

**验收结果：** 架构说明与实际依赖一致，关键边界可持续检查。因职责错误造成的复杂性已经处理；文件或目录调整必须体现责任改进，不能独立作为验收成果。

### AR-04 高内聚、低耦合

**要求：** 模块内部的行为和状态具有一致所有权，跨模块依赖明确、有限且必要。解决难以独立理解或修改的职责集中；必要的协调职责可以保留。接口按消费者需要表达能力，避免暴露内部细节。

**验收结果：** 以新增业务能力、修改共享交互及替换外部系统三类变更，说明前后影响范围和维护成本。局部变化不再无理由地牵动无关模块；拆分和保留均有实际依赖证据。

### AR-05 模块组合与扩展生命周期

**要求：** 明确代码包、业务包、组件和受控定义的发现、装配、配置、兼容、升级及退役边界。扩展复用原有身份、权限、租户隔离和执行治理；可选能力不形成无理由的强制依赖，客户扩展不依赖长期平台私有分叉。

**验收结果：** 在现有受支持的扩展模式下，实际证明代表性能力的接入、升级、替换或退出及依赖处理。新增行业能力通过公共契约完成，无需反复修改无关核心。运行时热插拔和插件市场不属于本项目的默认要求。

### AR-06 单一权威来源

**要求：** 业务对象、规则、权限、页面绑定、执行定义、资产版本、业务事实与接受结果均有明确权威。编辑器、代码 API、AI 工具和运行视图使用一致语义；派生数据可追溯，避免多处独立修改同一事实和人工同步相同规则。

**验收结果：** 跨入口观察和操作遵循一致的身份、规则、权限与版本。权威来源与派生关系能够解释，变更正确传播且历史含义保持。自治领域、缓存、投影、编译制品和不可变历史按各自责任保留，不强制合并为一个数据库或模型。

### AR-07 正向状态、执行与结果流

**要求：** 重要状态变化具有明确入口、归属、接受边界与结果，跨应用保留因果关系。消除绕过提交和授权边界的隐式写入及竞争性业务决定。区分接受结果恢复、历史重新计算、读取投影和外部执行。

**验收结果：** 同一业务决定可追踪到其定义、执行主体和结果；异步、重试与恢复不会重新解释或改变已接受的决定，不产生未声明的重复效果。“正向”约束依赖与权威传播，允许符合业务语义的反馈、循环和补偿。

### AR-08 业务模型与应用装配

**要求：** 对象、关系、查询、动作、页面和流程基于共同契约组合，代码、可视化和 AI 辅助创作不产生竞争权威。行业规则保留业务归属，共性能力由适当平台归属承接，保留身份、权限、版本与历史保证。

**验收结果：** 酒店和制造两类应用复用相同平台能力，保持各自业务含义；组合不以复制执行机制或独立维护同一语义为前提。所需查询、派生读取和历史快照具有明确责任。

### AR-09 共享服务整合

**要求：** 审查身份、组织、文件、搜索、知识、通知、审计、任务、查询和集成等共享能力。确定跨领域责任，收回行业应用中已被共享能力覆盖的重复实现，同时防止共享服务因单个业务需求无限膨胀。

**验收结果：** 共享能力具有稳定边界及可验证的跨行业复用价值，消费者完成迁移，冗余路径退出。共享能力与行业规则的区分能够由实际职责解释。

### AR-10 应用、资产与环境的完整生命周期

**要求：** 应用及其必要资源和外部依赖具有清楚的身份、版本和生命周期，贯通定义、构建、校验、测试、发布、运行、升级及退役。测试与正式运行隔离，环境配置和凭据按环境治理。客户扩展、在途任务和历史数据的兼容责任明确。

**验收结果：** 独立交付人员可完成 §5.2 两行业应用的目标环境交付、受支持升级及失败处置，实际运行版本与交付集合可核对。集成依赖不能因不在当前发布覆盖范围而遗漏；不支持的变更事先拒绝并说明，不用单项发布成功替代完整应用交付。

### AR-11 自动化、计算与 AI 的执行治理

**要求：** 动作、工作流、人工任务、普通计算、AI 函数和智能体具有明确职责，在组合时共用身份、授权、版本和结果规则。等待、取消、重试、人工接管和恢复可解释。模型、工具、上下文、预算及质量评估贯穿其实际调用入口。

**验收结果：** 已承诺的持续 Flow 路线完成；真实 AI 任务能说明依据、质量、成本和人工确认，建议与业务执行有明确边界。消除重复权威和竞争性执行路径，同时保留不同执行类型的必要语义，不要求合并为一个通用引擎。

### AR-12 外部集成与数据流治理

**要求：** 连接、来源、数据集、转换、同步、匹配、回写和外部效果构成可交付、可运营的能力。来源、加工关系及使用范围可追踪；重试、恢复、结果核对和人工处置有一致边界。连接器扩展不绕过业务权威。

**验收结果：** §5.2 的既有外部来源经实际数据流形成可用业务记录；回写结果可确认，失败可定位和恢复，结果不明确时不能报告成功。交付所需的环境配置、版本依赖及访问权限可完整管理。

### AR-13 前端组件与统一产品体验

**要求：** 基础控件、复杂组件、业务部件、页面绑定和工作区各有明确责任，避免重复的语义绑定和状态机制。构建者、业务人员与管理员的任务路径连贯；编辑、草稿、保存、发布和业务执行可区分。主题、双语、键盘与无障碍、反馈、性能及已支持设备范围保持一致规范。

**验收结果：** 表单、弹窗、表格、Inspector 与动作确认使用同源类型、约束、引用选项和错误口径。无效输入、无权、冲突、失败和重试可在原上下文处理，不无说明地丢失输入。两行业和构建者任务均经实际走查；以现有共享体系完成整改。

### AR-14 一致性、安全与恢复保证

**要求：** 明确业务提交的原子性边界及受支持故障下的恢复保证。人员、服务和 AI 的授权一致；记录、派生读取、搜索、预览、导出、引用和诊断遵守来源权限。租户与宿主管理职责、身份和故障隔离边界清楚。

**验收结果：** §5.2 路线证明允许、拒绝、撤权、租户隔离、版本更新和恢复行为符合声明。已接受的业务与安全不变量不得退化，恢复不重复裁决或外部效果；证据明确适用条件，不把局部通过宣传为全平台无条件保证。

### AR-15 运维、诊断与资源治理

**要求：** 从失败业务任务可以定位定义、版本、执行、数据来源与外部依赖，并按权限采取处置动作。资源、性能、容量、成本和保留责任可解释；长期存在的数据、日志、制品及队列具有清理与异常处置规则。

**验收结果：** 在 §7.2 的运行边界内能够诊断、恢复或明确终止，资源增长符合保留承诺。清理不会破坏仍需履行的历史读取和恢复义务。持续 Flow 及其制品的未完成生命周期属于本项目必须收口的实际缺口。

### AR-16 代码清理与复杂度治理

**要求：** 有依据地清理重复职责、废弃入口、无效导出、闲置依赖、临时脚本、过期文档、无价值抽象及契约逃逸。替代应同步迁移消费者和退出旧路径，不保留长期平行实现，也不把复杂性转移给前端或构建者。

**验收结果：** 实际处置可核对，已无必要的重复维护点被消除；仍承担历史兼容、恢复、审计或已发布接口义务的代码有保留依据。每项新增抽象有现实职责和复用收益，代码量、拆分数量均不作验收指标。

### AR-17 持续工程治理与独立交接

**要求：** 架构决策、能力归属、依赖方向和公共契约可持续维护和检查；生成物、现行文档与实现一致。复用现有开发、检查和交付路径，测试证明长期不变量及关键任务，代码审查处理重复建设、职责膨胀和边界逃逸。

**验收结果：** 独立于实现人员的 FDE 或接手团队能够构建、交付、变更和排障，现有检查覆盖调整后的关键边界。文档各有唯一维护位置，任务完成即退出执行队列；无需原作者隐性知识，也不以额外脚手架或长期报告体系维持结果。

## 5. 已下达的实施范围

### 5.1 必做范围

**审查覆盖全平台：** 内核契约、宿主、公开应用 API、平台与行业应用、跨应用协议、共享前端、工作区、构建器、交付运行方式及现行工程文档。第三方依赖和生成物检查其使用、契约与生成一致性，不重写第三方实现。

**重构覆盖实际缺陷：** 按 AR-01–AR-17 处理现行产品中的职责错误、重复权威、不必要耦合、契约旁路、冗余路径和治理缺口。对已满足要求的部分给出证据并保留；对需要整改的部分交付实际代码和迁移结果。代表性场景用于验收共性能力，不能成为只修演示应用、保留其他同类缺陷的理由。

**功能补全有明确边界：** 完成 §5.2 的实际任务链及其必要依赖，包括集成依赖的完整应用交付、既有持续 Flow 主线、共享输入体验、真实 AI 任务治理及相关版本、权限、恢复和资源生命周期。现有实现边界是差距证据，不能用于豁免本项目明确要求补齐的内容。

供应商先以现有审查证据完成全局功能、权威和依赖处置，再按完整功能块持续交付。当前持续 Flow 工作并入本项目，保留已实现成果和原接受条件。它不再是平台整体治理的唯一主线。

### 5.4 实施约束

- 保留现有平台宗旨、语言中立内核契约、受控扩展边界及有效业务数据语义。
- 复用已正确工作的能力；结构方案服务于实际职责和变更成本，不默认全量重写、微服务化或全面换框架。
- 不把一个复杂模块拆成大量相互依赖的小模块，不用更多适配器掩盖错误职责，不把后端复杂性转移给前端或构建者。
- 不要求所有功能采用同一个引擎、模型、菜单或存储；共同契约、权威和使用结果必须一致。
- 不以隐藏入口代替退役，不以临时垫片、Mock、TODO 或未来任务代替范围内完成。
- 不追加第二执行队列、长期报告体系、测试框架或辅助平台；新增抽象、验证和工具必须有当前任务的必要性。
- 保持平台独立性。技术选择不能引入未经确认的新业务权威或不可替换的专有依赖。

## 7. 验收、完成与变更

### 7.1 逐项验收

AR-01–AR-17 必须逐项有“实际交付内容、适用边界、交付版本、验证证据、验收结论”，并与 S-01–S-05 对应。现有正确能力可以直接凭有效证据满足要求；代码存在、接口存在或 ADR 状态为完成，均不能单独证明全部产品要求已满足。

架构验收看责任、权威和变更影响；产品验收看完整任务；可靠性验收看实际授权、版本与故障行为；维护性验收看重复路径退出和独立交接能力。不得以删除文件、组件数量、测试数量、覆盖率单一数字或文档厚度代替这些结果。

### 7.2 测量与运行边界

已有明确规模、预算、隔离及恢复承诺的，沿用原标准并提供实际证据，不能在重构中降低。尚无量化阈值的，供应商在首次实施前记录同环境、同数据与同任务的基线，在交付时提供可复现的前后比较和支持边界；不得隐瞒退化或凭空宣称生产级容量。

| 维度 | 必须呈现的证据 |
| --- | --- |
| 架构与维护成本 | 核心概念和归属可解释；典型变更涉及的责任域、重复修改与人工同步点得到治理 |
| 应用交付 | 两行业任务的实际交付步骤、依赖、环境绑定、升级和失败处置，接手人员可独立执行 |
| 使用一致性 | 相同语义跨入口的输入、错误纠正、冲突、无权与提交行为；双语、键盘和已支持视口的实际观察 |
| 运行与恢复 | 本项目关键路径在原支持故障范围内的结果，包含持续任务、外部效果及必要持久制品；恢复过程不破坏接受结果 |
| 资源与成本 | 与交付范围匹配的容量、资源增长、保留规则和 AI 用量；已知限制及达到边界时的行为 |
| 独立交接 | 接手团队依据正式材料完成交付与排障，不依赖实现人员私有说明 |

真实模型质量、负责人体验和部署环境效果分别记录。替身、静态检查、浏览器操作和持久恢复各自证明其覆盖内容，不能相互冒充。必需的凭据或外部环境未就绪时记录具体阻塞，继续其他工作；相关要求保持未验收，不能据此报整体验收通过。

### 7.3 最终完成条件

本项目同时满足以下条件才完成：

1. AR-01–AR-17 在本项目范围内全部满足，S-01–S-05 有完整且可复核的结果。
2. D-01–D-10 对应实际交付，应用、数据、契约、历史与安全保证按要求保留。
3. 必要的消费者迁移、旧路径退出、运行环境更新和现行文档修正已经完成。
4. 独立团队可以使用和维护交付结果，已知范围内阻断项关闭，没有隐蔽的临时双轨或未交付依赖。

能力已实现但使用验收未完成，应分别报告；范围内仍有必做缺口，就保持项目未完成。不能把必要收尾转成新项目或下一批收费任务。

### 7.4 变更控制

供应商在既定范围内自主持续实施。新增产品范围、额外费用、削减必做要求、扩大部署影响或对既有公共契约及业务保证作不兼容变更，才需要向负责人提交具体变更说明：原因、影响、替代方案、费用和验收变化。仅受该变更影响的部分等待决定，其余已授权工作继续。

正常重构、必要依赖修正、删除已被替代的无用路径、补足本项目要求的验证和更新文档均属于已授权工作，不另设开工审批。架构决策按仓库规范记录；记录决策不等于每个内部设计都需要负责人重新授权。
