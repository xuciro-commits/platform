本文件根据项目所有者的连续澄清、现有架构文档和外部一手资料，明确平台的长期产品方向，提出架构判断尺度。它属于长期设计依据；具体工程事实以代码为准，正式架构描述仍在 [Platform.md](Platform.md)，有长期成本的决定进入 [ADR](ADR/)，活动计划仍只维护在 [WorkQueue.md](WorkQueue.md)。

下文区分所有者明确表达的意图与顾问提出的方向性建议。外部参考用于解释选择，不自动成为项目规范。本评审不改变已接受的 ADR，不规定目录重组、语言更换、组件接口或开发顺序。项目维护者应结合已有实现和约束，自主决定如何落实这些意图。

## 1. 评审判断

现有架构已经明确“业务可以变化，底座应保持稳定”，也已经区分语言中立的内核契约、可替换能力与领域代码。这些方向与所有者的目标一致，具有保留和继续验证的价值。

目前的主要不足在于产品表达：内核假设、契约与参考切片已经具体化，但平台如何帮助开发者构建不同软件、让组织组合业务能力、让最终用户连续工作，还没有形成同等清晰的顶层描述。已有抽象的技术正确性，尚不能单独证明平台的产品完整性。

建议将**业务软件的构建、组合、运行与持续演化**确立为顶层主线。内核与通用能力的必要性，由它们对这条主线的贡献解释；已有 K1–K9 继续按证据评估，既不因为已经实现而永久固化，也不因为引入新参考而被整体推翻。

## 2. 所有者的产品意图

### 已明确的目标

- Platform 为不同软件提供共同的基础 UI 和底层支持。酒店、制造、零售、CRM、HIS 等体现其应能承载的业务多样性。
- 业务以类似“业务包”的方式接入，能够按需要组合成不同软件。平台不能被最初几个应用的业务形态限定。
- 一家大型组织能够利用这个底座管理不同业态；这一场景是平台需要支持的应用形态，并不将平台限定为一款集团管理软件。
- 顶层方向需要有长期一致性。具体设计和实施由持续维护项目、掌握实现细节的开发者负责。

### 建议采用的产品定义

> Platform 是一个可组合、可演进的业务软件构建与运行平台。
>
> 它提供一致的工作环境、基础 UI、通用技术能力和稳定的扩展契约。业务包定义各自的业务对象、关系、规则与可执行行动，并贡献相应的界面和运行能力。开发者通过组合这些能力形成具体软件，组织通过这些软件开展工作。
>
> 当产品、流程、组织结构或经营领域发生变化时，平台应支持业务能力的增加、调整、替换和退出，同时保持数据、历史、权限和工作状态的连续性。

这一定义综合了所有者的明确目标与本评审的建议。其中，“统一的业务行动模型”和“受管理的能力生命周期”是建议纳入的架构方向；让 AI 参与业务工作是应保留的扩展空间，其自动化程度尚未确定。它们都不意味着必须先建成一个完整的通用引擎，才能继续交付业务功能。

已有文档对个人、本地优先与边缘运行的支持仍然有效。本次澄清未授权取消这些场景，也未要求每个场景承担大型组织部署的全部复杂度。

## 3. 产品应带来的具体变化

| 使用者 | 应获得的能力 | 判断价值的方式 |
|---|---|---|
| 业务软件开发者 | 使用共同的 UI、运行支持和扩展契约，实现专业业务 | 新软件的主要工作集中于业务知识，重复基础设施显著减少 |
| 软件交付者与组织管理员 | 选择业务能力，管理权限、参数、版本和运行状态 | 能说明当前运行了什么、为何依赖它，以及变化会影响什么 |
| 最终业务用户 | 在一致的环境里完成专业工作，并跨业务能力协作 | 导航、对象上下文、操作反馈和异常处理连贯，专业交互不被压缩成统一表单 |

一个示意场景：酒店软件已经运行，后来需要加入客户与商机管理。新增能力应能够与预订业务建立明确的关系，使获授权的用户从客户进入相关预订，或由商机发起后续业务动作；预订与商机各自保持自己的规则和数据责任。组合的价值应体现在完整业务过程中。

另一团队可以在同一底座上构建医疗软件，复用工作台、UI、任务、文件和权限机制，同时拥有患者、预约、就诊等专业模型。共同的技术表达不要求把患者、客户和住客合并成一种通用业务对象。

这些例子描述目标体验，不指定下一条切片、实施范围或交付顺序。

## 4. 应同时考虑的三个架构视角

三个视角用于检验设计的完整性，不要求把仓库重划成三个层，也不预设它们必须对应独立服务。

### 业务表达与执行

平台需要让业务能力具有明确含义：系统里有什么对象，它们怎样关联，哪些查询和行动被允许，谁能够使用，以及行动产生什么结果。

建议业务包对外提供有责任归属的业务能力，使专业 UI、自动流程以及获授权的 AI 可以使用一致的业务规则。不同调用者可以拥有不同的可见范围、授权和人工确认要求；共享行动语义不意味着共享全部权限。

具体业务含义由业务包维护。通用模型的职责是支持表达、发现和受控调用，并保持可追溯性；它不应预先定义所有行业的实体，更不强制某种图数据库、统一存储或完整事件溯源实现。

新建业务和既有软件接入都应有位置。平台可以通过显式映射和接口接入外部系统，保留来源、数据责任和权威归属，避免把“使用平台”设定为“先迁移所有业务”。

### 能力组合与生命周期

业务包和可替换的平台能力应能说明自己提供什么、依赖什么、在什么范围内生效，以及如何开始和结束工作。

组合应覆盖依赖、兼容、激活、停用、升级和运行影响。界面入口、事件订阅、后台工作等应有明确归属，组件退出后能够清理其运行时贡献。对于依赖暂时不可用、版本不匹配或存在进行中工作的情况，系统行为应可解释、可验证。

必须分别处理三类变化：运行时资源释放、持久业务数据迁移、已执行业务行动的补偿。停用预订包不能抹去已接受的预订；移除事件处理器不能撤销已发生的外部操作。

运行时热替换、独立部署、按租户启用和构建时装配是不同选择。长期需要可演进，不等于当前所有组件都必须支持热插拔。能力可替换也不改变其应遵守的隔离、权限和正确性契约。

### 软件交付与工作体验

业务包应被理解为一块完整业务能力，可能同时包含模型、逻辑、接口、任务和 UI；这不规定它必须是一个物理包或一种语言。

包与包之间的协作、标准业务上的行业扩展、面向特定客户的差异，都需要有明确归属。独立的连接或扩展包是一种可选组织方式，其价值在于避免让每个基础包了解所有其他业务。

软件方案负责选择和组合能力，运行实例负责承载具体组织的使用。CRM、HIS 等可以由多个业务包组成，包的粒度应随真实复用和变化压力调整。

统一 UI 应降低重复建设，并提供一致的导航、实体引用、状态反馈和操作习惯。专业页面仍应有充分表达空间；跨业务组合还应维持上下文和授权边界，使用户能够完成连续工作。

### 两个需要明确的借鉴边界

**Palantir 的价值在于业务表达和执行的连贯性。** 本项目可以学习其对象、关系、逻辑、行动与安全的结合，不因此承诺重建完整 Foundry，不把统一语义理解为一套覆盖所有行业的实体模型。其应用与工具链是参考，当前类型化代码组合 UI 的原则没有因这份评审而改变。

**Cordis 的保证有明确适用范围。** 论文将可恢复范围限定在能够控制并恢复的位置；外部影响并不自动可撤销，不可信代码的沙箱也需要额外机制。接口版本兼容仍有需要处理的问题。Harness 当前标为开发者预览，论文为预印本；应借鉴其问题定义和机制，再验证是否适用于持久业务系统。[论文 §6.1、§6.3、§6.6](https://arxiv.org/pdf/2608.25512)、[Harness 状态](https://github.com/deepseek-ai/deepseek-harness)

配置选择已有能力、配置装配关系，与用配置语言实现复杂业务规则，应分别评估。可组合性并不要求将业务逻辑改写成配置。

## 6. 对当前项目的方向性建议

1. **以产品变化能力解释架构。** 新领域、业务协作和运行环境变化，应主要通过有边界的扩展完成。抽象是否成功，取决于实际变化的代价，而不是概念数量或组件数量。
2. **区分业务正确性契约与组合运行机制。** 当前内核关注身份、事实、决策、权限、同步等语义；Cordis 一类机制关注能力如何存在和协作。两者责任不同，应明确衔接，不预设替代关系或必须建设两个物理内核。
3. **让跨业务协作具有公开语义和责任。** 数据归属、行动权威和接口含义应明确。跨包关系由显式契约建立，避免依赖其他包内部表结构；不以通用对象模型抹平领域差异。
4. **同时设计人的工作体验与程序调用能力。** 同一业务规则可以被界面和自动化使用。AI 可以是受授权的调用者，也可以辅助开发，但不能因模型建议而绕过业务规则、权限或审计。
5. **用生命周期保证长期可维护。** 能力的引入、升级、退出必须考虑运行中工作与历史连续性。运行资源清理、数据迁移、业务补偿各有责任和验证方法。
6. **保持隔离与语义组合的边界。** 组织、业务包和租户承担不同职责。集团级汇总与跨业务协作需要明确授权与数据交换路径，不能由“统一平台”推导出无限制访问。
7. **保留现有工作的证据价值。** 契约、向量、参考切片、统一 UI 和离线提交机制应继续作为判断依据。新方向可以揭示缺口，但不构成整体重写、换栈或先暂停一切业务交付的理由。

## 7. 判断方向是否落实的证据

下表是产品与架构的评审尺度，不是一份要求全部立即实现的任务清单。维护者可以选择最有代表性的真实变化，以最小实现检验这些要求。

| 要求 | 应能观察到的证据 |
|---|---|
| 能承载差异明显的软件 | 新业务主要新增自己的代码；既有内核与宿主无需反复加入业务分支 |
| 业务能力可独立使用和组合 | 同一能力能够进入独立软件，也能参与另一软件的完整流程 |
| 语义和行动可复用 | 界面与获授权的自动化使用一致的业务含义、规则与结果记录 |
| 基础 UI 有价值，专业交互有空间 | 常用交互可以复用，房态、调度、就诊等专业工作方式能够自然表达 |
| 运行组合可解释 | 能说明某项能力为何启用、依赖什么，以及依赖失效或替换的影响 |
| 能力退出有确定行为 | 运行时贡献不泄漏，进行中工作有处置方式，历史数据不因卸载而失去归属 |
| 业务变化保持连续性 | 组织和流程调整后，引用、权限、历史与旧客户端兼容有明确处理 |
| 客户差异可以维护 | 标准能力和扩展的责任清晰，升级能够验证兼容，而非靠长期复制分叉 |

## 8. 留给Agent的判断空间

尚未由所有者确定的事项包括：业务包首先面向自有团队还是第三方生态；客户能修改到什么程度；AI 的自主执行范围；哪些场景需要运行时安装、独立发布或独立部署。这些事项应按真实需求作出决定，不从外部产品的功能表自动推导。

建议后续开发 AI 将本文件用于检查设计是否服务产品意图，结合代码说明哪些要求已经满足、哪些缺口值得处理，再自行提出合适的实现路径。既有机制能够达到目标时应优先复用；需要改变长期架构时，沿用项目的 ADR 与契约验证规则。

本评审提出的目标是：**让不同团队能够在稳定底座上表达专业业务能力，将这些能力组合成完整软件，并在业务与运行环境变化时保持可理解、可控制、可追溯的行为。** 具体实现应由项目中的证据和维护者的工程判断决定。

## 9. 顾问的实现构想：供项目Agent独立取舍

本节回应所有者的进一步提问：如果由我承担开发，我会怎样理解技术路线、界面交互和软件形态。以下以第一人称描述一条可能的路径，属于顾问个人判断，不是已经采纳的设计、开发指令或第二份工作计划。维护者可以采纳、改造或舍弃，无需逐条实现或回应。

我对所有者需求的理解来自本次连续对话和可见的项目记录：希望拥有一个长期服务自身业务变化的平台，重视基础 UI、底层复用、专业软件的组合能力，并希望开发 Agent 保持独立判断。这里没有假定掌握所有历史对话，也不把尚未提出的未来需求写成既定要求。这份文档可以保存已明确的意图，并随新的澄清更新；旧的顾问设想不应限制所有者未来的选择。

### 9.1 如果由我开发，我会怎样推进

我会从已有业务中选择一条足够真实的完整工作过程，观察对象如何被理解、动作如何被授权和执行、界面如何反馈、数据如何保存、失败后如何继续。平台抽象的价值，应能够在这个过程中被看见。

在此基础上，我会通过变化来检验设计：加入一项业务能力，让两个包合作，替换某个基础能力，或者把同一业务放到另一种终端。变化牵动了哪些代码、造成了哪些重复、是否破坏已有行为，比模块数量更能说明边界是否合适。反复出现的机制值得下沉；只有单一领域需要的知识继续留在业务中。

我的早期实现倾向是边界清楚的模块化服务端与统一 Web 工作台，优先使用当前代码可以承受的装配方式。需要独立扩容、发布、隔离或长时间离线运行时，再评估相应的部署边界。服务拆分和热替换分别解决特定问题，应有各自的收益证据。

Palantir 会促使我重视业务能力的统一表达；Cordis 会促使我重视依赖、作用范围与退出行为。我会在真实工作过程中实现这些性质，并根据缺口决定是否需要更通用的机制。这里没有指定必须先开发 CRM、HIS 或新的插件引擎，现有酒店、制造及其他积累都可以提供验证材料。

### 9.2 我倾向的技术栈及其职责

基于当前仓库，我会优先延续已有技术积累。以下列出选择理由和重新评估的条件，不固定版本、供应商或实现接口。

| 责任 | 我的初始倾向 | 选择理由与取舍空间 |
|---|---|---|
| 业务服务、事务与集成 | 延续 Go，按业务责任组织模块，通过公开契约协作 | 已有服务端和参考切片可复用；是否拆进程由运行与交付需求决定 |
| 业务 Web 界面 | 延续 TypeScript、React、Vite 与 `@platform/ui`，使用现有 Radix、Tailwind、TanStack 等积累 | 已有类型化页面和组件体系；新增界面族应由实际工作方式驱动 |
| 组织业务持久化 | 优先评估既有生产化方向中的 PostgreSQL | 希望领域状态与对应记录有清楚的事务边界、迁移与恢复路径；分析、检索和高频观测存储可按实际负载另选 |
| 跨平台桌面与本地能力 | 延续 Tauri；有持久草稿、离线队列或本地索引需求时评估 SQLite 等本地存储 | 让业务界面复用已有 Web 能力，原生部分承担确有必要的系统与设备接入；浏览器持久化另按其运行条件设计 |
| Apple 深度集成与特定本地产品 | 保留现有 Swift 路线 | 原生交互和 OS 集成需要有表达空间；哪些行为共用契约、哪些界面原生实现，由产品体验判断 |
| 边缘接入和专用计算 | 根据设备协议、部署条件和测量结果选择 Go 或 Rust | 语言增加应带来明确价值；不预设要将所有客户端统一到 Rust 内核 |
| 能力组合与插件机制 | 先借鉴显式依赖、服务契约、受控注册与生命周期管理；再评估具体运行时 | Cordis 值得做针对性验证，但采用它不自动意味着重写 Go 后端，也不保证跨进程、数据迁移和版本兼容问题已经解决 |
| AI 与外部系统 | 经受授权的业务接口或适配器接入，模型与供应方保持可替换 | 模型负责理解、建议或获授权的执行，业务规则、身份和记录仍有明确归属 |

上述倾向延续 [平台运行时设计](Platform.md)、[Web UI 决策](ADR/0004-web-ui-stack.md)及 [边缘实现决策](ADR/0005-no-shared-edge-core-yet.md)。Tauri 的 Web 界面与原生能力组合方式、PostgreSQL 的事务语义分别可参见其[官方介绍](https://v2.tauri.app/start/)与[事务文档](https://www.postgresql.org/docs/current/tutorial-transactions.html)；这些资料支持能力判断，不代替本项目的选型验证。

我会让契约和兼容性检查承担跨语言一致性的责任，避免仅为表面统一而让每种语言实现全部能力。已有测试、真实运行约束或维护成本证明其他选择更好时，应以这些证据调整我的初始倾向。

### 9.3 我会怎样理解软件形态

为了让终局可想象，我暂时按**五种承载形态：三类有界面的客户端、两类无界面的运行端**来考虑。它们共享业务能力，未必对应五套代码库、五个独立产品或五项近期任务。CRM、HIS、酒店等是业务组合；下表描述这些业务可能运行和被使用的方式。

| 形态 | 我想象的使用方式 | 为什么可能需要它 |
|---|---|---|
| 浏览器专业工作台 | 在同一工作环境中处理客户、工单、预订、分析和异常；按角色显示入口 | 作为大多数组织业务的主要入口，便于交付和集中维护 |
| 桌面或原生专业客户端 | 长时间工作、多窗口、本地文件与设备接入；必要时保存离线工作 | 承接浏览器难以充分满足的本地体验；Tauri 与已有 Swift 产品可以各按场景发挥价值 |
| 移动与现场任务端 | 手机、平板或触屏终端上完成扫码、检查、确认、采集、交接等短任务 | 现场操作需要更聚焦的交互；不应只把桌面密集界面缩小，Web 或原生实现由场景决定 |
| 服务与自动化运行端 | 业务 API、后台任务、系统集成和获授权的 Agent 调用 | 同一业务能力可在没有前台窗口的情况下运行，并向界面提供状态和结果 |
| 现场边缘网关 | 在门店、工厂或设备附近采集、缓冲和转发数据；按明确权威边界继续有限工作 | 处理网络、协议、设备与现场连续性要求，恢复连接后有确定的同步与对账行为 |

管理控制台、业务包开发工具和运行观察界面，我会先视为工作台中面向不同角色的视图；若使用方式明显分化，再考虑独立产品。AI 助手也可以嵌入已有界面，或由自动化运行端承载，其存在本身不必增加一种客户端。

个人本地软件、组织集中部署和多场所加边缘部署，可以选择不同组合。我的重点是复用合适的能力与契约，让每一种形态只承担自己的必要复杂度。

### 9.4 我对界面和用户交互的想象

我会把主要工作界面组织为“任务与对象相互连接”的工作环境。用户既可以从待处理任务、异常或提醒进入，也可以从搜索、列表、日历或专业视图找到对象；进入对象后，能看清当前状态、关联关系、依据、历史以及自己可以执行的动作。

对专业工作台，我倾向于延续现有的导航、实体路由、多标签与布局能力，并让信息密度服务实际工作。列表筛选、批量操作、键盘操作和并排比较适合持续处理大量业务；对象详情与上下文面板帮助用户判断；状态和反馈应明确到足以区分草稿、提交中、已接受、冲突和失败。

这只是交互结构设想，不是固定布局：酒店可以以房态和时间为主，制造可以以工序和资源为主，医疗可以以一次就诊的工作上下文为主。共用组件提供一致行为，业务包决定哪些专业关系值得展示。移动和触屏端则围绕当前任务减少分支，突出下一步与完成结果。

例如，一名计划员发现供货延迟后，可以沿关联关系查看受影响订单，对照替代方案，再通过获授权的动作调整安排。界面保留判断依据、执行状态和后续异常。相同过程可以由人直接操作，也可以由 AI 帮助检索、解释和准备方案。

如果加入 AI，我会让它出现在业务上下文中，能够说明建议依据、影响范围和执行结果，并在授权范围内调用已有动作。对话、表格、专业视图和直接操作可以互相补充；用户不必为了完成确定的常规工作而反复描述指令。自动执行到哪一步、何时需要人工确认，应由具体业务与所有者确定。

### 9.5 这些构想如何交给后续 Agent

我希望这些设想提供一个可以讨论和检验的终局画面。长期维护项目的 Agent 更接近工程事实，应自行比较现有实现、用户近期目标与上述设想，选择投入最小、验证价值最高的推进方式；也可以提出更好的形态分类、技术组合或交互方案。

本节不新增排期、工单或必须实现的产品线。采纳的工作仍进入唯一工作队列，形成长期成本的决定仍按既有方式记录。所有者后续表达的新需求可以修正这些设想，维护者无需为了迎合顾问方案而放弃独立判断。
