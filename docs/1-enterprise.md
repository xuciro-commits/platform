# 1 企业架构

## 目标

说明平台为谁存在、终局是什么，以及业务、应用、数据、技术四个视图如何组合。其他六层的取舍以本层的终局与质量目标为最终依据。

## 1.1 意图与终局

意图：让没有驻场工程团队的企业，也能把自己的数据变成受治理、可执行、可交付的业务应用。

为谁：需要私有化部署的中型企业（制造、酒店、供热等行业），以及为它们交付应用的构建者。它们的数据散在 ERP、MES、PMS 和表格里。Foundry 一类平台的模型能解决问题，但交付靠驻场工程师；低代码工具便宜，但只有表单与流程，没有受治理的业务语义。

主张：Foundry 的模型（本体、动作、治理）是对的，贵在交付；Frappe 的框架（一个类型开箱即得一整套应用能力）把交付做便宜了，但行为写在代码里、定制挡住升级、生成的界面是旧的。平台用前者的模型做出后者的体验，在四处下注：

| 下注 | 内容 | 成立的信号 |
|---|---|---|
| 产品包替代驻场 | 行业知识做成版本化的声明式产品包，经 Marketplace 安装；客户在其上扩展而不阻断升级 | 新客户从安装到业务用户执行第一个动作，平台方不改代码、不上门写配置 |
| 一条日志、一个进程 | 全部权威状态在一条接受结果日志里，宿主是一个 Go 进程 | 一台机器无 Docker 可部署；任一状态可逐字节重放与审计 |
| AI 是一等构建者 | 资源全部是声明式定义，写入全部经动作；智能体与人用同一批工具、同一套权限与审计 | 行业应用的主体由智能体经平台工具产出；宿主代码由 AI 代理按规范编写（[method](method.md)） |
| 界面由类型生成 | 声明一个对象类型，就得到列表、记录、录入、看板、收件箱与接口；界面是类型元数据驱动的官方模板，不为每个应用手写前端 | 一个新对象类型从声明到业务用户可用，不写一行前端代码；行业应用里没有手写页面 |

两个基准各管一面。内核的能力边界与资源模型对齐 Foundry（1.9），不另立模型；“超越 Palantir”只衡量同一个行业应用的交付时间、部署与升级的成本、由智能体完成的比例。应用框架的体验以 Frappe 为要胜出的对手（1.11）。功能数量不是目标。

终局分三段，按顺序推进，前一段不稳不进入下一段：

| 阶段 | 产出 | 判断已成的标准 |
|---|---|---|
| 平台成形 | 以 Palantir Foundry 为基准的构建平台：数据集成 → 本体 → 逻辑 → 应用，治理与 AI 横贯 | 一位构建者能在空租户里走完黄金路径（5-experience §5.2），不写代码、不改宿主 |
| 行业应用 | 用平台自己的工具构建的行业应用（制造 MES、酒店 PMS、供热等），以声明式产品包交付 | 行业应用只由平台资源组成；平台无行业专有代码 |
| 交付运营 | 经 Marketplace 安装到客户租户，客户构建者在其上扩展，版本可升级 | 客户扩展不阻断升级；升级只应用已接受映像 |

推论（这些推论约束其余各层）：

- 行业应用是探针，不是产品分支。行业需求先问“别的行业会不会也需要”：会，就成为平台能力；不会，就用平台资源表达，不进宿主代码。
- 平台的每项能力都要能被打包、安装、升级。不能进入产品包的能力不算完成。
- 客户与我们使用同一套工具。没有“内部专用”的构建路径。
- 自举指平台用自己的工具构建自己交付的应用：行业应用与内置应用都以产品版本经 Marketplace 安装。分两级：一级，行业产品包全部由平台工具产出；二级，能用本体、动作与 Workshop 表达的内置应用改为系统产品包（[2-product R8](2-product.md)）。自举不指把宿主源码放进平台管理（源码在 git；租户里的副本只能是只读陈列，并带来一条特例路径）。

## 1.2 参与方

| 参与方 | 是谁 | 关心 |
|---|---|---|
| 平台方 | 本项目负责人与 AI 代理 | 平台的一致性、可演进 |
| 行业应用构建者 | 起初是平台方自己 | 用平台工具高效构建、打包、发布行业应用 |
| 客户管理员 | 客户租户的 IT | 成员、权限、标记、模型供应商、安装与升级 |
| 客户构建者 | 客户的业务分析师与开发者 | 接入自有数据、扩展已安装应用、搭建新应用 |
| 业务用户 | 客户的一线员工与管理者 | 找到对象、执行动作、处理任务 |
| 宿主运维者 | 部署平台的一方 | 租户开通、升级、迁移、健康 |

所有租户同构，没有保存平台源码与发布记录的特殊租户。平台方构建行业应用时使用一个普通的构建租户；宿主运维者在 Host Console 工作；宿主的源码与发布在 git 与部署流程中。

## 1.3 业务视图

价值链：外部系统的数据 → 平台中的业务语义 → 受治理的业务动作 → 回写外部系统与决策。

- 平台方向客户交付两样东西：平台（宿主）与行业应用（产品包）。
- 客户在平台上产生三样东西：数据集与对象（客户数据）、扩展与新应用（客户资源）、业务事实（动作的接受结果）。
- 客户的数据与资源属于客户租户；行业应用升级不得覆盖客户资源。

## 1.4 应用视图

四个纵向层和两个横切面。每项能力只属于一层；上层只经下层的公开资源与协议使用下层。

| 层 | 职责 | Palantir 对照 |
|---|---|---|
| 数据集成 | 连接外部系统，拉取、变换、回写 | Data Connection、Pipeline Builder、Dataset Preview |
| 本体 | 把数据表达为业务语义（语义）与可执行变更（动能） | Ontology |
| 逻辑与自动化 | 计算与响应 | Functions、AIP Logic、Automate |
| 应用 | 面向业务用户的界面 | Workshop、Object Explorer |

| 横切面 | 职责 | Palantir 对照 |
|---|---|---|
| 治理 | 身份与权限、标记、分支与提案、打包发布、监控、审计 | Control Panel、Markings、Branching、DevOps、Marketplace、Data Lineage、Monitoring |
| AI | 模型接入、AI 函数、智能体、全局助手 | AIP Logic、Agent Studio、AIP Assist、Model catalog |

各层拥有的资源与产品见 [2-product §2.2](2-product.md)。

## 1.5 数据视图

数据流向固定，不开旁路：

外部系统 → 数据源拉取 → 数据集（带版本）→ 管道 → 数据集 → 对象类型数据源 → 对象（数据源支撑 + 动作编辑叠加）→ 函数、自动化、应用 → 经动作副作用与回写发回外部系统。

| 数据类别 | 权威来源 | 生命周期 |
|---|---|---|
| 定义（资源元数据） | 资源的接受结果；分支上为分支暂存 | 版本化，进入产品包 |
| 数据集 | 数据源拉取与管道的事务 | 每次加载一个版本，旧版本保留 |
| 对象 | 数据源投影 + 动作编辑事实 | 编辑事实只追加 |
| 业务事实 | 动作与数据源拉取的接受结果 | 不可改写，只能以新事实更正 |
| 制品 | 受控编译的函数与产品版本 | 不可变 |
| 审计 | 每次决定与接受 | 只追加 |
| 凭据 | 部署注入或受控加密托管 | 应用只保存引用 |

标记随血缘向下游传播，见 [6-domain/security](6-domain/security.md)。

## 1.6 技术视图

| 组成 | 选型 | 说明 |
|---|---|---|
| 宿主 | 一个 Go 进程 | 多租户；权威状态在共享表中按租户隔离，可选按租户的只读投影模式；不拆微服务 |
| 内核协议 | `contract/`（protobuf） | 提交、决定、接受结果、错误码；跨应用只走版本化协议 |
| 持久化 | PostgreSQL | 接受结果日志 + 按租户投影的记录 |
| 对象存储 | S3 兼容（本地 MinIO） | 文件、数据集载荷、制品 |
| 身份 | 外部身份服务；轻量模式用签名角色卡 | 宿主只信任已验证主体 |
| 隔离计算 | 独立进程，Unix socket | 租户函数受控编译、隔离执行 |
| AI 网关 | 宿主内模型网关 | 供应商与模型在 Control Panel 配置，推断许可由部署指定 |
| Web | React 19、TypeScript、Astryx（组件与官方模板）、StyleX、Vite | `frontend/`：一个外壳；界面由类型元数据驱动官方模板生成（[7-system/web](7-system/web.md)）。`web/` 是并行的另一条轨道，择优后只留一条（[roadmap](roadmap.md) 五） |
| 部署 | `make local`（热更新）、`make docker`、`make lite`（无 Docker） | 单一入口端口 8495 |

## 1.7 质量目标

按优先级排列；冲突时排在前面的胜出。

| # | 质量 | 场景（可检查） |
|---|---|---|
| Q1 | 正确与可追溯 | 任何权威状态都能追到一个接受结果与其决定；重启后只重放已接受映像，结果逐字节一致 |
| Q2 | 受治理 | 未获准的主体读不到带标记的数据，导出、AI 上下文、派生内容同样受限；拒绝都给出原因 |
| Q3 | 构建效率 | 构建者从空租户到可用应用的黄金路径每一步都有就地入口，无需离开当前工具查文档 |
| Q4 | 可演进 | 定义、协议、产品包都带版本；升级不改写当前格式纪元内的历史字节（[7-system §7.6](7-system/README.md)）；客户扩展不阻断升级 |
| Q5 | 可运营 | 运行、数据源拉取、自动化的失败在 Monitoring 可见，并能从失败处重试 |
| Q6 | 一致 | 同类问题只有一个实现、一个界面模式、一个名字 |

## 1.8 约束

- 凭据、跨权威一致性、租户扩展、双语与命名等项目级约束见 AGENTS.md 硬规则。
- 只引入负责人批准的依赖（当前已批准：OpenTelemetry、Playwright、MinIO 客户端、React Flow、Astryx 与 StyleX；Three.js 待用）。

## 1.9 与 Palantir 的对齐与偏离

对齐的是能力边界、资源模型和交互逻辑，不复刻像素与品牌视觉。

| 采纳 | 说明 |
|---|---|
| 资源模型 | RID、项目与文件夹、一类资源一个应用 |
| 本体 | 语义 + 动能；动作是唯一的对象写入 |
| 数据集与血缘 | 版本化数据集、管道、血缘与标记传播 |
| 权限三层 | 项目角色、标记、对象级策略 |
| 变更管理 | 分支、提案、DevOps 打包、Marketplace 安装 |
| AIP | AIP Logic、Agent Studio、AIP Assist |

| 暂不做 | 理由 |
|---|---|
| Gotham、Apollo | 不同产品线 |
| Contour、Quiver、Code Workbook、Code Repositories、Vertex | 分析与专业开发工具不在终局第一、二段；需要时作为新工具应用加入产品矩阵 |
| 本体动态层（模型、场景） | 先完成语义与动能 |
| 微服务拆分 | 一个进程内按服务包划界已足够，见 [7-system](7-system/README.md) |

| 偏离 | 理由 |
|---|---|
| 行业应用以声明式产品包交付 | 终局第二段要求平台无行业代码 |
| 中文为一等界面语言 | 目标客户 |
| 一条接受结果日志承载全部权威状态 | 任何状态可逐字节重放与审计（Q1），不靠多套存储对账 |
| 单进程，可无 Docker 部署 | 私有化与中小客户的交付成本 |
| AI 只经动作写入 | 智能体与人走同一条接受路径，同权、同审计 |

## 1.10 承重决定

整个架构立在下面八个决定上。它们互相支撑，改动任何一个都是方向性决定，由负责人作出；其余设计都可以在不违反它们的前提下重做。新设计先对照这张表：需要第二条写入路径、第二套模型或一条特例安装路径的方案，是错的方案。规则与理由在所链接的规范里。

| # | 决定 | 权威位置 |
|---|---|---|
| 1 | 一条写入路径：权威状态的每次改变都是提交 → 决定 → 接受结果 → 日志 → 应用 | [7-system §7.3](7-system/README.md)、[concurrency](7-system/concurrency.md) |
| 2 | 一套模型：资源（定义）、对象（实例）、动作（改变）；业务流程、内置应用、行业概念都用它表达 | [6-domain R8](6-domain/README.md)、[2-product R4、R7](2-product.md) |
| 3 | 一个进程：内核只懂车道、日志与读取映像；服务按包划界，经同一个拥有者接口接入 | [7-system §7.2](7-system/README.md) |
| 4 | 一种交付物：宿主之外的一切（行业应用、内置应用）都是产品版本，经同一条安装路径进入同构的租户 | [2-product R5、R8](2-product.md)、[6-domain/change](6-domain/change.md) |
| 5 | 一个授权决定点：读取、写入、导出、AI 上下文都过同一个授权引擎；标记沿血缘传播 | [6-domain/security](6-domain/security.md)、[lineage](6-domain/lineage.md) |
| 6 | AI 是调用者，不是旁路：智能体读取经 ObjectSet、写入经动作 | [2-product §2.3](2-product.md) |
| 7 | 一个格式纪元：宿主只读当前纪元的字节，纪元内不改写历史 | [7-system §7.6](7-system/README.md)、[6-domain R9](6-domain/README.md) |
| 8 | 一个界面运行时：界面 = 类型元数据 + 视图定义 + 官方模板改造的表现；入口是声明，不是代码；只有画布类构建工具手写界面 | [7-system/web “界面运行时”](7-system/web.md)、[4-interaction R13](4-interaction/README.md) |

## 1.11 与 Frappe 的对照

Frappe 是同类问题上最成功的开源答案：用 DocType 把企业应用的通用能力标准化，几十个业务产品复用同一个内核。平台在它强的地方追平（一个类型开箱即得的能力，清单见 [2-product §2.8](2-product.md)），在它结构上做不到的地方胜出。

| 体系 | Frappe 的做法 | 平台的做法 | 胜出点 |
|---|---|---|---|
| A 平台本体 | Framework：DocType 元数据生成表、List、Form、权限与 REST；行为写在 Python 控制器与 hooks 里 | 对象类型 + 动作 + 函数，全部是声明；一条接受结果日志；一个授权决定点 | 行为可声明、可审计、可重放；定制不靠覆盖代码。Frappe 生成的 Desk 是旧界面，新界面（CRM、Helpdesk）是逐个手写的应用；平台生成的就是现代界面 |
| B 部署与交付 | Bench、Pilot 管站点与进程；应用是 git 仓库，升级靠迁移补丁；云上另有一套控制面 | 一个进程多租户，无 Docker 可部署；应用是不可变的产品版本，经 Marketplace 安装、审阅、升级 | 版本内容寻址；不兼容在升级前列出；客户扩展在自己的项目里，升级不覆盖 |
| C 业务应用 | ERPNext、HRMS、CRM、Helpdesk，每个是一个 Python 应用 | 行业产品包，只由平台资源组成 | 应用可由智能体产出；客户与平台方用同一批工具扩展 |
| D AI | Skills、MCP、命令行加在框架之外；模型网关是另外的产品 | 智能体是调用者：读经 ObjectSet，写经动作；模型网关在宿主内 | 智能体做的每件事都在日志里，受同一套权限约束 |

胜出只在这五处衡量：

| 衡量 | Frappe 的基线 | 平台的目标 |
|---|---|---|
| 从类型到可用 | 定义 DocType，得到 Desk 的 List 与 Form | 声明对象类型，得到现代的列表、记录、录入、看板与收件箱，零前端代码 |
| 定制之后的升级 | 自定义字段、属性覆盖与脚本叠在应用上，升级时人工对补丁 | 扩展在客户项目里，升级只替换受管项目，不兼容由发布审阅列出 |
| 一次改变的可追溯 | 可选的版本记录 | 每次改变是一条接受结果，可重放 |
| 部署 | Python 环境、MariaDB、Redis、Node 与进程管理 | 一个二进制加 PostgreSQL |
| 智能体完成的比例 | 智能体写 Python 应用 | 智能体经平台工具声明资源，不写宿主代码 |

不从 Frappe 拿的：

- 不运行 Python Framework，不设 hooks 式的代码覆盖扩展点（那是第二条写入路径）。
- 不沿用 frappe-ui 的组件与样式；界面只来自 Astryx（决定 8）。
- 不把“兼容 Frappe 应用”当承诺。转换是构建工具：结构能转，行为要重建（见下）。

转换 Frappe 应用（负责人 2026-11-16 决定做）：把 Frappe 应用的定义读入，转成产品包的作者态源，作为行业产品包的起点。映射与流程见 [6-domain/packages §6.28](6-domain/packages.md)。

- 能转的是结构，转不了的是行为。读入器对 ERPNext（version-16，534 个 DocType，10587 个字段）全量运行的结果：7407 个数据字段里 136 个没有对应类型；251 个类型的控制器没有内容，但其中多数是明细行，独立的类型只有 34 个；189 个类型结构能转、行为要重建，客户、物料、仓库这些主数据都在其中；另有 197 个报表、72 个打印格式。行为用动作、函数与页面重新表达。
- 许可随来源走（2026-11-16 按 GitHub 的声明核对）：Framework、frappe-ui、Studio、Builder、release_tests 是 MIT；ERPNext、HRMS、Lending、Webshop、Education 是 GPLv3；CRM、Helpdesk、LMS、Insights、Drive、Gameplan 是 AGPLv3。
- 转换得到的包是原应用的衍生作品，沿用原许可，在包清单里记下来源与许可；它们放在本仓库之外，平台与宿主的代码不从中复制，也不用原产品的名字与商标。
- 先转 GPLv3 的 ERPNext 与 HRMS。AGPLv3 的应用只作交互参考，不转（经网络提供服务也要向使用者提供源）。
- 向客户交付含转换内容的包之前，负责人先取得法律意见：GPL 的包与宿主一同交付时边界在哪里，本文不作判断。
