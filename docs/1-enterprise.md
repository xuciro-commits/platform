# 1 企业架构

## 目标

说明平台为谁存在、终局是什么，以及业务、应用、数据、技术四个视图如何组合。其他六层的取舍以本层的终局与质量目标为最终依据。

## 1.1 使命与终局

使命：让构建者把企业的数据变成受治理、可执行、可交付的业务应用。

终局分三段，按顺序推进，前一段不稳不进入下一段：

| 阶段 | 产出 | 判断已成的标准 |
|---|---|---|
| 平台成形 | 以 Palantir Foundry 为基准的构建平台：数据集成 → 本体 → 逻辑 → 应用，治理与 AI 横贯 | 一位构建者能在空租户里走完黄金路径（5-experience §5.2），不写代码、不改宿主 |
| 行业应用 | 用平台自己的工具构建的行业应用（制造 MES、酒店 PMS、供热等），以声明式产品包交付 | 行业应用只由平台资源组成；平台无行业专有代码 |
| 交付运营 | 经 Marketplace 安装到客户租户，客户构建者在其上扩展，版本可升级 | 客户扩展不阻断升级；升级只应用已接受映像 |

推论（这些推论约束其余各层）：

- 行业应用是探针，不是产品分支。行业需求先问“别的行业会不会也需要”：会，就成为平台能力；不会，就用平台资源表达，不进宿主代码。
- 平台的每项能力都要能被打包、安装、升级。不能进入产品包的能力不算完成。
- 客户与我们使用同一套工具。没有“内部专用”的构建路径。
- 自举指平台用自己的工具构建自己交付的应用：行业应用与内置应用都以产品版本经 Marketplace 安装。分两级：一级，行业产品包全部由平台工具产出；二级，能用本体、动作与 Workshop 表达的内置应用改为系统产品包（[2-product R8](2-product.md)）。自举不指把宿主源码放进平台管理（源码在 git；租户里的副本只能是只读陈列，并带来一条特例路径）。

## 1.2 参与方

| 参与方 | 是谁 | 关心 |
|---|---|---|
| 平台方 | 本项目负责人与 AI 代理 | 平台的一致性、可演进 |
| 行业应用构建者 | 起初是平台方自己 | 用平台工具高效构建、打包、发布行业应用 |
| 客户管理员 | 客户租户的 IT | 成员、权限、标记、模型供应商、安装与升级 |
| 客户构建者 | 客户的业务分析师与开发者 | 接入自有数据、扩展已安装应用、搭建新应用 |
| 业务用户 | 客户的一线员工与管理者 | 找到对象、执行动作、处理任务 |
| 宿主运维者 | 部署平台的一方 | 租户开通、升级、迁移、健康 |

所有租户同构，没有保存平台源码与发布记录的特殊租户。平台方构建行业应用时使用一个普通的构建租户；宿主运维者在 Host Console 工作；宿主的源码与发布在 git 与部署流程中。

## 1.3 业务视图

价值链：外部系统的数据 → 平台中的业务语义 → 受治理的业务动作 → 回写外部系统与决策。

- 平台方向客户交付两样东西：平台（宿主）与行业应用（产品包）。
- 客户在平台上产生三样东西：数据集与对象（客户数据）、扩展与新应用（客户资源）、业务事实（动作的接受结果）。
- 客户的数据与资源属于客户租户；行业应用升级不得覆盖客户资源。

## 1.4 应用视图

四个纵向层和两个横切面。每项能力只属于一层；上层只经下层的公开资源与协议使用下层。

| 层 | 职责 | Palantir 对照 |
|---|---|---|
| 数据集成 | 连接外部系统，拉取、变换、回写 | Data Connection、Pipeline Builder、Dataset Preview |
| 本体 | 把数据表达为业务语义（语义）与可执行变更（动能） | Ontology |
| 逻辑与自动化 | 计算与响应 | Functions、AIP Logic、Automate |
| 应用 | 面向业务用户的界面 | Workshop、Object Explorer |

| 横切面 | 职责 | Palantir 对照 |
|---|---|---|
| 治理 | 身份与权限、标记、分支与提案、打包发布、监控、审计 | Control Panel、Markings、Branching、DevOps、Marketplace、Data Lineage、Monitoring |
| AI | 模型接入、AI 函数、智能体、全局助手 | AIP Logic、Agent Studio、AIP Assist、Model catalog |

各层拥有的资源与产品见 [2-product §2.2](2-product.md)。

## 1.5 数据视图

数据流向固定，不开旁路：

外部系统 → 数据源拉取 → 数据集（带版本）→ 管道 → 数据集 → 对象类型数据源 → 对象（数据源支撑 + 动作编辑叠加）→ 函数、自动化、应用 → 经动作副作用与回写发回外部系统。

| 数据类别 | 权威来源 | 生命周期 |
|---|---|---|
| 定义（资源元数据） | 资源的接受结果；分支上为分支暂存 | 版本化，进入产品包 |
| 数据集 | 数据源拉取与管道的事务 | 每次加载一个版本，旧版本保留 |
| 对象 | 数据源投影 + 动作编辑事实 | 编辑事实只追加 |
| 业务事实 | 动作与数据源拉取的接受结果 | 不可改写，只能以新事实更正 |
| 制品 | 受控编译的函数与产品版本 | 不可变 |
| 审计 | 每次决定与接受 | 只追加 |
| 凭据 | 部署注入或受控加密托管 | 应用只保存引用 |

标记随血缘向下游传播，见 [6-domain/security](6-domain/security.md)。

## 1.6 技术视图

| 组成 | 选型 | 说明 |
|---|---|---|
| 宿主 | 一个 Go 进程 | 多租户；权威状态在共享表中按租户隔离，可选按租户的只读投影模式；不拆微服务 |
| 内核协议 | `contract/`（protobuf） | 提交、决定、接受结果、错误码；跨应用只走版本化协议 |
| 持久化 | PostgreSQL | 接受结果日志 + 按租户投影的记录 |
| 对象存储 | S3 兼容（本地 MinIO） | 文件、数据集载荷、制品 |
| 身份 | 外部身份服务；轻量模式用签名角色卡 | 宿主只信任已验证主体 |
| 隔离计算 | 独立进程，Unix socket | 租户函数受控编译、隔离执行 |
| AI 网关 | 宿主内模型网关 | 供应商与模型在 Control Panel 配置，推断许可由部署指定 |
| Web | React 19、TypeScript、Tailwind v4、Vite | 一个工作区外壳装配所有应用 |
| 部署 | `make local`（热更新）、`make docker`、`make lite`（无 Docker） | 单一入口端口 8495 |

## 1.7 质量目标

按优先级排列；冲突时排在前面的胜出。

| # | 质量 | 场景（可检查） |
|---|---|---|
| Q1 | 正确与可追溯 | 任何权威状态都能追到一个接受结果与其决定；重启后只重放已接受映像，结果逐字节一致 |
| Q2 | 受治理 | 未获准的主体读不到带标记的数据，导出、AI 上下文、派生内容同样受限；拒绝都给出原因 |
| Q3 | 构建效率 | 构建者从空租户到可用应用的黄金路径每一步都有就地入口，无需离开当前工具查文档 |
| Q4 | 可演进 | 定义、协议、产品包都带版本；升级不改写当前格式纪元内的历史字节（[7-system §7.6](7-system/README.md)）；客户扩展不阻断升级 |
| Q5 | 可运营 | 运行、数据源拉取、自动化的失败在 Monitoring 可见，并能从失败处重试 |
| Q6 | 一致 | 同类问题只有一个实现、一个界面模式、一个名字 |

## 1.8 约束

- 凭据、跨权威一致性、租户扩展、双语与命名等项目级约束见 AGENTS.md 硬规则。
- 只引入负责人批准的依赖（当前已批准：OpenTelemetry、Playwright、MinIO 客户端、React Flow；Three.js 待用）。

## 1.9 与 Palantir 的对齐与偏离

对齐的是能力边界、资源模型和交互逻辑，不复刻像素与品牌视觉。

| 采纳 | 说明 |
|---|---|
| 资源模型 | RID、项目与文件夹、一类资源一个应用 |
| 本体 | 语义 + 动能；动作是唯一的对象写入 |
| 数据集与血缘 | 版本化数据集、管道、血缘与标记传播 |
| 权限三层 | 项目角色、标记、对象级策略 |
| 变更管理 | 分支、提案、DevOps 打包、Marketplace 安装 |
| AIP | AIP Logic、Agent Studio、AIP Assist |

| 暂不做 | 理由 |
|---|---|
| Gotham、Apollo | 不同产品线 |
| Contour、Quiver、Code Workbook、Code Repositories、Vertex | 分析与专业开发工具不在终局第一、二段；需要时作为新工具应用加入产品矩阵 |
| 本体动态层（模型、场景） | 先完成语义与动能 |
| 微服务拆分 | 一个进程内按服务包划界已足够，见 [7-system](7-system/README.md) |

| 偏离 | 理由 |
|---|---|
| 行业应用以声明式产品包交付 | 终局第二段要求平台无行业代码 |
| 中文为一等界面语言 | 目标客户 |
| 一条接受结果日志承载全部权威状态 | 任何状态可逐字节重放与审计（Q1），不靠多套存储对账 |
| 单进程，可无 Docker 部署 | 私有化与中小客户的交付成本 |
| AI 只经动作写入 | 智能体与人走同一条接受路径，同权、同审计 |

## 现存差距

- 自举一级（第 2 层，`deploy/packages/*.json`）：产品包仍含纪元前格式，尚未由平台工具在当前纪元重新产出。
- 特殊租户（第 7 层）：`system` 租户及其只读的源码、发布与激活记录仍在，界面仍把它显示为“平台自身”并提供只读的 Releases 视图；位置见 [7-system 现存差距](7-system/README.md#现存差距)。
