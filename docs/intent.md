# 意图

这份文档回答四个问题：项目为谁存在，凭什么赢，什么不做，哪些决定不能动。
别的文档与它冲突时以它为准。只有负责人能改它。

## 一句话

一个业务应用平台：声明业务对象，就得到能用的应用；行业知识做成能安装、能升级的产品包。

## 为谁

| 谁 | 处境 | 从平台得到什么 |
|---|---|---|
| 客户：中型企业（制造、酒店、供热等） | 数据散在 ERP、MES、PMS 和表格里，没有自己的工程团队 | 装上就能用的行业应用；自己能接着改，改完不挡升级 |
| 构建者：先是我们，后是客户的业务分析师 | 要把行业知识变成应用，又不能每个客户重写一遍 | 声明对象、动作与流程的工具；打包、发布、安装的通道 |
| 业务用户：一线员工与管理者 | 只想找到单据，把事办完 | 现代、一致、快的界面 |

交付方式：先做我们托管的多租户 SaaS。同一个二进制也能装进客户自己的机房，客户要求时提供。

## 凭什么赢

两个对手各做对了一半。

- Palantir Foundry 的模型是对的：业务对象、动作是唯一的写入、处处受治理。它贵在交付，要靠驻场工程师。
- Frappe 把交付做便宜了：定义一个 DocType 就得到列表、表单、权限与接口。但行为写在代码里，定制挡住升级，生成的界面是旧的。

我们用前者的模型做出后者的体验。内核的模型向 Foundry 看齐，应用框架的体验要胜出 Frappe。功能数量不是目标。

## 四个下注

| 下注 | 内容 | 成立的信号 |
|---|---|---|
| 界面由类型生成 | 声明一个对象类型，就得到列表、记录、录入、看板与接口 | 一个新类型从声明到业务用户可用，不写一行前端代码 |
| 产品包替代驻场 | 行业知识是版本化的声明式产品包，经市场安装；客户在其上扩展 | 新客户从安装到执行第一个动作，我们不改代码、不上门 |
| 一条日志、一个进程 | 全部权威状态在一条接受结果日志里，宿主是一个 Go 进程 | 一台机器无 Docker 可部署；任一状态可重放与审计 |
| AI 是一等构建者 | 资源全是声明，写入全经动作；智能体与人用同一批工具、同一套权限 | 行业应用的主体由智能体经平台工具产出 |

## 怎样算赢

只在这五处与 Frappe 比，别处不比。

| 衡量 | Frappe 的基线 | 我们的目标 |
|---|---|---|
| 从类型到可用 | 定义 DocType，得到旧界面的列表与表单 | 声明类型，得到现代的列表、记录、录入与看板，零前端代码 |
| 定制之后的升级 | 自定义字段与脚本叠在应用上，升级时人工对补丁 | 扩展在客户自己的项目里，升级只替换受管部分 |
| 一次改变的可追溯 | 可选的版本记录 | 每次改变是一条接受结果，可重放 |
| 部署 | Python、MariaDB、Redis、Node 与进程管理 | 一个二进制加 PostgreSQL |
| 智能体完成的比例 | 智能体写 Python 应用 | 智能体经平台工具声明资源，不写宿主代码 |

与 Foundry 只比三件事：同一个行业应用的交付时间、部署与升级的成本、由智能体完成的比例。

## 终局

客户在市场里装上一个行业应用，当天开始用；之后自己加字段、加动作、加页面；我们发新版本，他升级，自己的扩展还在。
这条链上的每一环都只用平台自己的工具，我们与客户用的是同一套。

由此得到三条推论，约束其余一切：

- 行业应用是探针，不是分支。一个需求别的行业也会要，就做成平台能力；不会，就用平台资源表达，不进宿主代码。
- 做不进产品包、不能安装和升级的能力，不算完成。
- 没有“内部专用”的构建路径。

## 不做

- 不在平台里写行业代码。总账、工单、房态、BOM 只能是产品包里的对象与动作。
- 不建独立的流程引擎。流程 = 对象的状态 + 动作 + 自动化 + 工作项。
- 不设 hooks 式的代码覆盖扩展点。那是第二条写入路径。
- 不拆微服务，不让部署依赖 Docker。
- 不做报表设计器、BI、通用脚本执行、每个应用自带的权限页与导入导出。
- 不承诺兼容 Frappe 应用。转换只是构建工具：结构能转，行为要重建（[domain](domain.md)“产品包”）。
- 不为单个类型手写页面，不养第二个前端、第二套组件库。
- 不做没有功能在等它的重构。

## 八个承重决定

整个设计立在这八个决定上。改任何一个都是方向性的决定，只由负责人作出；其余设计都可以在不违反它们的前提下重做。
一个方案需要第二条写入路径、第二套模型、第二个前端或一条特例安装路径，它就是错的方案。

| # | 决定 | 它排除了什么 | 详见 |
|---|---|---|---|
| D1 | 一条写入路径：提交 → 决定 → 接受结果 → 日志 → 应用 | 直接改存储；代码钩子里的写入 | [architecture](architecture.md) |
| D2 | 一套模型：资源（定义）、对象（实例）、动作（改变） | 流程引擎；每个应用自己的数据模型 | [domain](domain.md) |
| D3 | 一个进程：Go 宿主；内核只懂车道、日志与读取映像。要原生库或硬件的能力实现可以是宿主之外受管的独立服务，可选，经同一契约注册、授权与计量 | 微服务；必须容器化的部署；绕过契约直连宿主的进程 | [architecture](architecture.md) |
| D4 | 一种交付物：宿主之外的一切都是产品版本，走同一条安装路径 | 特例安装；手改客户租户 | [domain](domain.md) |
| D5 | 一个授权决定点：读、写、导出、AI 上下文都过同一个授权引擎 | 各应用自带的权限判断 | [domain](domain.md) |
| D6 | AI 是调用者：读经对象集，写经动作 | 智能体直接读写数据 | [domain](domain.md) |
| D7 | 一个格式纪元：宿主只读当前纪元的字节，纪元内不改写历史 | 就地改写已存数据；无版本的格式变化 | [architecture](architecture.md) |
| D8 | 一个界面运行时：界面 = 类型描述 + 视图定义 + 官方模板改造的表现 | 逐类型手写页面；第二个前端 | [frontend](frontend.md) |

## 质量的先后

冲突时排在前面的胜出。

1. 正确与可追溯：任何权威状态都能追到一条接受结果；重启后重放，结果逐字节一致。
2. 受治理：没获准的人读不到带标记的数据，导出与 AI 上下文同样受限；每次拒绝都给出原因。
3. 构建效率：从空租户到可用应用，每一步都有就地入口。
4. 可演进：定义、协议、产品包都带版本；客户扩展不挡升级。
5. 可运营：失败看得见，能从失败处重试。
6. 一致：同类问题只有一个实现、一个界面模式、一个名字。

## 只有负责人能决定

改承重决定；冻结或推进格式纪元；引入新依赖；删除用户看得见的能力；选旗舰产品包与第一个客户；动本文。
其余由 lead 与领到任务的 Agent 决定并负责，在汇报里说明所作的选择（[README](README.md)）。
