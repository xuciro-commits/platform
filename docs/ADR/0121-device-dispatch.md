# ADR-0121 — 设备与黑盒目标：派发、状态回读与人工介入

状态：已接受（2026-10-12，负责人指令）· 扩展 ADR-0112（跨系统协同）与 ADR-0014（出站效果）的执行面 · 补齐"下一次交付"（仓储与 AGV：立库 RCS、AGV WCS、黑盒下游指令）所要求的**形状预留**（ADR-0119 §6 规则 2） · 与 ADR-0120（观测）、0117（拒绝）配套

## 0. 意图

第一次交付（楼宇供暖）里已有门禁与设备联动；**下一次交付已确定**（负责人 2026-10-12）：大疆的 MES + WMS，要管立库 RCS、AGV WCS，并与下游做**黑盒集成**——"给下游发指令，比如 A 到 B"。

这与 ADR-0112 写的"请求-回执-对账"**形状不同**：

- 发给设备/AGV 的指令**没有业务回执**（对面不是业务系统，是控制器）；
- 长任务是常态（一次搬运要几十秒到几分钟），**"没回"不等于失败**；
- 指令有**物理后果**（会动、会撞、会夹）。

**判据**：构建者能表达"把 A 的货送到 B"，能看到它在途/完成/卡住/失败，能在卡住时介入；**并且平台从不假装它能保证设备一定执行**。

## 1. 与 ADR-0112 的区别

| | Confirmation（ADR-0112） | 设备/黑盒指令（本文） |
|---|---|---|
| 对面 | 业务系统（ERP、WMS、APS） | 控制器 / 库系统 / 黑盒下游 |
| 回执语义 | 有：接受、拒绝、附答复 | **多数只有状态**：已收、执行中、完成、失败、卡住 |
| 时长 | 秒到小时 | 秒到分钟（长任务） |
| 一致性 | 至少一次 + 对账 | **至少一次 + 状态回读**（不重发危险指令） |
| 人的角色 | 裁决部分成功 | **介入卡住的任务** |

**共同点**：都**不宣称 exactly-once**（ADR-0098 §9.3、Platform §10.3 D），都靠稳定身份 + 接收方幂等 + 对账。

## 2. 决定

### D1 指令是一等业务记录，不是"一条效果"

```go
// 一条下发到设备/黑盒目标的指令。
type Dispatch struct {
    Subject  TxnRef      // 业务主体（运单、搬运任务、门禁请求）
    Target   Endpoint    // 目标（设备/库系统/AGV 控制器/黑盒下游）
    Command  string      // 声明过的指令名（不是自由文本报文）
    Payload  []Set       // 参数（ADR-0101 的表达式求值）
    Key      string      // 幂等键（稳定，来自业务主体）
    Deadline Time        // 业务截止（ADR-0112 §D1 的语义）
    OnStuck  string      // 卡住时：escalate | compensate | retry | manual
    OnFail   string      // 失败时：同上
}
```

- **指令是声明过的**（`Command` 来自声明的指令表），不是任意报文。任意报文会让平台无法判断幂等与重发安全。
- 指令的**状态、尝试、回读结果**都是业务记录，因此**可查、可审计、可恢复**（不是运行期易失状态）。
- 指令的**幂等键来自业务主体**（如运单 ID），因此重发同一个搬运请求不会产生第二次搬运——**前提是目标侧也遵守幂等**；平台不假设、不承诺（D5）。

### D2 状态回读（对账）是必需的，不是可选的

因为多数控制器不返回业务回执，**"发出去了"与"做到了"之间只能靠回读**：

- 指令可以声明**状态回读方式**（读某个观测测点、查目标的查询接口、读它的状态记录）；
- 回读是**受属作业**（复用 ADR-0027/0013 的机制），按声明周期运行；
- 回读结果写回业务记录（`dispatch` 记录的状态字段），因此**卡住能被发现**；
- **结果不明（unknown）与失败（failed）区分**（沿 ADR-0112 §D4 的既有决定，扩展到设备）。

### D3 硬边界：控制回路不在平台（**这条最优先**）

**安全联锁、急停、闭环运动控制、实时调速——永远在设备/网关/PLC 本地。**

平台做的是**派发与回读**：它告诉目标"做什么"，然后看"做到没有"。平台**不**参与毫秒级的闭环，**不**承担实时性，**不**作为安全链路的一环。

这条必须在使用文档与构建器里写明。**不写死的后果**：第一次做 AGV 就会有人想在平台上做路径闭环——那是一条会伤人的错误。

平台也**不**检测"指令是否会撞"——那是目标侧/WCS 的职责；平台只传递业务意图与约束（例如"必须先出库后入库"由 ADR-0101 的规则表达）。

### D4 人必须能介入

- `OnStuck` / `OnFail` 的处理**必须显式声明**（与 ADR-0112 §D2 同一要求）：升级（通知角色）、补偿（反向指令）、重试、或**人工**。
- **人工介入是一等路径**：被授权成员可以裁定一条卡住的指令（重发、改目标、标记完成、取消）。走 work 的既有任务/审批机制（ADR-0017）。
- **卡住必须可见**：运行面显示在途指令、卡住的时长、原因（来自回读）。

### D5 重发的安全性分级

重发不是都安全：

| 指令类别 | 重发语义 | 声明要求 |
|---|---|---|
| **幂等**（查询状态、设置目标位置） | 可安全重发 | 声明 `Idempotent: true` |
| **需目标侧幂等**（创建搬运任务，带业务键） | 可重发，**依赖目标侧按业务键去重** | 声明业务键；文档说明依赖 |
| **不可安全重发**（开门、启动动作） | **禁止自动重发**；失败进入人工 | 声明 `Idempotent: false`；平台**拒绝**在自动重试策略里配置它 |

**平台必须能拒绝**："给一个不可安全重发的指令配置自动重试"在**发布期**就是错误。这是本 ADR 最实用的一条。

### D6 目标不是业务应用：协议与凭据

- 目标（设备、控制器、黑盒下游）**不是平台的应用**，没有对象类型，不需要实现协议（ADR-0011）——它是**外部端点**；
- 目标的**地址与凭据是环境绑定**（沿 ADR-0047/0107）；报文格式与协议栈由**能力包**封装（ADR-0119：设备对接是能力包，例如"AGV/RCS 接入"、"黑盒下游 HTTP/TCP 对接"）；
- **协议适配不在平台包内实现**（同 ADR-0120 §3 的口径）：平台只到"指令 + 参数 + 状态"这一层。

### D7 为下一次交付预留的形状（ADR-0119 §6 规则 2 的实例）

**下一次交付已命名**（仓储与 AGV），因此允许预留**形状**，不允许预留领域词汇：

| 预留什么 | 形态 | 不做什么 |
|---|---|---|
| 指令种类的扩展点 | 一个具名的 `Dispatch` 声明（`Command` 来自声明表） | 不预置"AGV""库位""RCS"等名称 |
| 状态回读的扩展点 | 一个具名的回读声明（读观测 / 查接口 / 读记录） | 不实现任何具体协议 |
| 目标类别的扩展点 | 一个具名的端点类别（设备/库系统/黑盒下游） | 不做第二套集成机制 |
| 数字化容器的对接 | **不预留**（负责人明示"很边缘的地方就不用再搞预留"） | — |

**预留的检查标准**（沿 ADR-0119 §6 规则 4）：三天后能插进来即为合格；**留下空方法、假支持或未接通入口即视为缺陷**。

## 3. 不做

- **不做闭环运动控制 / 实时控制**（D3）。
- **不做协议栈**（D6；西门子上百种协议、Modbus、BACnet、OPC UA 等均属能力包或外部库）。
- **不做"设备一定执行"的承诺**（§0）。
- **不做安全联锁的软件实现**（D3）。
- **不为未命名的交付预留**：除 D7 表内的四项，其他（如"未来可能接机器人"）不留形状。

## 4. 后果

- 第一次交付（供暖的门禁与设备联动）即可用最小版：`Dispatch` + 状态回读 + 人工介入。**不等下一次交付。**
- 下一次交付（仓储与 AGV）落地时，需要新增的是**能力包**（协议封装、设备对接）与**行业包**（仓储的对象骨架与规则模板），平台包只补 D7 的形状与实现——这正是 ADR-0119 §6 预留的目的：**改内核很麻烦，改能力包不麻烦**。
- 运行面需要"在途指令"视图（ADR-0107 §D3 的一部分）。
- 与 ADR-0120 的连接：设备状态回读天然读的是**观测**（温度、位置、状态码），因此 0120 的观测读取形状要支持 D2 的回读。

## 5. 验收

1. 一条指令声明 + 派发 + 状态回读 + 完成：业务记录反映真实状态，卡住能被发现。
2. **不重发断言**：把一条 `Idempotent: false` 的指令配置自动重试 → **发布期拒绝**。
3. **结果不明**：回读拿不到状态时进入 `unknown`（不是 `failed`），与 ADR-0112 一致，且人工可裁定。
4. **人工介入**：卡住的指令指派到角色，成员在任务里裁定，结果写回业务记录。
5. **边界断言**：使用文档与构建器里明确"控制回路不在平台"（用文档检查 + 构建器提示的存在性证明）。
6. **预留检查**：D7 的四项各有形状声明且**无实现**；检查是否有空方法/假支持（有则缺陷）。
7. **反例**：为边缘情况（数字化容器等）预留形状、在平台内实现协议栈、把目标做成一个平台应用 → 分别拒绝。
