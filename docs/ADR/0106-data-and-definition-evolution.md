# ADR-0106 — 数据与定义的演进：从可选标量到真实迁移

状态：已接受（2026-10-12，负责人指令，ADR-0098 C 块第一份）· 取代 ADR-0039 §As built「带数据的有界升级」只接受可选标量字段的口径；保留其候选/激活/环境绑定/恢复语义 · 落地顺序归 WorkQueue

## 0. 意图

客户把系统用起来之后，**一定会改模型**：给工单加一个字段、把"备注"拆成两类、给工序加质检点、改一个引用的目标类型。今天平台允许的只有一种：**新增一个可选标量字段**（text/longtext/integer/decimal/boolean/date/datetime），不填默认值、不改已有记录值。

ADR-0039 §As built 原文：*"必填、引用、选择、共享属性、金额、删除/重命名/类型变更及一般转换不在此 profile 内。"* 剩余边界一节又写：*"上述可选标量扩展之外的存储形状变更、拥有者草稿重命名/归档、动作退役及部分绑定变化仍受拒绝/升级门禁限制。"*

结果：客户第一次要改名一个字段，就撞墙。这不是能力不足，**这是"不能长期维护"**（ADR-0098 第三个判据）。

**判据**：构建者能执行一次真实的模型变更（新增带默认值的必填字段、重命名、拆分、改引用目标、退役一个动作），在**不改历史语义**的前提下让在途业务继续跑。

## 1. 现状与缺口

| 能力 | 现状 | 证据 |
|---|---|---|
| 候选/激活/晋级 | 已有，含依赖闭包、原子激活、环境绑定 | `platform/revision.go:16-45`；`accepted_release.go:320-383` |
| 在途实例版本绑定 | 已有（Flow 冻结启动版本与依赖闭包） | `flow_binding.go:22-58` |
| 记录迁移 | 有受权迁移入口（Host Console 的 Migrate records） | ADR-0047；`environment.go` |
| 升级计划 | 有，但只接受可选标量扩展 | ADR-0039 §As built |
| **重命名** | 拒绝 | 同上 |
| **必填 + 默认值** | 拒绝 | 同上 |
| **引用/选择/金额** | 拒绝 | 同上 |
| **删除/归档字段** | 拒绝 | 同上 |
| **类型变更/一般转换** | 拒绝 | 同上 |
| **动作退役** | 拒绝 | 同上 |
| **K7 动态演进** | 内核有 SchemaRegistry，宿主把 action schema 的 `SchemaRef.Version` 写死为 1 | `platform/ledger.go:40,66` |

**根因**：升级被当作"结构兼容性检查"，而不是**一次有计划的、可审阅的数据与定义迁移**。因为不承认要动数据，所以只能允许"不动数据"的改动。

## 2. 决定

### D1 升级 = 计划 + 数据迁移 + 定义激活，一次接受

引入**迁移计划**（`MigrationPlan`，构建器资产 + 宿主执行）：

```go
type MigrationPlan struct {
    From   ReleaseRef   // 源定义版本（封存）
    To     ReleaseRef   // 目标定义版本（封存）
    Steps  []MigrateStep
    Scope  string       // 目标记录范围（类型 + 可选过滤）
}

type MigrateStep struct {
    Kind   string   // add | default | rename | split | merge | retype | extract | retire-action | rebind
    Types  []string
    Fields []FieldChange
    Expr   *Expr    // 转换值（ADR-0101）
    Batch  int      // 分批大小（见 D3）
}
```

要点：

- **计划绑定两个封存版本**（源与目标），不是"当前"与"目标"——这样计划在审阅期间不会漂移。
- **转换用 ADR-0101 的表达式**：`split`（一个字段按表达式分到两个）、`merge`、`retype`（含显式转换与失败处理）、`extract`（从行到新对象）都是表达式 + 步骤类型，不是脚本。
- **不支持的转换必须显式拒绝**（有步骤类型清单，清单外拒绝），不静默跳过。清单外的复杂转换走 ADR-0044 的受控代码（Go/TinyGo Wasm）作为**显式选声明的步骤类型**。

### D2 每一类变更的确切语义

| 变更 | 语义 | 历史影响 |
|---|---|---|
| `add` + `default` | 新字段以表达式求值填既有记录 | 历史记录被**写入新事实**（一次真实迁移决策），不是改写旧决策 |
| `rename` | 字段名变更；**旧名保留为只读别名**，历史记录与旧发布继续按旧名解析 | 无（读时映射） |
| `split`/`merge` | 值按表达式重分布；源字段进入只读退役态 | 历史可读 |
| `retype` | 显式转换；转换失败的行**隔离并报告**，不静默置空、不丢行 | 历史可读 |
| `retire-action` | 动作停止出现在目录里；**已产生的历史决策继续重放**，在途等待审批按声明的处理（拒绝/重定向） | 无 |
| `rebind` | 引用的目标类型变更；必须提供目标的身份映射或拒绝 | 需显式映射 |
| **字段删除** | 不允许物理删除；只允许 `retire`（保留读取、不参与新写入） | 必须保留 |

**历史永远可读是硬线。** 今天"历史日志必须永远能重放"（ADR-0007/0038/0097）是最高优先；删除字段会破坏它，所以只提供退役。

### D3 迁移是分批的真实决策，不是原地改写

- 每一步按 `Batch` 分批执行，**每批是一个业务事务**（ADR-0100）：部分完成是显式可见的中间状态，可重入、可续接。
- 迁移决策的主体是**执行迁移的管理主体**，不是"系统假装那条记录当初就是这样"。审计上能区分"这条记录的字段是被迁移填的"与"它本来就有"。
- 迁移可中断、可恢复、可重跑（同键幂等）。失败批留下明确的进度与原因。
- **恢复不重跑迁移**（沿 ADR-0038/0097）。

### D4 在途工作跨版本的语义

| 在途物 | 语义 |
|---|---|
| 已启动的 Flow 实例 | 保留启动版本与依赖，继续按旧语义跑到结束（已有，`flow_binding.go:22-58`，不变） |
| 等待中的审批 | 按声明的处理：默认**拒绝**并要求重新发起（因为审批针对的是旧定义的动作语义）；可声明重定向到新动作 |
| 未派发的外部效果意图 | 按**固定执行描述符**继续（已有语义，ADR-0097 §7"接受后六类集成执行配置取原固定 descriptor"） |
| 单据上的业务版本固定 | 不变（ADR-0103）：迁移**不改变**已固定的业务版本，除非计划显式声明 |
| 定时作业 | 下次执行用新版本（它们是反复发生的，不是在途） |

### D5 K7 版本协商落地

宿主把所有 action schema 的 `SchemaRef.Version` 写死为 1（`platform/ledger.go:40,66`）。本 ADR 落地最小可用的版本演进：

- 定义发布带 **schema 版本**（内容哈希，沿 `revision.go` 的内容 ID）；
- 提交时声明它所依据的 schema 版本；宿主接受**同一 family 内**的版本（兼容声明由发布期校验给出）；
- 跨 family 的提交明确拒绝并要求客户端刷新定义。

**不做**内核 K7 的全部动态学习语义（那是"权威/鉴权从何而来"的问题，超出本 ADR）；做的是让平台**能说出自己用的哪一版**，并拒绝说不清的提交。

### D6 客户扩展的保留

ADR-0039 末句的"客户扩展保留仍未完成"是本 ADR 的核心交付之一：

- 客户在工作台给**共享类型**（`core.*`）追加的字段/动作（ADR-0058 的扩展记录）在基础包升级后**必须保留**；
- 保留的实现方式：扩展按**来源包版本**记录，基础包升级时逐条重放扩展声明并验证（字段还在、类型还兼容），不兼容的扩展**明确报告并暂停**，不静默丢弃；
- 扩展的冲突（基础包新增了同名字段）在升级计划里显式解决，不自动覆盖。

## 3. 不做

- **不做原地改写的存储迁移**：所有数据变更走决策。
- **不做零停机在线迁移的承诺**：分批执行 + 中间状态可见 + 可续接；具体停机窗口由环境决定，不在 ADR 里承诺（Platform §10.6 的容量与 RTO/RPO 承诺仍待验收）。
- **不做自动推断的迁移**：每一步都要构建者声明。
- **不做跨应用迁移的原子性**：跨应用沿 ADR-0112 的协同与对账。
- **不做历史清洗**：退役字段的历史值永远保留。

## 4. 后果

- ADR-0039 的"可选标量扩展"从**上限**变成**迁移计划的一个特例**（`add` + `default` 为空的退化情形）。
- 记录迁移从 Host Console 的受权入口扩展为有计划的、构建者可见的资产（前端归 ADR-0108）。
- 迁移会**改变数据**，因此必须在环境演练、备份、恢复路径上被覆盖；`make rehearse` 的两行业演练要加入一次真实迁移。
- 风险：迁移是可破坏的。控制手段是 §D3 的分批 + 可重入 + 幂等 + 显式拒绝清单，以及"计划绑定两个封存版本"。

## 5. 验收

1. 六类变更各一例：新增带默认值的必填字段、重命名（旧名只读别名）、拆分、改引用目标（带映射）、退役动作、退役字段。每例证明：历史仍可读、在途 Flow 仍按旧版本跑、迁移分批可续接。
2. 迁移中途中断：进度与原因可见，重启后从断点继续，已完成批次不重复。
3. 幂等：同计划重跑不产生第二次变更。
4. 客户扩展：给 `core.material` 加两个字段，升级基础包后扩展保留；制造一个冲突（基础包新增同名字段）并证明升级计划显式报告而不是覆盖。
5. 版本协商：用旧 schema 版本提交被接受（同 family）；跨 family 被拒绝并要求刷新。
6. 反例：清单外的步骤类型、把字段物理删除、对被引用的字段做不兼容 `retype` 而无隔离策略 → 计划创建期拒绝。

测试归发布 owner、build owner 与宿主包；`make rehearse` 加入一次真实迁移；`docs/Testing.md` 增"数据与定义演进"手测行。

## As built

**实施中，尚未达到 §5 的停止条件。** 应用 API 已有 `MigrationPlan` 的封存来源/目标、明确步骤、范围谓词、批次大小、引用映射与失败策略。计划和步骤拒绝未知属性、脚本/物理删除及缺少映射/隔离策略的转换；源码字段退役或重命名须在目标形状中保留为可读的只读字段。

`CompileMigrationPlan` 按源/目标形状绑定字段，复用 ADR-0101 编译器；`MigrationProgram.Transform` 产生独立映像，保留原始字段与输入字节，转换失败不返回部分结果。当前反例覆盖默认值保留显式 false、重命名别名、拆分、显式 decimal 转换、引用映射、退役、未知步骤与原字节保留。这是转换核心证据，不能作为持久迁移、恢复或在途兼容的完成证明。

`POST /v1/releases/migrations/review` 在原发布 owner 的私有安装视图里解析两个已保存版本的形状；来源须为当前封存激活版本。审阅前沿 ADR-0105 检查管理主体与来源行/字段，返回形状、记录量与逐行转换问题。审阅标识绑定计划、形状、来源映像、主体与求值时间；开始执行重新核对当前权限与来源，求值沿审阅时捕获的主体/时间。审阅不激活目标、不修改业务记录；当前目标必须已有 owner 草稿。

`build.migration` 保存不可变计划与实际进度；builder 通过原提交入口的 `start`、`advance`、`cancel` 操作它，权限、账本、1 MiB 接受预算及恢复继续由原 owner 承接。当前执行限于 build 自有对象；每批把数据映像、实际操作者历史和游标保存到同一个 `record-batch`，同键返回原答复，重放不运行转换。`reject` 转换失败只保存阻塞原因，不写该批先前成功的行；`quarantine` 保存成功行和逐行失败，有未解决失败不能激活。取消按批写补偿事实恢复源值、保留历史，再解除冻结；取消未完成时仍可续接。

迁移期间来源对象可读，普通写入及直接改存储定义被拒绝。每行接受结果与快照保留绑定源发布/字段形状的读取映像，目标事实独立保存；字段形状相同也按发布身份选择读取映像。完成后原发布 owner 验证目标值、引用和约束并激活已封存目标；没有第二套激活器，也不改旧日志或发布字节。当前仍保留可选标量升级 profile，完整迁移尚未覆盖的退役语义不借该 profile 放行。

自动证据归 `migration_review_test.go`、`migration_execute_test.go` 与应用 API `migration_test.go`：包括三行两批、同键重试、来源冻结、失败整批边界、隔离/取消、快照、实际日志文件关闭重开续接、激活恢复、未选中必填值拒绝及相同字段形状的发布选择。日志后端测试复用原 kit；配置 `PLATFORM_TEST_DATABASE` 时同路线运行 PostgreSQL，未配置时文件日志通过不能代替 PostgreSQL 证据。

原发布工作台已有数据迁移面板：固定源/目标封存版本，编辑受控步骤与范围表达式、审阅、开始、分批执行/取消、读取保存的进度及失败，再走原目标激活。操作复用 K5 outbox；回复丢失后重试原决定，编辑中的计划与尚未确认的决定阻止切换候选。当前步骤通过共享 JSON 草稿控件编辑，尚非通用可视化规则编辑器。`migration.spec.ts` 在浏览器覆盖重命名两批、接受后丢失回复/同键重试、刷新续接、激活及新字段编辑；桌面与窄视口有截图证据。

构建器字段声明支持 `readOnly` 与单层 `aliasOf`；重命名计划须在封存目标里声明原名的只读别名。字段归属方统一投影其值，标准写入拒绝旧名；读取、筛选/排序、派生与集合不能借别名扩大目标字段权限。字段退役保留原字段、值与历史，禁止新写；现有 `migration_alias_test.go` 覆盖迁移、后续编辑、权限反例与重放，退役一例证明旧值不改、新建不填写退役字段。它们尚不证明在途 Flow 跨版本任务。

**仍须交付：** 迁移资产生命周期注册、`extract`/`retire-action` 执行（当前开始时明确拒绝）、在途审批与旧 Flow 跨版本读取、客户扩展保留与冲突、schema family 协商，以及加入真实迁移的两行业持久环境演练。其他字段步骤已有执行路径，尚不能用当前默认值/重命名/退役证据代替 §5 的六类逐项验收；WorkQueue 保持 ADR-0106。
