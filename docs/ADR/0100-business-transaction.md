# ADR-0100 — 业务事务：单一权威内的多对象原子变更

状态：已接受（2026-10-12，负责人指令，ADR-0098 A 块第一份）· 修订 ADR-0026 的执行面口径（不改变其"跨权威不原子"结论）、扩展 ADR-0037/0040 的动作能力 · 落地顺序归 WorkQueue

## 0. 意图

客户在工作台配一个"工序完工"，它必须同时做到：结束当前工序记录、更新生产批次、写一条不合格品记录、结束父工单、给下一工序派工。今天这件事**配不出来**——不是因为没有画布，而是因为动作能改的东西太窄。

这份 ADR 把"一次业务操作可以原子地改多个对象、多条记录"变成平台的正式能力。

**判据**：构建者能在工作台里定义一个单据（头 + 行 + 编号 + 过账 + 状态流转），一次动作产生一个接受结果，里面含多个对象类型、多条记录；任何一条失败则**一条都不落盘**；重启恢复后逐字重现同一个结果。

## 1. 核验：今天到底能做到哪一步

| 说法 | 代码事实 | 裁决 |
|---|---|---|
| 一次决策只能改一条记录 | 不成立。`acceptedBatch`（`capabilities/server/accepted_batch.go:29-51`）承载 `Rows []acceptedBatchRow` + `Decisions []acceptedDecision`，行数无硬上限，只受 `maxAcceptedResultBytes = 1<<20`（`accepted_result.go:26`）约束。`apps/erp/server/erp.go:281-289` 已在同一 `apply` 闭包内写单据与分录行 | 引擎已具备，**表达层没有** |
| 一个应用能改自己的多个对象类型 | 成立。`accepted_nested_test.go:319-322` 断言一次日志分录含 3 个决策、2 行记录；`apps/erp/server/accepted_batch_test.go:17` 断言 `record-batch` 且 `Rows==3`，同时提交序列号 | 复用，不新造 |
| 构建器定义的动作能改关联对象 | **不成立**。`buildapi/Action`（`internal/host/buildapi/actions.go:24-50`）里只有 `Sets`（自己这条记录的字段）、`Creates []Create`（同一构建器下的子记录，须经 `Via` 回指，`apps/build/creates.go:18-56`）、`Posts []Post`（只写另一对象的 integer/decimal/money **余额字段**，`buildapi/posts.go:21-34`）、`Journal`（账簿）。没有"写另一条已有记录的普通字段"，没有归档，没有建关系 | **这就是墙** |
| 抽屉式的"一次动作改多对象"能绕过 | 不能。跨应用只能 `Probe`（只读，`platform/protocol.go:58-66`）与 `Request`（接受**之后**执行，`protocol.go:70-78`），是先后两个独立决策 | 只能最终一致，见 §3 |
| 多记录的原子性有保证 | 成立且有限。写入先落 fork，`accepted_batch.go:387-404` 保证"后到的非法子变更不能推进更早已接受的内容"；`apps/erp/server/accepted_batch_test.go:44-56` 证明追加失败后单据仍是草稿、编号未占 | 复用 |

**根因**：决策内容的模型是"一次提交 → 一个目标 → 一份载荷"（`contract/spec/K4-change-record.md:10`，`Submission` 单 `target`），而构建器只被允许在这个模型上表达"改自己"。所以今天的 MES 必须被拆成 `apps/mes`、`apps/erp`、`apps/mes/erp.go` 三方，用协议和写死的 Go 代码把一致性问题绕过去——**这正是要拆掉的东西**。

## 2. 决定

### D1 权威的粒度是应用，不是对象类型

应用（`platform.App`）是权威单位；它拥有的**全部对象类型**共享同一本账本、同一个提交边界。一次业务事务可以同时写它拥有的任意对象类型、任意条记录。

今天"一个对象类型一个应用"只是参考应用的实现习惯，不是平台语义；`apps/mes/erp.go` 这类"同一个人工拆出来的第二应用 + 桥接包"的做法不再有存在理由。

### D2 业务事务是唯一的多对象变更表达

新增定义契约 `BusinessTxn`（构建器资产，编译到宿主）：

```go
// 一次业务事务：同一应用、同一账本、同一接受结果内的全部变更。
type BusinessTxn struct {
    Subject   string       // 事务主体：单据、工单、批次…（事务的名称与审计对象）
    Steps     []TxnStep    // 有序；同一步骤内的记录以稳定键排序，保证重放确定
    Guard     []Condition  // 全部成立才继续；沿用 0101 的条件语言
    Idempotent string      // 幂等键的来源字段
}

type TxnStep struct {
    Kind    string   // create | update | archive | link | unlink | sequence | post | journal | effect | work
    Target  TxnRef   // {Type, ID, Via}：固定 ID、本事务内新建记录、或沿声明的引用路径
    Changes []Set    // update 时的字段赋值（沿用 0101 的赋值语言）
    When    []Condition
    // effect/work 步骤携带端点与载荷；sequence 携带命名序列
}
```

要点：

- **`Target.Via` 是关键**：行的父指向、子记录的归属、关联记录的定位都沿**已声明的引用路径**解析（复用 `platform/record_path.go`），所以构建者不需要写 ID，平台也不需要猜。
- **步骤是类型化的，不是 JSON 脚本**。每一种 `Kind` 由对应 owner 实现：`post`/`journal` 归 ADR-0063/0076 的既有实现，`effect` 归出站效果 owner，`work` 归 work 应用，`link` 归 links owner。新增 Kind 须扩展其规范主人，不在事务引擎里加特例。
- **`effect` 与 `work` 步骤只声明意图**，在事务被接受后由既有出箱/受属工作机制执行——它们**不在**原子范围内。事务原子的是状态；外部效果仍是至少一次（沿 ADR-0014、ADR-0102 §4）。

**每一种 Kind 的确切语义**（新增 Kind 须在此表登记，不在引擎里加特例）：

| Kind | 语义 | 在原子范围内 | 归属 |
|---|---|---|---|
| `create` | 新建一条记录；ID 由平台生成或按编号规则 | 是 | 记录 owner |
| `update` | 改一条**已存在**记录的字段；`Target` 必须解析到确定记录 | 是 | 记录 owner |
| `archive` | 归档（非删除；沿 `ledger.go:412-413` 的既有语义） | 是 | 记录 owner |
| `link` / `unlink` | 建/断一条**声明过的**关系；基数与删除策略由 ADR-0102 在事务级检查 | 是 | **ADR-0104 §D3**：同应用关系归该应用账本 |
| `sequence` | 取一个命名序列的下一个值（ADR-0024 的既有实现）；**拒绝不占号** | 是（与记录同批） | 宿主序列 owner |
| `post` | 向余额字段加减（ADR-0063 的既有实现） | 是 | 台账 owner |
| `journal` | 记凭证（ADR-0076 的既有实现） | 是 | core/账簿 owner |
| `effect` | 声明一条外部效果意图，接受后由出箱执行 | **否**（只声明意图） | 出站效果 owner |
| `work` | 声明一个受属工作/任务/审批 | **否** | work 应用 |
| `call` | 调用一个 `Side=pure` 的能力（ADR-0118 的 `Capability`），结果可赋给后续步骤 | 是（只读） | 能力主人 |

**步骤之间的顺序规则**（必须在发布期可检查，不能靠运行期碰运气）：

1. **同一记录在同一次事务中只能被一个步骤写**。两个 `update` 打同一条记录 → 发布期拒绝（否则结果依赖步骤顺序，重放的确定性没有依据）。
2. **`link` 的目标必须已经存在或在本事务的**更早**步骤创建**（`create` 先于 `link`）。反之（先 link 后 create）发布期拒绝。
3. **`call` 只能读**：它读到的值是**事务开始时的快照**还是**此前步骤的结果**，必须由声明决定。默认读快照（确定性强）；显式要求读前序步骤结果时，该步骤的依赖必须可静态排序。
4. **`ForEach`（ADR-0104 的集合迭代）内部不得再嵌套 `ForEach`**：一层迭代，深度固定。嵌套会破坏"结果可静态排序"这个前提。
5. **`Guard` 在全部步骤之前求值一次**；`When`（步骤级）在该步骤执行前求值。步骤级条件不成立＝**跳过该步骤**（不是拒绝事务）——这是显式的：需要"不成立就拒绝"时用 `Guard`。
6. **分级拒绝（ADR-0117）在顺序中求值**：`route` 改变后续步骤的路径，因此 `route` 之后不得再有写同一记录的步骤（发布期检查）。

### D3 原子性的确切含义

一次业务事务的保证是**全有或全无**，范围是**该应用账本加全部 owner 私有状态**：

1. 全部步骤在私有上下文上验证并试应用（fork）；任何一步被拒绝 → 整个事务拒绝，**不留部分状态、不占编号、不产生效果意图**；
2. 全部通过后形成**一个**接受结果，一次落盘；
3. 恢复时**逐字节应用已保存的映像**，绝不重跑规则、模型或外部调用（沿 ADR-0038/0097）；
4. 同键同内容重试返回原答复；同键异内容冲突（K4 幂等性）。

**不保证**：跨应用的原子性（见 §3）、外部系统的 exactly-once、事务内的读一致性跨越已提交的其他决策。

### D4 预算与拒绝

接受结果预算从 1 MiB 提高（具体值由实现期按真实单据测出，不预先承诺），并在编解码器上按**类型**给预算，而不是一个全局数字。**预算耗尽时必须显式拒绝并说明超出的内容**，绝不静默截断——静默截断会让"部分成功"从后门回来。

超过单次事务合理规模的操作（大批量导入、全量重算）不走事务，走受属工作分批执行；**每批是一个事务**，批次间的部分可见是显式声明的结果，不是缺陷。

### D5 事务不是流程

- 长流程（等待、重试、跨系统）归 Flow/Work；**每个流程步骤内部可以是一个事务**，流程本身不是事务。
- 审批：事务在审批**之前**完整构造（暂留），放行后以申请人身份执行整个事务。审批放行不拆散事务。

### D6 契约与语言边界

内核 `K4` 不变：一项决策仍只改**单一权威**。本 ADR 不引入跨权威原子组（ADR-0026 的否决继续有效），只是在单一权威内部把"能改什么"从"一条记录"扩到"一个应用的全部类型"。

`contract/` 不变更语义；`BusinessTxn` 是 `platform` 层的定义契约（沿 ADR-0097 §2 的 owner 划分）。

## 3. 不变的那些边界

- **跨权威不原子**。两个应用的业务确认仍是：请求 → 提供方独立裁决 → 回执 → 调用方独立裁决（ADR-0026 §设计 2）。本 ADR 的合并路线是让**一个业务系统是一个应用**，从而让绝大多数"跨权威"在事实上消失；真正的跨系统协同归 ADR-0112。
- **不引入租户代码**、不引入表达式语言（条件与赋值见 ADR-0101）、不允许事务提交任意 journal 字节（ADR-0097 §3.1）。
- **不做补偿式回滚**（ADR-0026 D1(c) 已否决）。事务失败不留痕迹，不需要补偿。

## 4. 后果

- 构建器第一次能表达"一个业务操作改了五张表"；MES 的完工、ERP 的过账、WMS 的收发货全部落在一条事务里。
- `apps/mes/erp.go`、`apps/erp` 里"为了跨应用一致性而存在的拆分"失去理由，进入 ADR-0114 的退出路线。这正是 ADR-0088 §未做 里"主数据落库"的前置条件。
- 参考应用里手写的 Go 业务规则被声明式事务取代；被取代的 Go 代码按 ADR-0114 退出。
- 风险：事务成为新的"什么都往里塞"。约束是 §D4 的预算与"长流程不是事务"；评审时看的是**单据语义**，不是行数。

## 5. 验收

1. `capabilities/server` 新增宿主测试：构建器定义"收货单据"（头 + 2 行 + 编号 + 过账 + 状态），一个事务动作产生 `record-batch`，含 3 个对象类型、≥4 行、1 个序列、1 个过账，且全部行指向同一子决策。
2. 同测试内注入第 3 步失败：单据仍是草稿、编号未占、无分录行、无效果意图、输入未被消耗；重试同键返回原答复。
3. 同测试内注入追加失败与进程崩溃：重新打开后按前驱恢复，逐字节重现同一结果。
4. 幂等：同键同内容返回原答复，同键异内容返回冲突。
5. 反例：跨应用的两个对象类型出现在一个事务里 → 组合期或提交期明确拒绝，不得静默降级为两个决策。
