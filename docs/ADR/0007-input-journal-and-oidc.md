# ADR-0007: 服务端持久化输入日志；操作主体统一源自 OpenID 提供商

> **由 [ADR-0031](0031-ai-application-platform.md) 修订，2026-09-27。** 输入重放 (input replay) 与全环境故障即停 (fail-stop) 仍是当前运行时的具体实现。已正式接受的目标是基于全新开发基线的已提交结果故障恢复 (committed-result recovery) 与租户分层监督机制；OIDC 身份集成与恢复过程绝不发起外部调用的原则保持不变。此注记记录最终目标；下方的历史决策与实际构建依然真实反映其所处时代的技术切片。

**状态：** 已接受 (2026-09-24)

**背景上下文。** #87 任务必须将制造领域切片推向工业级生产路径：确保状态能够经受住系统突然重启与全量数据恢复的考验，并且调用者身份必须由企业级身份提供商证明，而非依赖脆弱的硬编码令牌表。数据持久化架构曾有三种备选路线：(a) 为每个聚合根建立领域业务专属关系表，(b) 将内核底层日志作为记录直接存储，并由其异步重建领域只读投影，或者 (c) 针对所有被接受的输入建立保序日志 (journal)，通过能够接纳它们的业务代码执行确定性重放。纯粹依靠内核底层日志无法支撑路线 (b)：因为设备停机事件、其不透明的稳定全局 ID 与重定向关系、连接器增量游标以及 SFC 运行状态均是由领域业务代码从输入中动态推导得出的，并未全部内嵌在变更记录中。关于身份认证，我们坚决拒绝自行手写身份提供商（徒增庞大的安全漏洞攻击面，却无任何平台核心价值）；在评测比较中，Rauthy（基于 Rust、单容器轻量交付、原生支持带密码的 OIDC、MFA 与 Passkeys 硬件密钥）击败了 Pocket ID（仅支持 Passkeys，无法用于车间现场共享触控终端）、Kanidm（架构过重）以及 Zitadel（保留给未来有超大型多组织隔离需求的顶级客户）。

**决策。**
1. 领域服务端将每项已被接受的输入（业务提交、连接器数据分发）连同其当时的原始操作主体凭据与服务端物理时间戳，严格记录在 `platformserver.Journal` 中（基于 PostgreSQL 存储，每个租户分配一条严格保序的递增单调序列号）。对于未产生任何新记录的幂等重放输入，绝不重复写入日志。系统在启动时，使用相同的代码、以记录中原始主体的身份严格重放整个日志。重放过程中若遭遇任何非预期的拒绝或错误，服务端立即终止启动退出：表明持久化记录与当前代码逻辑发生了严重分化。
2. 每次日志追加均显式指定其期望的当前序列号，确保未重放完最新分录的第二个并发写入者报错失败，避免出现交错写入（满足 K5 中每个租户单一权威的铁律）。追加日志失败的操作在向调用者返回应答之前立即终止服务端进程（故障即停 fail-stop）；客户端的发件箱会在系统重启后负责自动重新发送该请求。
3. 连接器的心跳信号不记入持久化日志；系统重启后连接器的健康状态暂时呈现为陈旧 (stale)，直至收到下一次真实心跳。服务端物理时钟严格运行在微秒级高精度下，确保重放生成的记录完整继承其首次产生时的精确时间戳。
4. `platformserver.OIDC` 负责对客户端传入的访问令牌进行严密校验（验证签发方的 JWKS 签名、签发者合法性、过期时间戳、以及 `typ` 必须为 Bearer，严禁将 ID Token 当作访问令牌混用），并将调用者映射为统一的主体标识：普通用户为 `user:<经过验证的邮箱>`，使用客户端凭据模式的服务账号为 `client:<客户端 ID>`。领域内部的人员目录进一步将主体映射为具体的业务主体（遵循 K6：组织架构是领域数据，绝非身份提供商的数据）。浏览器端客户端使用带有 PKCE 安全加固的授权码模式进行单点登录 (`@platform/kernel` 的 `oidc.ts`)。
5. 基础设施完全代码化：维护 `deploy/local/compose.yaml`（包含 PostgreSQL、附带声明式初始化引导配置的 Rauthy、以及 mes-server）以及 `deploy/local/rehearse.sh` 自动化演练脚本，该脚本严密验证 OIDC 主体映射、容器硬重启、使用 `pg_dump` 备份转储并恢复至全新数据卷、以及发件箱重新自动补发备份遗漏请求的完整灾备全链路。执行 `scripts/verify.sh deploy` 可一键自动化运行演练。

**影响与后果。** 内核契约本身保持稳定未改。系统状态被严格形式化定义为持久化日志与当前业务代码的纯函数映射，因此一旦业务代码改动导致其拒绝了先前已被接受的某项合法历史输入，服务端将在启动重放时直接报错拒绝启动；任何此类代码变更必须能够成功重放既有的所有历史日志（制造领域测试集涵盖对所有业务场景日志的完整回放）。系统启动重放的耗时随日志体量的增大而线性增长。人员目录以邮箱为主键，因此修改人员邮箱必须同步更新目录映射。`deploy/local` 中配置的所有密钥严格限于本地开发测试环境；生产部署必须通过安全环境变量注入其自身密钥。切换外部身份提供商仅需简单修改签发者 URL 与 JWKS 终端地址即可无缝完成。

**重新评估时机：** 当日志重放耗时超出系统启动时间预算时（需要引入基于已重建内存状态的快照机制）、当业务规则调整绝不允许溯及既往历史时（重放机制届时需要直接读取记录在案的历史执行结果，而非重新执行业务逻辑校验）、当垂直领域需要依赖 PostgreSQL 原生 SQL 表达能力进行复杂查询时（在日志旁边建立 SQL 领域的只读模型与投影数据表）、或者当大型客户坚持要求接入其企业现有的私有身份提供商时。
