# ADR-0007: Servers persist an input journal; principals come from an OpenID provider

**Status:** Accepted (2026-09-24)

**Context.** #87 had to put one slice (manufacturing) on a production path: state that survives a restart and a restore, and callers proven by an identity provider instead of a token table. Persistence could be (a) domain tables per aggregate, (b) the kernel logs stored as records with domain projections rebuilt from them, or (c) a journal of the accepted inputs, replayed through the code that accepted them. The kernel logs alone are not enough for (b): downtime events, their opaque IDs and redirects, connector cursors and SFC states are derived by domain code from inputs, not stored in change records. For identity, writing our own provider was rejected (security surface without platform value); Rauthy (Rust, single container, OIDC with passwords, MFA and passkeys) was chosen over Pocket ID (passkeys only, unusable on shared plant terminals), Kanidm (heavier) and Zitadel (kept for multi-organisation customers).

**Decision.**
1. A domain server records each accepted input (a submission, a connector delivery) with the principal as it was and the server time, in `platformserver.Journal` (PostgreSQL, one numbered sequence per tenant). An input that adds no record (an idempotent replay) is not recorded again. On start the server replays the journal through the same code, as the recorded principals. Any refusal during replay stops the server: the record and the code disagree.
2. An append names the sequence number it expects, so a second writer that has not replayed the other's entries fails instead of interleaving (one authority per tenant, K5). A failed append stops the server before the input is answered (fail-stop); the client's outbox resends it after the restart.
3. Connector heartbeats are not recorded; health reads stale after a restart until the next heartbeat. The server clock runs at the journal's microsecond precision so replayed records carry their first times.
4. `platformserver.OIDC` verifies access tokens (signature by the issuer's JWKS, issuer, expiry, `typ` Bearer, so ID tokens are refused) and maps the caller to a subject: `user:<verified email>` or `client:<client id>` for client-credentials tokens. The domain's directory maps subjects to principals (K6: the organisation is domain data, not the provider's). Browser clients sign in with the authorization code flow and PKCE (`@platform/kernel` `oidc.ts`).
5. Infrastructure is code: `deploy/local/compose.yaml` (PostgreSQL, Rauthy with declarative bootstrap files, mes-server) and `deploy/local/rehearse.sh`, which checks OIDC principals, a restart, a restore from `pg_dump` into a new volume, and the outbox resending what the backup missed. `scripts/verify.sh deploy` runs it.

**Consequences.** The kernel did not change. State is a function of the journal and the code, so a code change that refuses an input it once accepted stops the server at start; such changes must replay existing journals (the manufacturing tests replay every scenario). Replay time grows with the journal. The directory is keyed by email, so an email change needs a directory change. Secrets in `deploy/local` are local-only; a deployment passes its own through the environment. Changing identity provider changes only the issuer and JWKS URL.

**Revisit when** replay exceeds a startup budget (snapshots of the rebuilt state), a rule change must not apply to history (replay then needs the recorded outcome, not a re-validation), a domain needs queries PostgreSQL should answer (read models in SQL beside the journal), or a customer brings its own identity provider.
