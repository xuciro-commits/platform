# ADR-0099：超越 Palantir 的意图驱动应用构建工作台 —— 从“底层零件孤岛”到“六步心流全栈画布”

**意图：** 彻底重构 Builder（应用构建工作台）的信息架构与创作交互范式。推翻 ADR-0052/0053 中对 Palantir Foundry“按底层技术零件切分 20+ 个孤岛菜单（Ontology / Workshop / Automate / Functions / Data Connection）”的表面模仿，转向**以构建者从零搭建完整企业应用的真实六步心流（立骨架 → 定生命 → 立规矩 → 搭界面 → 接协同 → 彩排发布）为主干的意图驱动全栈工作台（Intent-Driven Application Studio）**。在保持内核契约（`contract/`）、宿主单写者接受结果管线（ADR-0097）与声明式业务决定语义（ADR-0098）完全统一、零架构漂移的前提下，让 FDE 与业务玩家无需理解后端数据库概念或前端变量状态总线，即可从头到尾顺畅建出并长期维护完整工业级应用（如 MES）。

**状态：** 草案 / 待分波实施（2026-10-12）；作为构建者前端体验与交互改造的顶层设计 ADR，与 [ADR-0098](0098-declarative-business-decision-semantics.md)（全栈业务语义与三层工程正确性收口）协同推进。當本 ADR 实施完成后，将取代 ADR-0053 的构建者侧导航与多孤岛编辑器切分。

**基线：** `5ef221985379949d2b82115e8a5a4203d55bc835`。

## 1. 深度复盘：为什么现有工作台（表面模仿 Palantir）在实际建应用时走不通？

Palantir Foundry 的产品形态是其十余年间从大数据管道（Data Connection / Pipeline Builder）、知识图谱（Ontology Manager）、低代码大屏（Workshop）到自动化（Automate / AIP Logic）逐个团队拼接演化出来的历史产物。

在 ADR-0052/0053 中，我们模仿了 Foundry 的工具分类法，在 `web/packages/build/src/index.tsx` 的左侧导航栏摆出了 **7 大分组、22 个平铺的一级技术零件入口**：
- `Ontology`（Object types、Action types、Relationships、Shared properties、Queries）
- `Integration`（Connections、Data sources、Datasets、Pipelines、Writebacks、Matching rules、Integration health）
- `Interface`（Modules、Templates）
- `Logic`（Automations、Flows、Runs）
- `Functions`（AI functions、Code functions、Decision tables、Agents、Alert rules）
- `Releases`（Changes、Release history）

当一个真实用户（FDE 或业务专家）打开工作台，想要**从零开始把一套 MES 一步一步建起来**时，这套“表面模仿 Palantir”的界面暴露出五个致命的体验断层：

### 1.1 断层一：按“底层存储零件”切分菜单，打碎了人类的完整业务直觉
- 在人类的业务直觉里，**「批次完工过站（Complete Operation）」** 是一件事：*操作工在批次详情页点“完工”，如果还有下一道工序就推进工序号并回到排队态，如果是最后一道工序就变为已完工；当同一工单的所有批次都结束后，父工单自动变为已完工并触发向 ERP 报工。*
- 但在现有的 Palantir 式工作台里，为了做成这一件事，用户被迫在 **6 个完全割裂的编辑器** 之间来回横跳：
  1. 去 `Object types` 给 `SFC` 加状态；
  2. 去 `Relationships` 或 `Object types` 配 `Order ↔ SFC` 和 `Routing ↔ Operation` 的 `inverse` 反向关系名；
  3. 去 `Action types`（里面又有 Overview / Parameters / Form / Rules / Criteria / Side effects / Approval / Permissions **8 个子页签**，中间只是干瘪的列表，真正编辑全挤在右侧 280px 窄检查器里）配条件分支和父单更新；
  4. 去 `Queries` 配查询；
  5. 去 `Modules (Workshop)` 配页面变量、查询计划、按钮绑定；
  6. 去 `Automations / Flows` 配工单完工后的 ERP 回写流。
- **结论**：菜单呈现的是“平台数据库里有哪些 `build.*` 表”，而不是“构建一个业务应用的心智步骤”。

### 1.2 断层二：“先有鸡还是先有蛋”的发布死锁（Circular Authoring Deadlocks）
- 在现有编辑器中，许多选择器（如 `Reference object`、`Action.Creates` 的目标子对象、Workshop 页面绑定的对象）默认依赖**已经发布安装到宿主的定义**或要求先在子对象上手工填对 `inverse` 字符串：
  - 想建 `Product` 引用 `Routing` → 必须先退出来去建 `Routing` 并保存；
  - 想在 `Order` 的 `release` 动作里配置“拆批创建 `SFC`” → 因为 `SFC` 还没建或者还没指向 `Order`，`ActionTypeEditor` 的 `Create a related record` 按钮直接是灰色的（`Publish a related object with a reference to this object first`）！
- 用户在建模初期根本无法一气呵成地把领域图画出来，而是不断被“请先去另一个菜单创建并发布另一个零件”打断心流。

### 1.3 断层三：“盲人摸象”式的抽象 Schema 编辑 —— 没有实时样本数据伴随（Data-Blind Schema Authoring）
- 在 `ObjectTypeEditor` 和 `ActionTypeEditor` 中，用户全程面对的是冷冰冰的元数据结构（字段名、类型标识符、操作符下拉框）。
- 屏幕上**没有一行真实的业务样本数据**！当用户配置“10 件工单拆 3 个批次（4, 3, 3）”或“当设备能力包含工序全部所需能力时允许开工”时，他看不到当前车间里有哪些设备、看不到某道工序要求什么能力、也无法在配完规则的下一秒直接点一下“拿样本工单试跑一次”，亲眼看到 3 条子批次被生成出来。

### 1.4 断层四：把内部 DSL 语法暴露给用户手敲（Leaky String DSLs in Inspector）
- 在 MVP 阶段的 `ActionTypeEditor` 中，为了表达高阶规则，用户需要在输入框里手写：
  - `step:next(record.routing.operations,number,record.operation)`
  - `split:input.quantity:input.sfcs`
  - `rollup:sum(sfcs.quantity?state=done)`
  - `append:operation=record.operation,code=input.code,by=$me`
  - `action=rework`
- 这本质上是把 Go 代码换成了“塞在文本框里的迷你脚本语言”。任何拼写错误（比如把 `operations` 写成 `operation`）都要等到点保存/发布时才报错，业余玩家根本不可能背下这套语法。

### 1.5 断层五：Workshop 把前端 React 状态管理甩锅给构建者（The Workshop Variable Plumbing Tax）
- Palantir Workshop 最大的时代局限，就是把页面看作“一堆互不相识的 Widget，靠构建者手工声明 Page Variables、Query Plans、Resource Outputs 连线通讯”。
- 明明构建者在本体层已经声明了：
  - `SFC.operation` 引用 `Operation`；
  - `Operation.parameters` 是工艺参数表；
  - `Start` 动作的 `resource` 参数过滤条件是 `workcenter = operation.workcenter && capabilities contains all operation.requires`；
- 到了 Workshop 页面编辑器里，页面却像失忆了一样，要求构建者重新去配一套 `Page variables`、`Query plans`、`Selection variable`！这种“在本体层配一遍业务关系，又在 UI 层手工配一遍状态总线”的双重劳动，正是 Palantir Workshop 交付极其笨重的根源。

## 2. 从第一性原理出发：用户从零构建一套完整 MES 的真实六步心流

当我们问：**“当用户打开应用工作台之后，第一步做什么？第二步做什么？……一直到最后把一个 MES 一步一步建起来，它的心流是怎么样的？”**

答案非常清晰——人类构建任何企业级业务软件，永远遵循一条**从“看见业务全貌”到“赋予生命状态”，再到“立下交易规矩”、“生成岗位工作台”、“接通外部协同”，最后“沙箱彩排上线”的六步递进心流**：

```mermaid
flowchart LR
  S1["第一步 · 立骨架<br/>领域蓝图与样本数据<br/>(Domain Map & Live Data)"]
  S2["第二步 · 定生命<br/>状态轨与动作连线<br/>(Lifecycle & Transitions)"]
  S3["第三步 · 立规矩<br/>可视化业务决定流<br/>(Visual Decision Composer)"]
  S4["第四步 · 搭界面<br/>语义直绑岗位操作台<br/>(Role Cockpit Builder)"]
  S5["第五步 · 接协同<br/>外部数据源、回写与 AI<br/>(Connect, Automate & AI)"]
  S6["第六步 · 彩排与发布<br/>多角色沙箱演练与封存<br/>(Storyboard & Release)"]

  S1 --> S2 --> S3 --> S4 --> S5 --> S6
```

### 第一步：立骨架 —— 在一张领域蓝图画布上画出业务对象、连出关系、填好样本数据
1. **用户打开项目看到什么？**
   - 不是空白列表，而是**「领域蓝图画布（Domain Blueprint Canvas）」**（支持从行业脚手架一键初始化，或从零拖入对象卡片，或直接从外部数据源生成对象卡片）。
2. **在画布上怎么建 MES 的 8 个对象与关系？**
   - 用户在画布上直接放置卡片：`工作中心`、`设备资源`、`工艺路线`、`工序`、`产品`、`计划工单`、`车间工单`、`生产批次 (SFC)`。
   - **在卡片内直接加字段**（像 Notion 表格添加列一样直观）：
     - 给 `设备资源` 加 `能力 (多值标签 tags)`；
     - 给 `工序` 加 `工序号 (整数)`、`所需能力 (多值标签 tags)`、`工艺参数 (内嵌明细表 lines：参数名、规格类型、单位、目标值、下限、上限)`。
   - **从卡片拖线到另一张卡片 = 一步建立双向语义关系（消灭 `inverse` 手填与发布死锁）**：
     - 从 `工艺路线` 拖线到 `工序`，选择关系语义 **「包含有序步骤（1:N Ordered Steps，按 `工序号` 排序）」** → 平台在同一个项目草稿事务中自动为 `工序` 创建 `routing` 引用字段、为 `工艺路线` 注册 `operations` 反向集合与有序步进契约！
     - 从 `车间工单` 拖线到 `生产批次 (SFC)`，选择 **「主从拆分（1:N Master-Detail）」** → 自动建立 `order` 引用与 `sfcs` 反向集合。
3. **画布底栏：实时样本数据表格（Live Sample Sheet）**
   - 选中画布上任意对象卡片，底部 Dock 直接展开可编辑的**实时样本数据表**（自带沙箱种子或由用户随手填 3 行数据，例如填好 `RT-100` 的 `10 铸造 / 20 机加工 / 30 装配` 三道工序，以及 `ASM-1`、`ASM-2` 两台设备）。
   - **为什么这一步至关重要？** 因为有了这几行活的样本数据，接下来第 2、3、4、5 步配置任何状态、规则、表单下拉框和页面组件时，用户看到的都是**真实的车间数据预览**，而不是抽象的变量名！

### 第二步：定生命 —— 在对象卡片上展开状态机轨道，连线即创建业务动作
1. **用户怎么定义工单和批次的生命周期？**
   - 在领域画布上双击 `车间工单` 或 `生产批次 (SFC)`，进入该对象的**「生命周期与动作画布（Lifecycle & Action Canvas）」**。
   - 画布中央是清晰的状态泳道节点：
     - `SFC`：`排队中 (Queued)`、`加工中 (In Work)`、`质量挂起 (On Hold)`、`已完工 (Done)`、`已报废 (Scrapped)`。
2. **连线即动作（Edges Are Actions）**：
   - 从画布左侧的「新建入口（Creation Entry）」拖一条线到 `车间工单.已下达` → 命名为 **「下达车间工单 (Release)」**（自动标记为 `New: true` 语义化创建动作，并自动询问：“下达后是否仍允许普通角色使用裸字段新建？”默认关闭裸新建旁路！）；
   - 从 `排队中` 拖线到 `加工中` → **「开工 (Start)」**；
   - 从 `加工中` 拖出一条带菱形分叉的线指向 `排队中`（循环步进）与 `已完工`（末步完结）→ **「完工过站 (Complete)」**；
   - 从 `排队中 / 加工中` 拖线到 `质量挂起` → **「记录不良 (Log NC)」**；
   - 从 `质量挂起` 拖出分叉线指向 `质量挂起`（待签）、`排队中`（返工/让步）、`已报废`（报废）→ **「签字处置 (Sign Disposition)」**。
   - **心流优势**：用户一眼就能从这张图上看懂“一个批次在车间里是怎么流转的、每个状态下有哪些按钮可点、点完会去哪”，无需在多个菜单间拼凑脑补。

### 第三步：立规矩 —— 点击状态连线，进入“四段式可视化业务决定画布”（彻底告别手敲 DSL）
当用户点击任意一条动作连线（例如点击 `下达车间工单`、`开工`、`完工过站` 或 `签字处置`），主画布平滑展开为 **「业务决定编排器（Visual Decision Composer）」**。
它不再是现有的 8 个碎页签 + 280px 窄侧栏，而是**一屏贯通的四段式可视化决定流（左：输入与表单 → 中上：守卫不变量 → 中下：状态分支与本记录变更 → 右：跨对象创建与父单联动）**：

```text
┌───────────────────┬───────────────────────────┬───────────────────────────┬───────────────────────────┐
│ 1. 谁在何时填什么 │ 2. 必须满足什么业务不变量 │ 3. 本记录怎么变 (含分支)  │ 4. 连带产生/更新什么记录  │
│ (Actor & Inputs)  │ (Submission Guards)       │ (State & Field Branches)  │ (Multi-Record Effects)    │
├───────────────────┼───────────────────────────┼───────────────────────────┼───────────────────────────┤
│ • 执行角色与产线  │ • [唯一性卡片]            │ • [分支 1: 还有下一工序]  │ • [批量拆分创建卡片]      │
│ • 输入参数列表    │   车间工单中 不存在       │   当 工艺路线.下一工序    │   创建 生产批次 (SFC)     │
│ • [智能候选过滤]  │   计划工单 = 输入.计划单  │   不为空 时：             │   条数 = 输入.批次数      │
│   设备下拉框仅列：│ • [能力包含卡片]          │   → 状态设为 [排队中]     │   数量 = 均分(输入.数量)  │
│   工作中心匹配 且 │   输入.设备.能力          │   → 当前工序 = 下一工序   │ • [父单联动上卷卡片]      │
│   能力包含工序要求│   包含全部 当前工序.要求  │ • [默认分支: 末道工序]    │   当 父工单.全部SFC 已结束│
│ • [参数显隐联动]  │ • [会签职责分离卡片]      │   → 状态设为 [已完工]     │   → 父工单设为 [已完工]   │
│   仅返工时显示工序│   签名中 无 签署人=当前人 │   → 清空 当前加工设备     │   → 汇总 合格数 / 报废数  │
├───────────────────┴───────────────────────────┴───────────────────────────┴───────────────────────────┤
│ ▶ 实时样本试跑台 (Live Decision Sandbox)：选择样本 [SO-1-001 (工序 10 铸造)] + 试填参数 → 立即预演结果 │
└───────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **核心突破 1：点选式路径胶囊（Pill Path Picker）彻底消灭手写字符串**
  - 任何需要引用字段、路径、步进或聚合的地方，点击即弹出**级联语义树**：
    - 选 `输入参数 → 产品 → 工艺路线 → 工序列表 (有序) → 第一步`（底层自动生成并校验 `step:first` AST，界面上展示为可读胶囊 `[产品 ▸ 工艺路线 ▸ 首道工序]`）；
    - 选 `关联父记录 (车间工单) → 所有生产批次 (SFC) → 数量之和 (当状态 = 已完工)`（界面展示为胶囊 `[汇总求和: 同工单 SFC.数量 (状态 = 已完工)]`）；
    - 选 `按数量整数均分 (余数归前序批次)`（界面选总数字段 `输入.数量` 与份数字段 `输入.批次数`）。
- **核心突破 2：前后端同源的“智能引用候选器（Smart Reference Filter）”**
  - 在配置引用参数（如 `开工` 的 `设备 resource`）时，用户在参数卡上直接点「配置可选范围」：
    - 勾选 `设备.工作中心 = 当前批次.当前工序.工作中心`；
    - 勾选 `设备.能力 包含全部 当前批次.当前工序.所需能力`；
  - 平台**一次声明、两端生效**：
    1. 在前端打开 `开工` 弹窗时，`RecordLookup` 自动将该过滤条件编译为服务端受控查询（完整匹配全库、支持分页与搜索，绝不只过滤前 25 条）；
    2. 在后端提交 `start` 动作时，账本 `take` 自动执行完全相同的守卫校验！
- **核心突破 3：内嵌“实时样本试跑台（Live Decision Sandbox）”**
  - 编排器底部常驻试跑抽屉：直接选中第一步录入的样本记录（如 `SO-1-001`），选一个参数点「试跑」，右侧立刻高亮显示哪条分支被命中、哪些字段变成了什么值、哪条关联父记录被联动更新（不在生产账本落盘，走私有 `ForkDecision` 预演）。

### 第四步：搭界面 —— 语义直绑的“岗位操作台装配器”（消除 Workshop 变量管道税）
当第 1–3 步完成后，平台已经完整知道这个应用有哪些对象、哪些关系、哪些状态动作、哪些明细表、哪些有序工序。
此时进入 **「岗位操作台（Role Cockpits / Pages）」** 阶段，不再让用户面对空白画布去手工绑 `Page variables` 和 `Query plans`：

1. **按业务岗位一键生成工作台骨架（Role-First Page Generation）**：
   - 用户选择岗位（如 `计划主管`、`车间操作工`、`工艺工程师`），或围绕核心对象选择页面模式：
     - **「主从计划转单台」**（自动组合：上游 `计划工单` 表格 + 行级带参触发 `下达车间工单` 按钮 + 下游 `车间工单` 表格）；
     - **「批次过站执行操作台（Operator Cockpit）」**（自动绑定为 `SFC` 的专属打开页面 `Application.Opens["build.sfc"]`）；
     - **「工艺路线泳道浏览台（Craft Explorer）」**。
2. **语义路径直绑（Direct Semantic Path Binding —— 零手工变量配置）**：
   - 在操作台画布中选中任意组件（如表格、明细表、卡片），右侧检查器直接提供**「相对于当前选中记录的语义路径选择」**：
     - 例如在 `SFC` 操作台上放一个明细表组件，数据源直接点选 `当前选中 SFC ▸ 当前工序 (Operation) ▸ 工艺参数 (Parameters)`！Workshop 编译器自动在底层生成并管理受控页面变量与查询计划，构建者**完全不需要感知 `PageVariable` 或 `QueryPlan` 的存在**（高阶用户仍可展开高级面板微调）。
3. **一等声明式「工序/阶段泳道图组件（`ProcessFlow` Widget）」**：
   - 将工序流转图正式作为 Workshop 组件库中的标准组件（绝不在通用 `RecordPage` 里硬编码 MES 字段名）：
   - 检查器提供清晰的四个绑定槽位：
     - **步骤集合来源（Steps Source）**：如 `当前记录 ▸ 工艺路线 ▸ 工序列表`（支持按 `工艺路线版本` 过滤冻结）；
     - **步骤序号与标题字段（Order & Label Field）**：选 `工序号 (number)` 与 `工序名称 (name)`；
     - **泳道分组字段（Swimlane Field）**：选 `工作中心 (workcenter)`（自动解析引用记录的显示名称作为泳道标题）；
     - **在途状态叠加（Active Progress Overlay，可选）**：绑定当前 `SFC` 记录的 `当前工序字段 (operation)`、`状态字段 (state)` 与 `异常标记明细字段 (ncs)`。

### 第五步：接协同 —— 在状态与动作节点上原位挂载自动化、外部回写与 AI
- 用户不需要离开领域画布去翻找 `Integration` 或 `Automations` 菜单：
  - 在 `计划工单` 对象卡片上点「接入外部数据源」→ 原位配置从 ERP PostgreSQL / OData 同步计划单；
  - 在 `车间工单` 的 `已完工 (Completed)` 状态节点上点「挂载完成时自动化（On Enter State）」→ 直接串接 `ERP 报工 Writeback` 与失败时的 `AI 异常诊断 Agent`。

### 第六步：彩排与发布 —— 多角色故事板演练（Role-Play Storyboard）与一键封存上线
- 在工作台顶栏点击 **「全链路彩排（Rehearse Application）」**：
  - 打开一个**分角色故事板沙箱（隔离内存租户 `SimulateCandidate`）**：
  - 顶栏可一键切换角色卡（`计划主管` → `产线操作工` → `质检工程师`），按真实业务界面走完：
    *下达 10 件工单拆 3 批 → 试重复下达同一计划单被拒 → 选错设备被拒 → 选对设备开工完工过站 → 记录不良挂起 → 质检双人异义电子签名返工与报废 → 观察父工单自动变为已完工并算出合格数 7 / 报废数 3*。
  - 彩排通过后，点击「保存为回归测试并发布上线」：自动将刚才的操作序列固化为项目的 `build.testplan`，生成自闭合的不可变发布候选（`ReleaseCandidate`）并激活上线！

## 4. 架构不变量：为什么推翻旧构建器 UI 不会导致架构漂移？

本 ADR 推翻的是**前端构建器的信息架构、孤岛式菜单和手工字符串/变量配置体验**，而底层平台架构保持 100% 统一与收敛：
1. **内核契约（`contract/`）零变更**：K1–K9 依然不含任何领域词汇。
2. **宿主与提交管线（`capabilities/server` + ADR-0097）零漂移**：所有构建器产出物最终依然编译为标准的 `build.object`、`build.page`、`build.app`、`build.query`、`build.process`、`build.table` 资产，经 `AssetLifecycleOwner` 与 `ReleaseCandidate` 封存激活，运行时决定全部编译为 `platform.Transition` 并通过 `record-batch` 接受结果原子落盘与重放。
3. **前端组件库（`@platform/ui` & `@platform/app`）单一归属**：画布复用已有的 `RelationCanvas`、`FlowCanvas`、`FlowSteps`、`DataTable`、`Workbench`；新增的语义直绑与智能过滤在编译期/运行期投影为受控查询与页面契约，不建第二套 UI 运行时。

## 5. 分波实施路线（与 ADR-0098 三层门槛衔接）

| 波次 | 目标 | 核心交付内容 |
|---|---|---|
| **Wave 0（归 ADR-0098 收口）** | **落实业务决定正确性与真声明式配置底座** | ① 修复集合查询下推与完整性、父对象不变量校验、`Do/After` 原子变更封存、默认裸 `.create` 旁路拦截、工艺历史版本冻结；<br>② 将引用参数动态过滤接入服务端受控查询，将工序泳道图改为可声明字段绑定的 `ProcessFlow` 组件并完成 Workshop 操作台配置。 |
