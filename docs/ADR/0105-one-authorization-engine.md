# ADR-0105 — 一个授权引擎：四层判定合成一个决定

状态：已接受（2026-10-12，负责人指令，ADR-0098 B 块第三份）· 修订 ADR-0078 的分层判定口径、扩展 ADR-0033 的派生闭包 · 不实现 ReBAC `related` 谓词（维持 ADR-0078 §0 的既有边界）

## 0. 意图

ADR-0098 第二个判据是"**没有权限绕过**"。今天的判定分散在四层，各自为政、各自有边界：

| 层 | 实现 | 是否进统一引擎 |
|---|---|---|
| 动作 | `platform/authz/authz.go:75` `Decide`，顺序固定为 bypass → deny 策略 → 角色(RBAC) → allow 策略 | 是 |
| 行范围 | `records.go:1096` `visibleIn` → `:1127` `scoped`，按 `Scope.Levels/Unit/Structure/Owner` 取多角色并集（`platform/entity.go:211-227`） | **不是** |
| 字段 | `narrow.go:92` `readsField`（ADR-0028 D3 的 `read`/`write` 标签）+ `viewOf`/`masked` | **不是** |
| 派生 | `narrow.go:140` `narrowed` → `:272` `derive`，读时逐源重判（`narrow.go:33` `mayRead`，`:362` `readable` 要求全部源可读） | **不是** |
| 标记 | `transfer.go:179-180,245-256` `restricted()` 的独立 if | **不是** |

ADR-0078 自己的边界表就写明了这件事：行可见性与字段遮蔽不经 `authz.Decide`，引擎顺序里没有 ReBAC。

**后果**：每个新入口（新动作、新读取、新集合、新事务步骤、新导出）都要**重新问一遍这四层怎么组合**。集合（ADR-0104）与事务（ADR-0100）会让这个问题爆炸——一个事务要检查几十条记录、几个集合、多个字段。

**判据**：任意一次平台操作（读一条、读一个集合、执行一个事务、导出、跨应用请求）的授权结果是**一个决定**，有唯一定义、唯一定序、可复现、可审计。

## 1. 决定

### D1 一个决定类型

```go
// 一次授权判定的完整输入与输出。
type AuthzRequest struct {
    Principal   string        // 主体（含 agent / service 主体，沿 ADR-0078）
    Tenant      string
    Kind        string        // read | write | create | archive | action | derive | export | protocol
    Type        string        // 对象类型
    Record      string        // 记录 ID（集合判定时逐元素）
    Fields      []string      // 涉及的字段（读/写）
    Action      string        // 动作名（Kind=action）
    From        string        // 派生/协议：来源链（见 D4）
}

type AuthzDecision struct {
    Allowed   bool
    Reason    string          // 可读原因（英文 + zh-CN）
    Layers    []AuthzLayer    // 每一层的判定与依据，供审计与前端解释
    Withheld  []string        // 被遮蔽的字段
}
```

`Layers` 是**必须**的：用户问"我为什么看不到这条"，答案在决定里，不靠事后猜。

### D2 唯一定序

判定顺序**固定**，且每一层只能**收窄**，不能放宽前一层：

```
1. 租户隔离      跨租户一律拒绝（`admits`，narrow.go:23）
2. 主体有效性    主体存在、未撤权、未被停用（ADR-0078 的撤销语义）
3. 显式 deny     策略拒绝优先于一切允许
4. 动作/动词     该主体是否有权执行 Kind（RBAC，authz.go:76-99 的既有顺序）
5. 行范围        Scope.Levels/Unit/Structure/Owner（records.go:1127 的既有语义）
6. 字段          read/write 标签（ADR-0028 D3）
7. 派生闭包      全部来源可读才可读（narrow.go:362）
8. 标记          Markings 与分级随血缘传播（ADR-0075）
9. allow 策略    最后才是允许
```

第 3/9 层保持 `authz.Decide` 现有的 deny/allow 语义；第 4–8 层是今天散落的部分，**接入同一定序**，不再各自短路。

### D3 集合与事务：一次判定，逐元素结果

- 一个集合的读取产生**一个决定外壳** + 每个元素的判定结果。元素不可见不产生 `Allowed=false` 的失败，而是被过滤掉；`count` 只计可见元素，并提供"部分不可见"标记（ADR-0104 D5）。
- 一个事务（ADR-0100）的每一步都要过判定：**任一步不允许则整个事务拒绝**（与约束失败同一条路径），Layers 里指出是哪一步哪一层。事务的判定在**私有上下文**中做（沿 ADR-0097 §3.2 的"审批预检使用只读声明及私有 fork/savepoint，不写共享状态"）。

### D4 派生闭包是授权的一部分，不是事后修补

今天派生的规则是"读时逐源重判"（`narrow.go:33/140/272`），方向正确但**位置在读取之后**：先算出值，再检查能不能读。这留下两个洞：

1. **自由文本**：ADR-0033 §5 自己写明"未声明出处的自由文本保持全量可见"，且明确这是"Code Review 必须揪出的逃避漏洞而非宿主能兜底"；
2. **字段级检查只看 `m.Roles[et.info.App]`**（`narrow.go:69`），不叠加该记录自身的可见性。

决定：

- 派生**必须**在写入时声明来源（已有机制），且在**读取时按第 7 层判定**——保留，不移到写入时，因为权限会变（今天的正确选择）；
- 补齐第 2 个洞：字段判定必须叠加**该记录的行可见性**，记录不可见则其字段一律不可读；
- 自由文本（AI 生成、评论、备注）**必须声明来源类型**才能出现在派生读取的字段里；未声明来源的自由文本字段在派生上下文中**一律遮蔽**，并在构建期提示构建者声明。今天的"保持全量可见"取消。

这会让部分现有 AI/评论字段在派生读取里消失。**这是有意的**：ADR-0098 §0 要的是"没有权限绕过"，不是"看起来没绕过"。

### D5 递归与反向引用的边界

ADR-0104 D4 决定反向引用必须**声明**。本 ADR 明确：**不实现 ReBAC `related` 谓词**（ADR-0078 §0 的既有决定维持），因为任意深度关系遍历会让"派生授权完全闭包"（Platform §10.6）无法证明。声明的反向引用 + 有界深度（16 段）覆盖实际业务需要。

### D6 判定的记录与不可重放

- 接受结果保存**判定依据**（主体、角色、当时的定义版本、命中的层），因此审计不需要重新推导（沿 ADR-0097 §3：恢复不重新授权）。
- **恢复不重跑授权**：历史记录按当时已经确立的事实恢复。
- 撤权后的行为按 ADR-0097 的既有语义：新操作被拒，历史仍可读。

## 2. 不做

- **不做第二套权限引擎**，不引入 OPA/Cedar 之类的策略语言（ADR-0078 已拒绝策略表达式）。
- **不做 ReBAC**（见 D5）。
- **不做"管理员绕过"**：运维动作（记录迁移、修复）走 ADR-0105 之外的显式管理路径并留痕，不通过放宽判定实现。
- **不做前端权限判断**：前端只显示后端决定的结果（今天已有此原则，ADR-0008 §3）；判定结果里的 `Layers` 是给用户解释用的，不是给前端自己算的。

## 3. 后果

- 每个读取与写入入口要改成调用同一个决定点。这是**大范围但机械的改动**，风险在遗漏入口——用入口清单（ADR-0097 §3.1 的九类入口）+ 守门检查保证（`scripts/escapes.sh` 增加"直接读记录不经判定"的模式）。
- `narrow.go`、`records.go` 的可见性函数、`transfer.go` 的标记检查从"分散实现"变为"引擎的层"，实现可以留在原地，但**入口与顺序统一**。
- 前端"为什么我看不到"从 Cannot-see 的猜测变为可显示的解释（`Layers`）。
- 性能：集合判定逐元素过一次引擎，需要缓存（每次请求内的判定缓存，键为主体+类型+层+定义版本）。**缓存不得跨主体复用**。

## 4. 验收

1. 九类入口（Submit、Input、审批/协议、订阅/作业、外部应答、Agent 步骤、模型计量、Compute/来源、发布/组合/宿主管理）各有一个越权用例，全部在同一个决定点被拒，错误码与原因一致。
2. 定序：构造"第 5 层不允许但第 9 层允许"的场景，结果必须是拒绝；调换层级即测试失败（用一条断言锁住顺序）。
3. 集合：含不可见元素的集合，`count` 不泄漏、`all` 不默认通过、`Layers` 可解释。
4. 派生：记录不可见时其字段不可读；未声明来源的自由文本字段在派生读取里被遮蔽（含既有 AI/评论字段的行为变化用例）。
5. 撤权：撤权后新操作被拒、历史仍可读、恢复不重跑授权。
6. 反例：跨租户、未知 Kind、`related` 谓词被请求 → 明确拒绝。

测试归宿主 platform 包与 authz 包；`docs/Testing.md` 增"授权判定"手测行。
