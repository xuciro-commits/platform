# ADR-0115 — 自举约束：平台自己的应用由构建器构建

状态：已接受（2026-10-12，负责人指令，ADR-0098 F 块第三份）· 这是一份**约束性** ADR，不是功能 ADR；它为 ADR-0100–0114 提供防止回退的机制 · 修订 AGENTS「参考应用用来证明平台能力」的执行口径：从原则变为可检查的规则

## 0. 意图

ADR-0098 的最根本变化是"从开发一套套业务软件，转向开发生产业务软件的能力"。这件事**最容易在实现期走偏**：

- 配置不出来时，先写 Go 兜住（"以后再说"）；
- 组件不够用时，把行业页面搬进通用库；
- 事务表达不了时，加一个特例 Kind；
- 前端绑定不灵活时，加一个专用 props。

每一条单独看都是合理的技术决定，合起来就是今天这个状态：`apps/*` 有六个原生应用、`capabilities/server/apps/build` 有 48 个文件、`@platform/ui` 之外还有六个行业 UI 包。

**判据**：新能力必须**能被构建器用出来**，否则它不算完成。这条判据要有机制，不能只靠自觉。

## 1. 决定

### D1 自举规则（Bootstrap Rule）

> 任何为"支持客户构建业务应用"而新增的平台能力，必须同时提供一个**由构建器构建的用例**；没有用例的能力视为未完成。

具体到本仓库的形态：

| 交付物 | 必须附带 |
|---|---|
| 新的定义契约（对象、约束、事务步骤、组件…） | 一个**构建者能在工作台里做出**的资产（对象定义、页面配置、事务定义），随候选发布 |
| 新的执行能力（新的 Kind、新的算子、新的端口） | 一个**通过构建器配置**触发的测试场景（不是直接调用 API 的测试） |
| 新的界面能力 | 一个**由配置产生**的呈现示例（Catalog 的场景装配资产，ADR-0063/0045 的既有形态） |

**反例（不允许）**：新增一个只被 Go 代码使用的对象类型；新增一个只能由 `apps/*` 调用的执行路径；新增一个必须在 Go 里硬编码字段名才能用的组件。

### D2 两个方向的自举

**前向（新能力）**：D1 的规则。

**后向（已有能力）**：ADR-0098 §1 要求"通过构建完整 MES 反向验证平台是否具备足够的通用能力"。因此：

- **构建 MES 的过程中撞墙的每一次**，都是平台能力的**缺口登记**（ADR-0113 D4）；
- 缺口有两种结果：**补齐通用能力**（立 ADR）或**记录为已知不支持**（明确写进对应 ADR 的边界）。**不允许**的第三种结果是"在探针里绕过并且不记录"。

### D3 自举的检查点

自举不能靠事后审计，要在**交付流程里**检查：

| 检查点 | 检查什么 | 手段 |
|---|---|---|
| 新定义契约落地 | 是否有构建器侧的资产与该契约配套 | 评审清单（ADR 的 As built 必须写出构建器资产） |
| 新执行路径落地 | 是否只能由 Go 触发 | 检查该路径是否出现在构建器可用能力清单里（`/v1/apps` 的声明与操作目录） |
| 新组件落地 | 是否满足 ADR-0110 D5 的四条门槛 | 门槛检查（组件代码无业务词汇 + 两处配置） |
| 新事务步骤/Kind 落地 | 是否在第二个业务语义下成立 | 第二用例（不同行业语义的配置） |
| 行业代码增长 | `apps/*` 的行业规则是否净增 | `Subtraction` 的退出计数与逃逸脚本 |

**这些检查不做成新的脚本体系**：能用现有手段（`scripts/boundaries.sh`、`scripts/escapes.sh`、`scripts/verify.sh`、`make check`、Catalog 生成）表达的，不新建工具。评审清单是 ADR 段落，不是新文档。

**每一项检查的具体判定**（"看起来有用例"不算通过）：

| 检查点 | 通过的最小证据 | 不通过的样子 |
|---|---|---|
| 新定义契约 | 该契约的 ADR As built 里有一条指向**具体资产名**的记录（对象/页面/事务的名字），且该资产能被发布 | As built 只写"已实现该契约"；用例是直接调用 API 的 Go 测试 |
| 新执行路径 | 该路径出现在**构建器可用能力清单**里（`/v1/apps` 的声明或操作目录），并有构建器侧的触发用例 | 路径只能由 `apps/*` 的 Go 代码触发；用例是 `host.InstallX` 直调 |
| 新组件 | 两处**不同业务语义**的配置存在（ADR-0110 D5），且组件源码里搜不到业务词汇 | 只有一处配置；示例里出现"工序/库位/床"等词 |
| 新 Kind / 新算子 | 在**第二个业务语义**下有一个通过的场景，且该场景不是原用例的改名 | 只在 MES 语境内成立 |
| 行业代码增长 | `Subtraction` 的退出计数（已退出能力数）在本批**不为零**或净增为零的理由被写明 | 本批新增了行业 Go 规则且未登记退出计划 |

**检查的时点是"整块交付时"**，不是每个提交：这与 AGENTS「一个整块完成后跑一次适用检查」一致。单个提交只做通过性检查。

**评审只查一件事**：这份交付的构建器用例**存在且可运行**。不存在 → 该能力标为**未完成**，不进入 As built 的"已实现"段落——这是本 ADR 唯一强制的动作，其余靠 ADR 段落的自述。

### D4 与"复用主人"的优先级

自举规则**不凌驾**复用原则。撞墙时的顺序（与 ADR-0098 §4 一致）：

1. 已有能力是否可用（查 Catalog、查 `/v1/apps` 的声明）；
2. 通用能力缺口 → 在**归属方**补齐（AGENTS 硬规则 3：缺的能力在归属方扩展）；
3. 新原语 → 立 ADR，且必须在第二个业务语义下成立。

**不允许**：在行业应用里补平台缺失的能力（这正是今天 `apps/mes` 有 `canDo`、`apps/erp` 有过账链的原因）。

### D5 本文的修订与退出

- 本 ADR **没有完成日**：它是持续性约束，与 ADR-0100–0114 同生命周期。
- 当 ADR-0114 的退出清单走完（原生参考应用全部退出或收窄为平台能力），自举规则的**前向部分**（D1）继续有效，**后向部分**（D2 的"撞墙反推"）转为常规的产品需求来源。
- **重新评估时机**：当"自举"造成真实的交付延误（例如为了配出用例而推迟必要的平台修复）时，由负责人重新权衡，且必须明写放宽到哪一部分。**不允许默认放宽。**

## 2. 不做

- **不做"零代码"的教条**：ADR-0098 §4 明确"不应该为了追求所谓零代码，限制真正需要代码实现的行业算法和专业集成"。自举要求的是"**能被构建器用出来**"，不是"不能有代码"。ADR-0044 的受控代码是合法的构建手段。
- **不做自动化合规扫描器**：D3 的检查用现有手段 + 评审清单，不新建元工具（避免"工具代替判断"）。
- **不追溯惩罚已完成的工作**：规则自本文起生效；既有实现按 ADR-0114 的退出路线逐步收口，不要求立即补齐用例。

## 3. 后果

- 每个 ADR 的 As built 段落多一项义务：**构建器侧的用例**。这会真实地拉长单项交付时间，是本 ADR 承认并接受的代价。
- `apps/*` 的行业代码净增长成为**可观测的负面信号**；`Subtraction` 的退出计数成为正面信号。
- 与 AGENTS 硬规则 6（最简代码）一致：不保留永久重复路径；自举规则正是让"重复路径"（Go 实现 + 构建产物）中的一条**必然**退出。
- 风险：自举规则被用于拖延交付（"用例没做所以不算完成"）。控制手段是 D5 的显式重新评估权，以及 §D3 的检查点只覆盖**新能力**，不延伸到既有能力的补齐。

## 4. 验收

本 ADR 的验收是**跨 ADR 的**，通过对其它 ADR 的 As built 段落检查体现：

1. ADR-0100–0114 每一份的 As built 段落中，每一项新能力都有对应的构建器侧用例（或明确登记为缺口）。
2. `apps/*` 的行业规则在本文生效后**不再净增**（用 `git log` 与 `Subtraction` 的计数证明）。
3. `@platform/ui` 新增组件均满足 ADR-0110 D5 门槛（用门槛检查证明）。
4. 至少一次评审中，负责人明确判定某项交付"有实现无构建器用例 = 未完成"，并记录结果。
