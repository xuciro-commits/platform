# ADR-0024: ERP 应用 —— 财务会计、采购与库存管理、生产订单协同

**状态：** 已采纳 (2026-09-26, #115，ERP 架构关卡以及 [Platform.md](../Platform.md) §10.5 第七阶段的首个验证载体)。业务负责人委托智能代理推进本架构关卡（“u do go next dev step, I will test, u do u”），因此 D1 至 D10 均按推荐方案确立；业务负责人可在具体批次构建前随时调整。实际构建内容见“实际构建（As built）”：7a 至 7d 全部完成构建。

## 背景

当前已具备的能力：
- **工厂车间此前与一个虚拟的外部 ERP 通信：** 计划订单通过轮询外部 ERP 送达（`equipment.go` 中的 `DeliverPlanned`，K8 轮询输入机制）并作为断言保存；车间主管对照计划订单下达车间工单；当最后一个 SFC 完工时，完工确认流程（`erp.go`）向 ERP 端点发出外部效果并等待回执；当 ERP 拒绝时，智能代理自主提出更正提议。在本地测试中，该 ERP 由 `cmd/webhook-sink` 中的桩服务模拟（`POST /erp`）。
- **ERP 所需的绝大多数平台底层能力均已齐备：** 带有明细子行与金额的实体记录（[ADR-0016](0016-application-model.md)）、生命周期与审批链（[ADR-0017](0017-lifecycles-approvals-tasks.md)）、基于记录的聚合分析（[ADR-0019](0019-read-models-analytics-snapshots.md)）、支持自动补偿且能调用协议操作的业务流（[ADR-0020](0020-flows.md)）、跨应用解耦协议（[ADR-0011](0011-apps-interoperate-through-protocols.md)）以及标准化脚手架（[ADR-0023](0023-meaning-languages-api-contract.md) 6d）。
- **单笔决策支持原子化写入多条实体记录：** 决策的规则返回一个闭包函数，统一提交该决策所修改的全部记录，仅在决策被正式接受时一次性生效并持久化为单条日志分录。同一应用内部的多项变更天然同生共死；内核 K4 留存的跨变更记录原子组仅在跨应用事务时才需要。

此前欠缺的核心能力：
- **资金金额、记账过账与会计期间：** 没有任何应用管理会计科目；没有复式记账法引擎；没有机制能够严正拦截发生在已结账期间内的回溯修改。
- **连续无断号单据序列（Number sequences，第七阶段核心能力）：** 记录 ID 此前由客户端随机生成（`newId`），无法按各国会计法硬性要求的无断号、连续自增规则生成会计凭证号。
- **采购管理与库存管理**，以及由 MES 负责执行的**生产制造订单**，均需要平台原生支持。

业界参考平台的做法：

| | SAP S/4HANA | Odoo 19 |
|---|---|---|
| 日记账分录 | 通用日记账表（ACDOCA）：单张行级物理表承载所有过账分录，科目余额动态实时派生 | `account.move` 搭配 `account.move.line`；草稿状态，过账生效；余额由分录行动态汇总 |
| 纠偏与冲销 | 已过账单据绝对禁止直接修改；冲销（Reversal）表现为一张全新的冲正单据 | 已过账分录物理锁定；点击“冲销（Reverse）”自动生成一张反向对冲分录 |
| 单据编号 | 按公司代码、单据凭证类型与会计年度管理号码范围（Number ranges） | 按日记账账簿与年度管理自增序列；仪表盘主动监控并告警断号漏洞（[发票序列号规范](https://www.odoo.com/documentation/19.0/applications/finance/accounting/customer_invoices/sequence.html)） |
| 会计期间 | 按公司代码严格开启与关闭记账期间 | 锁定日期（Lock dates）；硬锁定具有不可逆性（[年结流程规范](https://www.odoo.com/documentation/19.0/applications/finance/accounting/reporting/year_end.html)） |
| 存货与物料 | 物料凭证（Material documents）；按标准成本或移动加权平均法计价 | 库存移动（Stock moves）；按标准成本、移动平均或先进先出（FIFO）管理计价层 |
| MES 制造集成 | ERP 下达生产订单；MES 通过 `API_PROD_ORDER_CONFIRMATION_2_SRV` 或 BAPI 接口回传确认良品数、报废数与组件消耗（[SAP 官方文档：生产订单集成](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/21aead0c98bd4755abdacd91c99e3393/7d61c9ecd5754e8cb0e925639b5d8bb0.html)；云端对应业务范围 IY5） | 在同一数据库中基于 `mrp.production` 及其库存移动紧密协作 |

另参照 ISA-95 / B2MML 国际制造标准：ERP 下发生产排程，MES 向上反馈生产实绩。当前开发环境受限无法直接外网访问 Odoo 原文页面，上表引用的 Odoo 规范来自客观检索结果。

业界核心共识：
- **过账即终局（Posted is final）。** 业务更正必须通过全新凭证冲销；会计期间一经关闭严格封账。
- **每一笔过账都是明细行；** 科目余额纯属由明细行派生计算得出，绝不作为持久化真相存储。
- **编号按账簿序列与年度严格递增**，且严格在单据正式过账生效时核发。
- **ERP 掌控生产订单并接收制造实绩确认**；MES 专注于车间生产执行。

我们的架构约束：系统重放绝不调用外部系统；业务日志保持小巧以确保重放极速；业务规则严格保留在类型化代码中（[ADR-0008](0008-packages-customization-and-callers.md)）；不引入新第三方依赖；`contract/` 绝不混入具体业务词汇；ERP 保持轻量精简（[Platform.md](../Platform.md) §9 风险 3）：其核心价值在于施加资金、过账、编号、期间与生产订单的严密逻辑压迫感，而非追求铺张的功能广度。

## 设计

1. **ERP 作为标准应用存在**（`apps/erp`，Go 代码包 `erp`），由 `cmd/new-app` 脚手架生成，源码层面完全不依赖其它业务应用。像所有应用一样声明其实体类型、生命周期与目录操作；字典自首个提交便全面配备中文。
2. **财务会计：** `erp.account`（会计科目：科目编码、科目名称、科目类别：资产、负债、权益、收入、费用）。`erp.entry`（记账凭证：账簿、凭证日期、参考业务单号、包含借贷方的会计分录行、摘要文本）先以草稿形式创建，随后通过记入日志的**过账（post）**决策正式生效，规则校验严格核对借贷必须完全平衡、涉及的每个科目均真实存在且处于启用状态、凭证日期所归属的会计期间处于开启状态。过账决策占用凭证编号，并在同一决策中为每条分录行写入一条 `erp.posting` 记录；`erp.posting` 绝对禁止任何二次修改。**凭证冲销（Reversal）**自动生成一张借贷方向完全调转的全新凭证，并打上原凭证已冲销的标记。科目余额、科目余额表（试算平衡表）与科目明细账纯属基于 `erp.posting` 的聚合分析结果（[ADR-0019](0019-read-models-analytics-snapshots.md)），绝不作为持久化数据存储。
3. **会计期间：** `erp.period`（按月份划分）包含开启与关闭状态；关账结账属于 ERP 财务主管的特权决策，重新开账同样如此，全程受到完整审计。发生在已关闭期间的记账凭证过账将被严正拒绝。
4. **单据编号序列（Number sequences）作为平台级通用能力：** 应用在其清单中声明自增序列（`platform.Sequence`：序列名称、格式化模板如 `{year}/{n:5}`、是否按年重置计数）。在决策提交应用的执行函数内部，通过 `Caller.Next(r, sequence, date)` 获取下一个递增编号；被业务规则拒绝的决策不会消耗任何编号，确保生成的单据编号绝对连续零断号。计数器状态归属于宿主：通过日志重放精确重建，并由快照机制持久化保护。ERP 使用该能力按账簿为凭证编号；服务台应用紧随其后作为第二个用户为工单编号。
5. **采购与库存管理：** `erp.partner`（合作伙伴：供应商与客户，归属于 ERP 自有）；`erp.product`（物料/产品：计量单位、标准成本、对应过账科目、工厂制造产成品所需的 BOM 组件）；`erp.purchase`（采购订单：明细行、状态：草稿、已下单、已收货、已开票；超额采购通过协作应用由主管审批）；采购入库生成 `erp.move` 记录（产品、出入库库位、数量、出入库原因），并同时自动生成记账凭证（借：库存商品，贷：应付暂估 / 物料采购）；收到供应商发票后对冲暂估（借：应付暂估，贷：应付账款）。实时库存纯属基于出入库移动记录的聚合结果。
6. **生产制造订单**（`erp.production`：产出产品、计划数量、交期截止日；状态：草稿、已下达、已确认、已关闭）。定义标准协议 `production.orders/1`（`protocols/production`），**由 ERP 负责提供实现，由 MES 负责消费订阅**：
   - 读取接口 `orders`：查询处于已下达状态的生产订单，即车间可以对照下达排产的计划订单；
   - 目录操作 `confirm`：上报完工良品数、报废数以及关联的车间工单，由 ERP 裁决：确认接收后，ERP 按标准成本自动扣减投产组件库存并增加产成品入库（生成库存移动并自动过账一张生产制造账簿凭证：结转在制品、产成品入库、报废计入制造费用），生产订单状态更新为已确认；若 ERP 拒绝，工厂端流程即刻捕获拒绝回执；
   - 协议事件 `released`：生产订单下达发布时自动通知车间主管。
   工厂车间的完工确认流程通过该协议发起调用（[ADR-0020](0020-flows.md) 中 `Act.Protocol`），且负责纠正被拒绝确认的智能代理直接查阅该协议下的可用订单。
7. **车间与 ERP 通信收敛为唯一样式：** 在同时挂载了 ERP 应用的租户中，该标准协议彻底替代了此前脆弱的外部轮询与出站效果。对于外部异构 ERP（如真实 SAP），车间原先的连接器与出站效果被剥离收敛为一个独立的轻量适配器应用（Adapter app），由该适配器提供完全相同的协议实现（7d 阶段）；工厂车间自身不再保留任何特定 ERP 的专有代码，桩服务中的模拟逻辑也随之平稳交接。
8. **运行时集成：** 制造宿主（自 7d 阶段起命名为 `plant-server`，对应部署演练中的制造工厂企业）统一挂载 MES 与 ERP；部署演练中通过标准协议走通订单确认并直接查验自动生成的记账凭证。
9. **确定性重放：** 每一笔业务变更均为 ERP 或工厂的独立决策，完整持久化记入日志；单据编号、科目余额与实时库存全部由此重建；`CheckReplay` 覆盖每个构建批次。

## 影响

- 平台正式具备承载企业核心财务资金的能力：单据编号、记账过账、会计期间与冲销机制均在真实业务规则下得到严格验证，绝非浮于表面的演示系统。
- 连续单据序列成为面向所有业务应用的平台级通用基础设施。
- MES 车间彻底摆脱了对具体 ERP 实现细节的耦合依赖：面向抽象协议编程，底层可自由切换原生 ERP 应用或异构系统适配器。
- ERP 应用严格保持克制：仅在平台能力需要其施加架构压力时才做针对性深化。

## 实际构建（As built）

### 7a: 连续单据序列与财务会计核心 (#115)

- **单据编号序列** (`platform/sequence.go`, 宿主 `sequence.go`)：`Manifest.Sequences` 声明 `platform.Sequence{Name, Pattern, Yearly}`（支持 `{n}`, `{n:5}`, `{year}` 占位符；在组合编排时完成静态校验）；在正式接受的决策所执行的应用闭包中，通过 `Caller.Next(r, sequence, date)` 获取下一个流水号，在探查模式下或缺乏变更记录时严正拒绝核发。编号计数器（`<app>/<sequence>/<year>`）归宿主集中管理，在重放中精确重建并通过快照持久化保护。服务台为工单连续编号（`HD-2026-0001`），ERP 按日记账账簿分别编号（`GJ/2026/00001`, `PJ/…`, `MJ/…`）。
- **ERP 财务模块** (`apps/erp`，由 `cmd/new-app` 脚手架生成)：`erp.account`（科目编码即为主键 ID；包含科目类别）；`erp.entry`（包含账簿、凭证日期、业务参考单号、借贷明细分录行；状态：草稿、已过账、已冲销）；`erp.posting`（每条过账分录行对应一条，绝不允许任何编辑修改）；`erp.period`（按月份划分，由财务主管通过 `erp.period.open` 开账，并支持关账与重新开账）。过账作为生命周期的核心状态迁移操作：规则严密校验必须包含两行以上分录、每行必须指向启用的有效科目且只能单侧填写真实金额、币种必须与租户币种严格一致、借贷总额必须完全相等，且凭证日期必须处于开账状态的期间内；随后在同一决策事务中核发单据编号并写入过账明细记录。已过账的凭证既无法编辑也无法归档。冲销操作生成编号为 `<id>-R` 的借贷对调新凭证，冲销日期可采用原凭证日期或另行指定的业务日期。读取端点 `trial-balance` 自动对过账记录按科目聚合汇总求和。角色划分：会计人员（负责凭证处理）与财务主管（兼管会计科目表与期间开闭）。
- **租户基准币种统一管理（演进发现）：** 金额此前除 UI 套件默认的 `EUR` 外无全局配置。新增平台通用配置项 `platform/currency` 作为法定记账本位币以及用户界面的默认输入币种；业务应用通过 `Caller.Setting("platform/currency")` 读取，`/v1/me` 对外暴露该设置，统一工作空间在加载时自动同步 UI 套件的默认币种（`setCurrency`）。
- **UI 套件明细子行能力增强（演进发现）：** 宿主支持自描述明细行字段的列结构（`FieldInfo.Fields`；UI 套件无法识别的未知列结构自动回退为只读）；UI 套件在记录详情页将明细行渲染为标准表格，在表单中以宽屏对话框（`Dialog wide`）编辑明细行；通用列表视图自动隐藏复杂的明细行；自动生成的表单针对实体引用字段及明细行中的引用列，统一提供标准的选择器组件（兑现了 [ADR-0016](0016-application-model.md) 中推迟实现的引用选择器）。
- **排查修复的重要细节：** 修复了 `Tenant.Member` 此前错误使用登录主体而非成员 ID 进行查询的缺陷；修复了模板嵌套层级上限仅为 3 层导致展示 5 个枚举选项时报错的问题，现已扩展为 8 层；操作完成后的操作反馈提示（Toast）统一以阅读者的母语输出。
- **经过全面验证：** `apps/erp` 中的 `TestBooks`（验证被拒绝的过账不消耗编号、借贷不平/单边分录/已关账期间过账被拦截、已过账单据禁止二次编辑、编号绝对连续零断号、凭证平稳冲销、开账关账流转、试算平衡表借贷严格平衡、结合快照的 `CheckReplay` 重放校验）以及 `TestChinese` 中文测试；`TestHelpdeskTriage`（验证服务台工单创建被拒绝时不留下编号空洞，重放严格一致）；`scripts/verify.sh composition` 与 `web` 校验通过。在真实浏览器中通过 ERP 开发宿主完成全中文验证：财务主管起草包含两行分录的凭证，成功过账为人民币凭证 GJ/2026/00001，试算平衡表实时呈现借贷完全平衡。

### 7b: 采购与库存管理体系 (#115)

- **业务声明** (`apps/erp/server/purchasing.go`)：`erp.partner`（合作伙伴：供应商、客户或双重身份）；`erp.product`（物料编码即主键 ID；原料或产成品；计量单位；标准成本）；`erp.purchase`（采购订单：供应商、采购日期、包含物料/数量/单价的明细行；状态：草稿、已下单、已收货、已开票、已取消）；`erp.move`（库存出入库移动记录：按标准成本计价，写入后不可篡改）。采购员角色负责订单下达与收货入库；会计科目表新增 6403 采购价格差异 科目。
- **采购下单** (`order`)：规则校验供应商身份合法性、物料必须存在、数量与单价必须大于零且币种相符，并自动计算采购总额；正式下单时核发专属采购订单编号（`PO/2026/00001`）。根据 ERP 的 `approval-limit` 配置（整单阈值默认为 10,000 单位），超过限额的采购订单自动通过协作应用（[ADR-0017](0017-lifecycles-approvals-tasks.md)）发起审批流，由财务主管审批通过后方可正式生效。
- **收货入库** (`receive`)：要求当前日期所在的会计期间必须开启且存货科目有效；在同一决策事务中，记录商品入库移动，并自动在采购账簿中过账收货凭证：借记库存商品（按标准成本计价），贷记应付暂估（按订单合同价计价），差额计入采购价格差异科目。
- **供应商开票对冲** (`bill`，会计人员或财务主管执行，录入供应商发票号)：自动过账开票凭证，借记应付暂估，贷记应付账款。
- **实时在手库存：** 读取端点 `on-hand` 自动对各产品的库存移动记录及其金额进行汇总求和；库存移动记录本身作为标准实体记录同样支持通用聚合分析。
- **前端交互** (`@pkg/erp`)：采购订单支持在界面上录入明细行并在详情页直观驱动生命周期流转，清晰展示实时库存、出入库移动明细、物料产品及合作伙伴。修复了记录详情页此前在单次决策两次更新记录时重复展示两条相同行的展示缺陷。
- **经过全面验证：** `TestPurchasing`（验证客户不能作为供应商采购、限额内订单直接生效而超额订单须经主管审批、采购员无权做账开票、收货与开票在采购账簿中按序编号、实时库存动态吻合、库存/价差/应付账款科目做账准确且暂估科目完全冲平、`CheckReplay` 确定性重放）与 `TestChinese`。在真实浏览器中以采购员身份验证：录入采购订单，下单（PO/2026/00001），点击收货，实时库存瞬间呈现 200 kg 价值 1,000.00 元。
- **暂未构建：** 部分收货与分批开票、采购退货、付款对账；供应商发票号此前未弹窗录入（F-27，已在 #118 中修复表单弹窗收集）。

### 7c: ERP 与 MES 之间的生产制造订单协同 (#115)

- **标准解耦协议** (`protocols/production`, `production.orders/1`)：暴露 `orders` 读取端点（查询处于已下达和已确认状态的生产订单：订单号、产出物料、计划数量、交期、状态）、`confirm` 完工确认操作（接收车间工单、良品完工数、报废数）以及 `released` 订单下达事件。
- **ERP 作为提供方实现该协议** (`apps/erp/server/production.go`)：`erp.production`（产出物料、计划数量、交期截止日；状态：草稿、已下达、已确认、已取消），当计划员或财务主管执行下达操作时核发生产订单号 `MO/2026/00001`；仅当产成品维护了 BOM 组件清单（`Product.Components`，声明每单位所需的原料配方）时才允许下达。协议操作 `confirm` 严密校验上报数量不得超过计划量、会计期间必须开启且科目存在；确认通过后，在制造账簿中自动生成单笔记账凭证（`MJ/…`），按标准成本自动出库原料组件、入库完工产成品、冲销在制品并将报废损失计入生产制造差异（6404 科目）。一旦采购单、下达单或已过账单据生效，严格禁止任何篡改。协议读取端点支持对任意被授权的消费方开放，宿主严格鉴权。
- **工厂车间消费该协议** (`apps/manufacturing/server/production.go`，可选挂载)：ERP 下达的订单直接映射为车间的计划订单，车间主管可据此下达现场工单（执行严格的物料匹配检查，且车间智能代理能够直接读取它们）；完工的车间工单在车间自身决策的业务规则中（符合内核 K4 C10 规范）通过该协议发起完工确认，ERP 即刻做出接受或拒绝裁决，车间的完工确认流程无缝向下流转，且主管的重新发送同样以该标准协议确认。对于外部异构 ERP 的计划订单，在 7d 阶段前继续保持连接器与外部效果共存。
- **生产制造解决方案** (`solutions/plant`, `cmd/plant-server`)：将平台通用应用、MES 车间与 ERP 有机组合；`plant.Seed` 初始化人民币记账本位币、会计科目表、开启当期会计期间，并预置工厂产成品及其 BOM 配方；开发宿主预置车间主管（兼具 ERP 财务主管角色）、会计、机台操作工以及质检员身份。`scripts/verify.sh composition` 现已自动扫描所有协议与解决方案。
- **演进中的细节完善：** 采购账簿与生产制造账簿此前因首字母相同而共享了 `PJ` 前缀；现已明确规范各自的独立前缀（通用总账 `GJ`、采购账簿 `PJ`、生产账簿 `MJ`）。
- **经过全面验证：** `solutions/plant` 中的 `TestProductionThroughTheProtocol`（草稿单据不作为可用计划订单、超额排产被拦截、通过协议排产工单并成功确认实绩、ERP 订单同步结转良品数/工单号/库存与财务账务、已关账期间遭遇 ERP 拒绝能瞬间触达车间流程，且主管重新开账后重发顺利被接受入账、`CheckReplay` 确定性重放）、`apps/erp` 中的 `TestProduction`，且车间自有的全部历史测试保持百分之百通过。在制造开发宿主上通过 HTTP 完整跑通：ERP 生产订单下达，操作工执行车间工单，宿主自有机制作业通过协议成功确认（MO/2026/00001，良品完工 2 件）；在真实浏览器中查验 ERP 生产订单呈现纯正中文，且变更历史中清晰记录了来自车间的完工确认实绩。

### 7d: 车间面向任意 ERP 的唯一样式架构收敛 (#115)

- **ERP 外部适配器应用** (`apps/erplink`，应用标识 `erplink`，显示名称“ERP 链路”；在 [ADR-0025](0025-one-shape-for-every-app.md) 8b 中正式更名为 `apps/erpadapter`)：面向外部异构 ERP 统一提供 `production.orders/1` 协议服务。`erplink.order` 映射外部 ERP 的计划订单（沿用外部 ERP 的原始 ID），由外部 ERP 服务账号（持有 `erp` 角色）通过轮询连接器（`erplink.Poll`；遵循内核 K8 规范，基于游标严格保证 Exactly-once）逐页推送交付。协议操作 `confirm`（`erplink.order.confirm`，由计划员角色或消费端自动化进程执行）接收尚未发送或确认的订单，校验完工数与报废数不超标，并在同一决策中发出防重键为 `<order>#<n>` 的不可逆外部效果 `erplink/confirmation`；若未配置外部端点则立即标记订单失败。`Answerer` 接收并记录外部 ERP 的最终回执（附带外部单号确认、附带拒绝原因驳回、或执行失败）；对于已经重新发送的订单，迟到的陈旧回执不产生任何干扰。其读取端点直观展示每笔订单所处阶段。`@pkg/erplink` 提供前端订单列表。
- **生产制造协议状态语义完备化：** `Order` 扩充了 `ShopOrder`、`Confirmation` 与 `Detail` 字段，并在已下达与已确认之外增加了 sent（已发送）、refused（已拒绝）与 failed（失败）中间状态；提供 `Order.Answered(shopOrder)` 状态判定。原生 ERP 应用对外返回确认凭证的记账凭证号（`MJ/…`），而非仅返回订单自身编号。
- **车间面向 ERP 的唯一实现路径** (`apps/manufacturing/server/production.go`，现已规范为 `apps/mes/server/erp.go`；自 ADR-0026 起调整为决策后发起请求，不再内嵌于规则执行体内)：完工的生产工单统一在车间决策规则中通过协议发起确认，未关联计划订单的独立工单由车间直接拒绝。若提供方支持同步确认（如原生 ERP 应用），回执当场持久化入库；否则订单标记为已发送，确认流程异步等待提供方状态更新，随后通过车间操作 `mes.order.answer` 将结果正式入账（F-28）。该业务流仅在租户挂载了提供方应用时激活。彻底删除淘汰的历史孤岛代码：车间私有的轮询输入、计划订单断言及其在下达时的存证逻辑、`erp-confirmation` 外部效果及其回执处理、`erp` 角色与连接器、`cmd/mes-server` 及其 Dockerfile、`cmd/gateway-sim` 中的 ERP 轮询逻辑，以及本地桩服务中的 `POST /erp` 接口。
- **部署与演练全面升级：** `solutions/plant` 支持灵活挂载底层账套（`NewTenant(id, erp.New(id) | erplink.New(id), seats…)`）并接入网关；传入 `plant-server -erp external` 即可一键启动适配器模式。`Deployment.Seed` 统一为全新租户初始化空白环境下的预置数据，在内存与 PostgreSQL 中保持一致，使 Docker 中的制造宿主开箱即具备科目表、开启的月份与产成品物料（`erp-server` 同样复用该逻辑）。Docker Compose 与本地演练脚本全面切换为运行 `plant-server`（对应 `solutions/plant/Dockerfile`、`deploy/local/plant/directory.json`，其中 `sup-1` 兼任 ERP 财务主管）；彻底废除 Rauthy 中的 `mes-erp` 客户端。
- **排查修复的重要细节：** 发现 7c 曾导致 MES 独立镜像构建失败（Dockerfile 中缺失 `protocols/production`），此前因演练脚本隐藏了 `compose up` 输出而未暴露；演练脚本现已默认打印构建日志。排查发现智能代理直接向 ERP 应用提交完工确认时，若代理未在 ERP 中持有角色会被严厉拒绝，且该操作并未像外部效果一样自动挂起等待人工裁决（F-29）。
- **经过全面验证：** `apps/erplink` 中的 `TestConfirmedToTheERP`（分页 Exactly-once 幂等、角色权限校验、无端点拦截、正常确认/拒绝驳回/全新键重发、后续分页仅修改需求量的幂等校验、无需调用真实 ERP 的确定性重放）、`solutions/plant` 中的 `TestConfirmedToAnERPOutside` 与 `TestCorrectedByTheAgent`（车间原有的 ERP 集成测试，现全部基于适配器与 HTTP 模拟外部 ERP 运行：完工确认、拒绝驳回通知主管、基于匹配计划订单的代理纠偏、无计划订单工单被车间拦截、助手完工确认强制挂起直至人工审批、收件箱中一键批准代理提议、确定性重放）、结合记账凭证号的 `TestProductionThroughTheProtocol`，以及包含 Swift 与 Docker 在内全链路测试在业务负责人 Mac 本地通过 `scripts/verify.sh` 全面绿灯。基于 `plant-server` 运行本地部署演练：ERP 下达 3 笔订单，车间通过协议成功确认 WO-2 且 ERP 自动过账，助手重发被 ERP 拒绝而主管重发被顺利接受，智能代理纠偏提议成功确认，服务重启、快照截取与数据恢复一如既往稳健。Playwright 路由 16 通过 HTTP 对照桩服务顺利完成走查。
- **暂未构建：** 部分确认与按物料组件精细消耗；对接真实 SAP 系统的官方报文绑定（当前效果报文采用平台通用规范，而非直接采用 `API_PROD_ORDER_CONFIRMATION_2_SRV` 报文结构）；ERP 应用拒绝完工确认时返回的原因此前仍仅为机器错误码（F-23）。
