# ADR-0040: One semantic model for relationships, actions and application composition

**Status:** Accepted (2026-09-28, #138). The owner authorized direct execution or an adversarial self-review followed by execution; D1–D4 are accepted with the implementation limits below. ADR-0031's platform direction and ADR-0037's bounded single-record actions remain accepted; this decision extends them.

## Context

The upper design already names object **and link** types, action/function, page/component, flow/agent, AI function, integration/query and application/package assets (Platform.md §10.3). The current Builder navigation instead exposes Objects, Process and access, Pages, and Applications (`web/packages/build/src/index.tsx`). That is a first vertical slice, not a complete ontology or application studio.

Current code evidence (2026-09-28):

| Area | What runs now | Gap for a builder |
|---|---|---|
| Objects and relationships | `build.Object` has typed fields including one `reference`; `relations.Link` can connect any two records and `Caller.Links` reads visible neighbors | No named link-type asset, inverse names, cardinality/ownership rule, typed traversal, dependency impact or link editor. A generic link has no declared business meaning |
| Actions and rules | `build.Action` compiles input, condition, same-record field changes, lifecycle transition and optional approval into the canonical ledger/work path | No link or other-record edit, typed result contract, reusable deterministic function or query. `checkProcess` checks referenced names but not comparison operand types; `holds` falls back to text order when numbers do not parse |
| Pages and interaction | Ten widgets bind to records/actions; selected record and per-object filter are shared inside `ComposedPage`; host checks sections at publish | The shared state is hard-coded, not a typed variable/event graph. No relationship traversal, conditional visibility, reusable component contract, module inputs/outputs or dependency view in the editor |
| Product/release | Three-pane editors, saved draft and publish, generated pages | Object fields and application settings still use generated record editing. Process inspector stacks every rule in one long pane. Invalid process rules are mostly refused at publication. Republish replaces the installed descriptor; no immutable candidate/release or stateful isolated preview (#135/#136) |

An important distinction: `PagePreview` for a simple `list-detail` page fabricates sample rows. The composed-page editor renders the normal `ComposedPage` with `useHost().source`, so it reads the builder's authorized **live** records while disabling writes. Neither path is an isolated stateful simulation. The 2026-09-28 browser screenshots in `web/e2e/test-results` show behavior and layout, not owner acceptance of visual quality or an isolated test environment.

The shared principle is a **typed semantic graph** consumed by multiple authoring and operating surfaces. It does not require copying Foundry or putting all platform concepts into one editor menu.

## Our constraints

- The app API owns public asset contracts and typed code extensions; the host validates, authorizes and executes; `build` owns tenant drafts/editing; `relations` owns record-link storage and traversal; `@platform/app` owns UI binding, `@platform/ui` owns components. No parallel record/action/link executor or app-private expression interpreter.
- No domain vocabulary enters `contract/`. Business meaning lives in named, versioned assets. Cross-app mutations respect actions and protocols; one builder action cannot directly write another app's private state.
- Code, visual and AI authoring converge on the same asset identity, permissions and release checks. No arbitrary tenant code. Preview never calls live effects or writes production. Replay calls nothing outside; accepted-result recovery and immutable revisions are separate #135/#136 gates.
- Editor quality requires an observed builder task and operator task, with realistic records, Chinese, keyboard and narrow-screen states. A browser test or generated screen alone is not visual acceptance.

## Design

1. **Semantic graph and ownership.** Add a `LinkType` asset to the app API/registry with stable qualified identity, version, source and target object types, names for each traversal direction, cardinality, requiredness, authority and deletion/evolution rules. `reference` fields and generic record links are inputs to or implementations of this contract where appropriate, not substitutes for it. `relations` stores/queries instances through the host's canonical authorization. The builder shows the graph, its dependencies and what a change would break. A simple first slice supports one-to-many backed by a reference; later many-to-many or attributed links require an explicit storage/action contract. Document exactly which constraints are enforced at commit time.
2. **Action semantics.** Keep ADR-0037's one-record transition as a supported small case. Give every action a typed input/result and effect summary, server-validated rule operands, explicit authority and failure messages. A later same-authority multi-record/link action uses #135's atomic accepted-result boundary; cross-app work uses declared protocols and flows. A reusable pure function/query is a separately named asset, callable by actions, pages, AI logic and code through typed inputs and authorized outputs. Do not simulate cross-object atomicity by chaining tenant-side form writes.
3. **Page composition as bindings.** Extend `platform.Page`/registered component contracts with typed page variables (selection, filter, route input and bounded derived query), widget input/output bindings and declared events (set variable, navigate, submit a named action). Link traversal binds related lists/details and master/detail tasks. Reuse the same bindings for code pages, visual tools and AI proposals; reject type/authority/dependency errors at their source. Avoid copying Workshop's entire variable system or Appsmith's JavaScript expressions.
4. **One product with two authoring spaces.** Use an umbrella name such as **Application Studio** (Chinese: 应用设计台) for the builder journey, with **Business model** (objects, relationships, actions/rules, authority, data source) and **Experience** (applications, pages, components, bindings) as its main workspaces; **Test and release** exposes validation, candidate diff, dependencies, isolated preview and activation. “States and actions” belongs inside an object's behavior view; access has a clear ownership/scope view. Names and navigation are product copy, not a new runtime contract. Progressive inspectors show the common action path first (when, who, result), then inputs, rules, approval and advanced effects; show a compact before/after/example and inline errors.
5. **Preview, publication and evolution.** Label the current composed canvas honestly as an authorized live-data, read-only editing view. A separate fixture-backed preview/simulation uses an isolated candidate and can show the result of a proposed action without production writes/effects. #136 owns immutable revisions, dependency closure and activation; this ADR's link/function/page contracts must participate. Rename, delete, cardinality and authority changes report impacted pages, actions, AI tools and running work before activation.
6. **Proof of use.** A minimal hospitality and manufacturing probe each define or reuse an object, relate it to another object, use that relationship in a page and a governed action, and complete an operator task. The same assets are discoverable in code/API and available to AI only through declared permissions. Measure authoring completion/errors and operator task completion with the owner; application-specific feature depth waits.
7. **A typed graph surface, not a graph executor.** `@platform/ui` owns a React Flow based canvas and a controlled node catalog: each node kind declares its category, semantic asset reference and version when available, named input/output ports, port types and connection capacity. The semantic owner supplies an adapter from its canonical definition to canvas nodes/edges and applies validated edits back to that definition. Canvas positions, selection and zoom are presentation metadata; they cannot confer execution or access. The catalog grows by platform capability: object/link topology, lifecycle/action, flow, AI function/agent and later bounded media or physical-world models can each have their own adapters, validation and controls. A structural object graph can cycle; a lifecycle can revisit states; a deterministic dataflow needs an explicit cycle/delay rule. A common renderer must not impose one graph's execution semantics on another. FDEs get a node list, typed connection feedback, inspectable configuration, dependency impact, keyboard alternatives and versioned changes; customer editing is limited to granted node kinds. The existing read-only `Graph` stays the operating view. [React Flow's custom nodes and handles](https://reactflow.dev/learn/customization/handles) and [connection validation](https://reactflow.dev/examples/interaction/validation) provide the interaction substrate; our catalog and host contracts supply meaning.

## Decision points for the owner

| # | Question | Options | Recommendation |
|---|---|---|---|
| D1 | Is a named relationship a first-class, versioned semantic asset? | `LinkType` with bidirectional names, cardinality and authority; or continue with `Field.Ref` plus generic `platform.link` | First-class. The current pair cannot express or validate the business relationship the UI and AI must share. Start with a reference-backed one-to-many slice and honest enforcement semantics. |
| D2 | How far may one tenant-authored action change state? | Keep only same-record transitions; or add same-authority object/link edits after #135 while cross-app work remains protocol/flow based | Add bounded same-authority edits after the atomic commit boundary. Preserve the simple transition editor for common cases and refuse unsupported cross-app atomic claims. |
| D3 | How do page widgets coordinate beyond selection/filter? | Typed variables and declared events in the shared page contract; or accumulate more hard-coded widget couplings | Typed variables/events, introduced by one relation-backed master/detail journey. This is the smallest shared contract that can grow without a new special case per widget. |
| D4 | How do FDEs edit graphs with different meanings without fragmenting platform semantics? | A reusable typed node catalog and React Flow canvas with per-capability adapters; or separate app-owned graph editors | One UI-kit canvas and catalog contract. Semantic assets and host validation remain authoritative; adapters own each graph's legal edits, persistence and cycle rules. The first lifecycle adapter edits existing `Action.From/To`, then relation, flow and AI adapters follow their platform owners. |

Declined: a Foundry-shaped database, all domain logic as workflows, arbitrary tenant JavaScript, a second builder-only runtime, and claiming the present live-data canvas is an isolated preview. Existing ADR-0038/0039 owner decisions remain separate and are prerequisites where noted.

**Adversarial review before implementation (2026-09-28).** D1's first relationship slice is reference-backed and may initially be read-only: a display declaration must not imply that generic `platform.link` records or a reference field already enforce a named link's cardinality, deletion or authorization rules. Those rules are reported as guarantees only when the canonical write path checks them. D2 cannot be implemented by calling two existing actions in sequence: without #135's atomic result boundary, partial state is possible; cross-app work remains protocol/flow work. D3's page variable graph must use caller-scoped reads and action declarations at every edge; merely hiding a widget is not an access rule. D4 rejects an untyped node graph as a new business interpreter: rendered nodes resolve to governed assets or a typed draft, and no drag/connect gesture bypasses the existing action, flow or AI execution path. These limits narrow the first slices without reversing D1–D4.

## Consequences

The public model grows beyond four asset kinds, so compatibility and dependency checks become stricter. A named relation and typed page variables improve reuse but require deliberate migration for existing reference fields and generic links. Existing data and ADR-0037 behavior stay valid until an explicit supported evolution path; no automatic reinterpretation of published customer data or in-flight work is implied. The Builder may be reorganized incrementally, but completion is judged by the whole construction and operator journey rather than the number of navigation entries.

## As built (2026-09-28, #138 21a first slice)

The host rejects an action input assigned to an incompatible field, checks choice-input values against the destination field, rejects currency-blind money comparisons, and checks condition operands and ordered operators by declared type before publication. Runtime comparisons use that type and do not fall back to text order for malformed values; date values normalize from stored timestamps to their calendar day. The Application Studio (`build` app ID) opens an object in one editor for fields, lifecycle and authority; its action inspector keeps the common path visible and folds approval and input/rule details. Early editor hints expose common rule mistakes while the host remains authoritative. The UI kit's `NodeCanvas` and `NodeCatalog` validate named ports, matching types, duplicate edges and connection limits. The first adapter maps state/action nodes and connections to the existing action `From/To` declarations; deleting connections edits those declarations. Its node positions are local view state and are not a published semantic asset. The existing read-only `Graph` and lifecycle executor remain unchanged. **Open correctness debt:** an omitted optional scalar field is materialized as its Go zero value, so an absent optional number and an explicit zero are indistinguishable to a condition. 21a remains open for a presence-aware field contract and editor feedback. This slice does not implement named relationship assets, typed page variables, immutable versions or general flow/AI graph authoring; those remain 21b–21d and #133/#135/#136.
