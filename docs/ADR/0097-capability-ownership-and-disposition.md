# ADR-0097 能力归属与处置：状态口径、权威术语与检查的诚实失败

状态：已接受并实施（2026-10-10）。这是 SRS/SOW 阶段 A 的归属与处置决定；现状摘要归 [Platform §2.4.1/§2.5](../Platform.md)，顺序归 [WorkQueue](../WorkQueue.md)，各能力的实现边界仍归原 ADR 的 As built。

## 1. 范围与证据

对全平台现行能力做增量核对（SRS/SOW §2 基线上），回答 AR-01–AR-04 的问题：每项能力给谁用、由谁维护、依据什么定义、支持到哪里、怎样验收和退出。本次实跑的证据（仓库 `8733ed8`，2026-10-10）：

| 检查 | 结果 |
|---|---|
| `capabilities/server`：`go build ./...`、`go vet ./...` | 通过 |
| `capabilities/server`：`go test -count=1 ./...` | 当时根包 `TestTenantDefinedActions` 失败；本次按 §6 修正后全绿 |
| `scripts/escapes.sh` | 通过：7 项已知例外、6 个文件，无新增 |
| `scripts/boundaries.sh` | 在本机沙箱无法分析应用模块（离线、模块缓存为空）；修正前静默退出，§5 改为显式失败 |
| Web | 依赖冻结安装通过（pnpm v12.5.1）；未在浏览器观察 |

## 2. 决定：状态口径与处置只有一个维护位置

能力状态（存在 / 有界实现 / 可交付 / 已接受 / 补全中 / 按条件保留 / 取消）与处置（保留 / 整合 / 下沉 / 独立 / 退役 / 补全）定义在 [Platform §2.4.1](../Platform.md)。§2.4 全部条目的默认处置是保留；例外表列在 §2.4.1，并各自给出依据与终点。WorkQueue 只维护顺序与停止条件，不再承担状态表达；ADR 状态行只声明决策状态与 As built 边界。

理由：同一能力的状态此前需要同时读 Platform、WorkQueue 与多份 ADR（SRS/SOW F1），三处口径会互相漂移。本次核对后，未在 §2.4.1 例外表中列出的能力一律按"保留、有界实现"处理，供应商不得以"需要重构"为名重复建设。

## 3. 决定：身份与业务概念的权威归属

账号/成员、人员、岗位、组织、地点、模型元素与业务记录各自只有一个权威来源，关系表归 [Platform §2.5](../Platform.md)。要点：

- 账号/成员是宿主身份与权限（`Console.Member`、`/v1/host/me`）；人员是 `core.person` 业务主数据；`core.person.member` 是二者唯一的连接点。
- 岗位与组织在企业模型 `enterprise` 中是 UAF 定型的模型元素；成员可见范围的"结构单元"仍是宿主结构（`Caller.Units`）。角色/席位是权限，不是岗位。
- 业务记录由各应用账本裁决，可引用主数据与模型元素，但不得直接写另一应用的记录。

不得因为名称相近合并这些概念，也不得在行业应用里复制组织、人员、地点或主数据表（SRS/SOW F5、AR-02、AR-09）。

## 5. 决定：检查在无法分析时显式失败

`scripts/boundaries.sh` 原先用 `deps=$(cd "$dir" && go list -deps ./...)`：`go list` 失败时依赖集合为空，脚本在 `set -e` 下静默退出（sandbox 实测：退出码 1，无任何输出）。这既掩盖环境问题，也可能在部分成功时读到不完整的依赖集合。修正：

- 新增 `list()` 帮助函数：`go list` 失败即报出模块与原因，不再静默；
- 读源码的列举不继承调用者的 `-mod=vendor`（`apps/*/server` 没有 vendor 目录，导出该标志会让每个应用因非边界原因失败）；
- 模块 glob 为空时显式失败，避免空集合让全部规则空过。

检查方法的归属仍是 Testing；这不是第二套检查体系。

## 6. 决定：测试与 ADR-0096 D5 的口径一致

根包测试 `TestTenantDefinedActions` 断言必填输入缺失时拒绝文本包含应用作者写的句子（"needs Handed to"），而 ADR-0096 D5 的统一输入路径返回表单级句子"Correct the highlighted fields."并把字段作为类型化诊断（`code`/`path`/`message`）随答复返回。二者矛盾，测试在交付时是红的。

决定：以 ADR-0096 D5 的契约口径为准——表单级句子说明"要修什么"，字段由诊断定位，表单在字段标签（作者写的标题）旁显示诊断消息。测试改为断言该诊断钉在声明的输入上（`code=required`、`path=["to"]`），并保留原有"作者写的条件消息"断言。这不是放宽检查：它把检查从句子匹配改成契约匹配，正是 AR-13 要求的同源错误口径。

## 7. 变更影响复核（AR-04 / F4）

用三类典型变更核对职责与依赖，结论是：现有枢纽是**受控的协调点**，没有需要机械拆分的证据；保留但它们的能力必须在本次场景中闭合（§8）。

| 变更 | 触及面（实测） | 结论 |
|---|---|---|
| 新增一项业务能力 | 应用 API（`platform/app.go` 422 行）声明 + 宿主路由（`routes_*.go` 合计 1059 行）+ 平台应用实现；`capabilities/server` 内 285 个 Go 文件导入应用 API（含测试），业务应用不导入宿主运行时（`boundaries.sh` 规则 2/4） | 依赖方向单向，新增能力不改内核、不改行业应用 |
| 修改共享交互（如统一输入，ADR-0096） | `platform/input.go`（252 行）与 `platform/app.go` 的诊断类型 + 宿主 `host.go`/`staged_decision.go`/`server.go` 的答复封套 + `@platform/ui`/`@platform/app`/`@pkg/build` 的消费点 | 面广但各层职责清楚：语义在应用 API，封套在宿主，表现在 UI Kit；无第二份输入实现 |
| 替换外部系统 | 走集成织物（Connection/Source/Dataset/Pipeline/Writeback）的**声明**，不改平台应用代码；历史 `erpadapter` 退役即此模式的证据 | 外部差异留在声明与部署，不进入执行器 |

`internal/host` 被 19 个文件导入（宿主与平台应用），`definitions.go`（1005 行）与 `apps/build/build.go`（1299 行）是最大的两个枢纽。它们承担定义安装/恢复与构建资源管理，属于 SRS/SOW 认可的合理协调；本次不为拆分而拆分，其缺口按 §8 的能力补全处理。

## 8. 保留、补全与退出的结论

- **保留（凭证据）**：§2.4 中未列入例外表的能力，含内核契约、宿主运行时、应用 API、协议、记录/动作/审批/查询/候选、共享 UI 与 Catalog、包与环境生命周期、AI 治理机制、企业模型与共享主数据、行业验证应用。
- **补全（本项目，终点明确）**：持续 Flow 窗口到默认图算子与制品生命周期（S-03）；集成依赖的完整应用交付与结果核对（S-01、S-02）；真实 AI 任务的质量、权限与人工接管（S-04）；共享输入与扩展的实际走查（S-05）；应用交付的版本、授权、失败处置与资源生命周期（AR-10、AR-14、AR-15）。
- **按条件保留 / 取消**：见 WorkQueue 表的处置列；不把"尚未实现"累计为统一欠账（SRS/SOW F8）。
- **不做**：机械拆文件、统一全部模型、第二执行器、通用插件市场、运行时热插拔（§5.3）。

## 9. 代价与边界

- 状态口径集中到 Platform §2.4.1 后，忘记登记新能力会立刻成为文档缺口；这比三处漂移更可见，但要求每次能力变更同时改一行。
- 逃逸检查仍是启发式 grep：MES/PMS 的事实日志与四个 UI 表格保留，意味着这些行必须随能力变化同步复核，否则会成为绕过检查的通道。
- 变更影响表来自当前树的结构与导入关系，不含历史提交计数；它证明依赖方向与触及层，不证明每个未来变更的成本。
- 沙箱无法分析 `apps/*/server`：本次边界结论在可解析应用模块的环境（本地/CI）仍需跑一次 `scripts/verify.sh composition-static` 确认。
