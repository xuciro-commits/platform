# ADR-0117 — 拒绝、异常与纠正：失败是业务的一部分

状态：已接受（2026-10-12，负责人指令，ADR-0098 A 块第四份，补齐后端第 2 项"异常处理"与前端第 3 项"异常、返工"的表达）· 扩展 ADR-0037 的条件失败语义、ADR-0096 的输入拒绝路径与 ADR-0017 的审批/任务恢复 · 与 ADR-0100（原子性）、0102（约束）、0112（跨系统补偿）配套

## 0. 意图

ADR-0098 §1 把"异常与质量"（暂停、返工、报废、检验、处置）列为 MES 基准的一个范围，并明确要求：**"如果无法配置返工，就研究状态与业务决定能力"**。

今天"失败"只有一种形态：操作被拒绝，返回一个错误码，事务消失。这是正确的**原子性**语义（ADR-0100 §D3），但它把三类完全不同的失败混成了一件：

| 失败 | 例子 | 今天的处理 |
|---|---|---|
| **策略拒绝** | 你没有权限、字段不可写 | 返回 `POLICY_DENIED`，界面禁用控件（ADR-0109 D4） |
| **约束拒绝** | 数量为负、编号重复、已下达不可改 | 返回约束错误（ADR-0102 D6） |
| **业务拒绝** | 设备不支持该工序、批次已报废、物料被冻结 | 无区分；与上面两类一样只是"失败" |
| **技术失败** | 外部系统超时、集成错误 | 进入效果重试/`unknown`（ADR-0112） |

**业务拒绝不是错误，是业务的正常结果。** "这台设备不能加工这道工序"不是系统故障，是业务事实；它需要被**记录、呈现、驱动后续动作**（改派、返工、降级、让步接收），而不是只变成一个红色提示。

**判据**：构建者能声明"这个操作在什么条件下被拒，被拒之后业务上发生什么"；被拒的事实留下痕迹；纠正后能重试且不产生重复。

## 1. 决定

### D1 业务拒绝是一等结果

业务事务的每一步可以声明**拒绝出口**（`Refusals`）：

```go
type Refusal struct {
    When    *Expr    // 不成立即继续；成立即按 Level 处理
    Level   string   // block（阻止事务）| flag（继续但记录）| route（转到另一条路径）
    Code    string   // 稳定码：供界面区分与统计
    Message string   // 给人读的原因（英文 + zh-CN）
    Route   *TxnRef  // Level=route 时：改走哪个事务/动作
    Record  *TxnStep // Level 时：要留下什么记录（如不合格品记录）
}
```

- `block`：整个事务拒绝（今天的语义），但与约束拒绝**区分码**；
- `flag`：事务继续，但在记录上留下可见标记（让步接收、超差放行）。**这是今天完全没有的能力**，而它正是制造业真实运作的一部分；
- `route`：改走另一条业务路径（返工、降级、改用替代工艺）。**这就是"返工"的一般形态**——返工不是特例代码，是"被拒之后走另一条事务"。

### D2 三类失败的处理位置不同

| 层 | 谁处理 | 在哪声明 |
|---|---|---|
| 策略拒绝 | 平台（ADR-0105 的单一决定点） | 不可声明；它是门禁 |
| 约束拒绝 | 平台（ADR-0102 的约束） | 对象类型上（模型的一部分） |
| **业务拒绝** | **构建者的业务逻辑** | 事务/动作上（本 ADR） |
| 技术失败 | 平台（ADR-0112 的效果/作业机制） | Confirmation / 效果声明上 |

**不允许**把业务拒绝实现成约束拒绝（用约束表达"设备不支持就比较复杂了"会把业务规则塞进模型层）；也**不允许**把它实现成策略拒绝（那就成了权限问题）。

### D3 纠正与重试的语义

一次被拒的操作，人改了输入再来一次——这必须是明确的：

- **输入被修改后重试：新的幂等键**（这是新的意图，不是重试）。历史里两次都能看到，且能看到第二次基于第一次的哪些修改。
- **输入未变的重试：同键返回原答复**（K4 幂等性），不产生第二次拒绝也不产生第二次变更。
- **拒绝不消耗资源**：不占编号（沿 ADR-0076 编号的既有语义"拒绝不占号"）、不产生外部效果意图、不留下部分状态。
- 界面上的"重试"必须区分"原样重试"与"改了再试"，并在改了再试时保留原值作为参考（今天 `DraftSession`/history 已有草稿与历史，`ADR-0096 §9`）。

### D4 异常的可见与升级

- **拒绝必须可见且可查**：按应用、按类型、按码统计（这是 ADR-0107 §D3 运行面的一块：拒绝率与主要拒绝码）。
- **重复拒绝触发升级**：同一记录/同一操作反复被拒可以声明升级（通知角色、创建任务，走 work 的既有机制）。
- **拒绝不是丢弃输入**：被拒的输入保留在草稿与拒绝答复里（沿 ADR-0097 §3.4 的"拒绝不留下可见变更或效果；同键同内容返回持久的原答案"）。
- **暂停（hold）**：业务对象可以进入一个"暂停"状态（等待裁决、等待物料、等待检验结果），由生命周期表达（已有的状态机），并**到时间触发升级**（沿 ADR-0060 的定时自动化）。

### D5 纠正路径本身要有历史

- 让步接收（`flag`）必须在记录上留下：谁批的、依据什么、什么时候、原值是什么。这不是"悄悄通过"。
- 返工（`route`）创建的返工记录与原始记录之间**有声明的关系**（ADR-0104 的集合），因此"这个批次返工过几次、每次因为什么"可查。
- 报废与让步在同一个对象上有不同的后续语义（报废进报废台账、让步入正常流程但带标记），由**事务的目标状态**表达，不新增执行器。

### D6 与 AI、人工的接口

- AI 的提议被驳回：进入本 ADR 的拒绝路径（重新提议、升级人工、或按 `route` 改走别的路径）。**驳回不是错误**，是提议生命周期的一个状态（ADR-0116 §D3）。
- 人工裁决（审批、接管、让步接收）走 work 的既有机制（ADR-0017/0116 §D4），本 ADR 只要求它们在**业务对象上留下可见结果**，而不是只留在任务收件箱里。

## 2. 不做

- **不做补偿式回滚**（ADR-0026 D1(c) 已否决；ADR-0100 §3 重申）。业务拒绝不留痕迹，不需要补偿。
- **不做重试策略的通用编排**：重试是效果/作业的既有机制（ADR-0014/0027），本 ADR 不管传输层重试。
- **不做异常工作流引擎**：`route` 就是指向另一个事务，不必引入状态机描述语言。
- **不做"自动纠错"**：平台不猜业务上该怎么办。

## 3. 后果

- 事务定义多了 `Refusals`；ADR-0100 的 `BusinessTxn` 相应扩展（`Guard` 是"不成立即整体拒绝"，`Refusals` 是"分级处理与改路"，两者语义不同，不能合并）。
- 界面上需要区分四类失败并给出对应动作（重试、改了再试、改派、升级、让步），归 ADR-0109 的权限与错误呈现。
- 让步接收与返工的历史要求让"记录上的标记"成为审计对象，需要在运行面可见。
- 这一条直接支撑 ADR-0113 的"异常与质量"范围：暂停、返工、报废、检验、质量处置**全部落在本 ADR 的表达里**，不写 MES 专用代码。

## 4. 验收

1. 三个级别各一例：
   - `block`：设备不支持 → 事务整体拒绝，不占编号、无记录、无效果；
   - `flag`：超差但让步接收 → 事务完成，记录上有标记（谁批、依据、时间）；
   - `route`：返工 → 走另一条事务创建返工记录，与原记录有关系可查。
2. 区分码：策略拒绝、约束拒绝、业务拒绝分别返回可区分的码与原因，界面据此给出不同动作。
3. 纠正：改了输入重试产生新意图（新键），历史可看到两次的关系；原样重试返回原答复，不重复。
4. 暂停与升级：对象进入暂停状态并到期后升级（通知或任务），裁决结果回到业务对象上可见。
5. 统计：运行面能看到该应用的拒绝数与主要拒绝码分布。
6. AI 驳回：提议被驳回进入拒绝路径，提议生命周期状态正确，不产生业务记录变更。
7. 反例：用约束表达业务拒绝、用策略拒绝表达业务规则、`flag` 却不留痕、`route` 未声明目标事务 → 发布期或运行期明确拒绝。
