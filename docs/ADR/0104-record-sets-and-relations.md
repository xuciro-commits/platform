# ADR-0104 — 记录集与关联：集合是一等公民

状态：已接受（2026-10-12，负责人指令，ADR-0098 B 块第二份）· 修订 ADR-0040 的关联模型与 relations 应用的归属边界、ADR-0058 的 Interface 查询口径 · 与 ADR-0101（量词/聚合）、ADR-0102（基数）配套

## 0. 意图

客户要配"这批货里有没有不合格品"、"这道工序要求的设备能力，这台设备都具备吗"、"这张工单下所有工序是否都已完成"——**这些都在问一个集合**。

今天平台只能问一条记录：条件读取走单条记录的反射字段与单跳引用（`apps/build/actions.go:432-453`），关系取值只接受 `len(path)==1`（`platform/page_compute_resource.go:28`），流程里的记录路径只沿声明的单记录引用（`record_path.go:7-26`，运行时 `flow_reads.go:177-182`）。**没有"一组记录"的概念**，所以集合类判断只能落到行业 Go 代码里（`apps/mes` 的 `canDo`、`reworkable` 全是 Go 函数）。

同时，关系本身今天**不在记录的提交边界里**：`RelationLink` 是 relations 应用自己的状态（`platform/relations.go:38-43`），写入即该应用的一次独立决策（`apps/relations/relations.go:315-320`），持久化形态是 owner state 而非 rows（`accepted_relations_test.go:44-47`）。于是"建一条记录并同时建它和另一记录的关系"**不是原子的**，而基数约束（`platform/link_type.go:16-45`）也就没有和记录写入同一事务。

**判据**：构建者能声明一个集合（沿某关系的下游、或查询结果），对它求量词与聚合，用结果驱动条件、约束、界面与事务；关系写入与记录写入在同一个接受结果里全有或全无。

## 1. 决定

### D1 集合由"声明的关系 + 可选的过滤"定义，不由查询语言定义

```go
type RecordSet struct {
    From   string   // 关系名 / 查询名 / 反向引用（inverse）
    Path   []string // 可选的过滤路径（沿声明引用）
    Where  []Expr   // ADR-0101 表达式；对集合元素的字段求值
    Order  []Sort   // 稳定排序：量词与聚合的重放确定性来源
    Limit  int      // 有界；默认由实现期定，超界拒绝而不是截断
}
```

- `From` 可以是：**声明的 LinkType**（正向或 `inverse`）、**命名查询**（`platform.NamedQuery`，已有，`/v1/queries/{app}/{name}`）、或对象类型上的**父/子引用字段**（`Ref[T]` / 反向）。
- **不做新的查询语言。** 集合的构造复用三层已有机制：LinkType（ADR-0058 的关系）、NamedQuery、引用字段。`Where`/`Order` 用 ADR-0101 的表达式。
- **`Limit` 必须显式且有界**：集合语义在无界时无法给重放确定性，也无法给性能承诺。超界=拒绝并说明，不静默截断。

### D2 集合上的四类操作

| 操作 | 用途 | 实现归属 |
|---|---|---|
| 量词 `any`/`all`/`none` | 条件、约束（"所有工序都已完成"）、界面可见性 | 求值器（ADR-0101） |
| 聚合 `count`/`sum`/`min`/`max` | 计算字段（"批次总数量"）、约束（"合计等于头"）、KPI | 求值器；**已有聚合读取**（`/v1/aggregates`，ADR-0019）复用其实现 |
| 迭代 | 事务里对集合每个元素执行一步（拆批、派工、逐行过账） | ADR-0100 的事务步骤 `ForEach` |
| 呈现 | 表格、看板、甘特、时间线 | 已存在（75 个 widget），归 ADR-0109 |

**迭代必须是确定性的**：集合的排序是事务结果的一部分，因此 `Order` 是必填的（缺省用稳定键：类型 + ID）。测试要能证明"同一事务在同一集合上重放产生同一结果"。

### D2.5 量纲上限（起点值，按真实需要调整）

**没有上限就没有重放确定性，也没有容量承诺。** 以下是**起点值**，落在代码常量里并在发布期检查；调整须有实测依据，不在实现期临时放宽：

| 量 | 上限 | 超出的行为 | 依据 |
|---|---|---|---|
| 集合 `Limit`（单次读取） | 10000 | 拒绝并说明，不截断 | 对齐 `AggregateWindowMaxRows = 100000`（`aggregate_window.go:17`）的 1/10，留出聚合余量 |
| 事务内 `ForEach` 迭代次数 | 1000 | 拒绝并说明 | 与接受结果预算耦合：1000 步 × 每步最小行大小已接近 1 MiB 量级 |
| 单次事务的步骤数 | 256 | 发布期拒绝 | 步骤数与语义复杂度直接相关；超过即应拆为流程 |
| 集合嵌套深度 | 1（不得嵌套） | 发布期拒绝 | ADR-0100 §D2 顺序规则 4 |
| 引用路径深度 | 16 | 拒绝（已有） | `platform/record_path.go:7-26` |
| 关系遍历的跳数 | 1（单跳） | 拒绝 | 多跳用声明的集合；不做通用图遍历（§D4） |
| 每个对象类型声明的集合数 | 64 | 发布期拒绝 | 防止"每个字段一个集合"式的声明爆炸 |

**这些值不是承诺的性能指标**：它们是**正确性与可预测性的下限**。真实的容量承诺（Platform §10.6 的 RTO/RPO、规模）仍按实际演练证据声明，不由本表代替。

**拒绝的理由必须说明"哪一步超了、当前是多少、上限是多少"**——超限不是模糊失败。

### D3 关系归记录所有者，进同一个提交边界

这是本 ADR 最硬的一条。今天 relations 是独立应用，导致三个后果：

1. 关系与记录不原子；
2. 基数约束不能与记录写入同时判定；
3. 跨应用遍历的权限要经过第三个 owner 的判定（`link_types.go:94-135` 的 `linkTraversalDomain`）。

决定：

- **一个应用拥有的对象类型之间的关系，由该应用自己的账本承载**（同 ADR-0100 D1 的权威粒度）。关系写入是事务步骤 `link`/`unlink`，与记录写入同生共死。
- `relations` 应用保留的职责收窄为**跨应用**的关系声明与呈现（记录动态、评论、提及、关注者），它的跨应用链接仍是独立决策——**跨权威不原子**的边界不变。
- 同应用内的关系，其**基数与删除策略**（`Cardinality`、`DeletePolicy`）由 ADR-0102 的约束在事务级检查。今天"归档父记录时有未归档子记录就拒绝"（`record_archive_links.go:14,37-73`）是零散检查，成为 `cardinality` 约束的一个实例。

### D4 反向引用必须是声明的

"谁引用我"今天在两个地方各做一遍：企业模型的 `UsedBy`（ADR-0084 D5，走 `/v1/enterprise-references` 递归读取）与 LinkType 的 `inverse`。

决定：**反向引用是一个声明的属性**（对象类型上的 `Inverse` 或 LinkType 的 `inverse`），由**引用的所有者**维护索引，读取按调用者权限逐段过滤。一处声明，多种呈现（记录详情的"被引用"、影响面分析、删除前置检查）。

**不做通用图遍历**。反向引用只沿**声明过**的引用方向，深度有界（沿用 16 段），不提供"任意深度找所有相关"的能力——那会把权限闭包变成不可证明的东西（ADR-0105）。

### D5 集合的读取权限

集合的每一次读取都按调用者权限过滤，规则明确：

- 集合的**元素**必须逐条通过行范围与字段裁剪（复用 `records.go:1096` `visibleIn`、`narrow.go`）；
- 集合的**大小**（`count`）也受限：不能读的元素**不计入**计数，且调用者能区分"总数为 0"与"存在但不可见"（返回可见数 + 一个明确的"部分不可见"标记），否则计数本身泄漏了信息（沿 ADR-0033 的派生读取闭包要求）；
- 量词的短路行为必须保守：`all` 在遇到不可见元素时**不能默认通过**，必须按声明语义给出确定答案并留下原因。

这条与 ADR-0105 配套：集合是权限漏洞最容易出现的地方，**默认不泄漏**。

## 2. 不做

- **不做通用查询语言**（无 SQL、无 join 语法、无子查询）。集合由声明的关系与已有查询构成。
- **不做跨应用集合的原子写入**：跨应用仍是先后独立决策。
- **不做递归/传递闭包查询**（"物料的所有祖先"）。需要时用企业模型的层级结构（`core.location` 的 `parent`、UAF 关系）表达，深度有界。
- **不把 relations 应用整体并入每个应用**：它的记录动态/评论/关注者职责与关系铁是两件事。

## 3. 后果

- 集合类判断从行业 Go 代码（`apps/mes` 的 `canDo`/`reworkable`）迁到声明式表达式；这是 ADR-0113 的 MES 基准里"资源约束"一行的直接支撑。
- relations 应用的关系存储形态要改（owner state → 与所属应用同一账本），这是 ADR-0097 §7 之外的**新**结构变更，需要一次显式的迁移与历史读取兼容（旧 `RelationLink` 记录继续可读，不重写字节）。
- 已有 `LinkType`（`platform/link_type.go`）的 `Cardinality`/`DeletePolicy` 语义保留，执行点从零散检查移到约束。
- 前端"关联列表"从"单跳取值"扩展到"声明集合"，归 ADR-0109。

## 4. 验收

1. 构建者声明一个集合（某对象的子记录，按序），对它求 `all`/`any`/`count`，用于一个条件、一个计算字段、一个约束；三处结果一致。
2. 事务里的 `ForEach`：拆批把 N 行分到 2 个批次，重放产生完全相同的分组。
3. 关系原子性：创建记录 + 建关系 + 违反基数，整体拒绝，不留记录也不留关系。
4. 反向引用：改引用后"被引用"视图立即正确；删除前置检查按 `DeletePolicy` 拒绝并说明。
5. 权限：集合含不可见元素时，`count` 不泄漏存在性，`all` 不默认通过；调用者能看出"部分不可见"。
6. 无界集合：超过 `Limit` 的集合被拒绝并说明，不截断。
7. 反例：未声明的关系名、缺 `Order` 的迭代、超出 16 段的路径 → 发布期拒绝。

测试归宿主、relations 与 build owner 包；`docs/Testing.md` 增"记录集与关联"手测行。

## As built

当前已实现记录集与同权威关系的基础层，尚未完成本 ADR 的整块验收。对象的 `sets` 声明支持固定版本的 NamedQuery、LinkType 正反向、单记录引用与声明的 inverse；发布、安装和依赖重验共用校验。`Where` / `Order` 使用 ADR-0101 求值器，排序以 ID 作稳定末级键，显式 Limit 为 1–10000，超限拒绝。过滤引用路径目前须写在 `Where` Expr 内；非空独立 `Path` 明确拒绝，避免声明被静默忽略。

`RuleCollection.Set` 绑定当前对象的声明集合，复用动作、计算与约束的规则上下文。读取沿调用者行范围、字段与派生来源权限，仅返回可见记录和 `partial` 布尔标记。`all` / `none` 对部分不可见集合拒绝，`count` 只计可见元素。规则上下文仍沿 ADR-0101 的 1000 元素和 256 KiB 预算；声明集合的 10000 行上限不等于聚合或事务已支持同样规模。

`LinkType.Storage=edge`（contract 4）将关系行存入端点所属应用的 `<app>.__relation` 类，Build 已声明该类；其他代码 owner 须显式声明同一实体与账本类。`Caller.PutOwnedRelation` 只接受私有决策、同权威端点、保留的关系声明和获准角色。关系行与业务行复用 accepted-result，基数与 restrict-active 在最终状态检查，发布也复用相同检查；存储身份不得随版本改变，基数和删除保证不得放宽。`Required` 的 edge 声明暂不接受。历史 reference 类型的存储与已发布字节保持原形。

宿主回归覆盖新建端点与关系共同接受、父/子基数冲突整批拒绝、归档拒绝、解除关系、已接受结果重放、可见范围、排序与 Limit 拒绝。尚未实现事务 DTO 的 `link` / `unlink` / `ForEach`、迭代顺序进入接受结果、独立过滤 Path、关系专用编辑体验、旧 relations owner-state 的显式迁移与职责收窄，以及 HTTP aggregates 与声明集合聚合的完整统一。未声明浏览器验收或完成 §4 全部判据；继续沿本 ADR 收口。
