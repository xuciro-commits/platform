# ADR-0110 — 专业业务组件：企业级表达，通用模型配置

状态：已接受（2026-10-12，负责人指令，ADR-0098 D 块第三份，对应前端第 4 项的后半）· 扩展 ADR-0046 的 widget 体系与 ADR-0004 的 UI Kit 归属 · 与 ADR-0109（模型驱动绑定）配套

## 0. 意图

客户要建 MES，必然需要工艺路线图、工作站、批次谱系、设备能力矩阵这类**专业呈现**。今天的分工是：

| 组件 | 现状 | 归属 |
|---|---|---|
| 表格/看板/甘特/时间线/散点 | 通用 | `@platform/ui`（`RecordGantt.tsx`、`RecordKanban.tsx`、`RecordTimeline.tsx`…）+ `@platform/app` 的 widget 适配层 |
| 工艺路线图 `RoutingFlow` | **MES 私有函数**，靠 `defineApp` 的 `views`+`opens` 挂载 | `web/packages/mes/src/index.tsx:226` |
| ERP/CSM/PMS 的原生表单 | 各应用私有 | `web/packages/{erp,csm,pms}` |

于是有这样一条危险的路："把原生 MES 页面迁进 Workshop 冒充通用组件"——**ADR-0098 §4 明确点名禁止**。因为把 `RoutingFlow` 换一个包放，它仍然是 MES 的形状：泳道是工作中心、节点是工序、叠的是批次位置，换个行业就用不了。

**判据**：工艺路线图、工作站、批次谱系这类组件在工作台里**可以被非 MES 客户配置出来**，配置方式与 MES 无关；同时 MES 客户能配出专业级的呈现，不是降级的通用表格。

## 1. 决定

### D1 专业组件 = 通用视图 + 业务模型绑定，不是专用代码

任何一个"专业"呈现都可以分解为**一个通用视觉结构** + **一组模型绑定**：

| 专业呈现 | 通用结构 | 模型绑定 |
|---|---|---|
| 工艺路线图（制造） | **分层有向图**（已存在：`FlowCanvas`/`BlockCanvas` + `FlowSteps` 的泳道，ADR-0087 D4） | 节点=工序、层级=工作中心、边上叠当前状态 |
| 组织与汇报关系图（任意行业） | 同上（分层有向图） | 节点=组织单元、层级=上级结构、边上叠生效期 |
| 配送/供应链网络（贸易、物流） | 同上（分层有向图） | 节点=站点、层级=区域、边上叠线路 |
| 合同审批链（专业服务） | 同上（分层有向图） | 节点=审批阶段、层级=审批人角色 |
| 工作站（制造） | **表单 + 集合 + 状态条**（已存在：`editor` 三栏 + 表格 + `StatusBar`） | 当前工序、参数、可用设备、报工输入 |
| 受理台（酒店、服务台） | 同上（表单 + 集合 + 状态条） | 当前单据、服务项、可选资源、登记输入 |
| 批次谱系（制造） | **有向无环图（树/图）**（已存在：`Graph`/`NodeCanvas`） | 批次关系的方向与标签 |
| 单据版本沿革（任意行业） | 同上（有向无环图） | 版本记录的方向与标签 |
| 能力/资质矩阵（制造、服务业） | **矩阵/交叉表**（需新增：通用交叉表） | 行=资源、列=能力、单元格=表达式结果 |
| 报价/费率对照表（贸易、专业服务） | 同上（矩阵/交叉表） | 行=客户或方案、列=计费项、单元格=表达式结果 |
| 产能/排程负荷（制造） | **时间轴 + 条形**（已存在：`RecordGantt` 的时间轴） | 资源为行、占用为条 |
| 房态/工位占用（酒店、服务） | 同上（时间轴 + 条形） | 资源为行、占用为条 |
| 检验/质量图表（制造） | 图表族（已存在：`page_histogram/trend/scatter/heatmap` 等） | 度量与分组 |
| 满意度/成本趋势（任意行业） | 同上（图表族） | 度量与分组 |

**关键读法**：左列是**同一批通用结构**在不同行业语义下的呈现；真正的通用结构只有六类（分层有向图、表单+集合+状态条、有向无环图、矩阵/交叉表、时间轴+条形、图表族）。**构建者用配置把左列的任意一行做出来，组件代码零改动**——这就是"专业组件"的含义，也是 ADR-0098 §4 禁止"把 MES 页面搬进通用库"的原因：搬走的是左列的名字，通用性在右列。

**结论**：今天缺的不是"MES 组件"，缺的是：
1. **通用交叉/矩阵视图**（唯一真正缺失的视觉结构）；
2. **把已有通用结构配置成专业呈现的能力**（依赖 ADR-0109 的模型绑定）；
3. **专业呈现的密度与信息层级**（视觉规范，不是新组件）。

### D2 组件注册契约扩展：允许"结构 + 绑定"的复合组件

`pageui/widgets.json`（`capabilities/server/platform/pageui/widgets.json` → `page_widgets.go:14` → `host.ts`，ADR-0046 §8 的单一契约来源）增加一类组件：**复合视图（composite view）**。

```json
{
  "componentID": "layered-graph",
  "configVersion": 2,
  "propsSchema": { "layers": "binding", "nodes": "binding", "edges": "binding", "overlay": "binding" },
  "inputPorts": [{"name":"selection","type":"record"}],
  "outputPorts": [{"name":"selection","type":"record"}],
  "events": ["select","activate"]
}
```

要点：
- **绑定是契约的一部分**（`"binding"` 类型的属性），因此 Inspector 能生成模型选择器，发布期能做校验（ADR-0109 D1）；
- 复合视图**不拥有业务语义**：它不知道"工序"是什么，只知道"节点有层级、节点有边、节点可叠状态"；
- 同一个 `layered-graph` 既能画工艺路线（层级=工作中心），也能画组织架构（层级=部门）、配送网络（层级=区域）、审批链（层级=阶段）。

### D3 MES 的专业呈现由配置产生，代码不搬

- `RoutingFlow`（`web/packages/mes/src/index.tsx:226`）**不作为组件迁移**。它的呈现由 `layered-graph` + MES 应用的绑定配置产生；
- MES 应用（无论是原生参考应用还是客户构建的应用）通过**配置**表达"工序图的层级是工作中心"；
- 原生 MES 的 `RoutingFlow` 在 ADR-0114 的退出路线里随之退役；**在构建侧的等价呈现可用之前不删**（这是硬要求：不能先删再看）。

### D4 视觉规范与信息密度

专业呈现的品质不靠"更多组件"，靠规范：

- **密度**：沿用 `@platform/ui` 的紧凑信息质感（ADR-0004 的 28px 行高、等宽数字、语义色调）；
- **信息层级**：每类专业视图有明确的"一眼看到什么、二次点击看到什么"（沿 ADR-0084 §D7 的"每块写清它证明了什么"）；
- **状态色**：业务状态映射到五种语义色调（`StatusTag` 的既有机制），构建者声明映射，不硬编码；
- **窄屏**：专业视图在窄屏降级为列/表（今天记录工作区已有此行为，保留）。

视觉规范归 Catalog（ADR-0045）；**不写像素断言**（ADR-0082）。

### D5 组件的门槛

新增一个通用组件的门槛（沿 ADR-0004 的"两个业务领域同时需要"规则，在本文收紧为**可验证的形式**）：

1. 它在**至少两个不同的应用配置**里被使用，且这两处配置由不同的人写；
2. 它不包含任何业务词汇（"工序"、"库位"、"床"等等不得出现在组件代码与 props 名里）；
3. 它的绑定是模型引用（ADR-0109），不是硬编码字段名；
4. 它的默认呈现从模型推导（ADR-0109 D2）。

**不满足四条的一律不进 `@platform/ui`。** 这条门槛是对 ADR-0098 §4"把原生 MES 页面迁入 Workshop 冒充通用组件"的**机制性防线**：想搬可以，先在两个行业里各配一次。

## 2. 不做

- **不把业务专用页面搬进通用组件库**（见 D5）。
- **不建第二套 UI 库**（ADR-0004 的归属不变）。
- **不做 GIS/3D/甘特的深度专业实现**：只在具体任务需要时进入队列（沿 Platform §10.3 B 的既有边界）。
- **不做组件的可视化搭建器**（拖组件搭新组件）：复合视图由**配置**产生，不由嵌套搭建产生。

## 3. 后果

- 唯一的**真实新增**是通用交叉/矩阵视图；其余靠 ADR-0109 的绑定能力 + 配置。
- `RoutingFlow` 的退役与 ADR-0114 绑定；先建等价呈现，再删。
- Catalog（ADR-0045）需要收录复合视图的配置示例（"用 layered-graph 画工艺路线"的完整配置），作为场景装配资产。**示例本身是资产，不是文档。**
- MES 基准（ADR-0113）的"专业工作站"一行依赖本文的可配置性证明。

## 4. 验收

1. 用同一个通用组件（如 `layered-graph`）在**两个不同业务语义**下各配一次（例如工序图与组织架构图），由两份配置产生，组件代码零改动。
2. `RoutingFlow` 的等价呈现由配置产生，与原生呈现的**信息内容一致**（不是像素一致）；负责人走查确认可用。
3. 交叉表：设备能力矩阵由"能力表达式结果"配置，行/列/单元格都来自模型绑定。
4. 工作站：由表单 + 集合 + 状态条配置，参数按类型渲染、可用设备来自服务端同一规则（ADR-0109 验收第 1 条）。
5. 门槛检查：组件代码内不含业务词汇（用一个检查脚本或人工清单证明）；至少两处配置由不同的人写。
6. 反例：把 MES 专用页面作为组件加入 `@platform/ui` → 门槛检查失败（记录该反例作为防线的证据）。

测试：`make check-web` + Catalog 示例的构建；`docs/Testing.md` 增"专业组件配置"手测行。
