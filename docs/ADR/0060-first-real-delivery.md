# ADR-0060 — 第一次真实交付：楼宇供暖，以及武器库的第一次沉淀

<a id="adr-0060"></a>

**状态：** 现行 · 2026-10-12 · 第一次交付是楼宇供暖，MES 是第一探针（并入原 0052）。

当前接入准备已按 [ADR-0061](0061-pluggable-protocol-packages.md#11-as-built) 实现协议包、独立网关、模拟点位与 S7 本地报文读取。模拟不替代本 ADR 的真实上线、多城市和行业资产判据。

## 0. 负责人指定的事实

- **第一次交付的场景是楼宇供暖管理系统**：从数据采集到整套楼宇智能，到暖通，到门禁，到楼宇数据的分发、楼宇健康状况排查、AI 介入。
- **开发范围**：门禁包含在内；数据分发同时包括推送、看板报表与导出/API。当前仍是开发阶段，平台功能与开发流程须先完成，真实使用不是平台工程继续开发的前置条件。
- **执行者就是负责人本人**：他此前做 MES/ERP 企业数字化，**楼宇供暖是他不熟的领域**。
- 供暖系统**直接对接物业**，不直接对接业主（已经做过：用 ThingsBoard 做的，后续还有第二、三、四栋楼，**分布在不同城市**）。
- **产品定位**：为**无数个 FDE** 设计产品。FDE 像律师——有的精通婚姻法、有的精通商业法；有的精通 ERP、有的精通 IoT、有的精通家电制造、有的精通离散制造。他们**都需要自己在专业领域的武器库**，而中国现在没有这套武器库。

## 1. 为什么验收对象从 MES 换成供暖

**这是本 ADR 最重要的判断，理由只有一条：MES 是负责人能给自己出的最差考题。**

他做 MES/ERP 出身，因此构建 MES 时会在**无意识中替平台填掉所有的坑**：他知道工序要带参数、知道返工要指定工序、知道设备能力要匹配——所以他配置时不会漏、不会困惑、不会卡住。**而那些坑恰恰就是平台的缺口。**

一个律师测试法律工具，用他不熟的领域才能发现工具不好用；用熟得能背下来的领域测，测出来的是**他的经验在起作用**，不是平台在起作用。

**供暖正好相反：数据采集、时序、多子系统（暖通/门禁/楼宇智能）、数据分发、健康诊断、AI——这些他都不熟。** 这不凑巧，这是最好的第一次。

因此：

| | 旧（原 0052） | 新（本文） |
|---|---|---|
| 第一次交付 | 完整 MES | **楼宇供暖管理系统**（真实客户、真实上线） |
| MES 的位置 | 唯一验收对象 | **第二探针**（域中立性仍有价值，但不是第一次） |
| 执行者 | "未参与底层开发的 FDE" | **负责人本人**（现阶段他是唯一的 FDE） | 本文 的**八个 MES 范围、反例清单、撞墙处理规则、两工厂配置**全部保留——它们对第二探针继续有效，只是**不再是第一次**。

## 2. 第一次交付要过的判据

沿用 本文 §D4 的撞墙规则与 §D2 的反例清单，替换场景：

**必须证明的三件事**（对应 ADR-0038 §0 的三判据）：

1. **能构建出来**：从空白项目建出供暖管理系统的范围：采集接入、暖通监控、门禁、数据分发、健康诊断、AI 介入。**不写行业 Go/React 代码。**
2. **能正确运行**：权限无绕过、关联业务一致、状态变化正确、历史不失真（ADR-0038 §0 判据 2）。
3. **能长期维护**：一次真实的模型变更（加字段 + 重命名 + 退役一个动作/规则）在途业务继续按旧语义跑（ADR-0045 的验收在供暖语境内重跑）。

**反例清单**（沿 本文 §D2，逐条适用）：

| 反例 | 为什么是失败 |
|---|---|
| 供暖专用代码进入 `capabilities/server`、`apps/build`、`@platform/ui` | 违反 ADR-0038 §4 |
| 把 ThingsBoard 的既有页面搬进工作台冒充通用能力 | 同 ADR-0048 D5（组件门槛） |
| 为通过基准放宽约束/权限 | 违反判据 2 |
| 需要修改内核 `contract/` | 通用能力不足或场景设计错 |
| 采集与协议栈进入业务宿主/内核 | 违反 ADR-0051 §3、ADR-0051 §3；ADR-0061 的独立协议能力包允许自行开发 |
| 只在**一栋楼**的配置下成立 | 有多栋楼、**不同城市**，必须用第二个配置复核 |

**多城市是这次交付的真实结构**：第二、三、四栋楼在不同城市 → 这是**第二个工厂配置**的天然形态（本文 §D3 的判据继续适用：同一套机制、零代码差异、只有配置不同）。它同时是 ADR-0046 的**多环境交付**的真实用例（同工件交付到不同环境，重新验证绑定与权限）。

## 3. 交付完成 = 系统上线 + 一件可复用的行业资产

**这是本 ADR 相对 本文 最重要的新增，也是"武器库"从口号变成机制的地方。**

负责人："他们需要武器库，需要一辆好车，才能把客户送到对岸。"武器库里装的是**行业判断**，而今天这些判断的载体是：开发者的脑子、`apps/*` 里的 Go 代码、`docs/Apps.md`——**三个都不是武器库**。

**因此第一次交付的停止条件包含两项，缺一不算交付完成**：

1. **系统上线**：客户在跑（§2 的三件判决通过）；
2. **产出一件可复用的行业资产**，即 **楼宇供暖行业包的首版**（ADR-0057 §2 的行业层），内容至少包括：
   - **对象骨架**：楼宇、楼层、区域、设备、测点、暖通回路、门禁点、告警、工单；
   - **规则模板**：阈值与趋势判定、误报抑制、告警分级、健康评分、门禁策略；
   - **页面装配**：楼宇总览、设备详情、告警处理台、门禁管理、健康看板；
   - **样本数据与验收场景**：可复现场景（ADR-0050 的样本集）；
   - **构建步骤与工时记录**：怎么理解的、怎么切的对象、哪一步卡住、客户改了什么、改了几次。

**最后一项不是文档，是资产**：它的作用是让下一个人（精通 IoT 的 FDE、或别的城市部署的人）**不必重新摸索一遍**。本文 §D4 的"撞墙清单"是它的技术版本，"客户改了三次什么"是它的业务版本。

**行业包必须从交付里长出来，不能事后整理**：事后整理的行业包会丢掉"为什么这样做"（那正是判断），只留下"做了什么"（那只是配置）。

## 4. 供暖暴露的能力缺口（已知，须在交付中验证并登记）

| 缺口 | 依赖 | 状态 |
|---|---|---|
| **观测与时序** | ADR-0051、ADR-0061 | 外部读取、窗口规则、结果入账及模拟协议接入已实现，S7 只读包通过本地服务检查；真实设备与生产时序存储未接入，本次交付仍须验证环境前置 |
| **多环境多城市交付** | ADR-0046 §D4、ADR-0045 | 机制已有（环境绑定、迁移计划）；**多城市是第一次真实使用** |
| **数据分发**（负责人："楼宇数据的分发"） | ADR-0051 + 集成织物 | 负责人已确认推送、报表/看板与导出/API 三者均包含；分别复用外发、模型页面与原受权导出/读取，不建行业专用传输路径 |
| **健康诊断** | ADR-0055 + 0040 | 判定在平台内（0058 §D3），诊断规则的**领域化**属行业包（§3） |
| **门禁** | ADR-0044 + 本文 §5 | 见下 |
| **AI 介入** | ADR-0008 | 已有 ADR；本次交付第一次真实使用 |

**撞墙的处理规则不变**（本文 §D4）：先查已有能力 → 记通用缺口 → 确认需新原语则立 ADR；**不允许在探针里绕过**（这正是 AGENTS 硬规则 4 必须改的原因）。

### D5 门禁：物理权限与逻辑授权是两套

门禁是**物理通行权限**（谁能进哪栋楼、哪层、哪个机房），**不是** ADR-0044 的逻辑授权（谁能读哪条记录）。两者必须分开：

- 逻辑授权归 ADR-0044；物理通行权限是**业务数据**（通行证、区域、时段、记录）；
- 门禁设备是**目标**（ADR-0051 的 `Dispatch` 与状态回读）；
- **不允许**把物理通行权实现成平台的角色/scope——那会让"忘了配 scope"变成"门开了"。

这条要在本次交付里落地并写进行业包。

## 5. 第二次交付：别人的领域

负责人："**我要给无数个 FDE 设计产品**。"

由此**推导**（不是加码）：第一次交付（供暖）证明**域中立**——平台在负责人不熟悉的领域仍成立；但它**证明不了武器库能被别人用**，因为执行者仍是同一个人。

**因此判据是两次，不是一次**：

| | 证明什么 | 执行者 |
|---|---|---|
| 第一次（楼宇供暖） | 域中立、时序与 IoT 可行、多城市交付可行 | 负责人 |
| **第二次** | **武器库可移交**：精通另一领域的 FDE 能用行业包/能力包建出他的系统 | **另一个人**（现阶段：负责人之外的 FDE，哪怕起步慢、哪怕兼职） |

**第二次交付的候选已确定**（负责人 2026-10-12）：大疆的 MES + WMS（立库 RCS、AGV WCS、黑盒下游集成）。**但它不保证用平台做**：

> "是确定的下一单，但是我下一单不一定用我们平台来做。我们平台现在才是在开发迭代的。如果迭代快，那就尝试去用它做，做的过程中一定一定会发现能力不够的，我们再回来补。只不过在内核里面要给它做预留，否则我们改内核是很麻烦的。"

**这改变了第二次交付的性质**：它不是一个"必须用平台完成"的验收，而是一个**可选的使用尝试**——用，是为了**发现缺口**；不用，平台也不能假装它被验证过。

- 因此：**第二次交付不设"必须成功"的停止条件**，它的产出是**能力缺口清单**（以及可能的行业包/能力包增量）；
- 缺口按 ADR-0057 §6 的分类处置：**平台包的缺口要改内核层级，所以按 §D7 预留；能力包的缺口随时补**；
- **ADR-0053 的退出判定不依赖第二次交付**（因为它是可选的）；退出的依据回到第一次交付 + 第二探针（MES）。

**这需要在本次交付后重新审视**：如果第二次交付未发生，"武器库可移交"这一条**没有被证明**，必须如实记录为未验证（沿 Platform §10.6 的"不得把内部演练当作外部交付"）。

## 6. 不做

- **不把 ThingsBoard（或任何既有 IoT 平台）纳入平台**：它是采集/可视化的既有实践，与 ADR-0051 的"观测存储是环境绑定"一致，平台不重做它。
- **不在第一次交付里追求覆盖**：负责人明示"一次你覆盖不全的，但是你的内核要稳"。
- **不为边缘情况预留**（ADR-0057 §6）：除 ADR-0051 §D7 的四项（下一次交付已命名）之外不留形状。
- **不把行业包做成客户可见**（ADR-0057 §2）。
- **不宣称第二次交付已验证**（§5）。

## 7. 验收

1. **第一次交付**：楼宇供暖系统上线，§2 三件判据通过；反例清单逐条检查（行业代码为 0、内核未改、协议栈独立运行、约束与权限未被放宽）。
2. **多城市**：同一工件交付到第二个城市的环境，重新验证绑定与权限；两份配置零代码差异。
3. **行业资产**：产出一份楼宇供暖行业包首版，含 §3 的五项；用一个复现场景证明**只配应用包、不改行业包与平台包**即可再建一栋楼。
4. **门禁**：物理通行权限作为业务数据，**不是**平台角色/scope（用一个"未配 scope 不影响门禁、门禁配置错误不开放逻辑读取"的对照测试证明）。
5. **缺口登记**：列出本次全部撞墙点、处理方式（复用/记缺口/立原语）、对应 WorkQueue 项；其中"数据分发"的实际形态被确认并登记。
6. **第二次交付的记录**：无论是否发生，如实记录结论（发生了→缺口清单；未发生→"武器库可移交未验证"）。
7. **演进**：一次真实模型变更在途业务继续按旧语义跑。

测试：`make check` 全量 + `scripts/verify.sh composition` + `make rehearse` 的供暖场景 + 浏览器路线的负责人走查；`docs/Testing.md` 增"楼宇供暖"路线与手测行；`docs/Apps.md` 增可执行用法。

## As built

`deploy/packages/heating.json` 提供模拟行业包 `industry.heating`：楼宇/楼层/区域/设备/测点/暖通回路/门禁点/告警/工单/通行证十类对象；三种 Observation、原维修 Flow、阀位审批与 Dispatch、五个页面、版本化业务场景和合成样本。`deploy/examples/heating/harbin.json` 与 `jinan.json` 仅是两份环境配置，不是实际客户楼址。样本不自动导入业务库，页面子表沿原关系绑定，设备数据保留业务结果而非原始采样。

行业包的构建说明记录建模判断、接入/复用步骤和本轮装配时段，不伪造客户实施工时或变更次数。只读 `heatingadvice` 经原 AI 函数/实测评估使用已接受证据；当前模型检查采用受控提供方，不证明诊断品质。数据分发暂按向独立 HTTP 端点推送紧凑业务告警验证，现行范围同时包含推送、看板报表和导出/API，现场接收方、业务指标及调用方在接入时配置。

这次构建发现并在原归属补齐：行业定义创建草稿、普通业务场景的版本交付、同批对象/集成/函数/Flow 声明解析、私有候选的连续安装、原依赖发现、跨草稿赋值保存，以及草稿与正式发布的环境检查区分。隔离试跑复用原 Work 审批与候选定义；运行诊断不再阻断修复尚未绑定的集成。文件与 PostgreSQL 共用封存结果，JSONB 调整字段次序后仍比较同一有效载荷。没有新增行业 Go/React 运行代码，没有改变 `contract/` 或放宽正式发布权限。

`TestIndustryHeatingDelivery` 已在文件日志及 PostgreSQL 下完成两城市配置：同一 ApplicationArtifact、三项普通业务计划、异常告警与维修工单、HTTP 通知、受控 AI 评估、关闭重开日志、增加字段/重命名/退役动作后的在途维修，以及阀位回复丢失后只由新采样确认结果。此处的模型变更与城市均为模拟数据，不能替代客户实际变更和城市上线记录。

浏览器 `heating-application` 已完成安装行业包、生成应用草稿、配置模拟协议与物业连接、同批评估/激活，以及普通成员选择楼宇、确认告警和请求实际 AI 建议。桌面与 390px 页面已观察；模型列表的正常刷新保留原选中项，查询条件或权限改变仍使旧读取失效。页面投影使用独立模型副本，避免并行读取修改原定义。实测评估完成后沿原发布审阅刷新激活资格。

**提供的客户资料**：2026-10-15 已读取负责人指定的 `/Volumes/团队文件-uhanv云存储/01_Projects_业务项目/IoT_物联网/中睿iot项目` 中的 V03 需求、工作范围说明、2025-06-17 会议纪要及风柜/高效机房点表。资料范围是园区厂务与暖通，V03 明确排除安防、考勤；云端经本地系统间接访问设备、离线可查看及云/本地各自授权是资料中的要求。会议选择单体部署；另一个多租户技术选型报告不据此替换本平台架构。负责人已明确本次包含门禁，旧 V03 的排除项不改变这一现行范围；旧文件中的建议、待确认算法和历史日期不作为已经确认的现场事实。

可确定的点位格式已用于 ADR-0061 的 Modbus 只读包与十点配置；地址、类型和比例取自工作簿，现场地址、设备数量/单元编号和读数仍是本地模拟。空设备清单模板与仅三行示意的采集清单不足以确认实际型号/固件；带 S7 字节地址的标志位不自动转换为 Modbus 寄存器位。`industry.heating@0.1.0` 继续作为原封存模拟包，不用厂务文件覆盖同版本内容或虚构已确认的门禁策略。

**真实交付尚未完成**：具体楼栋与在用设备映射、生产时序存储、物业实际权限与门禁策略、负责人走查、客户变更记录及真实多城市上线，仍按本文原判据执行。模拟行业包不是客户上线证明，原生参考应用尚未因此退出。

## 并入：MES 基准（原 0052）

MES 是第一探针的证据面，不再是验收对象；八个范围与反例清单仍然有效。

### 0. 意图

ADR-0038 §1 定的是：**唯一基准是完整 MES**，不是"能跑三道工序的演示"。**它的位置已改变**：第一次真实交付是楼宇供暖（本文），MES 是**第二探针**——因为负责人做 MES 出身，在熟悉的领域测出的是经验在起作用，不是平台在起作用（本文 §1）。八个范围（基础主数据、工艺管理、生产管理、现场执行、异常与质量、生产追溯、资源约束、跨系统协同）不是要写进内核的功能清单，是**反向要求平台具备通用能力**的探针。 本文把这件事变成**可执行、可判定、不可自欺**的路线。

**判据（第二探针）**：一名没有参与底层开发的 FDE，按业务需求从空白项目构建、测试、交付并升级这套 MES，全程不写行业 Go/React 代码。它用于提供域中立性的第二份证据；第一次供暖真实交付仍未完成，当前模拟行业包与内部检查的边界归 [本文 As built](0060-first-real-delivery.md#as-built)，不能写成已经取得第一份真实交付证据。

### 1. 基准的形态

### D1 八个范围，逐项给出"构建者做什么"与"平台上要靠什么"

| # | 范围 | 构建者要建的 | 依赖的平台能力 | 依赖的 ADR |
|---|---|---|---|---|
| 1 | 基础主数据 | 产品、物料、设备、工作中心、生产组织 | 对象与字段、共享本体（`core`）、企业模型、**主数据落库** | 0020, 0022, **0042** |
| 2 | 工艺管理 | 工艺路线、工序、工步、参数、版本 | **业务版本**、约束（唯一、区间）、界面 | **0042, 0041**, 0048 |
| 3 | 生产管理 | 计划、工单、拆批、派工、执行 | **业务事务**（拆批是一次多行变更）、集合迭代、编号 | **0039, 0043** |
| 4 | 现场执行 | 工作站、开工、过站、报工、完工 | 事务、状态、参数呈现、专业组件配置 | **0039, 0049**, 0048 |
| 5 | 异常与质量 | 暂停、返工、报废、检验、质量处置 | **返工是一次状态+关联业务变化**（事务 + 约束），不是新的执行器 | **0039, 0040, 0041** |
| 6 | 生产追溯 | 批次、人员、设备、物料与操作历史 | 记录历史（已有）、因果链诊断、集合查询 | 0043, 0046 §D3 |
| 7 | 资源约束 | 设备能力、占用、人员资质、产能规则 | **能力匹配是集合量词表达式**（今天在 `apps/mes` 的 `canDo` Go 函数里） | **0040, 0043** |
| 8 | 跨系统协同 | ERP、WMS、APS、设备 | **Confirmation、补偿、对账** | **0051** |

**第 7 行是本基准的核心价值**：本文 D4 今天用"服务端算、服务端拒"的 Go 实现 `canDo`，这是对的临时做法；基准要求这条规则**由构建者声明一次**，在页面候选、服务端拒绝、AI 工具三处共用同一实现。**如果配不出来，要研究的是关系与约束能力，不是给 MES 加代码。**

### D2 探针有明确的反例清单

基准不只是"能建出来"，还包括**这些都不能发生**：

| 反例 | 为什么它是失败证据 |
|---|---|
| 任何 MES 专用代码进入 `capabilities/server`、`apps/build` 或 `@platform/ui` | 违反 ADR-0038 §4 |
| 把 `apps/mes` 的 Go 规则翻译成等价的 Go 后放进客户应用 | 同上（换个位置不等于通用能力） |
| 为了通过基准而放宽某条约束/权限 | 违反 ADR-0038 §0 的第二判据 |
| 构建过程中需要修改内核 `contract/` | 说明通用能力不足或探针设计错（见 D4） |
| 需要"操作工手输一个数组下标"这类在服务端可以算出来的输入 | 违反 本文 D2 已经修掉的教训 |
| 基准通过但只在一个工厂的配置下成立 | 需要第二个配置的复核（见 D3） |

### D3 两个工厂配置，证明不是硬编码

基准必须跑**两个语义不同的工厂配置**（沿 本文 的种子设计：不同工作中心、不同能力集合、不同工艺路线版本）：

- 配置 A：装配为主，工序要求多项能力，能力匹配不平凡（沿用 本文 D4 的 ASM-1/ASM-2 设计）；
- 配置 B：加工为主，有返工路径与外协工序，跨系统协同更重（外协要等 ERP 与供应商确认）。

**两个配置用同一套定义机制、同一套组件、零代码差异。** 只有配置不同。这条是对 ADR-0038 §4"不硬编码 MES 规则"最直接的检验。

### D4 撞墙的处理规则

撞墙时按顺序走：

1. **先查是不是已有能力没用上**（复用主人，ADR-0038 的规则 3）；
2. 若是通用能力缺失 → **记录为能力缺口**，在本 ADR 的 As built 里登记，进入 WorkQueue；**不在探针里绕过**；
3. 若确认需要新原语 → **新原话必须由 ADR 立**，且新原语必须**在第二个业务语义下也成立**（否则它不是通用能力）；
4. **不允许**的第三条路：在行业 Go 代码里实现后宣称基准通过。

**第 2 条是本 ADR 真正的产品**：撞墙清单就是平台下一阶段的需求来源，比任何需求文档都可靠。

### D5 基准的完成不与"交付"混同

- 基准完成 = **构建者能建出来、能正确运行**（ADR-0038 判据 1 与 2）；
- **长期维护与演进**（判据 3）由 ADR-0045、ADR-0046、ADR-0050 的能力加一次真实的升级演练证明；
- **独立 FDE 交付**（第四阶段）由 ADR-0053 判定，本 ADR 只负责"构建得出来"。

### 2. 与现有 MES 参考应用的关系

- `apps/mes`（含 `apps/mes/server/mes.go`、`erp.go`）**保留为对照实现**：它不是要被模仿的对象，而是"同一件事的 Go 写法"，用来对照构建产物的语义是否等价；
- **不允许**把 `apps/mes` 的页面/组件搬进工作台（ADR-0038 §4 第二条，ADR-0048 D5 的机制防线）；
- 退出路线归 ADR-0053：先有等价的构建产物，再有退出。

### D6 等价性的判定人与形式

**谁判定**（这是 ADR-0053 退出能否真实发生的关键，必须有名有实）：

| 角色 | 职责 | 不得是 |
|---|---|---|
| **构建者**（未参与底层开发的 FDE） | 从空白项目建出基准；报告撞墙点 | 平台开发团队的人 |
| **对照测试** | 同一场景跑原生实现与构建产物，逐个断言接受/拒绝、记录变化、拒绝码一致 | 只比"能跑通" |
| **负责人** | 判定是否语义等价、是否允许退出 | — |

**判定形式固定为三件，缺一不算**：

1. **逐场景对照清单**：每个能力单元（如 `canDo`、`reworkable`、`DemoMaster`）列出它覆盖的业务场景，原生实现与构建产物**各跑一遍**，结果并排。
2. **不等价的显式登记**：任何不一致的项**必须写出来并判定**是"构建产物更正确"（则原生实现是 bug，记录之）还是"构建产物缺失"（则退出中止）。**不允许"差不多"**。
3. **负责人的一次走查**：由负责人实际操作构建产物完成基准任务，记录观感与阻断。

**判定人不得是作者本人**：实现该能力单元的人不能判定它等价；构建者不能判定自己的产物等价。这条与 §D3 的"两个工厂配置、由不同的人写"同源。

### 分批生产协同的保留场景

原生 ERP/MES 一次整单确认不足以表达实际分批完成。仍有效的场景是：首批开工向上游发送 start；每批良品/报废形成独立 confirm 与稳定身份，累计数量、剩余可排产数量、终结标志和对应入库分开保存；累计超量明确拒绝，多工单可共享同一订单的剩余额度。

该场景通过声明的事务、Flow、Confirmation 和版本化 production 协议表达，单步只改所属权威，恢复不发外部请求。取消早期“先扩充原生 ERP/MES 再迁移”的施工安排及已退出适配器要求；没有等价构建产物前不删原整单协议实现。

`production.orders/2` 与原整单 v1 并存；两个受控包 `production-provider.json` / `production-consumer.json` 通过原 Connection、Writeback 和 Confirmation 协作。上游保存订单累计/剩余量与每批事实，达计划或显式 final 时完成，短缺终结仍保留剩余量，超量拒绝。每批良品在原事务创建 stockreceipt、保存本批引用并 post 到 finishedstock；原 Core journal 意图随后由 Core 独立接受，不把库存接受冒充财务已经记账。

原 `ConfirmationRead.keyInput` 从启动时封存的动作输入选取本批匹配键，未配置时仍使用 subject ID。HTTP 成功但答复丢失后按批回读，不自动重发。新声明式提供能力及其输入合同、权限、绑定与恢复归 ADR-0006，不扩充原生行业执行器。

这是可复用的受控构建场景；真实地址、凭据、科目与成本仍需在实际交付中配置。工程测试使用两个独立租户与本地 HTTP 服务，不代表真实 ERP、设备、网络服务保证或负责人业务使用已经验证。
