# ADR-0131 — XXL：有证据的性能与资源收敛

状态：接受执行（2026-10-17），归 ADR-0125 XXXL。性能是实现结果，不是增加缓存/索引的理由。

## 规则

先测可重复的热点和输入规模，后选择简单方案；同时报告代码净变化。任何优化不得改变可见记录集、顺序、权限、接受结果、历史或外部效果。任何新增 cache/index 都要说明唯一写入 owner、失效条件、重建路径和资源上界；无可量化收益则不引入。

## 第一组 workload

1. Host records：recordStore fork/promote，单记录读，授权记录查询与排序分页；至少 1k/10k 合成记录，有窄/宽字段及不同授权作用域。测 `go test -bench -benchmem` 的 ns/op、B/op、allocs/op；固定 Go 版本、种子与机器。
2. Accepted result/recovery：重复安装已保存对象/页面和批量决策恢复；区分 JSON decode、验证、索引刷新和锁等待。测量不能用无持久化 mock 代替真实路径。
3. Build/Workshop：查定义、草稿模型/页面 Inspector 编辑、保存与发布。用代表性资产数量和 React profiler / 浏览器 performance trace，记录长任务、重渲染组件和网络请求。
4. Workspace：切换 app、打开记录详情、搜索应用，记录初始化耗时、bundle/chunk 大小和数据请求重复数。不得用本地暖缓存掩盖首开成本。

## 优化选择

优先删重复序列化/遍历，采用已存在的 `recordIndex`、页面合约和查询结果。只有简单基于现有 owner 的查找仍达不到目标，才增量索引；不添加第二业务缓存、租户数据镜像或大型全局 memo。锁改动先用竞争/阻塞 profile 证明；异步化不得削弱持久语义。

## 验收

benchmark 至少 5 次可重跑，报告基准和改后中位数、离散范围、分配；没有可信基准就只写优化的复杂度/重复工作推理，不声称变快。性能收益必须足以抵消新增状态/代码；长期维护成本更高则回退优化。
