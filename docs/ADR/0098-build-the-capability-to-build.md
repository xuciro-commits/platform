# ADR-0098 — 产品是构建业务应用的能力：下一阶段的转型目标与开发范围

状态：方向已接受（2026-10-12，负责人指令）；§1/§5 的首次交付对象已由 [ADR-0122](0122-first-real-delivery.md) 改为楼宇供暖，MES 为第二验证场景；§11/§12 的首次实施安排保留为历史，当前顺序唯一归 WorkQueue。整个项目的收敛范围与文档分工见 [ADR-0124](0124-platform-consolidation.md)，本文仍负责应用构建方向、能力范围与 §9 边界 · 承接 ADR-0057、0069、0097

## 0. 这次变的不是功能，是产品定义

制定本文时，平台主要**承载原生业务应用**：CRM、MES、ERP 等应用跑在宿主上，构建者用工作台改页面、加字段、配流程。本文接受的方向是**一个能够构建、运行和持续演进完整业务应用的平台**——客户不需要我们预先写好的行业 Go 后端与 React 前端，就能按自己的业务建起并长期维护一套企业管理系统。后续已交付部分见各能力 ADR 的 As built，不能把本节的起点当作当前实现。

这意味着对待 `apps/*` 里现有原生应用的口径要正式改变：**它们是验证和完善平台的参考应用，不是产品形态**。`apps/mes`、`apps/erp`、`apps/crm` 的存在理由是当探针；当 FDE 能在工作台里构建出等价物时，它们应当逐步退出（沿 [Subtraction](../Subtraction.md)）。交付给客户的是**构建这类系统的能力**，不是这些系统本身。

三个结果判定成熟度，取代"内置了多少应用、提供了多少 Widget、存在多少 Action 类型"：

1. **能不能构建出来？** 从空项目到可上线应用，不写行业 Go/React 代码。
2. **能不能正确运行？** 复杂规则执行正确，没有权限绕过、关联业务不一致、错误状态变化、历史失真。
3. **能不能长期维护与演进？** 升级、诊断、恢复、在途业务语义保留。

## 1. 目标形态与唯一验收对象

```text
FDE Application Studio   理解业务 · 设计应用 · 配置规则 · 构建界面 · 验证发布
        │
        ├── MES / ERP / CRM / WMS / HCM / 其他行业应用   平台构建产物
        │
        └── 统一业务平台   业务模型 · 业务规则 · 业务执行 · 数据与集成 · 协同与 AI · 应用生命周期
                │
                └── Platform Kernel / Host   权威、权限、一致性、历史、运行与恢复
```

关键不在让所有应用长得一样，而在**开发、执行与治理机制统一**：不同工厂保留完全不同的生产流程、管理规则与操作界面，共用同一套语义、权限、发布与恢复。

**第一次真实交付是楼宇供暖，判据归 [ADR-0122](0122-first-real-delivery.md)；完整 MES 是第二验证场景**，不再是唯一验收对象。原 MES 范围由 [ADR-0113](0113-mes-baseline.md) 保留：基础主数据（产品/物料/设备/工作中心/生产组织）、工艺管理（路线/工序/工步/参数/版本）、生产管理（计划/工单/拆批/派工/执行）、现场执行（工作站/开工/过站/报工/完工）、异常与质量（暂停/返工/报废/检验/处置）、生产追溯（批次/人员/设备/物料/操作历史）、资源约束（设备能力/占用/人员资质/产能规则）、跨系统协同（ERP/WMS/APS/设备）。

**这些功能一条也不写进内核。** 构建 MES 的过程是**反向探测平台**：

| 撞墙处 | 要研究的通用能力 |
|---|---|
| 配不出设备能力校验 | 关系与约束能力 |
| 配不出返工 | 状态与业务决定能力 |
| 配不出专业工作站 | 界面构建与交互装配能力 |
| 处理不了多系统业务确认 | 通用协同与协议能力 |

始终求解通用缺口，不为 MES 增加特殊代码。复杂排程、路径优化、工业设备控制等专业算法仍走受控扩展（[ADR-0044](0044-capability-fabric.md)），不要求它们变成可视化规则。

## 2. 后端六个范围

本节记录转型时的后端范围与当时的缺口，不是当前待办清单。实现与剩余限制见 §8 所列各 ADR 的 As built；当前施工归 WorkQueue。重点是企业业务的通用表达与执行能力。

| # | 核心领域 | 目标 | 当时已有的能力（不重造） | 当时的缺口 |
|---|---|---|---|---|
| B1 | 完整的业务建模能力 | 自行定义对象、属性、关联、层级、业务版本、主数据与业务约束 | 对象/字段（ADR-0034）、共享本体与 Interface（ADR-0058）、企业模型（ADR-0067/0068）、计算字段（ADR-0064） | 层级与递归结构、业务版本（工艺路线式修订）成为一等概念、约束的表达与校验面 |
| B2 | 完整的业务规则与决定能力 | 复杂条件、关联判断、状态转移、多对象变化、业务计算，以及必须共同成功或失败的操作 | 生命周期与动作编译（ADR-0037）、决策表（ADR-0062）、过账与冲销（ADR-0063/0076）、公式（ADR-0064） | **多对象、多记录在一次决定内共同成立或共同失败**，跨对象条件与赋值，关联业务一致性 |
| B3 | 统一的业务权威与权限 | 不同应用、角色、入口遵守同一套授权与不可绕过的规则 | 行/字段/动作 scope（ADR-0028/0037/0066）、租户与授权（ADR-0078）、标记（ADR-0075） | 派生读取的闭包证明、跨应用委派、规则在所有入口一致执行的证据 |
| B4 | 可靠的业务流程与跨系统协同 | 审批、等待、重试、异常处理、跨应用交互、外部集成 | Flow/Work（ADR-0044/0047）、协议（ADR-0011）、外发效果与回写（ADR-0014/0072） | 多系统业务确认的统一表示、异常与补偿的表达、对账与结果不明的处置 |
| B5 | 业务版本与持续演进 | 应用、模型、工艺配置可升级；在途旧业务不因新版本失去原语义 | 不可变候选与激活（ADR-0039/0048/0097）、实例版本绑定、环境晋级 | 数据迁移的通用能力、扩展保留与退役、在途工作跨版本迁移 |
| B6 | 完整的应用运行与交付 | 构建出的应用可独立发布、运行、升级、监控、诊断、恢复、长期维护 | 宿主运行/恢复（ADR-0097/0038）、Runs、控制面板、Host Console | 以应用为单位的运行与诊断视图、容量与保留承诺、独立交付证据 |

**其中最重要的是 B2。** 客户在工作台配置 MES 的"工序完工"，平台必须能理解：完成当前工序、判断下一工序、处理质量异常、更新生产批次、必要时结束父工单、触发后续业务——而不是去调用一套写死的 MES 服务。目标是把业务规则做成平台**能理解和执行的正式定义**。多对象一致性必须走真实提交边界（[ADR-0046 §7](0046-application-studio-fusion.md) 的既有约束：跨记录原子操作须走真实提交边界，UI 规则不直接 mutate 对象），不能靠 UI 规则绕过。

## 3. 前端六个范围

FDE 应在统一环境中从零构建完整应用。本节与 §2 一样记录当时的设计范围；当前实现与体验验证边界归各能力 As built。

| # | 核心领域 | 目标 | 当时已有的能力（不重建） | 当时的缺口 |
|---|---|---|---|---|
| F1 | 统一 Application Studio | 围绕一个应用项目走完构建全程，不在割裂工具间反复跳转 | Shell、门户、投影（ADR-0052）、IDE 式工作空间（ADR-0054）、工作台模型（ADR-0055） | 围绕业务意图的连续工作流；六步流程只作设计起点，须真实用户验证 |
| F2 | 可视化业务领域建模 | 直接建立对象、属性、关系、主数据、关联结构，并看懂整个业务系统 | 对象模型工作台、Ontology 画布（ADR-0084/0085/0086）、企业画布 | 业务人员视角的领域总览，而非资产清单 |
| F3 | 可视化业务行为设计 | 在对象上定义状态、操作、条件、规则、异常、返工、审批与关联业务变化 | 对象编辑器（ADR-0037）、决策表、Flow 画布（ADR-0086/0087） | 把 B2 的多对象/关联规则表达出来；异常与返工是同一能力而非特例 |
| F4 | 完整的应用界面构建 | 数据管理页、专业操作台、表格、图表、工艺路线、业务详情、复杂交互 | 页面编辑器与原生插件（ADR-0046）、UI Kit（ADR-0004）、统一输入（ADR-0096） | 企业级专业组件（工艺路线/工作站/批次/审批），**以通用业务模型配置而非 MES 专用** |
| F5 | 数据、流程与 AI 的统一装配 | 把业务操作、数据来源、自动化、外部系统与 AI 组合进应用 | 集成织物（ADR-0070–0075）、Automate、AI Functions/Agents（ADR-0077） | 装配面统一；AI 与集成的入口在应用构建语境中而不在治理语境中 |
| F6 | 调试、预览、测试与发布体验 | 用真实业务样本验证操作、切换角色、检查结果、发现错误、完成发布 | 候选测试、沙箱预览、发布工作台（ADR-0040/0048）、统一输入 | 构建者以业务样本驱动验证；角色切换下的真实结果检查 |

两条硬要求：

1. **前端必须与业务模型真正贯通。** 客户定义了"设备属于工作中心""工序需要某些设备能力"，配置设备选择器时就应直接使用这些关系和条件，而不是重写一套前端逻辑（沿 ADR-0088 D4 的"服务端算、服务端拒、前端只显示"）。
2. **业务组件必须具备企业级表达能力，且只通过通用业务模型配置。** 工艺路线、工作站、设备关系、生产批次、审批流可以有专业呈现，但不能只能用于 MES。

现有 Workshop 能力（页面契约、原生插件、编辑器交互）继续复用并重组使用方式，**不另建平行前端框架**。

## 4. 明确的边界

**应该做的：** 完善通用业务语义、业务执行、领域建模、应用构建、界面装配、调试验证与完整交付能力。

**不应该做的：**

- 为通过测试硬编码 MES 规则；
- 把原生 MES 页面迁进 Workshop 冒充通用组件；
- 为新的 Studio 再建一套运行时；
- 重复实现 Kernel、Host、Flow、Release 已提供的基础设施；
- 为追求"零代码"而限制真正需要代码的行业算法与专业集成。

## 5. 四阶段

本节保留原转型阶段的重心与依赖，不是当前施工顺序。前端体验设计可以提前推进，**但核心业务正确性不能留到最后补救**。首次交付与执行者已由 ADR-0122 修订。

| 阶段 | 重心 | 判据 |
|---|---|---|
| 一 | **业务语义与执行正确性** | 构建出的应用能正确执行复杂规则：无权限绕过、关联业务不一致、错误状态变化、历史失真 |
| 二 | **真正完成全栈声明式构建** | 从业务模型贯通到表单、页面、操作台、自动化与发布；不依赖原生行业代码走通完整业务链路 |
| 三 | **FDE 工作台整体体验重构** | 构建者围绕业务意图连续工作，不必了解 Platform 内部组件与服务如何连接 |
| 四 | **完整行业应用的交付验证** | 首次供暖交付由负责人完成，MES 保留独立构建者的第二验证；验证与退出分别沿 ADR-0122、0113、0114 的条件判断 |

四阶段的执行顺序与停止条件只归 [WorkQueue](../WorkQueue.md)。逐块的接口、契约与兼容边界在实施时另立 ADR；本文不预置它们的实现细节。

## 6. 产品定位的正式表述

> Platform 是一个面向复杂组织和企业业务的应用构建与运行平台。它提供统一的业务语义、可靠的执行机制和完整的可视化构建环境，使 FDE、开发者及具备相应权限的业务构建者能够自主创造、交付和持续演进企业级应用，而不必为每个行业重新开发一套底层业务系统。

最根本的变化：**从"开发一套套业务软件"转向"开发生产业务软件的能力"。**

## 7. 对现有文档的影响

- [ADR-0069](0069-phase-two-coexist-absorb-replace.md)（共存→吸收→替代）的排序是**以我们的产品替代 SAP/Palantir**；本文确定的是**能力形态**——客户自己构建，未必由我们交付。两者不冲突：集成织物、业务核与 AI 运营是这套能力的组成部分，仍按原 ADR 的边界维护。本文修订的是它们的目标口径：业务核的"退出判据"不是"`core` 配置取代 `apps/erp` 采购链"，而是**构建者能在工作台内配出这条链**。
- [Platform §10.1](../Platform.md#101-目标终点构建者与参考产品) 与 [§10.6](../Platform.md#106-验收与证据) 的目标终点与验收维度描述的是"我们能交付什么行业方案"；本文补充的是"客户能构建什么"。两者的证据分别记录，不用其一代替另一。
- [Intent](../Intent.md) 的"应用是验证载体，不定义平台真理"保持有效；本文把它从研发取舍提升为**产品口径**：原生应用的逐步退出是预期路径，不是意外。
- 现有的 [Subtraction](../Subtraction.md) 清单继续有效。新增候选只在对应能力真正可替代时进入，不由本文直接开列删除项。

**关键路径是 0100 → 0101 → 0102 → 0104 → 0108**：没有业务事务与规则语言，后面的建模、界面、验证都无处附着。**0108 可以提前开始**（ADR-0098 §5 允许前端体验设计先行），但它的 Interface/Behavior 工作区在 0100–0104 落地前只能搭骨架，不得以"体验先行"为由绕过核心业务正确性。

**0119–0122 是交付形态与第一次真实交付**：其中 0122 **取代本文 §1 与 ADR-0113 的验收对象**——第一次交付是楼宇供暖（负责人不熟的领域），MES 降为第二探针。

**0123 补充协议能力包的运行与配置**：按需用 Go 实现，下游协议在独立网关运行；不改变 §9 的内核、权威与历史边界。模拟接入与 S7 本地读取已实现，工程范围与真实交付状态分别归该 ADR As built 和 ADR-0122。

**0118 覆盖 A–F 每一块**：它不交付功能，但它规定新能力如何声明自己对外的能力与依赖。任何 ADR 落地时若引入新的 `Capability` 或新的资产类型，先按 0118 登记，否则该项标为设计未完成。

依赖不应被读成完全串行：B 块与 C 块内部、D 块与 A/B 之间都有可并行的工作面。`0116`（AI 与人工）与 `0117`（拒绝与纠正）分别补齐了 §2 后端第 2 项与 §3 前端第 3、5 项此前只被隐含覆盖的部分。

## 9. 不可动的边界

本文与 0100–0118 讲的是**要变成什么**。下面讲**改了就是错的**——接手开发的人必须先读这一节，它优先于任何"顺手优化"。

### 9.1 内核与契约

1. **`contract/` 不含领域词汇。** Protobuf 不定义业务含义（AGENTS 硬规则 1、ADR-0002）。本次转型**不向内核加入事务、约束、记录集、业务版本等任何词汇**——它们是 `platform` 层的定义契约。
2. **内核变更先改规范与向量，再改实现。** 顺序不能颠倒；`v1` 语义变更须 ADR。
3. **`K4` 的权威边界不动：一项决策只改一个权威。** 跨权威原子性被 [ADR-0026](0026-decisions-across-apps.md) 明确否决，**本次不重开**。ADR-0100 扩大的是**单一权威内部**能改什么，不是权威的粒度。

### 9.2 提交与恢复

4. **权威状态的新写入必须经接受结果。** 不得新增绕过暂存 → 校验 → 持久接受 → 纯应用的直接修改路径（ADR-0097 §3.1）。事务是这条路径上的新内容，不是新的路径。
5. **恢复不重跑规则、不重新授权、不发起外部调用。** 恢复是应用已保存的映像（ADR-0038/0097），任何"恢复时重新判定"的实现在本程序里都是错误。
6. **历史永远可读。** 已产生的日志、旧格式、旧定义字节**不重写**；退役（字段/动作/应用）不等于删除读取义务（ADR-0106 §D2、ADR-0114 §D4）。

### 9.3 并发与持久化

7. **每租户单写者保留**，锁义务见 `capabilities/server/doc.go`。
8. **锁外 I/O 遵守 prepare → revalidate → accept**：只捕获固定定义、主体、来源与世代；锁外读写有界不可变字节；回锁复核当前权限、版本、前驱后再接受（ADR-0097 §5）。**不强制经过唯一串行 I/O 执行器。**
9. **不宣称跨系统 exactly-once**；外部效果是至少一次，靠稳定身份、接收方幂等与对账处理结果不明（Platform §10.3 D、ADR-0112）。

### 9.4 归属与门槛

10. **应用只导入 `platformserver/platform`**；跨应用走 `protocols/`；客户端只用 `@platform/ui` 与 `@platform/app`（AGENTS 硬规则 3）。`scripts/boundaries.sh` 与 `scripts/escapes.sh` 的**已知逃逸只减不增**——本次转型不得增加逃逸。
11. **生成文件不手改**：`contract/go/gen`、`web/packages/kernel/src/gen/host.ts`、`web/apps/catalog/src/gen`（AGENTS 硬规则 2）。宿主类型变化后运行 `go run ./cmd/api-types`；文案变化后补 `i18n/zh-CN.json` / 包内 `i18n.ts`，否则 `TestAPIContract`、`TestLanguages` 失败。
12. **不在宿主直接执行租户脚本**；租户扩展只走受控编译与执行（AGENTS 硬规则 5、ADR-0044）。
13. **零代码不是目标。** 真正需要代码的行业算法与专业集成走 ADR-0044 的受控代码，是合法构建手段（ADR-0098 §4）。

### 9.5 本程序自身

14. **替换，不是增量**（ADR-0100 §1.5）。不得让新旧两套表达长期共存；被取代的旧路径在本批冻结并登记退出。
15. **一个语义只有一个实现**（规则求值、约束检查、授权判定、依赖解析各一份）。
16. **自举约束**（ADR-0115）：新能力必须能被构建器用出来，否则记为未完成。

**这 16 条与 0100–0118 冲突时，以本节为准**；确需突破时先改本节并说明理由，不得在实现中静默越过。

## 10. 既有数据的共存（棕地）

本次转型不是"新租户才生效"。**已存在的租户、应用、记录与日志必须与新的内容模型共存**，规则如下（这是 0106 没有覆盖的部分——0106 管的是未来的升级，本节管的是当下的共存）：

1. **不重建开发期基线，不丢有效能力。** Platform §10.3 D 的既有许可保留：开发期日志可另建基线；**但真实客户数据永远不删**（Platform §10.3 D 的末句）。
2. **既有原生应用继续运行，直到其能力被构建产物接管**（ADR-0114）。它们**不**被改造为新的事务模型——改造等于把行业代码换个写法，违反 §4 与 0115。
3. **一个数据类别的写入路径同一时刻只有一条。** 某个应用的对象类型要么仍由它的 Go 实现写入，要么已交由构建产物写入；**不允许双写**（那正是 ADR-0100 §1.5 禁止的两个真相）。`apps/*` 的 `erp` 采购链这类"重叠"对象，按 ADR-0114 的顺序整链退出，不逐字段迁移。
4. **本地两宿主（酒店 8495、制造 8490）保留原数据卷**（AGENTS 沙箱规则 6）。转型期间它们的升级走 `deploy/local/update.sh`，**不做数据重建**；需要重建时先备份并显式声明。
5. **旧的开发者草稿可以不可编辑。** 中间态允许"旧定义的草稿不能在新编辑器里改"（ADR-0100 §1.5 已声明中间态允许难看）；但**旧定义的运行与读取不受影响**。
6. **迁移是替换的一部分**（0100 §1.5 约束 2）：每个能力块落地时，它取代的既有数据如何处置（继续读 / 一次性迁移 / 保持冻结）必须在该块的 As built 里写明，不得留作未说。

## 11. 未决

当前实现与剩余限制归各能力 ADR 的 As built，施工顺序和块的范围唯一归 WorkQueue。原来等待首批实施的事务、依赖描述与平台文档同步已有后续实现，不再列为本 ADR 的未决任务；资产类型及兼容范围见 [ADR-0118 As built](0118-blocks-and-dependencies.md#as-built)。真实交付与负责人使用仍按 ADR-0122 记录，不能从工程实现推定完成。

## 12. 交给开发者的交付指引

**本节保留首次实施 ADR-0100 的历史方案与验证理由，不再指挥当前施工。** 该能力已有实现和完整单据/恢复证据，见 [ADR-0100 As built](0100-business-transaction.md#6-as-built--完整业务事务)；当前工作取 WorkQueue。

**当时的第一块 = ADR-0100 的最小切片**（验证整个程序依赖的接受结果能力）：

- 一个构建器定义的事务，含**三种**步骤：`create`、`update`、`sequence`（不做 Kind 全表、不做 `ForEach`）；
- 场景形状：头 + 2 行 + 编号，一次动作产生**一个**接受结果；
- 必须证明的五件事：
  1. 多对象类型、多条记录在**一个**接受结果里落盘（`record-batch`）；
  2. 任一步失败 → 一条不落盘、编号未占、无效果意图；
  3. 同键同内容返回原答复，同键异内容冲突；
  4. 进程崩溃后重新打开，按前驱恢复并**逐字节重现**同一结果；
  5. 跨应用的对象类型混进一个事务 → 明确拒绝。
- **当时优先验证的假设**：接受结果能承载跨对象类型的事务且恢复语义不变。它决定了随后业务语言和界面的实现依据；现有结果见 ADR-0100，而不是重新从该切片开始。

**首次实施时同时确认的三件事**（保留原预算、前驱和授权检查的理由）：

- 1 MiB 接受结果预算（`maxAcceptedResultBytes`，`accepted_result.go:26`）对这个单据形状够不够；不够时**先按 ADR-0100 §D4 显式拒绝**，把真实数字报回来，不要偷偷提高预算。
- `Before` 前驱校验（`accepted_batch.go:31`）在跨对象类型的批次上是否仍然成立。
- 事务的逐步骤授权（ADR-0100 §D3.5）在私有上下文里能否拿到"本事务更早步骤产生的记录"。

**后续交付**：实现与替代的旧路径写在对应 As built；§8 说明依赖，WorkQueue 决定下一块。每块的停止条件写在它自己的验收节，不在这里复制。

**交付方式**：按 AGENTS 整块交付（一次做完一个可交付的整块），检查按影响面选（Go 宿主 → `make check` + 对应 `make test-go`）；纯文档 → 链接与 `git diff --check`。未运行的检查、未观察的 UI 不得报为通过。
