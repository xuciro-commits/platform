# ADR-0098 — 产品是构建业务应用的能力：下一阶段的转型目标与开发范围

状态：方向已接受（2026-10-12，负责人指令）；后端/前端十二个范围只定边界与判据，逐块落地另立 ADR，执行顺序唯一归 WorkQueue · 承接 ADR-0057（一个工作台构建完整应用）、ADR-0069（共存→吸收→替代）、ADR-0097（提交、资产与宿主收敛）

## 0. 这次变的不是功能，是产品定义

平台今天是一个**承载业务应用的平台**：CRM、MES、ERP 等原生应用跑在宿主上，构建者用工作台改页面、加字段、配流程。下一阶段平台要变成**一个能够构建、运行和持续演进完整业务应用的平台**——客户不需要我们预先写好的 Go 后端与 React 前端，就能按自己的业务建起并长期维护一套企业管理系统。

这意味着对待 `apps/*` 里现有原生应用的口径要正式改变：**它们是验证和完善平台的参考应用，不是产品形态**。`apps/mes`、`apps/erp`、`apps/crm` 的存在理由是当探针；当 FDE 能在工作台里构建出等价物时，它们应当逐步退出（沿 [Subtraction](../Subtraction.md)）。交付给客户的是**构建这类系统的能力**，不是这些系统本身。

三个结果判定成熟度，取代"内置了多少应用、提供了多少 Widget、存在多少 Action 类型"：

1. **能不能构建出来？** 从空项目到可上线应用，不写行业 Go/React 代码。
2. **能不能正确运行？** 复杂规则执行正确，没有权限绕过、关联业务不一致、错误状态变化、历史失真。
3. **能不能长期维护与演进？** 升级、诊断、恢复、在途业务语义保留。

## 1. 目标形态与唯一验收对象

```text
FDE Application Studio   理解业务 · 设计应用 · 配置规则 · 构建界面 · 验证发布
        │
        ├── MES / ERP / CRM / WMS / HCM / 其他行业应用   平台构建产物
        │
        └── 统一业务平台   业务模型 · 业务规则 · 业务执行 · 数据与集成 · 协同与 AI · 应用生命周期
                │
                └── Platform Kernel / Host   权威、权限、一致性、历史、运行与恢复
```

关键不在让所有应用长得一样，而在**开发、执行与治理机制统一**：不同工厂保留完全不同的生产流程、管理规则与操作界面，共用同一套语义、权限、发布与恢复。

**唯一验收对象是完整 MES**，不是"能跑三道工序的演示"。基准范围：基础主数据（产品/物料/设备/工作中心/生产组织）、工艺管理（路线/工序/工步/参数/版本）、生产管理（计划/工单/拆批/派工/执行）、现场执行（工作站/开工/过站/报工/完工）、异常与质量（暂停/返工/报废/检验/处置）、生产追溯（批次/人员/设备/物料/操作历史）、资源约束（设备能力/占用/人员资质/产能规则）、跨系统协同（ERP/WMS/APS/设备）。

**这些功能一条也不写进内核。** 构建 MES 的过程是**反向探测平台**：

| 撞墙处 | 要研究的通用能力 |
|---|---|
| 配不出设备能力校验 | 关系与约束能力 |
| 配不出返工 | 状态与业务决定能力 |
| 配不出专业工作站 | 界面构建与交互装配能力 |
| 处理不了多系统业务确认 | 通用协同与协议能力 |

始终求解通用缺口，不为 MES 增加特殊代码。复杂排程、路径优化、工业设备控制等专业算法仍走受控扩展（[ADR-0044](0044-capability-fabric.md)），不要求它们变成可视化规则。

## 2. 后端六个范围

后端下一阶段的重点不是继续增加行业业务接口，而是补齐企业业务的通用表达与执行能力。

| # | 核心领域 | 目标 | 现有零件（不重造） | 缺口 |
|---|---|---|---|---|
| B1 | 完整的业务建模能力 | 自行定义对象、属性、关联、层级、业务版本、主数据与业务约束 | 对象/字段（ADR-0034）、共享本体与 Interface（ADR-0058）、企业模型（ADR-0067/0068）、计算字段（ADR-0064） | 层级与递归结构、业务版本（工艺路线式修订）成为一等概念、约束的表达与校验面 |
| B2 | 完整的业务规则与决定能力 | 复杂条件、关联判断、状态转移、多对象变化、业务计算，以及必须共同成功或失败的操作 | 生命周期与动作编译（ADR-0037）、决策表（ADR-0062）、过账与冲销（ADR-0063/0076）、公式（ADR-0064） | **多对象、多记录在一次决定内共同成立或共同失败**，跨对象条件与赋值，关联业务一致性 |
| B3 | 统一的业务权威与权限 | 不同应用、角色、入口遵守同一套授权与不可绕过的规则 | 行/字段/动作 scope（ADR-0028/0037/0066）、租户与授权（ADR-0078）、标记（ADR-0075） | 派生读取的闭包证明、跨应用委派、规则在所有入口一致执行的证据 |
| B4 | 可靠的业务流程与跨系统协同 | 审批、等待、重试、异常处理、跨应用交互、外部集成 | Flow/Work（ADR-0044/0047）、协议（ADR-0011）、外发效果与回写（ADR-0014/0072） | 多系统业务确认的统一表示、异常与补偿的表达、对账与结果不明的处置 |
| B5 | 业务版本与持续演进 | 应用、模型、工艺配置可升级；在途旧业务不因新版本失去原语义 | 不可变候选与激活（ADR-0039/0048/0097）、实例版本绑定、环境晋级 | 数据迁移的通用能力、扩展保留与退役、在途工作跨版本迁移 |
| B6 | 完整的应用运行与交付 | 构建出的应用可独立发布、运行、升级、监控、诊断、恢复、长期维护 | 宿主运行/恢复（ADR-0097/0038）、Runs、控制面板、Host Console | 以应用为单位的运行与诊断视图、容量与保留承诺、独立交付证据 |

**其中最重要的是 B2。** 客户在工作台配置 MES 的"工序完工"，平台必须能理解：完成当前工序、判断下一工序、处理质量异常、更新生产批次、必要时结束父工单、触发后续业务——而不是去调用一套写死的 MES 服务。目标是把业务规则做成平台**能理解和执行的正式定义**。多对象一致性必须走真实提交边界（[ADR-0046 §7](0046-application-studio-fusion.md) 的既有约束：跨记录原子操作须走真实提交边界，UI 规则不直接 mutate 对象），不能靠 UI 规则绕过。

## 3. 前端六个范围

FDE 不应是一个集中管理各类编辑器的工具箱，而应是能从零构建完整应用的统一环境。

| # | 核心领域 | 目标 | 现有零件（不重建） | 缺口 |
|---|---|---|---|---|
| F1 | 统一 Application Studio | 围绕一个应用项目走完构建全程，不在割裂工具间反复跳转 | Shell、门户、投影（ADR-0052）、IDE 式工作空间（ADR-0054）、工作台模型（ADR-0055） | 围绕业务意图的连续工作流；六步流程只作设计起点，须真实用户验证 |
| F2 | 可视化业务领域建模 | 直接建立对象、属性、关系、主数据、关联结构，并看懂整个业务系统 | 对象模型工作台、Ontology 画布（ADR-0084/0085/0086）、企业画布 | 业务人员视角的领域总览，而非资产清单 |
| F3 | 可视化业务行为设计 | 在对象上定义状态、操作、条件、规则、异常、返工、审批与关联业务变化 | 对象编辑器（ADR-0037）、决策表、Flow 画布（ADR-0086/0087） | 把 B2 的多对象/关联规则表达出来；异常与返工是同一能力而非特例 |
| F4 | 完整的应用界面构建 | 数据管理页、专业操作台、表格、图表、工艺路线、业务详情、复杂交互 | 页面编辑器与原生插件（ADR-0046）、UI Kit（ADR-0004）、统一输入（ADR-0096） | 企业级专业组件（工艺路线/工作站/批次/审批），**以通用业务模型配置而非 MES 专用** |
| F5 | 数据、流程与 AI 的统一装配 | 把业务操作、数据来源、自动化、外部系统与 AI 组合进应用 | 集成织物（ADR-0070–0075）、Automate、AI Functions/Agents（ADR-0077） | 装配面统一；AI 与集成的入口在应用构建语境中而不在治理语境中 |
| F6 | 调试、预览、测试与发布体验 | 用真实业务样本验证操作、切换角色、检查结果、发现错误、完成发布 | 候选测试、沙箱预览、发布工作台（ADR-0040/0048）、统一输入 | 构建者以业务样本驱动验证；角色切换下的真实结果检查 |

两条硬要求：

1. **前端必须与业务模型真正贯通。** 客户定义了"设备属于工作中心""工序需要某些设备能力"，配置设备选择器时就应直接使用这些关系和条件，而不是重写一套前端逻辑（沿 ADR-0088 D4 的"服务端算、服务端拒、前端只显示"）。
2. **业务组件必须具备企业级表达能力，且只通过通用业务模型配置。** 工艺路线、工作站、设备关系、生产批次、审批流可以有专业呈现，但不能只能用于 MES。

现有 Workshop 能力（页面契约、原生插件、编辑器交互）继续复用并重组使用方式，**不另建平行前端框架**。

## 4. 明确的边界

**应该做的：** 完善通用业务语义、业务执行、领域建模、应用构建、界面装配、调试验证与完整交付能力。

**不应该做的：**

- 为通过测试硬编码 MES 规则；
- 把原生 MES 页面迁进 Workshop 冒充通用组件；
- 为新的 Studio 再建一套运行时；
- 重复实现 Kernel、Host、Flow、Release 已提供的基础设施；
- 为追求"零代码"而限制真正需要代码的行业算法与专业集成。

## 5. 四阶段

顺序只表达重心与依赖，不表示完全串行——前端体验设计可以提前推进，**但核心业务正确性不能留到最后补救**。

| 阶段 | 重心 | 判据 |
|---|---|---|
| 一 | **业务语义与执行正确性** | 构建出的应用能正确执行复杂规则：无权限绕过、关联业务不一致、错误状态变化、历史失真 |
| 二 | **真正完成全栈声明式构建** | 从业务模型贯通到表单、页面、操作台、自动化与发布；不依赖原生行业代码走通完整业务链路 |
| 三 | **FDE 工作台整体体验重构** | 构建者围绕业务意图连续工作，不必了解 Platform 内部组件与服务如何连接 |
| 四 | **完整行业应用的独立交付验证** | 未参与底层开发的 FDE 从空白项目构建、测试、交付并升级 MES；验证通过后逐步退出相应原生参考实现 |

四阶段的执行顺序与停止条件只归 [WorkQueue](../WorkQueue.md)。逐块的接口、契约与兼容边界在实施时另立 ADR；本文不预置它们的实现细节。

## 6. 产品定位的正式表述

> Platform 是一个面向复杂组织和企业业务的应用构建与运行平台。它提供统一的业务语义、可靠的执行机制和完整的可视化构建环境，使 FDE、开发者及具备相应权限的业务构建者能够自主创造、交付和持续演进企业级应用，而不必为每个行业重新开发一套底层业务系统。

最根本的变化：**从"开发一套套业务软件"转向"开发生产业务软件的能力"。**

## 7. 对现有文档的影响

- [ADR-0069](0069-phase-two-coexist-absorb-replace.md)（共存→吸收→替代）的排序是**以我们的产品替代 SAP/Palantir**；本文确定的是**能力形态**——客户自己构建，未必由我们交付。两者不冲突：集成织物、业务核与 AI 运营是这套能力的组成部分，仍按原 ADR 的边界维护。本文修订的是它们的目标口径：业务核的"退出判据"不是"`core` 配置取代 `apps/erp` 采购链"，而是**构建者能在工作台内配出这条链**。
- [Platform §10.1](../Platform.md#101-目标终点构建者与参考产品) 与 [§10.6](../Platform.md#106-验收与证据) 的目标终点与验收维度描述的是"我们能交付什么行业方案"；本文补充的是"客户能构建什么"。两者的证据分别记录，不用其一代替另一。
- [Intent](../Intent.md) 的"应用是验证载体，不定义平台真理"保持有效；本文把它从研发取舍提升为**产品口径**：原生应用的逐步退出是预期路径，不是意外。
- 现有的 [Subtraction](../Subtraction.md) 清单继续有效。新增候选只在对应能力真正可替代时进入，不由本文直接开列删除项。

## 9. 未决

- **WorkQueue 的排序**：本次未改动 [WorkQueue](../WorkQueue.md)。它当前只保留 W4 的独立接手与体验验收；ADR-0100–0118 是否在其后开启、以什么顺序开启，以及 W4 是否先收口，由负责人决定后写入队列。ADR 只定依赖，不定批次。
- **每一块的规模与拆批**：本文与后续 ADR 定了边界与判据，具体拆批（含 XXL 内部的分批）在 WorkQueue 立项时确定。
- **平台架构文档的同步**：Platform §10 与 §2.4 的能力地图尚未反映本文的产品口径（"客户能构建什么"）。它应在第一批落地时随实际实现更新，而不是现在预先改写——避免文档写出尚未成真的状态。
- **0118 的资产类型扩展**：`AssetRef`/`AssetKind` 需要容纳事务、约束、记录集等新资产类型。新增哪些 kind、如何保持向后兼容，归 0118 落地时确定；本文不预先枚举。
