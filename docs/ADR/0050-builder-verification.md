# ADR-0050 — 构建者验证：用真实业务样本证明它能跑

<a id="adr-0050"></a>

状态：已接受（2026-10-12，负责人指令，ADR-0038 D 块第四份，对应前端第 6 项）· 取代 ADR-0047 的固定样本测试与 ADR-0015 的 `simulate` 在**构建者日常验证**上的地位：既有实现保留为底层机制，但从"提交后测试"变为"构建中随手可用" · 与 ADR-0045（迁移计划）、ADR-0046（交付）配套

## 0. 意图

ADR-0038 第三阶段要的是：构建者能"用真实业务样本验证操作、切换角色、检查结果、发现错误并完成发布"。

本决定解决原先必须先封存候选才能试跑、缺少应用样本管理和多成员结果对照的问题。现已实现草稿试跑、样本集与多成员对照，具体支持范围见 §5。页面预览只读，业务动作由隔离试跑或正式运行执行；不能再按旧预览的真实提交方式理解当前构建器。

**判据**：构建者能在**构建过程中**（不必先发布）用一套业务样本试跑一次操作、以一个指定角色的身份看结果、看到每一步发生了什么、然后把问题带回去修。

## 1. 决定

### D1 草稿级试跑：不发布也能验证

- 试跑的对象是**草稿闭包**（当前应用的全部草稿资产），不是候选。今天 `Tenant.SimulateCandidate` 针对候选（ADR-0047 21d 的"空内存租户的固定样本"，明确"非物理沙箱"）；本 ADR 增加**草稿级试跑**，走同一个隔离机制。
- **隔离性与候选试跑完全相同**：空内存租户、固定样本、不触碰生产状态、不产生外部效果（沿 ADR-0047 21d 的既有边界）。
- 试跑**不产生权威定义变更**：它是私有上下文里的一次执行，结果不落盘为业务记录。

### D2 以角色身份试跑

```go
type TrialRun struct {
    As       []Roles     // 以哪些角色/成员身份跑（可多个，逐个跑同一场景）
    At       Time        // 业务时间（ADR-0042 的有效期判定用）
    Sample   SampleSet   // 业务样本（见 D3）
    Steps    []TrialStep // 依次执行：取记录、执行动作/事务、读取
}
```

- **同一场景在多角色下各跑一次**，并**并排显示差异**：谁看得到、谁做得了、谁被拒、拒绝原因是什么。这是"权限闭包"在构建期的可用形态（ADR-0044 的 `Layers` 直接呈现）。
- 身份来自**受控的模拟主体**（沿 `simulation_owner.go` 的既有机制），不是"假装我是管理员"。

### D3 业务样本是一等资产

- **样本集**（`SampleSet`）是应用的一等资产：一组对象/记录/关系的具体值，属于应用的草稿与版本；
- 样本**不来自生产数据**（`simulate.tsx:212` 的既有边界），由构建者准备或从模板生成；
- 样本随应用版本走，因此"这一版跑通的场景"可复现；
- **样本可在试跑中修改**（试跑是隔离的），修改不回流到样本定义，除非构建者显式保存（这是明确的选择：试跑不应意外改样本）。

### D4 每步可见

试跑结果必须显示每一步的：输入、被调用的规则与它读到什么、判定结果（ADR-0044 的 `Layers`）、约束检查（ADR-0041 的约束名）、产生的记录变化（ADR-0039 的事务步骤逐个）、以及被阻断的原因。

**"哪一步不对"必须在构建期可见**，而不是发布后在生产单据上猜。这是 ADR-0038 第一阶段判据（"不存在权限绕过、关联业务不一致、错误状态变化"）的发现机制。

### D5 从试跑到发布的连续路径

```text
草稿试跑（D1–D4） → 候选（复用 ADR-0011） → 迁移计划（ADR-0045） → 交付（ADR-0046）
```

- 试跑通过**不自动**使候选通过：候选仍是独立的封存与审查（沿 ADR-0011）。
- 但试跑的场景**可以保存为候选测试**（`TestPlan` 的既有形态），因此回归有据可依。
- **不新建第二套测试体系**：`build.testplan` 保留，草稿试跑是它的前置阶段，两者共用样本集与步骤表达。

### D6 预览态与生产态的同一性

预览复用正式页面的绑定、展示规则和校验，并阻止业务写入；需要验证实际动作时进入隔离试跑或正式运行。试跑与正式运行使用同一原执行器与规则，差异是数据与身份；**不允许另做前端宽松规则模拟器**（ADR-0048 §2 的第一条不做）。

## 2. 不做

- **不做物理沙箱**（隔离进程/容器）：沿 ADR-0047 21d 的既有边界，候选执行是共享进程内的隔离；物理隔离是更大范围的工程（Platform §10.3 D 的租户级承诺），不在本 ADR 承诺。
- **不做生产数据脱敏副本**：样本由构建者准备或从模板生成。需要真实数据形态的验证走环境晋级（ADR-0046 D4）。
- **不做前端规则模拟器**（见 D6）。
- **不做"运行时暂停生产改定义"**：试跑是隔离的，生产定义只通过候选改变。

## 3. 后果

- 构建循环从"发布-测试-回改"缩短为"试跑-回改"，这是本 ADR 最主要的收益，也是 ADR-0047 第三阶段体验重构的关键支撑。
- 试跑需要**草稿闭包**能被隔离执行——即 `AssetDraft` 的完整形状能在私有 scope 构造（沿 ADR-0037 §7 的 `BeginAssetBootstrap` 既有机制）。这是一次真实的工程收敛，不是新机制。
- 多角色并排结果的呈现是新的界面工作（归 ADR-0047 的 Verify 工作区）。
- 样本集成为资产后，Catalog（ADR-0014）可以收录"业务样本场景"作为装配资产。

## 4. 验收

1. 构建者在**未发布**的状态下试跑"工单完工"事务，看到每一步的记录变化、命中的规则、约束检查与结果。
2. 同一场景以三个不同角色各跑一次，并排显示谁看得到、谁做得了、拒绝原因（来自 `Layers`）。
3. 试跑不触碰生产状态：试跑前后生产记录字节不变、无外部效果产生、无权威定义变更。
4. 样本集随应用版本保存；重跑同一版本的同一场景结果一致。
5. 试跑中的临时数据修改不回流样本定义，除非显式保存。
6. 试跑场景可保存为候选测试（`TestPlan`），并成为回归证据。
7. 反例：在预览里通过但生产被拒的场景 → 必须能定位到是数据/身份差异，不是语义差异（用一条对照测试锁住）。

测试：宿主 simulate owner 的既有测试扩展 + `make check-web` + 一条 e2e 路线；`docs/Testing.md` 增"构建者验证"手测行。

## 5. As built

工程主线已实现，构建者从应用 **Verify / 验证** 工作区进入 **Draft trial / 草稿试跑**。原 `POST /v1/simulate/candidate`、`build.testplan` 与空内存租户继续是唯一执行路径。

- **应用闭包**：`Build.ApplicationDrafts` 沿原 release descriptor 的 `Requires` 遍历应用可达草稿，包含已安装资产的当前草稿；未引用的租户草稿不纳入。闭包最多 128 份草稿，由原联合候选编译器冻结。构建者试跑不保存候选、不激活定义；封存候选可按 ID 重跑。
- **样本归属**：`build.sample-set` / `sample-set` 归 Build，按稳定名称保留至多 64 个不可变版本，依赖样本对象模型，应用通过原 `Resources` 引用。候选激活、工件投影与恢复沿原 asset lifecycle。最多八类模型、每类 100 条、每条 32 KiB、总计 256 KiB；记录与引用均由构建者准备，不从生产复制。新建进入原专用编辑器；普通记录复用保存模型的原动作字段表单，ID 与生命周期状态单独填写，复杂值与故意错误的输入保留高级 JSON。编辑试跑输入不会调用样本保存；只有 **Save application sample / 保存应用样本** 更新原定义。定义保存与加入应用分别处理，关联失败重试同一记录，不覆盖同时加入的其他成员。
- **真实身份对照**：最多三名不同的已知成员，在同一份冻结定义、固定时间与样本上分别运行独立租户；不构造额外角色或扩大权限。结果并排显示读取、操作、拒绝及原授权 Layers，分别显示每位成员与每一步是否符合预期；预期拒绝不等于测试失败，整体结果综合全部成员。固定测试摘要包含定义、输入、主体与当时的权限材料。
- **原执行器解释**：观察原 `EvaluateRule` 的表达式、实际引用值与来源，原授权决定、具名约束及事务步骤/记录前后值。观察器只在隔离租户启用，不参与接受或持久化；不可读字段和被拒绝读取的记录 ID 不进入解释，相同读取拒绝合并以免泄露隐藏行数。拒绝的暂存写入明确标为回滚，提交结果只列该步可读的变化。每步解释最多 512 项 / 1 MiB，过大事实或达到预算时显示截断标记，执行结果保持原语义。
- **连续场景**：原 `TestPlan` 增应用、样本、对照成员和固定候选版本，以及读取步骤；试跑输入可保存并重载为同一测试计划。本地计划只指定具名样本时沿原运行器加载样本，不用空数组覆盖；临时输入与显式清空仍可单独选择。应用试跑提供原运行器已支持的推进时钟步骤，可创建合成记录、推进固定时间、再读取流程结果；读取步骤不推进时间。保存对象修订后，候选动作输入随之更新，不继续使用应用修订未变时的旧字段。结果可旁边打开原模型、动作或流程编辑器，原测试页和输入保留。通过不产生候选评审或激活资格。对象、流程和函数的原固定测试入口继续使用同一个 runner。
- **业务场景交付**：原 `build.testplan` 现可用具名对象/流程 `roots` 保存为 `test-plan` 资产，保留固定时间、合成记录和原类型化步骤；不携带本地草稿、成员或模型绑定。具名范围保存后固定，应用新增成员不自动扩大原计划；编辑器显示范围并可明确改用当前应用的对象和流程。应用工件沿原 Samples 投影携带版本。AI 的 `evaluation-set` 保持原格式与实测要求，两者共用原 TestPlan 发布与保留实现。应用 New 菜单的新业务测试计划进入 Verify 的原编辑器，保存后关联原资源；关联失败重试不重复修改已保存计划。轮询不覆盖未保存输入，下拉切换计划不被原 URL 重新载回。包内计划沿同一入口编辑、试跑和发布；旧本地计划继续使用原语义。
- **闭包内的非执行资产**：样本、评测、迁移与集成声明保留在私有应用闭包里，不导入其生产连接、凭据、数据集或迁移运行。业务步骤只允许候选对象和原 AI 固定测试入口；带普通审批动作的 Build 模型使用原 Work 的独立测试实例，不再仅因含审批声明而整件拒绝。原生业务动作、原生 Flow 与复杂原生 scope 仍需要对应隔离 owner，缺失即拒绝，不能转调生产；未扩展真实外部调用。

证据：`TestApplicationTrial` 覆盖未发布完工事务、已发布依赖的当前草稿、无关草稿排除、闭包内数据集声明、三身份结果、后续步骤拒绝后的整笔回滚、规则/约束/权限解释、不可读字段、生产快照字节不变、受控主体/样本/构建入口反例、同一场景保存为 TestPlan、封存后草稿变化不影响结果、候选激活及恢复重跑，并对照同一生产事务的拒绝。原 Go owner 测试、`make check`、Web 包测试及 `application-studio` 浏览器证据保留。样本与计划的界面更新通过 `make check-web`、`TestLanguages` 与 `builder-verification` 原两条业务任务：正常 New 入口、类型化样本、未完成 JSON 阻止运行、定义保存后关联失败重试、其他成员保留、旧具名样本及可交付转换、多成员预期拒绝/不匹配、返回编辑器后未保存输入保留；角色结果桌面/390px 画面已查看。另一任务从空白应用经普通界面配置未发布对象、事务动作与状态触发流程，Validate 后保存/重载测试计划，创建合成记录、推进时钟并读取完成状态与实际流程轨迹，核对原草稿和正式定义未变。独立 FDE 与负责人体验走查仍待进行，不把这些工程证据视为完整 MES、真实模型质量或原生退出验收。
