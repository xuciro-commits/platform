# ADR-0059 — 设备与黑盒目标：派发、状态回读与人工介入

<a id="adr-0059"></a>

状态：已接受（2026-10-12，负责人指令）· 协议能力包运行与配置由 ADR-0061 补充（2026-10-15）· 扩展 ADR-0051（跨系统协同）与 ADR-0004（出站效果）的执行面 · 补齐"下一次交付"（仓储与 AGV：立库 RCS、AGV WCS、黑盒下游指令）所要求的**形状预留**（ADR-0057 §6 规则 2） · 与 ADR-0058（观测）、0055（拒绝）配套

协议实现见 [ADR-0061](0061-pluggable-protocol-packages.md#11-as-built)：模拟包与 S7 只读子集已在独立 Go 网关运行；模拟命令接入本文原派发、未知结果与回读，真实 S7 写入尚未开放，现场控制边界不变。

## 0. 意图

第一次交付（楼宇供暖）里已有门禁与设备联动；**下一次交付已确定**（负责人 2026-10-12）：大疆的 MES + WMS，要管立库 RCS、AGV WCS，并与下游做**黑盒集成**——"给下游发指令，比如 A 到 B"。

这与 ADR-0051 写的"请求-回执-对账"**形状不同**：

- 发给设备/AGV 的指令**没有业务回执**（对面不是业务系统，是控制器）；
- 长任务是常态（一次搬运要几十秒到几分钟），**"没回"不等于失败**；
- 指令有**物理后果**（会动、会撞、会夹）。

**判据**：构建者能表达"把 A 的货送到 B"，能看到它在途/完成/卡住/失败，能在卡住时介入；**并且平台从不假装它能保证设备一定执行**。

## 1. 与 ADR-0051 的区别

| | Confirmation（ADR-0051） | 设备/黑盒指令（本文） |
|---|---|---|
| 对面 | 业务系统（ERP、WMS、APS） | 控制器 / 库系统 / 黑盒下游 |
| 回执语义 | 有：接受、拒绝、附答复 | **多数只有状态**：已收、执行中、完成、失败、卡住 |
| 时长 | 秒到小时 | 秒到分钟（长任务） |
| 一致性 | 至少一次 + 对账 | **至少一次 + 状态回读**（不重发危险指令） |
| 人的角色 | 裁决部分成功 | **介入卡住的任务** |

**共同点**：都**不宣称 exactly-once**（ADR-0038 §9.3、Platform §10.3 D），都靠稳定身份 + 接收方幂等 + 对账。

## 2. 决定

### D1 指令是一等业务记录，不是"一条效果"

```go
// 一条下发到设备/黑盒目标的指令。
type Dispatch struct {
    Subject  TxnRef      // 业务主体（运单、搬运任务、门禁请求）
    Target   Endpoint    // 目标（设备/库系统/AGV 控制器/黑盒下游）
    Command  string      // 声明过的指令名（不是自由文本报文）
    Payload  []Set       // 参数（ADR-0040 的表达式求值）
    Key      string      // 幂等键（稳定，来自业务主体）
    Deadline Time        // 业务截止（ADR-0051 §D1 的语义）
    OnStuck  string      // 卡住时：escalate | compensate | retry | manual
    OnFail   string      // 失败时：同上
}
```

- **指令是声明过的**（`Command` 来自声明的指令表），不是任意报文。任意报文会让平台无法判断幂等与重发安全。
- 指令的**状态、尝试、回读结果**都是业务记录，因此**可查、可审计、可恢复**（不是运行期易失状态）。
- 指令的**幂等键来自业务主体**（如运单 ID），因此重发同一个搬运请求不会产生第二次搬运——**前提是目标侧也遵守幂等**；平台不假设、不承诺（D5）。

### D2 状态回读（对账）是必需的，不是可选的

因为多数控制器不返回业务回执，**"发出去了"与"做到了"之间只能靠回读**：

- 指令可以声明**状态回读方式**（读某个观测测点、查目标的查询接口、读它的状态记录）；
- 回读是**受属作业**（复用 ADR-0007、ADR-0027 的机制），按声明周期运行；
- 回读结果写回业务记录（`dispatch` 记录的状态字段），因此**卡住能被发现**；
- **结果不明（unknown）与失败（failed）区分**（沿 ADR-0051 §D4 的既有决定，扩展到设备）。

### D3 硬边界：控制回路不在平台（**这条最优先**）

**安全联锁、急停、闭环运动控制、实时调速——永远在设备/网关/PLC 本地。**

平台做的是**派发与回读**：它告诉目标"做什么"，然后看"做到没有"。平台**不**参与毫秒级的闭环，**不**承担实时性，**不**作为安全链路的一环。

这条必须在使用文档与构建器里写明。**不写死的后果**：第一次做 AGV 就会有人想在平台上做路径闭环——那是一条会伤人的错误。

平台也**不**检测"指令是否会撞"——那是目标侧/WCS 的职责；平台只传递业务意图与约束（例如"必须先出库后入库"由 ADR-0040 的规则表达）。

### D4 人必须能介入

- `OnStuck` / `OnFail` 的处理**必须显式声明**（与 ADR-0051 §D2 同一要求）：升级（通知角色）、补偿（反向指令）、重试、或**人工**。
- **人工介入是一等路径**：被授权成员可以裁定一条卡住的指令（重发、改目标、标记完成、取消）。走 work 的既有任务/审批机制（ADR-0007）。
- **卡住必须可见**：运行面显示在途指令、卡住的时长、原因（来自回读）。

### D5 重发的安全性分级

重发不是都安全：

| 指令类别 | 重发语义 | 声明要求 |
|---|---|---|
| **幂等**（查询状态、设置目标位置） | 可安全重发 | 声明 `Idempotent: true` |
| **需目标侧幂等**（创建搬运任务，带业务键） | 可重发，**依赖目标侧按业务键去重** | 声明业务键；文档说明依赖 |
| **不可安全重发**（开门、启动动作） | **禁止自动重发**；失败进入人工 | 声明 `Idempotent: false`；平台**拒绝**在自动重试策略里配置它 |

**平台必须能拒绝**："给一个不可安全重发的指令配置自动重试"在**发布期**就是错误。这是本 ADR 最实用的一条。

### D6 目标不是业务应用：协议与凭据

- 目标（设备、控制器、黑盒下游）**不是平台的应用**，没有对象类型，不需要实现协议（ADR-0006）——它是**外部端点**；
- 目标的**地址与凭据是环境绑定**（沿 ADR-0016、ADR-0046）；报文格式与协议栈由**能力包**封装（ADR-0057：设备对接是能力包，例如"AGV/RCS 接入"、"黑盒下游 HTTP/TCP 对接"）；
- **协议适配不在平台包内实现**：业务宿主只到"指令 + 参数 + 状态"这一层；具体 Go 协议包与独立网关按 ADR-0061 开发，通过原 Writeback/Dispatch 接入。

### D7 为下一次交付预留的形状（ADR-0057 §6 规则 2 的实例）

**下一次交付已命名**（仓储与 AGV），因此允许预留**形状**，不允许预留领域词汇：

| 预留什么 | 形态 | 不做什么 |
|---|---|---|
| 指令种类的扩展点 | 一个具名的 `Dispatch` 声明（`Command` 来自声明表） | 不预置"AGV""库位""RCS"等名称 |
| 状态回读的扩展点 | 一个具名的回读声明（读观测 / 查接口 / 读记录） | 不实现任何具体协议 |
| 目标类别的扩展点 | 一个具名的端点类别（设备/库系统/黑盒下游） | 不做第二套集成机制 |
| 数字化容器的对接 | **不预留**（负责人明示"很边缘的地方就不用再搞预留"） | — |

**预留的检查标准**（沿 ADR-0057 §6 规则 4）：三天后能插进来即为合格；**留下空方法、假支持或未接通入口即视为缺陷**。

## 3. 不做

- **不做闭环运动控制 / 实时控制**（D3）。
- **业务宿主不做协议栈**（D6；具体协议按 ADR-0061 属独立能力包或外部库，不另建派发权威）。
- **不做"设备一定执行"的承诺**（§0）。
- **不做安全联锁的软件实现**（D3）。
- **不为未命名的交付预留**：除 D7 表内的四项，其他（如"未来可能接机器人"）不留形状。

## 4. 后果

- 第一次交付（供暖的门禁与设备联动）即可用最小版：`Dispatch` + 状态回读 + 人工介入。**不等下一次交付。**
- 下一次交付（仓储与 AGV）落地时，需要新增的是**能力包**（协议封装、设备对接）与**行业包**（仓储的对象骨架与规则模板），平台包只补 D7 的形状与实现——这正是 ADR-0057 §6 预留的目的：**改内核很麻烦，改能力包不麻烦**。
- 运行面需要"在途指令"视图（ADR-0046 §D3 的一部分）。
- 与 ADR-0058 的连接：设备状态回读天然读的是**观测**（温度、位置、状态码），因此 0058 的观测读取形状要支持 D2 的回读。

## 5. 验收

1. 一条指令声明 + 派发 + 状态回读 + 完成：业务记录反映真实状态，卡住能被发现。
2. **不重发断言**：把一条 `Idempotent: false` 的指令配置自动重试 → **发布期拒绝**。
3. **结果不明**：回读拿不到状态时进入 `unknown`（不是 `failed`），与 ADR-0051 一致，且人工可裁定。
4. **人工介入**：卡住的指令指派到角色，成员在任务里裁定，结果写回业务记录。
5. **边界断言**：使用文档与构建器里明确"控制回路不在平台"（用文档检查 + 构建器提示的存在性证明）。
6. **预留检查**：D7 的四项各有形状声明且**无实现**；检查是否有空方法/假支持（有则缺陷）。
7. **反例**：为边缘情况（数字化容器等）预留形状、在平台内实现协议栈、把目标做成一个平台应用 → 分别拒绝。

测试归宿主 effects 与 work owner 包；`docs/Testing.md` 增"设备派发"手测行；`docs/Apps.md` 增可执行用法。

## As built

指令表由原业务对象的 `dispatchCommands` 声明，事务以 `BusinessTxn.dispatch` 选择具名命令、逻辑目标连接、标量参数、来自主体的稳定键、业务截止和异常策略。参数使用 ADR-0040 的同一表达式求值器。发布拒绝未声明命令、缺少回读、缺少复核角色、不安全自动重试和未声明反向命令；确认与设备派发各自保持明确语义，同一事务不能混用。指令属于原对象/动作资产，依赖由同一 `DescribeAsset` 从冻结绑定产生，沿原候选保存和激活，不增加内核类型、资产 kind 或独立发布入口。

封存对象中的目标、Writeback 和回读来源使用原集成 owner 的逻辑名称；安装、激活及保留版本执行通过同一 `integrationID` 解析成目标环境的本地 ID。对象内容版本按同一逻辑名称计算，换环境不改变源候选字节，也不携带源地址或密钥。`TestDeviceDispatchPromotesWithTargetLocalIntegrations` 用不同 ID、地址与凭据的两个环境检查晋级、目标激活、派发与回读完成。

运行记录是 `build.dispatch`，主体事务、指令和效果意图在原接受结果里一起保存。状态、目标、稳定键、尝试、最近回读及原请求/定义分别留存。专用 `Writeback.On = dispatch` 只提供原连接的请求映射，不再走普通动作订阅或答复字段回写；HTTP 接受仅表示 `accepted`，完成必须来自声明的状态回读或授权人工证据。具名端点类别是能力适配的声明，具体协议栈和设备名称不进入平台包。

ADR-0061 的协议请求由原派发填写运行/尝试身份、业务键、有效期、连接修订与包摘要；业务映射只提供具名命令和值。网关保存发送前的最小技术收据，同次尝试不再发送，HTTP 200 的 unknown 仍保留未知；原配置回读不被新版地址映射替换。模拟器验证了答复丢失后靠新鲜状态完成，S7 包只读。

派发复用原效果队列、连接环境和 `effect-result`。不能安全重发的命令在发网络前先持久接受开始尝试；追加失败不发送，发送中断后保持 `unknown`，重开后不自动再次发送。HTTP 临时错误也不能把它变成通用自动重试；效果控制台的直接操作被原派发审核取代。幂等或明确依赖目标侧按业务键去重的命令保留原安全重试机制，各次尝试使用相同业务键，反向命令使用独立补偿键。平台不承诺设备执行成功或 exactly-once。

必需回读支持原 Source、Observation 和有读取权限的业务状态记录，按具名映射得到 accepted / running / completed / stuck / failed / unknown。复用原来源循环，读取在租户锁外，接受前复核运行修订、当前权限及相关记录变化；原始观测点不保存。未找到、歧义、未映射和读取失败均保留 `unknown`，不冒充设备失败。业务截止由原受属作业检查；卡住/失败按声明手工、通知、可安全重试或发送已声明的反向命令处理。

同次尝试的状态、值、原因和证据均未变化时，后续回读不再追加接受结果，不改写首次证据时间；业务截止仍按原声明处理。与业务确认共用 `statusReadSchedule` 的到期、占用、每轮预算及清理，锁外读取前后共用申请人、来源发布者、凭据和相关记录世代的一致性比较；状态含义、当前授权、候选及证据解释仍归原派发代码。读取间隔和并发占用只留在租户临时缓存，按尝试身份区分，结束后清理；重启后继续读取并与原已接受证据比较。人工重发或补偿的首次状态独立留存，旧读取仍须复核修订和权限，不能覆盖人工裁定。`TestDeviceDispatchStatusWritesOnlyChanges` 覆盖重复状态/错误、间隔、并发读取、截止、重放后继续读取、新尝试及人工完成。

人工处置沿原 work 任务分配到当前角色。成员必须能读取主体并提交证据，才能重发、改目标、标记完成或取消；AI 不能代替人裁定。原收件箱与记录页对派发任务的直接 Done 按钮已替换为 Review dispatch，避免任务已完成而指令仍未处理。构建器、业务记录、任务引用和应用运行页共用原入口及同一进度卡，显示状态、等待/卡住时间、原因和尝试记录。构建器与使用说明明确控制回路、安全联锁、急停和实时控制归设备/网关/PLC；取消业务记录不代表设备已经停止。

改目标的候选接口只给当前复核者返回已就绪目标的 ID 和名称，不要求授予连接管理权限，也不返回地址与凭据；它加入原实时读取机制。窄屏显示当前完整工作组，回桌面恢复原分栏。派发记录默认展示进度与处理，原始字段及历史放在折叠的技术详情中。

既有业务确认、普通 Writeback 和旧不可变发布继续按原语义读取与运行，原历史字节不重写。设备派发不复用业务确认的 accepted→confirmed 结论，也不新建第二套外部集成、调度或任务系统。Source/Observation/记录读取是已接通的状态读取方式；D7 的具体 RCS、WCS、HTTP/TCP 能力适配仍只有领域中立的声明位置，没有空方法、假协议支持或未接通的产品入口。

工程检查：`make check`、相关宿主/Build/platform 测试及 `device-dispatch` 浏览器路线通过；已查看桌面与 390 宽度截图。覆盖不安全重试发布拒绝、未知结果不重发、真实文件日志关闭重开、三类状态读取与补偿证据区分、普通复核者的目标选择/重发/改目标/完成，以及不同环境晋级。HTTP 控制器和观测适配器使用受控本地服务；模拟协议与 S7 本地读取的补充证据见 ADR-0061。真实设备与客户现场尚未接入，本批未重跑 PostgreSQL 故障恢复，也不代替负责人体验验收。
