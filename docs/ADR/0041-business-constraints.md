# ADR-0041 — 业务约束：模型自带的不变式

<a id="adr-0041"></a>

**状态：** 现行 · 2026-10-12 · 约束是模型自带的不变式。

## 0. 意图

ADR-0040 管"这一次操作在什么条件下允许"。它管不了另一类要求：**不论谁、从哪个入口、用什么方式写，某些事实永远不能成立**。

- 单据编号在租户内唯一且不跳号；
- 已下达工单的工艺版本不可改；
- 有未归档子记录的库位不能被归档（今天靠 `record_archive_links.go:14,37-73` 的孤儿检查兜住了一部分）；
- 工序要求的每一项设备能力都必须被资源持有（今天只在 `apps/mes` 的 `canDo` Go 函数里，见 ADR-0060 D4）；
- 数量必须为正；结束时间不早于开始时间；关账期间的日期不被接受。

这些今天散落在三处：Go 结构体标签（`platform/entity.go` 的 `Required`/`Ref`/`Choices`）、宿主记录写入的零散检查（`records.go:588-603` 引用校验）、以及**行业应用的 Go 代码里**。于是同一个规则在不同入口（记录表单、CSV 导入、AI 动作、协议写入、事务步骤）**执行得不一样**，而"不同入口执行不一样"正是 ADR-0038 §0 第二个判据要消灭的东西。

**判据**：一条约束声明一次，在**所有**写入路径上以同一实现、同一拒绝码、同一原因文本生效。

## 1. 与 ADR-0040 的分工

| | 条件（ADR-0040） | 约束（本 ADR） |
|---|---|---|
| 位置 | 动作/事务上 | 对象类型、字段、关系上 |
| 语义 | "这次允许吗" | "这个事实能成立吗" |
| 谁执行 | 该动作的执行 | 每一次写入，无论来自谁 |
| 能否带消息 | 可以（构建者写的失败消息） | 可以（约束自带说明） |
| 能否被绕过 | 不适用（它本身就是门禁） | **不能**；不存在"跳过约束"的入口 |

两者共用 ADR-0040 的表达式语言。约束不重复条件的表达力，它只是**把条件挂到模型上**。

## 2. 决定

### D1 约束是模型的一部分，写在对象类型上

```go
// 对象类型声明的约束（buildapi.Object.Constraints）
type Constraint struct {
    Name    string   // 稳定名，出现于拒绝码与原因
    Kind    string   // required|unique|range|pattern|expression|cardinality|immutable|temporal
    Fields  []string // 涉及的字段
    Expr    *Expr    // 0040 的表达式；expression / range / pattern 用
    Message string   // 给人读的原因（英文原文 + zh-CN，沿 ADR-0005）
    Translations map[string]string // 可选的 zh-CN 原因；发布内容的一部分
    Scope   string   // 唯一性的作用域：tenant | parent | <path>（见 D3）
    Level   string   // record（默认）| txn（见 D4）
    Reads   *RuleReadSpec // 固定的本应用查询/版本/父绑定；只接受 complete
}
```

### D2 八类约束，语义各自明确

**每一类在多个领域下都用得上**；下表给出跨行业的实例，证明它们不是为某个行业定制的：

| 类型 | 制造业 | 酒店 | 贸易/零售 | 专业服务 |
|---|---|---|---|---|
| required | 报工时必填数量 | 确认预订必填房价方案 | 出库必填承运商 | 结案必填工时 |
| unique | 同一工单下行号唯一 | 同一房型同一天不重复放房 | 同一 SKU 同仓批次号唯一 | 同一项目内计费单号唯一 |
| range | 结束不早于开始 | 入住不早于预订 | 折扣 0–100% | 计费率不超合同上限 |
| pattern | 批次号格式 | 房号格式 | 条码格式 | 案件编号格式 |
| expression | 工序要求能力 ⊆ 设备能力 | 房型容量 ≥ 入住人数 | 库存 ≥ 出库量 | 指派顾问具备该资质 |
| cardinality | 库位下有子记录不可归档 | 房型下有房态记录不可删 | 供应商有在途单不可停用 | 客户有在执行合同不可归档 |
| immutable | 已下达工单不可改工艺版本 | 已入住不可改房价 | 已过账不可改金额 | 已签署不可改条款 |
| temporal | 报工时间落在班次内 | 入住时间落在有效期内 | 促销价落在有效期内 | 计费落在合同期内 |

1. **required**：字段在记录成为"生效"状态时必须非空。注意与今天的 `FieldInfo.Required` 区别——后者是**表单必填**，这里是**存储不变式**；两者不互相代替。
2. **unique**：字段组合在 `Scope` 内唯一。**作用域是一等参数**：租户级（编号）、父记录级（同一工单下的行号）、或沿路径（同一物料下的替代料顺序；同一房型同一天的房态）。**并发下的唯一性由编号序列或宿主加锁保证，不由"先查再写"保证**——先查再写是竞态，不能作为实现。
3. **range / pattern**：值域与形态（数值区间、日期区间、文本模式）。区间端点可以是表达式，所以"结束不早于开始"是 range 的一个实例，不需要新机制。
4. **expression**：任意 ADR-0040 表达式必须为真。全量求值，读不到的字段使约束**拒绝并说明**（不是静默通过）。
5. **cardinality**：关系上的基数（沿用 `platform/link_type.go:16-45` 的 `Cardinality` 与 `DeletePolicy`），并补一条今天缺的语义：**基数约束在关系写入时检查，与记录写入同一事务**（今天 relations 是独立应用的决策，`platform/relations.go:38-43`，所以关系与记录不原子）。
6. **immutable**：字段一旦离开初始状态即不可改（已下达工单的工艺版本）。**immutable 的判定依据是状态与历史，不是"当前值是否为空"**。
7. **temporal**：日期/时间表达式必须为真，例如 `within-period` 检查包含两端的有效期；采用本次提交固定的时间上下文，不读取外部时钟或系统。

执行细节：`required` 在对象没有生命周期或记录离开初始状态时生效；数值 0 与布尔 false 是已提供的值，空白文本、null 和空集合为空。`immutable` 检查写入前的状态与已保存状态历史；返回初始状态也不解除锁定。`range`、`pattern`、`expression`、`cardinality`、`temporal` 使用布尔 Expr；文本模式复用 ADR-0040 的 `matches`，不建立第二个模式执行器。

### D3 作用域与"父"的含义

`Scope` 里的父沿**已声明的引用路径**解析（复用 `record_path.go`）。这使"同一工单下唯一"、"同一批次下序号连续"这类真实的行业约束可以声明，而不需要为每个行业加 Go 代码。

唯一性以对象类型为命名空间，默认 `tenant`；`parent` 只有在该对象恰好一个标量引用字段时可用，否则须选择明确路径（最多 16 段）。组合中有空值时不占唯一键，非空要求另行声明；归档不释放键。检查覆盖完整的本应用私有记录库，由租户单写者把检查与接受串在一起，不以调用者可见窗口代替唯一性。

### D4 记录级与事务级

- `Level: record`（默认）：在**每条记录写入时**检查，适用于唯一、非空、类型、基数。
- `Level: txn`：在**事务的全部步骤应用之后、落盘之前**检查，适用于跨记录的不变式——"借贷合计相等"（ADR-0026 §1 的容差 0.005）、"工序序列连续"、"批次总数量等于各行之和"。

单条动作、导入行、受权 AI 动作和协议提供方决定也有确定的接受边界，因而同样执行事务级门禁。最终检查包括受已声明路径/查询影响但没有直接修改的记录；例如改单行数量也必须重查其父单的合计。与本次写入无关的旧记录不会触发历史清洗。

**两级都必须存在。** 只有记录级则跨记录约束写不出来；只有事务级则单条记录写入（含 CSV 导入、AI 动作）没有兜底。当事务级约束失败，整个事务拒绝（ADR-0039 §D3），不留部分状态。

### D5 约束不可被入口绕过

所有改变权威状态的路径都经过同一约束检查点：

| 入口 | 今天的检查 | 本 ADR 后 |
|---|---|---|
| 标准动作（create/edit/archive） | 结构体标签 + 零散检查 | 约束 |
| 构建器事务（ADR-0039） | 无 | 约束（逐记录 + 事务级） |
| CSV 导入（`POST /v1/import/{type}`） | 部分 | 约束；违规行**整行拒绝并报告**，不静默跳过 |
| AI 提议的动作 | 走标准动作 | 同标准动作 |
| 协议写入（跨应用） | 宿主通用检查 | 提供方应用的约束（在自己的权威内检查） |
| 历史恢复 | **不重跑** | 不重跑（沿 ADR-0010、ADR-0037）。约束只在**新写入**时执行 |

**历史恢复不重跑约束**：今天能读的历史必须永远能读。约束收紧后，旧记录可能"违反"新约束——这是允许的，**约束是写入门禁，不是历史清洗**。需要修数据的场合走显式的更正事务。

### D6 拒绝的形状

每次拒绝返回：约束名、涉及字段、**为什么**（可读消息，英文 + zh-CN）、以及**当前值**（在调用者有权限读取的范围内）。今天的 `CONFLICT`/`POLICY_DENIED` 错误码保留，约束拒绝使用独立的可区分码，便于前端就地把字段标红（沿 ADR-0048 的输入错误路径，`ErrorBody`）。

## 3. 不做

- **不做数据库触发器式的副作用**：约束只能拒绝，不能改数据。
- **不做跨应用约束**：约束的作用域是**本应用的全部类型**。需要跨应用的条件走 ADR-0051 的协同与对账，或在 ADR-0039 §3 的应用合并中消失。
- **不做约束的运行时开关**：约束随定义版本走，不能在租户里临时关掉。关闭一条约束=发布一个新版本（走候选、试装、激活），这样"什么时候变了"永远可查。
- **不做异步校验**：约束在提交路径上同步执行。一个需要外部系统才能判断的规则不是约束，是协同（ADR-0051）。

## 4. 后果

- 行业应用里手写的守卫（`apps/mes` 的 `canDo`、`reworkable`，`apps/erp` 的过账平衡）逐步迁到约束声明，Go 代码按 ADR-0053 退出。**迁移时必须证明新旧拒绝结果一致**，否则会出现"以前能过的现在过不了"。
- 唯一性从"先查再写"变成编号序列或加锁：现有 `platform.Sequence`（ADR-0026）是编号唯一的正解，其他唯一约束需要宿主提供同等强度的机制，不能退化成查询。
- 基数约束与关系写入的原子化要求 relations owner 与记录写入共用同一提交边界（ADR-0039 的账本），这是 relations 应用当前的独立决策形态（`accepted_relations_test.go:44-47` 显示它落 owner state）需要改的地方；具体归 ADR-0043。
- 导入路径的行为变化是可见的：以前静默跳过的违规行现在整行拒绝。这是有意的，但需要在发布说明里写明（开发期日志基线可重建，沿 Platform §10.3）。

## 5. 验收

1. 同一组约束（唯一编号、正数量、结束不早于开始、已下达不可改工艺）在以下入口各测一次，拒绝码与原因一致：标准动作、构建器事务、CSV 导入、AI 动作、协议写入。
2. 事务级约束（借贷平衡、行数量合计）在一部分步骤被拒时使整个事务消失，编号未占、无分录、无效果意图。
3. 唯一性并发：并发的同值写入只有一个成功，另一个得到约束拒绝；不得出现两个都成功。
4. 历史：收紧约束后，已有违反约束的历史记录**仍可读取与恢复**；新写入被拒。
5. 基数与关系：关系写入与记录写入在同一个接受结果内落盘（失败时一起消失）。
6. 反例：未知约束种类、作用域路径超出 16 段、事务级约束出现在无法判定事务边界的上下文 → 发布期拒绝。

测试归宿主与 build owner 包；`docs/Testing.md` 增"业务约束"手测行。

## 6. As built

对象上的 `Constraints` 已贯通受控定义、生成 Entity、草稿、冻结候选与激活；构建器对象编辑器的“Business constraints / 业务约束”沿原 DraftSession、共享输入 buffer、撤销/重做与发布菜单保存，不另建运行时。约束与其读取依赖封存在原 object 资产中；它没有独立可调用的能力，Expr 是 pure，唯一可写入口仍是原 action/transaction（ADR-0057）。组合与发布检查种类、字段、类型、路径、完整查询、同应用归属及接受边界；每对象最多 64 条，每条 1–16 个字段，原因每种语言最多 512 字节。

所有新记录写入在原 `stagedDecision.Put` 检查记录级约束，非恢复的 live runtime 写入明确拒绝；同一 `checkConstraint` 实现于接受前检查事务级及受影响的关联记录，读取实际私有视图，任一步失败使记录、编号、效果意图和观察全部消失。唯一性在完整私有库加锁检查，包含归档记录；只读/缺失事实明确拒绝。关系实例采用原引用字段存储，创建头和两行的引用与记录在同一个 `record-batch` 接受结果内共同落盘。独立 `relations` 图与 M:N 的替换仍归 ADR-0043；既有原生应用按 ADR-0038 §10 保留运行，不把它们改写为新模型冒充退出。

影响发现与求值仍分开：`checkFinalConstraints` 将原依赖路径准备一次，关联检查复用同一结果，不再逐记录重复解析。一个类型的全部约束只读取本行时，只排序并检查本次写入且最终仍存在的记录；Reads、引用 scope、路径、集合与窗口继续按原完整类型扫描和 `constraintDepends` 判断，未命中不求值。类型、记录和约束的拒绝顺序不变；唯一性比较仍读取完整私有库，归档记录仍参与。当前私有库没有 Versioning 类型时不再遍历原库搜集无人使用的 pins；有版本类型时继续原固定版本及声明集合检查。没有新增持久索引或第二套求值器，也未消除关联规则的全局遍历。

`BenchmarkFinalConstraintScan` 在 Apple M3 Pro / darwin-arm64、GOMAXPROCS=12 上测量已准备私有决定的最终检查：同 owner 的 N 条记录、每条 3 个成功表达式约束，另有 1 条无约束记录，本次仅写 1 行。当前实现下，1,000 / 10,000 / 100,000 条记录的无关写入分别为 0.329 / 0.317 / 0.308 µs/op；直接写约束记录分别为 95.615 / 90.596 / 87.904 µs/op。100,000 条单行检查不再承担优化前所测的 46.914 ms 全量候选扫描。已有决定 trace 实测并断言每次求值仍为 0 / 3，而非 N×3。数据准备不计时，最终检查包含版本检查入口；此数据没有 Versioning 类型、实际历史 pins、唯一性或关联集合，不含完整提交、持久化及并发压力。每项计时 100 ms，100,000 条直接写入为 1,366 次迭代；这是本行规则候选选择的局部成本证据，不是关联规则、版本固定或生产容量承诺。

拒绝复用原 `FieldIssue`/`ErrorBody`：宿主码 `CONSTRAINT_VIOLATION`、issue 码 `constraint_violation`、稳定约束名、记录引用、字段及 relatedPaths、英中原因、读取范围内的有界值与失败类别。内核保留 `ERROR_CODE_INVALID_ARGUMENT`，未扩展契约词汇。拒绝事实按原接受结果路径保存为 refusal v3，同键重试返回原决定，旧 v1/v2 字节仍可恢复；发送诊断时再次过滤当前行/字段权限。CSV 每行明确返回 Error 与问题；空白单元格表示清空，不能静默保留旧字段。预览在私有副本执行同一门禁，不应用到权威状态；业务约束没有跳过开关。

棕地与替换：旧已发布定义、记录和日志不迁写；新约束只影响新写入，收紧后旧违规记录仍可读取与恢复，不在恢复时求值。新模型的不变式归统一约束门禁，表单 Required/InputConstraints 保留输入语义，原行业 Go 守卫按 ADR-0060、ADR-0053 的等价构建产物退出，不形成新模型的第二写入实现。完整规则可视化编辑归 ADR-0048，本块用已有 JSON 输入编辑复杂 Expr 与固定查询集合。

验收证据：`TestBusinessConstraintsAllWriteEntrances`（四种不变式 × 标准动作、事务、CSV 预览/导入、受权 agent 动作、协议；另测忽略 Put 错误与 live runtime 绕过）；`TestBusinessConstraintsTransactionTotalsAndReferenceCardinality`（合计与借贷 0.005 容差、单行改变触发父记录门禁、归档基数、同一接受结果、编号回滚与恢复）；`TestBusinessConstraintsUniqueConcurrentAndHistory`（并发唯一、状态返回仍锁定、收紧后历史恢复）；required/pattern/temporal/父作用域与空 CSV、关联来源改变和遮蔽字段反例；平台与 Build 的发布/冻结反例。`rule-language` 浏览器路线走构建器配置 → 冻结候选 → 激活 → 重复值拒绝、保留输入 → 更正成功。
