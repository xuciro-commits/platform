# ADR-0042 — 业务版本与业务时间：主数据不是种子

<a id="adr-0042"></a>

**状态：** 现行 · 2026-10-12 · 业务版本与业务时间是机制，不是种子数据。

## 0. 意图

客户要配"这道工序要用这台设备、这个温度、这一版工艺"，平台必须能回答三个问题：

1. 这条工艺**现在**是哪一版？
2. 三个月前下达的那张工单，**当时**用的是哪一版？
3. 改工艺会不会动到已经在车间里的批次？

今天的答案：`Routing{ID, Name, Version int, Operations}` 是 `apps/mes` 的 **Go 内存种子**（`apps/mes/server/mes.go:81-84`），`(ID, Version)` 是键，`SFC` 下达时固定 `Routing` + `RoutingVersion`（`mes.go:189-192`），`released()` 读批次自己的版本、`routingFor()` 读最新版（`mes.go:292-298`）。**机制是对的，位置错了**——它在行业 Go 代码里，别的行业要重来一遍；而且 ADR-0060 D5 自己写明"主数据仍是种子、无落库、无权限、无变更台账"。

**判据**：构建者能用平台定义的机制建一张带版本的工艺路线表，下达单据时**自动**固定版本，改版本不动在途单据；全程不写行业 Go 代码。

## 1. 现状：我们有几种"版本"，各管什么

| 概念 | 类型 | 管的什么 | 证据 |
|---|---|---|---|
| 记录修订 | `Record.Revision uint32` | 并发控制：编辑时校验没被别人改过（K4 C12） | `platform/entity.go:27`；`records.go:402,418,434` |
| 定义发布 | `ReleaseAsset`/`AssetBinding`/`ReleaseCandidate` | 构建产物：规范字节 + 内容 ID + 闭包 | `platform/revision.go:16-45` |
| 实例绑定 | Flow 实例持有的启动版本 | 在途流程不因新版发布改语义 | `flow_binding.go:22-58` |
| 业务版本 | **无** | — | — |
| 业务时间（valid time） | 内核 K4 有 `valid_time` 字段，业务层未使用 | — | `contract/spec/K4-change-record.md` |

所以今天"改一版工艺让它对**新单据**生效、对**旧单据**无影响"这件事，客户**没有可用的原语**，只能像 MES 那样自己在 Go 里造。

## 2. 决定

### D1 业务版本是一等字段属性，不是新对象类型

对象类型可以声明一个**版本键**（`versionKey`）与**生效策略**：

```go
// 对象类型上的声明（buildapi.Object）
type Versioning struct {
    Key        string   // 业务标识
    Version    string   // 版本字段：integer 或 text（如 v1/v2 或 A/B/C）
    ValidFrom  string   // 生效业务时间
    ValidUntil string   // 失效业务时间（可空）
    Pin        string   // 固定策略：none | on_create | on_state:<state>
}
```

**这套机制不针对任何行业。** 同一份声明在四个不同领域下的样子（都不需要代码）：

| 领域 | `Key` | `Version` | 用途 | 单据如何固定 |
|---|---|---|---|---|
| 制造业 | 工艺路线编号 | 1、2、3 | 改工艺不动在途批次 | `Pin: on_state:released` 固定到工单 |
| 酒店 | 房价方案编号 | 2026-A、2026-B | 调价不动已确认订单 | `Pin: on_create` 固定到订单 |
| 零售/贸易 | 价格表编号 | 季度版本 | 促销价到期自动失效 | `ValidUntil` + `Pin: on_create` |
| 专业服务 | 合同模板编号 | 修订号 | 改条款不动已签合同 | `Pin: on_state:signed` |

- `(Key, Version)` 唯一（约束实例，ADR-0041 D2 unique with `Scope: tenant`）。
- `Pin: on_create` 表示：**引用它的单据在创建/进入指定状态时把版本写进自己的字段**，此后不再跟随。
- 平台**不**替业务决定该固定哪一版——那是业务语义。平台提供机制：固定=把版本值写进单据，并在单据上声明它是从哪条记录固定来的。
- 引用单据声明 `VersionPins: [{Reference: "routing", Version: "routingversion"}]`，明确引用字段和接收版本的字段；接收字段由平台设为只读。来源的 `Pin` 决定何时自动复制所选记录的版本，不用字段名猜测，也不自动挑选“最新版”。固定收据随单据记录保存来源、版本值与固定时间。
- 版本**不是**"对象类型的版本"（那是发布候选的职责），也**不是**"记录修订"（那是并发控制）。三者不可互代。

### D2 业务时间（effective time）与记录时间分开

内核早有 `valid_time`（业务发生时间）与 `recorded_time`（记录时间）的区分。业务层今天只用后者。

- 对象可以声明 `ValidFrom`/`ValidUntil` 字段，构成**业务有效期**。
- 读取默认只返回**当前有效**的行（`ValidFrom <= $now < ValidUntil`），并且这是一个**可关闭的默认**，不是硬编码过滤：查询可以显式要求"当时的有效集合"。
- 企业模型（ADR-0022）已经在做这件事（`From/Until`、`ActualOrganizationRole` 的生效期，ADR-0022 的"当天有效且 stereotype 相符"校验），本 ADR 把它统一为**同一套业务时间语义**，不建立第二个时间模型。

**不做双时态。** 平台提供"按业务时间看当时的集合"，不宣称提供完整 bitemporal 数据模型（这是 Platform §10.3 D 已有的边界，本文不变）。

### D3 主数据必须落库

本 ADR 实施前，MES 工艺路线主要依赖内存种子，缺少普通记录的权限、历史与变更管理。

决定：主数据是**普通对象类型 + 普通记录**，走同一套权限、约束、历史与恢复。参考应用里的 `DemoMaster()` 种子（`apps/mes/server/mes.go`）降级为**演示数据**，不能作为产品形态。

- 种子仍可存在（测试与演示需要可重现基线），但**产品路径必须是记录**。
- 普通主数据落库解决原 0032 的持久管理问题；它不把 `core.person` 与企业模型的 `ActualPerson` 自动合成一条记录。两者保留各自语义与权威，现行边界见 ADR-0022，不新增双向同步任务。

### D4 引用版本必须跟着走

ADR-0041 D2 的 immutable 约束（已下达工单的工艺版本不可改）与 ADR-0039 的事务一起使用：

- "下达"是一个事务：创建工单 + 写 `Routing` + `RoutingVersion` + 创建第一批工序行；
- "工艺版本不可改"是对象类型上的 immutable 约束；
- "哪些工序可用"由 ADR-0040 的表达式对**该工单自己固定那一版的**工序集合求值——不是对"最新版"求值。

今天 `released()` 与 `routingFor()` 的双路径（`mes.go:292-298`）正是这个语义，但它写在 Go 里且只有 MES 有；本 ADR 使它成为可声明的机制。

### D5 版本的退役

业务版本可以**失效**（`ValidUntil`），不能删除（沿 ADR-0020、ADR-0022 的历史保留）。失效后：新单据不能引用它；已有单据继续按它执行；界面把它显示为"已失效"并标注日期（沿 ADR-0022 的已关闭元素标注，`ElementPicker` 的既有做法）。

## 3. 不做

- **不做 BOM 展开/多级版本的专用引擎**。多级版本（产品 → 工艺 → 工序 → 参数）用普通引用表达；展开是 ADR-0040 的聚合或事务步骤，不是新原语。
- **不做通用有效期的自动清理**：过期数据不删。
- **不做价格/税率的专门版本对象**。价格是带 `Versioning` 的普通对象，具体规则（哪个客户哪个价）由约束与表达式表达。
- **不把企业模型改成通用版本对象**：它保持自己的 UAF 形态，只统一业务时间语义。

## 4. 后果

- MES 的主数据从 Go 种子迁到记录（`apps/mes/server` 的 `MasterData`、`DemoMaster` 进入 ADR-0053 的退出清单）。
- 前端需要"版本与有效期"的呈现与编辑（工艺路线的版本切换、单据上的"已固定版本"标注），归 ADR-0048。
- 主数据落库后，权限与历史立即继承现有机制——不需要新能力，这是"复用主人"的一例。
- 风险：把"版本"当成万能解释。约束是 §3 的"不做"清单；评审时看的是**有没有在途单据受影响的语义**，不是有没有版本字段。

## 5. 验收

1. 构建者定义一张带 `Versioning` 的工艺路线表（记录，非种子），发布后在页面上建两个版本。
2. 下达工单：工单固定当时的版本；此时发布第三个版本，工单的工序集合不变，新工单用新版本。
3. 单据上"已固定版本"在界面上可见并标注；试图改一个已下达工单的工艺版本被 immutable 约束拒绝。
4. 业务时间：查询默认返回当前有效行；显式查询返回当时有效集合；失效版本不可被新单据引用，已有单据仍可读。
5. 历史与恢复：主数据的每一次变更走正常决策与恢复路径；重启后逐字重现。
6. 反例：(Key, Version) 重复、ValidUntil 早于 ValidFrom、引用已失效版本创建新单据 → 分别拒绝并给出原因。

测试归宿主与 build/core owner 包；`docs/Testing.md` 增"业务版本"手测行；MES 的对应迁移路线归 ADR-0060。

## As built

`platform.Versioning` 与 `VersionPinBinding` 已接入普通对象、Build 草稿、发布/候选、宿主安装及生成类型。业务标识与版本必须是必填字段，版本为 integer / text；有效期为同类型 date / datetime。业务标识和版本共同降低为原 `unique` 约束；记录归属方保留其身份，拒绝倒置或空起点的有效期。发布后不能撤去或改变既有版本/固定声明。普通记录的权限、历史、接受结果和恢复共用原路径，没有新增版本对象或版本账本。

引用单据通过声明映射自动固定版本，支持 `on_create` 和 `on_state:<state>`。固定在原计算与校验之前准备，普通动作和事务写入共用同一准备实现；保存结果包含实际版本值及来源收据。此后引用和版本字段均不可改变，业务 immutable 约束仍用于声明单据状态后的其他锁定。已被单据固定的主数据内容及其声明集合在接受前保护；另建版本可继续演进，允许通过 ValidUntil 退役，拒绝归档。新版记录不会替换旧单据的明确记录 ID，创建新单据时仍由业务选择当前有效版本。

记录列表、聚合和声明集合使用同一有效期谓词。默认按读取/接受时钟过滤；`Query.businessTime` 支持 `{at: "2026-01-01"}`（datetime 使用含时区的 RFC3339）或 `{all: true}`，后者只关闭有效期过滤，不扩大权限。date 使用成员当地日期，datetime 按实际时点比较；企业模型的 `ActiveOn` 委托同一半开区间判断。按 ID 读取保留版本可继续读失效数据，新引用或尚未完成的固定须重新验证有效性。固定字段和收据在每次读取时按原来源行与版本字段权限裁剪，撤去来源权限不会留下复制值的泄漏。

构建器的 Business versions 页提供版本键、有效期、固定策略和引用映射；单据显示 Pinned version，失效记录显示 Expired 及日期。浏览器路线已通过配置 → 不可变候选激活 → 页面创建两个主数据版本 → 配置单据固定 → 新旧单据版本保持 → 失效标注；截图已检查。宿主回归覆盖进入状态固定、内容/工序集合保护、重复版本与倒置时间拒绝、失效新引用拒绝、当前/历史/全部查询和来源权限撤回。真实文件日志关闭重开后，恢复保存映像与记录字节一致；定义恢复按固定来源依赖安装，不重新求值业务规则。

既有未声明 Versioning 的对象和发布字节不改写，也不替既有单据补造固定收据。原生 MES 的 MasterData / DemoMaster 仍为退出前的演示路径，其数据接管归 ADR-0060、ADR-0053；本块证明的是构建者可用普通记录实现版本主数据。更完整的版本切换呈现、专业业务组件及在途定义升级仍归 ADR-0048、ADR-0045。本块不声明双时态、自动挑版、客户数据已迁移或完整 ADR-0038 已完成。
