# ADR-0112 — 跨系统协同：确认、补偿与对账

状态：已接受；声明式确认与 HTTP/协议 profile 已实现（As built §5；负责人业务体验与真实外部交付待验证），ADR-0098 E 块，对应后端第 4 项· 扩展 ADR-0026（跨应用请求/回执）、ADR-0014（出站效果）、ADR-0072（回写）与 ADR-0011（协议）的执行面 · **不改变**跨权威原子性被拒绝的结论

## 0. 意图

ADR-0100 把"一个应用内的多对象一致性"解决了。**跨系统仍然只能最终一致**——这是内核的硬边界，不存在"跨 SAP 的事务"。

但今天的跨系统机制只覆盖了最简单的形态：一次请求 → 一个回执。真实的制造业协同需要的是：

| 场景 | 今天 | 需要 |
|---|---|---|
| 向 ERP 报工，ERP 未应答 | 请求 + 回执（`ADR-0026 §设计 2`） | 结果不明时的**识别与对账** |
| 收货要同时确认 ERP、WMS、质检 | 三次独立请求，各自成败 | **一个业务确认由多个系统共同完成**，部分成功可见、可收敛 |
| 设备控制指令超时后实际已执行 | 无机制 | **补偿**（反向指令）与**对账**（读源确认） |
| 一小时的窗口内多系统逐步确认 | 无机制 | **跨系统的业务确认进度**是一等状态 |
| 外部系统回执到达时业务已改变 | 回执记入，但归因弱 | 回执按**当时的定义版本与请求身份**归因 |

**判据**：构建者能表达"这张收货单必须在 ERP 与 WMS 都确认后才算完成；任何一方拒绝或超时要能看到、能重试、能人工裁决；恢复后不重复发货"。

## 1. 决定

### D1 业务确认（Confirmation）是一等状态

```go
// 一次需要多个外部系统共同完成的业务确认。
type Confirmation struct {
    Subject    string        // 谁在等确认（收货单、工单、批次）
    Parties    []Party       // 需要哪些系统的确认（端点 + 协议 + 期望结果）
    Deadline   Time          // 业务截止（不是重试截止）
    OnComplete Expr          // 全部满足时的语义（通常是事务的一个条件）
    OnPartial  string        // partial 时的处理：hold | proceed-with-flag | reject
    OnExpire   string        // 超时时的处理：hold | escalate | compensate
}
```

- Confirmation **不是新的事务引擎**：它是**受属工作 + 外部效果 + 现有 Flow** 的组合声明。落盘的是它的进度（哪些方已确认、答复原文、时间），执行由既有出箱与作业机制承担。
- **Confirmation 的状态属于业务记录**（一个记录上的确认子状态，或一条独立的确认记录），因此**可查、可审计、可恢复**，不是运行期易失状态。
- 界面上必须可见："这张单在等谁、等多久了、谁拒了、原因是什么"。

### D2 三种结束：全部确认、部分确认、超时

| 结束 | 语义 | 数据后果 |
|---|---|---|
| 全部确认 | 业务完成 | 由 `OnComplete` 的表达式驱动，通常触发一个事务把单据推进到下一状态 |
| 部分确认 | 一部分成功 | 按 `OnPartial` 声明：持有（有人裁决）、带标记推进、或整体拒绝。**带标记推进时标记必须可见**，不能静默 |
| 超时 | 到 `Deadline` | 按 `OnExpire` 声明：持有、升级（通知角色）、或**补偿**（见 D3） |

**不允许"部分成功被当作成功"**：今天 `ADR-0026 §设计 4` 让记录状态跟着流程走，但"部分成功"没有一等表达；本 ADR 补上它，并要求构建者**显式选择**处理方式。

### D3 补偿与对账

外部系统**不能回滚**，所以只有两条路：

1. **补偿（Compensate）**：发出反向指令（取消工单、冲销过账、释放预留）。补偿是**一个新的意图**，有自己的幂等键，与原始意图一起构成可审阅的因果链。补偿**不保证成功**（外部系统可能拒绝），因此它本身也进入 Confirmation 的语义（"补偿已被确认"）。
2. **对账（Reconcile）**：读源确认实际发生了什么（`Source` 回读，ADR-0072 已有"回写具备投递应答回填，当前仅支持 Build 所有对象，没有源回读对账"——本 ADR 把源回读对账补齐）。对账是一个**受属作业**，按声明周期运行，比对本地意图与源实际状态，产出**差异报告**。

**两者的分工必须明确**：能读源就对账（事实优先），不能读源就补偿（意图优先）。构建者选择，平台不猜。

### D4 结果不明（unknown outcome）必须显式

一次外部投递"没有答复"有三种可能：没送到、送到了没回、送到了执行了没回。今天的处理是重试（ADR-0014 的指数退避到 12 次后标记失败）。

决定：
- **结果不明是一个独立状态**（`unknown`），不是 `retry` 的延伸；
- 进入 `unknown` 时**必须有显式的收敛路径**：对账（读源）或人工裁决（`Reply` 是普通受权动作，沿 ADR-0026 §设计 5 的既有决定）或补偿；
- **`unknown` 状态的意图不能被静默丢弃**，也不能被当作失败（失败意味着"确定没做"）；
- 界面上 `unknown` 与 `failed` 区分显示（沿 ADR-0097 §7 的既有语义扩展）。

### D5 跨应用（宿主内部）与跨系统（外部）同一套语义

ADR-0100 §3 保留了跨应用不原子。本 ADR 要求**跨应用与跨系统用同一套协同原语**（Confirmation、协议、回执、补偿、对账），因为对业务来说它们没有区别（今天 ADR-0026 §设计 2 已经这样做了：宿主内应用"能够瞬间就地应答"，但语义相同）。

区别只在**传输与重试**：宿主内同请求生命周期、外部按适配器的重试策略（ADR-0026 D2 的既有决定保留）。

### D6 归因与版本

回执必须能回答"这个答复是针对哪一次的意图、依据哪一版定义产生的"：

- 回执记录**请求的意图 ID 与幂等键**（已有）、**当时的定义版本**、**当时的执行描述符**（沿 ADR-0097 §7"接受后六类集成执行配置取原固定 descriptor"）；
- 定义升级后到达的旧回执**按原请求处理**；缺固定映射的旧请求跨版本时**明确拒绝**（沿 ADR-0097 §7 的既有边界，本 ADR 要求这一拒绝在界面上可见而不是仅日志）。

## 2. 不做

- **不做分布式事务/两阶段提交**（ADR-0026 D1(a) 已否决，重申）。
- **不做通用消息总线/ESB**：Confirmation 是记录 + 受属工作，不是中间件。
- **不做"保证恰好一次"**（Platform §10.3 D 的既有边界）：外部效果是至少一次，靠稳定身份 + 接收方幂等 + 对账处理结果不明。
- **不做自动补偿决策**：补偿是构建者声明的行为，平台不替业务判断该不该取消。
- **不做跨系统的实时一致性承诺**：收敛时间由 Deadline 与对账周期声明。

## 3. 后果

- 出站效果的既有实现（ADR-0014 的出箱、尝试、退避、`effect-result` 封套）**保留**，新增 `unknown` 状态与收敛路径。
- 源回读对账补齐 ADR-0072 的"做减法"里明确留出的缺口。
- 界面需要"协同进度"呈现（等谁、等多久、谁拒了、差异报告），归 ADR-0108 的 Assemble/运行面。
- MES 基准（ADR-0113）的"跨系统协同"一行（ERP/WMS/APS/设备）依赖本文；今天 `apps/mes/erp.go` 的手写协同是被取代的对象。

## 4. 验收

1. 一个收货单声明需要在 ERP 与 WMS 都确认：两方都确认后单据推进；一方拒绝时按 `OnPartial` 处理并留下可见标记。
2. 一方超时：按 `OnExpire` 处理（持有/升级/补偿），界面可见等谁、等多久。
3. 结果不明：外部投递无答复 → 进入 `unknown`，与 `failed` 区分显示；对账（源回读）收敛；人工裁决可用。
4. 补偿：发出反向指令并跟踪其确认；补偿失败时可见且可再裁决。
5. 归因：定义升级后到达的旧回执按原请求处理；缺映射的旧请求被明确拒绝**且在界面上可见**。
6. 恢复：重启后待确认的进度、未完成意图、对账作业全部恢复，不重复投递（同键幂等）。
7. 反例：未声明 `OnPartial`/`OnExpire` 的 Confirmation、把 `unknown` 当失败处理、声称 exactly-once → 配置期拒绝或文档明确拒绝。

测试归宿主 effects 与集成 owner 包，真实 PostgreSQL 演练覆盖恢复；`docs/Testing.md` 增"跨系统协同"手测行。


## 5. As built

`BusinessTxn.Confirmation` 由原动作编辑器 Transaction 面配置：1–8 方，显式部分结果/截止处置、完成动作、复核角色；每方选确认专用 Writeback 或协议动作，可声明反向请求与 Source 回读。发布期检查策略、动作与传输引用；启动事务在同一接受结果内保存 `build.confirmation` 及各方意图，任何接受失败仍整批不生效。运行态、回执、差异与完成结果归 Build 的记录；截止与完成沿原受属作业，外部发送沿原出箱，未增加事务引擎或调度器。

- **确认与截止。** 全部确认后以原申请人的当前权限执行保存的原完成动作；拒绝按 hold / proceed-with-flag / reject 处理，部分标记留在确认记录。截止按 hold / escalate / compensate 处理；升级通知和裁决任务走原通知/work owner。截止后到达的确认保留原超时，复核者须有证据地恢复完成；完成拒绝在记录上可见。
- **结果不明与对账。** Webhook/HTTP Writeback 无答复，以及回写答复不完整或超出证据预算，保存 `unknown`，不自动重发、废弃或移除端点。确认按原 Source/Connection 描述符在锁外回读，再在接受内复核当前主体、读取权限、确认修订和来源访问；按声明键/结果字段保存匹配或差异。重复键、缺行、读取失败或超额证据均不能当作确认。每轮最多 64 次源读取，优先最早到期；未完成记录分页读取，历史完成项不挡住后继工作。
- **补偿与人工裁决。** 反向意图有独立幂等键、`Compensates` 因果边、固定请求和独立答复/时间/原因；一次截止为全部已确认或结果不明的参与方入队。补偿被拒或失败可以原键重试；原请求/补偿结果不明只能凭证据裁决，不猜测重发。补偿确认收敛原不明意图，不再挡住该连接。裁决须当前复核角色、可读业务记录和非空证据，agent 不能代替人。
- **归因与界面。** 每方保留请求身份、回写版本、源版本、协议原提供方/映射与答复。普通旧回写缺原映射时保留投递结果及 `CallbackError`，在 Integrations 的 Receipt refusal 显示。业务记录页显示各方状态、等待时长、截止、部分标记、补偿与差异报告；原审批/工作收件箱仍可进入记录。英中界面沿原共享组件。
- **版本与恢复。** 完成用原封存对象/规则闭包，协议重试与补偿固定原提供方和请求身份；原提供方版本或映射不可用时明确拒绝，并保存补偿拒绝原因。新进度/差异/控制状态均走接受结果。回执拒绝元数据使用新格式 3，旧格式 1/2 的回调拒绝封套仍按原语义解码。保存 `unknown` 后重开日志应用原结果，不重跑规则、重新授权或发外部请求；恢复后尚未发送的意图仍可按原键投递。

**替代与既有数据：** 确认专用回写不再冒充对象事件，不从普通事件监听重复派发；只由声明事务排队。`unknown` 取代 HTTP 无答复后的盲目退避，原已保存 retry/effect/accepted-result 字节继续读取。早期确认回写映像的虚拟动作依赖只保留读取兼容，用于新候选前须重新发布；不改写历史。`apps/mes` 的行业协同实现仍随 ADR-0114 的等价构建探针退出，本块不改造或删除原生应用、不新增行业代码。

**证据边界：** `TestBusinessConfirmation*` 覆盖多方独立答复、三种部分处置、截止升级/全部补偿、未知结果裁决、稳定补偿重试、源回读期间的修订变化、原完成定义、内部协议及日志回放；`TestBusinessConfirmationDurableUnknownRecovery` 对文件与真实 PostgreSQL 注入追加后/应用前故障，关闭重开并核对未知状态和纯恢复。浏览器路线 `business-confirmation` 从动作编辑器配置两方与 Source，操作员创建/启动收货，观察 unknown → 源匹配 → 原完成动作；保存桌面和窄屏截图。检查方法归 [Testing](../Testing.md)。

本 profile 的回读使用已有有界 Source reader，只接受未分类的源投影；不是任意外部系统的专有对账连接器。SMTP、模型与 A2A 仍沿各自适配器语义。本块不证明真实 ERP/WMS/设备交付、生产容量、网络发送与落盘之间没有重投，或 exactly-once；外部接收方仍须按稳定身份幂等。业务负责人体验走查未由自动路线替代。
