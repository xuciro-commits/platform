# ADR-0051 — 跨系统协同：确认、补偿与对账

<a id="adr-0051"></a>

**状态：** 现行 · 已实现，真实外部交付待验证 · 出站效果、设备派发、观测与跨系统补偿共用一条可恢复通道（并入原 0004、0058、0059）。

## 0. 意图

ADR-0039 把"一个应用内的多对象一致性"解决了。**跨系统仍然只能最终一致**——这是内核的硬边界，不存在"跨 SAP 的事务"。

但今天的跨系统机制只覆盖了最简单的形态：一次请求 → 一个回执。真实的制造业协同需要的是：

| 场景 | 今天 | 需要 |
|---|---|---|
| 向 ERP 报工，ERP 未应答 | 请求 + 回执（`ADR-0006 §设计 2`） | 结果不明时的**识别与对账** |
| 收货要同时确认 ERP、WMS、质检 | 三次独立请求，各自成败 | **一个业务确认由多个系统共同完成**，部分成功可见、可收敛 |
| 设备控制指令超时后实际已执行 | 无机制 | **补偿**（反向指令）与**对账**（读源确认） |
| 一小时的窗口内多系统逐步确认 | 无机制 | **跨系统的业务确认进度**是一等状态 |
| 外部系统回执到达时业务已改变 | 回执记入，但归因弱 | 回执按**当时的定义版本与请求身份**归因 |

**判据**：构建者能表达"这张收货单必须在 ERP 与 WMS 都确认后才算完成；任何一方拒绝或超时要能看到、能重试、能人工裁决；恢复后不重复发货"。

## 1. 决定

### D1 业务确认（Confirmation）是一等状态

```go
// 一次需要多个外部系统共同完成的业务确认。
type Confirmation struct {
    Subject    string        // 谁在等确认（收货单、工单、批次）
    Parties    []Party       // 需要哪些系统的确认（端点 + 协议 + 期望结果）
    Deadline   Time          // 业务截止（不是重试截止）
    OnComplete Expr          // 全部满足时的语义（通常是事务的一个条件）
    OnPartial  string        // partial 时的处理：hold | proceed-with-flag | reject
    OnExpire   string        // 超时时的处理：hold | escalate | compensate
}
```

- Confirmation **不是新的事务引擎**：它是**受属工作 + 外部效果 + 现有 Flow** 的组合声明。落盘的是它的进度（哪些方已确认、答复原文、时间），执行由既有出箱与作业机制承担。
- **Confirmation 的状态属于业务记录**（一个记录上的确认子状态，或一条独立的确认记录），因此**可查、可审计、可恢复**，不是运行期易失状态。
- 界面上必须可见："这张单在等谁、等多久了、谁拒了、原因是什么"。

### D2 三种结束：全部确认、部分确认、超时

| 结束 | 语义 | 数据后果 |
|---|---|---|
| 全部确认 | 业务完成 | 由 `OnComplete` 的表达式驱动，通常触发一个事务把单据推进到下一状态 |
| 部分确认 | 一部分成功 | 按 `OnPartial` 声明：持有（有人裁决）、带标记推进、或整体拒绝。**带标记推进时标记必须可见**，不能静默 |
| 超时 | 到 `Deadline` | 按 `OnExpire` 声明：持有、升级（通知角色）、或**补偿**（见 D3） |

**不允许"部分成功被当作成功"**：今天 `ADR-0006 §设计 4` 让记录状态跟着流程走，但"部分成功"没有一等表达；本 ADR 补上它，并要求构建者**显式选择**处理方式。

### D3 补偿与对账

外部系统**不能回滚**，所以只有两条路：

1. **补偿（Compensate）**：发出反向指令（取消工单、冲销过账、释放预留）。补偿是**一个新的意图**，有自己的幂等键，与原始意图一起构成可审阅的因果链。补偿**不保证成功**（外部系统可能拒绝），因此它本身也进入 Confirmation 的语义（"补偿已被确认"）。
2. **对账（Reconcile）**：读源确认实际发生了什么（`Source` 回读，ADR-0024 已有"回写具备投递应答回填，当前仅支持 Build 所有对象，没有源回读对账"——本 ADR 把源回读对账补齐）。对账是一个**受属作业**，按声明周期运行，比对本地意图与源实际状态，产出**差异报告**。

**两者的分工必须明确**：能读源就对账（事实优先），不能读源就补偿（意图优先）。构建者选择，平台不猜。

### D4 结果不明（unknown outcome）必须显式

一次外部投递"没有答复"有三种可能：没送到、送到了没回、送到了执行了没回。今天的处理是重试（本文 的指数退避到 12 次后标记失败）。

决定：
- **结果不明是一个独立状态**（`unknown`），不是 `retry` 的延伸；
- 进入 `unknown` 时**必须有显式的收敛路径**：对账（读源）或人工裁决（`Reply` 是普通受权动作，沿 ADR-0006 §设计 5 的既有决定）或补偿；
- **`unknown` 状态的意图不能被静默丢弃**，也不能被当作失败（失败意味着"确定没做"）；
- 界面上 `unknown` 与 `failed` 区分显示（沿 ADR-0037 §7 的既有语义扩展）。

### D5 跨应用（宿主内部）与跨系统（外部）同一套语义

ADR-0039 §3 保留了跨应用不原子。本 ADR 要求**跨应用与跨系统用同一套协同原语**（Confirmation、协议、回执、补偿、对账），因为对业务来说它们没有区别（今天 ADR-0006 §设计 2 已经这样做了：宿主内应用"能够瞬间就地应答"，但语义相同）。

区别只在**传输与重试**：宿主内同请求生命周期、外部按适配器的重试策略（ADR-0006 D2 的既有决定保留）。

### D6 归因与版本

回执必须能回答"这个答复是针对哪一次的意图、依据哪一版定义产生的"：

- 回执记录**请求的意图 ID 与幂等键**（已有）、**当时的定义版本**、**当时的执行描述符**（沿 ADR-0037 §7"接受后六类集成执行配置取原固定 descriptor"）；
- 定义升级后到达的旧回执**按原请求处理**；缺固定映射的旧请求跨版本时**明确拒绝**（沿 ADR-0037 §7 的既有边界，本 ADR 要求这一拒绝在界面上可见而不是仅日志）。

## 2. 不做

- **不做分布式事务/两阶段提交**（ADR-0006 D1(a) 已否决，重申）。
- **不做通用消息总线/ESB**：Confirmation 是记录 + 受属工作，不是中间件。
- **不做"保证恰好一次"**（Platform §10.3 D 的既有边界）：外部效果是至少一次，靠稳定身份 + 接收方幂等 + 对账处理结果不明。
- **不做自动补偿决策**：补偿是构建者声明的行为，平台不替业务判断该不该取消。
- **不做跨系统的实时一致性承诺**：收敛时间由 Deadline 与对账周期声明。

## 3. 后果

- 出站效果的既有实现（本文 的出箱、尝试、退避、`effect-result` 封套）**保留**，新增 `unknown` 状态与收敛路径。
- 源回读对账补齐 ADR-0024 的"做减法"里明确留出的缺口。
- 界面需要"协同进度"呈现（等谁、等多久、谁拒了、差异报告），归 ADR-0047 的 Assemble/运行面。
- MES 基准（ADR-0060）的"跨系统协同"一行（ERP/WMS/APS/设备）依赖本文；今天 `apps/mes/erp.go` 的手写协同是被取代的对象。

## 4. 验收

1. 一个收货单声明需要在 ERP 与 WMS 都确认：两方都确认后单据推进；一方拒绝时按 `OnPartial` 处理并留下可见标记。
2. 一方超时：按 `OnExpire` 处理（持有/升级/补偿），界面可见等谁、等多久。
3. 结果不明：外部投递无答复 → 进入 `unknown`，与 `failed` 区分显示；对账（源回读）收敛；人工裁决可用。
4. 补偿：发出反向指令并跟踪其确认；补偿失败时可见且可再裁决。
5. 归因：定义升级后到达的旧回执按原请求处理；缺映射的旧请求被明确拒绝**且在界面上可见**。
6. 恢复：重启后待确认的进度、未完成意图、对账作业全部恢复，不重复投递（同键幂等）。
7. 反例：未声明 `OnPartial`/`OnExpire` 的 Confirmation、把 `unknown` 当失败处理、声称 exactly-once → 配置期拒绝或文档明确拒绝。

测试归宿主 effects 与集成 owner 包，真实 PostgreSQL 演练覆盖恢复；`docs/Testing.md` 增"跨系统协同"手测行。

## 5. As built

`BusinessTxn.Confirmation` 由原动作编辑器 Transaction 面配置：1–8 方，显式部分结果/截止处置、完成动作、复核角色；每方选确认专用 Writeback 或协议动作，可声明反向请求与 Source 回读。发布期检查策略、动作与传输引用；启动事务在同一接受结果内保存 `build.confirmation` 及各方意图，任何接受失败仍整批不生效。运行态、回执、差异与完成结果归 Build 的记录；截止与完成沿原受属作业，外部发送沿原出箱，未增加事务引擎或调度器。

- **确认与截止。** 全部确认后以原申请人的当前权限执行保存的原完成动作；拒绝按 hold / proceed-with-flag / reject 处理，部分标记留在确认记录。截止按 hold / escalate / compensate 处理；升级通知和裁决任务走原通知/work owner。截止后到达的确认保留原超时，复核者须有证据地恢复完成；完成拒绝在记录上可见。
- **结果不明与对账。** Webhook/HTTP Writeback 无答复，以及回写答复不完整或超出证据预算，保存 `unknown`，不自动重发、废弃或移除端点。确认按原 Source/Connection 描述符在锁外回读，再在接受内复核当前主体、读取权限、确认修订和来源访问；按声明键/结果字段保存匹配或差异。重复键、缺行、读取失败或超额证据均不能当作确认。每轮最多 64 次源读取，优先最早到期；未完成记录分页读取，历史完成项不挡住后继工作。
- **重复读取的成本。** 首次差异、观测/错误变化与状态变化仍走原接受结果；状态、观测值和错误均相同的后续轮询不再写日志，也不更新首次证据时间。与设备派发共用 `statusReadSchedule` 的到期、占用、每轮预算与清理步骤；来源读取和业务证据解释仍各自负责。读取间隔和并发占用只留在租户临时调度缓存，结束后清理；重启丢弃缓存，继续与原持久差异比较。读取后先复核修订、当前权限、申请人/来源发布者身份与凭据、连接标记和人工裁定，再判断是否重复。凭据仅参与内存中的一致性比较，不进入记录或结果；读取期间凭据变化的答复丢弃，下一次按原周期重新读取。`TestConfirmationReadRevalidatesCredentialAndExcludesConcurrentPoll` 检查并发轮询不重复读取、凭据变化后旧答复不被接受，以及新读取完成时不重发未知请求；`TestBusinessConfirmationReconciliationWritesOnlyChanges` 验证重复结果/错误不增长日志、变化仍保存、间隔有效、重放后继续读取及旧读取不能覆盖人工决定。
- **补偿与人工裁决。** 反向意图有独立幂等键、`Compensates` 因果边、固定请求和独立答复/时间/原因；一次截止为全部已确认或结果不明的参与方入队。补偿被拒或失败可以原键重试；原请求/补偿结果不明只能凭证据裁决，不猜测重发。补偿确认收敛原不明意图，不再挡住该连接。裁决须当前复核角色、可读业务记录和非空证据，agent 不能代替人。
- **归因与界面。** 每方保留请求身份、回写版本、源版本、协议原提供方/映射与答复。普通旧回写缺原映射时保留投递结果及 `CallbackError`，在 Integrations 的 Receipt refusal 显示。业务记录页显示各方状态、等待时长、截止、部分标记、补偿与差异报告；原审批/工作收件箱仍可进入记录。英中界面沿原共享组件。
- **版本与恢复。** 完成用原封存对象/规则闭包，协议重试与补偿固定原提供方和请求身份；原提供方版本或映射不可用时明确拒绝，并保存补偿拒绝原因。新进度/差异/控制状态均走接受结果。回执拒绝元数据使用新格式 3，旧格式 1/2 的回调拒绝封套仍按原语义解码。保存 `unknown` 后重开日志应用原结果，不重跑规则、重新授权或发外部请求；恢复后尚未发送的意图仍可按原键投递。

**替代与既有数据：** 确认专用回写不再冒充对象事件，不从普通事件监听重复派发；只由声明事务排队。`unknown` 取代 HTTP 无答复后的盲目退避，原已保存 retry/effect/accepted-result 字节继续读取。早期确认回写映像的虚拟动作依赖只保留读取兼容，用于新候选前须重新发布；不改写历史。`apps/mes` 的行业协同实现仍随 ADR-0053 的等价构建探针退出，本块不改造或删除原生应用、不新增行业代码。

**证据边界：** `TestBusinessConfirmation*` 覆盖多方独立答复、三种部分处置、截止升级/全部补偿、未知结果裁决、稳定补偿重试、源回读期间的修订变化、原完成定义、内部协议及日志回放；`TestBusinessConfirmationDurableUnknownRecovery` 对文件与真实 PostgreSQL 注入追加后/应用前故障，关闭重开并核对未知状态和纯恢复。浏览器路线 `business-confirmation` 从动作编辑器配置两方与 Source，操作员创建/启动收货，观察 unknown → 源匹配 → 原完成动作；保存桌面和窄屏截图。检查方法归 [Testing](../Testing.md)。

本 profile 的回读使用已有有界 Source reader，只接受未分类的源投影；不是任意外部系统的专有对账连接器。SMTP、模型与 A2A 仍沿各自适配器语义。本块不证明真实 ERP/WMS/设备交付、生产容量、网络发送与落盘之间没有重投，或 exactly-once；外部接收方仍须按稳定身份幂等。业务负责人体验走查未由自动路线替代。

## 并入：出站效果、设备派发与观测（原 0004、0058、0059）

出站效果是写入账本的意图，设备派发是它的一种目标，观测是反方向的只读结果；三者共用一条可恢复的投递路径，不各自建通道。

### 决策条款

1. **操作意图 (Intent)、物理尝试 (Attempt) 与最终结果 (Outcome) 彻底三权分立。**
   - **操作意图 (Intent)：** 在某个顶级输入被接受处理的内部由业务应用发起声明 (`Caller.Emit`)，例如“向端点 E 发送客房预订 B 已取消的通知”。它是该输入处理过程中具备绝对确定性的派生产物，因此系统重启日志重放时会完全确定性地重新生成该意图。**但在日志重放期间，系统绝对不向外发起任何真实的网络请求**。
   - **物理尝试 (Attempt)：** 由宿主内部的出站分发器驱动，作为受管的受属工作 (K9) **在租户排他锁之外**独立异步发起。日志重放期间严禁触发任何尝试。
   - **最终结果 (Outcome)：** 外部调用的尝试结果，作为一条完全独立的顶级日志分录记入租户持久化日志：包含已成功确认 (confirmed)、携带下游应答报文的已拒绝 (rejected)、或超时引发的状态未知 (unknown)。系统启动重放日志时，直接读取该条已被记录在案的客观历史结果，绝不再向外部发起实际调用。因此，从历史灾备备份中恢复出来的租户，能够精确无误地知晓哪些外部效果已经完结、哪些尚处于未决状态。
2. **基于稳定的全局幂等键实现“至少一次”交付。**
   - **唯一幂等键设计：** 每个外部效果均被分配全局唯一键 `<tenant>:<change id>:<n>`。该键在每一次网络尝试中均强制携带对外发送（作为 HTTP 头的 `Idempotency-Key`，对于 Webhook 则同时作为 `webhook-id`），外部接收方统一基于该键实施精确去重。
   - **系统意外崩溃容错：** 若系统在向外发送请求与将调用结果记入日志之间的极窄时间窗口内突发断电崩溃，重启后系统会使用完全相同的原始幂等键重新发起补发。这完全遵从内核 K5 “状态未知 → 使用原键安全重试”的核心铁律，这也是在不可靠网络环境下唯一诚实守信的工程保证。
3. **按效果类别定制专属的指数退避重试策略。** 结合抖动算法在长达数小时或数天的宽广时间跨度上进行平滑重试：针对 Webhook 跨越数小时（Stripe 规范支持长达 3 天），针对邮件外发跨越数分钟。
   - 一旦超出重试时间跨度上限，该外部效果被系统正式标记为**已失败 (failed)**，清晰呈现在系统设置中心，管理员可以通过发起一项受审决策一键重新重试或彻底废弃丢弃该效果。
   - 为每个外部目标目的地配备熔断器机制：高频连续失败将自动触发熔断暂停，并将其标记为不健康状态，与连接器的治理方式保持一致。
4. **外部系统的应答数据作为客观事实 (Facts) 接入。**
   - 对业务具有重要业务价值的外部系统应答，自动转化为带有来源出处的一项客观观察 (K2/K3)，将该目标端点记录为事实出处：例如 SAP 返回的正式工单编号、第三方支付平台返回的交易流水号、或邮件服务器返回的退信跳票通知。
   - 内部业务应用通过订阅这些客观观察事实并进而发起新的业务决策 (K4)。外部系统的应答绝不能直接、越权绕过业务规则去修改系统状态。
   - 内核契约本身无需为此引入任何新概念。
5. **端点 (Endpoints) 是宿主通用能力，绝非内核概念。**
   - **端点**是企业租户管理员在系统设置中心“系统集成”模块下，通过发起一项受审决策进行配置维护的外部目的地实体。它涵盖：
     - 目标 URL 统一资源定位符或服务网络地址；
     - 端点类型类别（Webhook、SMTP 邮件服务器、标准出站 REST 调用）；
     - 对企业安全凭据的引用命名（绝不直接存储明文机密密钥）；
     - 各项安全与性能硬限制（每分钟调用频率上限、超时阈值、单次有效负载体积上限）；
     - 实时连通健康度状态。
   - 业务应用在其清单中必须显式声明其能够对外发出的效果类别 (`Emits`)。应用仅能向外发出其清单中已合法声明的类别，且只能投递给管理员明确绑定至该类别的合法端点，严禁应用随心所欲向任意自行拼接的 URL 乱发网络请求。
   - 内核 K8 连接器概念严格限制在入站数据集成范畴。出站通信唯有在存在第二个独立运行时（例如独立的 Rust 边缘端设备）明确需要遵循相同规范向外发射效果时，方可考虑升级晋升为内核契约的一部分。
6. **Webhook 对外分发无需应用编写任何专用代码。**
   - 租户管理员可以将某个 Webhook 端点直接订阅至特定的业务事件（某项具体动作的成功执行，或某个协议层业务事件）。*在 #104 任务中正式修订：* 端点完全由企业系统管理员负责配置，因此端点天然拥有管理员级别的全局视野：能够自由订阅租户名下声明的任意业务事件，订阅未声明的非法事件则予以拦截拒绝。针对更细粒度成员目录的事件过滤，推迟至后续系统正式支持普通非管理员成员亦可自主配置专属端点时再行引入。
   - 平台管理应用负责在底层自动将每一个命中的业务事件无缝转换为对应的出站外部效果。
   - 对外发送的有效负载严格遵循国际 Standard Webhooks 规范实施数字签名，并强制携带该事件对应的模式版本号 (K7)。
7. **敏感机密密钥绝不进入持久化日志。**
   - 访问凭据统一保存在专门的企业密钥存储库中，系统内部仅通过逻辑名称进行安全引用。首期版本通过安全挂载的物理文件或环境变量注入实现；后续平滑扩展支持 HashiCorp Vault 或云厂商托管的 KMS 服务。
   - 写入持久化日志的分录，仅包含对应操作意图的全局引用标识以及实际对外发送报文主体的 SHA-256 摘要哈希值，严禁在日志中记录任何明文 Token 或签名密钥。
8. **对外部通信目标实施严苛的安全沙箱边界约束。**
   - 仅允许向企业管理员已经显式审核并配置好的合法端点发送数据。
   - 严格拦截拒绝任何私有局域网地址 (RFC 1918) 或链路本地地址 (Link-local)，坚决防范内网 SSRF 探测攻击，除非管理员在配置该端点时显式开启了特许豁免开关。
   - 在生产正式运行环境中，强制要求采用 HTTPS 安全加密传输。
   - 目标域名的 DNS 解析在发起网络连接的当下实时执行，并在握手建立前对解析出的底层 IP 进行二次强校验。

### 供平台负责人决策的核心裁决项

| # | 核心抉择议题 | 权威推荐建议方案 |
|---|---|---|
| D1 | 底层可靠性交付保证等级 | 针对所有类别的外部效果，一律采用**基于稳定幂等键的至少一次交付保证**（包含邮件外发场景；接收方是否去重须由实际协议与实现证明，Message-ID 本身不构成不重复交付保证） |
| D2 | 消息分发保序规则 | **在单端点粒度上实施严格保序分发**（为外部接收方提供极其可靠的因果时序预期）；无序并发投递作为后续高级选项按需开放 |
| D3 | 端点实体的架构层级归属 | 定位为由宿主统领、并在系统设置中心集中治理的**平台级高级通用能力**；暂不上浮至内核底层契约范畴 |
| D4 | 外部系统的业务应答如何闭环吸收 | 外部应答统一作为 **K2 客观观察事实** 录入系统；应用通过标准规则对该事实发起新的决策裁决 |
| D5 | 企业级机密密钥存储底座 | 当前阶段采用**基于安全挂载文件或逻辑环境变量的按名称安全引用**机制；待大型商业客户提出合规硬指标时平滑平移接入 Vault 或云端 KMS |
| D6 | AI 智能体引发不可逆效果的防线机制 | 凡被显式标记为**不可逆 (Irreversible)** 的效果类别（如实际对外转账划款、向外部社会公众或客户个人发送正式邮件），一旦其触发源头追溯为 AI 智能体，**该效果必须强制自动挂起暂留 (held)**，直至具备合法权限的真实人类操作员在后台人工审核通过后方可正式向外发射 |

| D8 | 外部效果报文主体的归档生命周期 | 在持久化日志中永久保留其数字摘要哈希值；完整的报文请求与应答明文主体在系统中默认保留 30 天以供技术支持与排障钻取，过期后自动物理销毁仅保留摘要备查 |

### 1. 分界：观测是事实，不是决策

平台今天有两种入账：

| | 决策（decision） | 观测（observation） |
|---|---|---|
| 是什么 | 一次**权威变更**：谁、在何时、把什么改成了什么 | **来源处真实发生的事**：某设备在某时刻的读数 |
| 内核 | K4 变更记录 | K2/K3 事实日志（observation/claim） |
| 现状 | 全部业务写入 | **已有类型，但实际使用极少；规范自己写明"高频观察的批量聚合处于开放状态"** |
| 体积 | 随业务操作增长 | **随点数增长** |

**决定：原始观测不进租户决策日志。**

原因不是性能调优，是**语义**：决策日志的可恢复性、幂等性、前驱校验（ADR-0010、ADR-0037）是为"权威变更"设计的。把每秒一个温度点写成决策，等于让恢复时间、日志体积、快照大小全部随**物理采样率**增长——而这些点**不改变任何权威状态**。

### 2. 决定

### D1 三样东西分开放，各有归属

```text
采集侧（外部，不在平台内）
  设备 / 网关 / 采集器 / 协议适配库（西门子上百种协议等）
     │  只上传：结果与聚合
     ▼
平台侧
  ├─ 观测存储（外部依赖，非租户决策日志）
  │    时序点、原始读数、保留与降采样策略
  ├─ 业务记录（租户日志）
  │    判定结果：预警、告警、工单、聚合值、状态
  └─ 判定（平台内，声明式）
       阈值、趋势、组合条件、误报抑制 → 走 ADR-0040 的规则语言
```

| 层 | 归属 | 谁的职责 | 本 ADR 是否实现 |
|---|---|---|---|
| 设备协议、采集、边缘缓冲 | **外部运行**（既有采集器或 ADR-0061 的独立网关与能力包） | 采集侧 | 本文不实现；自研按需协议包见 ADR-0061 |
| 观测存储 | **外部依赖**（时序库，如负责人既有实践所用的 TSDB/物联网平台） | 运维与采集侧 | **不实现**：只定义平台的**连接方式与读取形状** |
| 观测 → 判定的规则 | 平台 | 构建者声明 | 实现（D3） |
| 判定结果 → 业务记录 | 平台 | 平台（事务，ADR-0039） | 实现（D4） |

### D2 观测存储是环境绑定，不是内置

- 观测存储的**地址与凭据是环境绑定**（沿 ADR-0018、ADR-0046：凭据永不进入工件）；
- 工件里声明的是**逻辑连接**（"这个应用需要一类时序源"）与**读取形状**（某设备的某个测点在某时间窗的序列/聚合）；
- 平台**不规定**用哪个时序库。更换时序库是环境变更，不是应用变更。
- **不在平台内实现第二套时序存储**（AGENTS 硬规则 6、ADR-0038 §9.5 一个语义一个实现）。

### D3 判定在平台内，用同一门语言

"抓关键信息"（设备预警、水表超限、趋势异常）是**判定**，走 ADR-0040 的规则语言，读的是**声明过的观测**：

- 阈值：`value > limit`、`within-period`（已有算子）
- 趋势与速率：需要新的观测算子（`rate`、`delta`、`over-window`），**须按 ADR-0040 的规则扩展算子表**，不建第二套求值器
- 组合与抑制：`any`/`all` + 抑制定时（复用 ADR-0007 的定时自动化）
- **预警不是告警记录**：判定产生的是**业务记录**（预警/告警/工单），进 ADR-0039 的事务

**观测的可读性受 ADR-0044 的同一套授权**：观测数据不是"随便读"的，它按声明的来源与调用者权限收窄（K2/K3 的来源语义 + ADR-0009 的派生声明）。

### D4 只把结果写进业务记录

判定产生的结果进入业务记录的形态有三类，**都不含原始点**：

| 结果 | 形态 | 举例 |
|---|---|---|
| 聚合值 | 记录字段（由 ADR-0040 的聚合算子算出） | 当日累计用水量 |
| 状态变化 | 生命周期迁移（ADR-0044） | 设备状态：正常 → 预警 |
| 下游指令 | 事务步骤或外部效果（本文） | 给 MES 报设备预警、给 ERP 报水表读数汇总 |

**原始点永不进入业务记录。** 需要追溯原始点时，**按声明回到观测存储读取**（带对象与测点标识），而不是在记录里留存副本。

### D5 保留、降采样与"多久"

- **保留策略归观测存储**（外部），工件里声明它**期望**的保留与粒度；实际保留由环境实现。
- **降采样归观测存储**。平台不实现降采样。
- **平台侧只保留判定结果与聚合**；聚合的历史保留按业务需要（例如"三年的月度用水量"），归业务记录的保留声明（ADR-0046 §D5 的 `AppProfile`）。
- **超出保留的原始点不可恢复，且不宣称可恢复**——这与业务记录的"历史永远可读"（ADR-0038 §9.2）**不是同一件事**，必须在使用文档里讲清，避免客户以为"平台什么都能查"。

### 3. 明确不做的（这是本 ADR 的主要篇幅）

本 ADR 不把以下内容放进业务宿主或内核。原先“采集协议不开发/不预留”的范围已由 ADR-0061 的新指令替代：

- 设备协议适配——**独立协议能力包或外部库/采集器的职责**，按 ADR-0061 按需开发，不承担全型号历史兼容；
- 采集器的部署、边缘缓冲、断线续传、时钟同步——**采集侧职责**；协议包安装与部署配置设计归 ADR-0061，不在业务宿主中运行采集循环；
- 时序库自身的实现、索引、压缩、降采样——**外部依赖职责**；
- 边缘规则引擎——判定放平台（D3），采集侧只做必要的安全联锁（本文 §D3）。

**"我们只要结果"的准确含义**：业务宿主要的是**判定结果与聚合值**，以及**回到原始点的读取能力**（D4）；采集实现归独立网关/能力包，时序存储仍为外部依赖。

### 1. 与 本文 的区别

| | Confirmation（本文） | 设备/黑盒指令（本文） |
|---|---|---|
| 对面 | 业务系统（ERP、WMS、APS） | 控制器 / 库系统 / 黑盒下游 |
| 回执语义 | 有：接受、拒绝、附答复 | **多数只有状态**：已收、执行中、完成、失败、卡住 |
| 时长 | 秒到小时 | 秒到分钟（长任务） |
| 一致性 | 至少一次 + 对账 | **至少一次 + 状态回读**（不重发危险指令） |
| 人的角色 | 裁决部分成功 | **介入卡住的任务** |

**共同点**：都**不宣称 exactly-once**（ADR-0038 §9.3、Platform §10.3 D），都靠稳定身份 + 接收方幂等 + 对账。

### 2. 决定

### D1 指令是一等业务记录，不是"一条效果"

```go
// 一条下发到设备/黑盒目标的指令。
type Dispatch struct {
    Subject  TxnRef      // 业务主体（运单、搬运任务、门禁请求）
    Target   Endpoint    // 目标（设备/库系统/AGV 控制器/黑盒下游）
    Command  string      // 声明过的指令名（不是自由文本报文）
    Payload  []Set       // 参数（ADR-0040 的表达式求值）
    Key      string      // 幂等键（稳定，来自业务主体）
    Deadline Time        // 业务截止（本文 §D1 的语义）
    OnStuck  string      // 卡住时：escalate | compensate | retry | manual
    OnFail   string      // 失败时：同上
}
```

- **指令是声明过的**（`Command` 来自声明的指令表），不是任意报文。任意报文会让平台无法判断幂等与重发安全。
- 指令的**状态、尝试、回读结果**都是业务记录，因此**可查、可审计、可恢复**（不是运行期易失状态）。
- 指令的**幂等键来自业务主体**（如运单 ID），因此重发同一个搬运请求不会产生第二次搬运——**前提是目标侧也遵守幂等**；平台不假设、不承诺（D5）。

### D2 状态回读（对账）是必需的，不是可选的

因为多数控制器不返回业务回执，**"发出去了"与"做到了"之间只能靠回读**：

- 指令可以声明**状态回读方式**（读某个观测测点、查目标的查询接口、读它的状态记录）；
- 回读是**受属作业**（复用 ADR-0007、ADR-0044 的机制），按声明周期运行；
- 回读结果写回业务记录（`dispatch` 记录的状态字段），因此**卡住能被发现**；
- **结果不明（unknown）与失败（failed）区分**（沿 本文 §D4 的既有决定，扩展到设备）。

### D3 硬边界：控制回路不在平台（**这条最优先**）

**安全联锁、急停、闭环运动控制、实时调速——永远在设备/网关/PLC 本地。**

平台做的是**派发与回读**：它告诉目标"做什么"，然后看"做到没有"。平台**不**参与毫秒级的闭环，**不**承担实时性，**不**作为安全链路的一环。

这条必须在使用文档与构建器里写明。**不写死的后果**：第一次做 AGV 就会有人想在平台上做路径闭环——那是一条会伤人的错误。

平台也**不**检测"指令是否会撞"——那是目标侧/WCS 的职责；平台只传递业务意图与约束（例如"必须先出库后入库"由 ADR-0040 的规则表达）。

### D4 人必须能介入

- `OnStuck` / `OnFail` 的处理**必须显式声明**（与 本文 §D2 同一要求）：升级（通知角色）、补偿（反向指令）、重试、或**人工**。
- **人工介入是一等路径**：被授权成员可以裁定一条卡住的指令（重发、改目标、标记完成、取消）。走 work 的既有任务/审批机制（ADR-0007）。
- **卡住必须可见**：运行面显示在途指令、卡住的时长、原因（来自回读）。

### D5 重发的安全性分级

重发不是都安全：

| 指令类别 | 重发语义 | 声明要求 |
|---|---|---|
| **幂等**（查询状态、设置目标位置） | 可安全重发 | 声明 `Idempotent: true` |
| **需目标侧幂等**（创建搬运任务，带业务键） | 可重发，**依赖目标侧按业务键去重** | 声明业务键；文档说明依赖 |
| **不可安全重发**（开门、启动动作） | **禁止自动重发**；失败进入人工 | 声明 `Idempotent: false`；平台**拒绝**在自动重试策略里配置它 |

**平台必须能拒绝**："给一个不可安全重发的指令配置自动重试"在**发布期**就是错误。这是本 ADR 最实用的一条。

### D6 目标不是业务应用：协议与凭据

- 目标（设备、控制器、黑盒下游）**不是平台的应用**，没有对象类型，不需要实现协议（ADR-0006）——它是**外部端点**；
- 目标的**地址与凭据是环境绑定**（沿 ADR-0018、ADR-0046）；报文格式与协议栈由**能力包**封装（ADR-0057：设备对接是能力包，例如"AGV/RCS 接入"、"黑盒下游 HTTP/TCP 对接"）；
- **协议适配不在平台包内实现**：业务宿主只到"指令 + 参数 + 状态"这一层；具体 Go 协议包与独立网关按 ADR-0061 开发，通过原 Writeback/Dispatch 接入。

### D7 为下一次交付预留的形状（ADR-0057 §6 规则 2 的实例）

**下一次交付已命名**（仓储与 AGV），因此允许预留**形状**，不允许预留领域词汇：

| 预留什么 | 形态 | 不做什么 |
|---|---|---|
| 指令种类的扩展点 | 一个具名的 `Dispatch` 声明（`Command` 来自声明表） | 不预置"AGV""库位""RCS"等名称 |
| 状态回读的扩展点 | 一个具名的回读声明（读观测 / 查接口 / 读记录） | 不实现任何具体协议 |
| 目标类别的扩展点 | 一个具名的端点类别（设备/库系统/黑盒下游） | 不做第二套集成机制 |
| 数字化容器的对接 | **不预留**（负责人明示"很边缘的地方就不用再搞预留"） | — |

**预留的检查标准**（沿 ADR-0057 §6 规则 4）：三天后能插进来即为合格；**留下空方法、假支持或未接通入口即视为缺陷**。

### 3. 不做

- **不做闭环运动控制 / 实时控制**（D3）。
- **业务宿主不做协议栈**（D6；具体协议按 ADR-0061 属独立能力包或外部库，不另建派发权威）。
- **不做"设备一定执行"的承诺**（§0）。
- **不做安全联锁的软件实现**（D3）。
- **不为未命名的交付预留**：除 D7 表内的四项，其他（如"未来可能接机器人"）不留形状。
