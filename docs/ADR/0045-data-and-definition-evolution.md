# ADR-0045 — 数据与定义的演进：从可选标量到真实迁移

<a id="adr-0045"></a>

状态：已接受并实现 §5 的有界验收（2026-10-12 接受，负责人指令，ADR-0038 C 块第一份）· 取代 ADR-0011 §As built「带数据的有界升级」只接受可选标量字段的口径；保留其候选/激活/环境绑定/恢复语义 · 落地顺序归 WorkQueue

## 0. 意图

客户把系统用起来之后，**一定会改模型**：给工单加一个字段、把"备注"拆成两类、给工序加质检点、改一个引用的目标类型。本 ADR 实施前平台允许的只有一种：**新增一个可选标量字段**（text/longtext/integer/decimal/boolean/date/datetime），不填默认值、不改已有记录值。

ADR-0011 §As built 原文：*"必填、引用、选择、共享属性、金额、删除/重命名/类型变更及一般转换不在此 profile 内。"* 剩余边界一节又写：*"上述可选标量扩展之外的存储形状变更、拥有者草稿重命名/归档、动作退役及部分绑定变化仍受拒绝/升级门禁限制。"*

结果：客户第一次要改名一个字段，就撞墙。这不是能力不足，**这是"不能长期维护"**（ADR-0038 第三个判据）。

**判据**：构建者能执行一次真实的模型变更（新增带默认值的必填字段、重命名、拆分、改引用目标、退役一个动作），在**不改历史语义**的前提下让在途业务继续跑。

## 1. 现状与原缺口

| 能力 | 现状 | 证据 |
|---|---|---|
| 候选/激活/晋级 | 已有，含依赖闭包、原子激活、环境绑定 | `platform/revision.go:16-45`；`accepted_release.go:320-383` |
| 在途实例版本绑定 | 已有（Flow 冻结启动版本与依赖闭包） | `flow_binding.go:22-58` |
| 记录迁移 | 有受权迁移入口（Host Console 的 Migrate records） | ADR-0016；`environment.go` |
| 升级计划 | 已有封存迁移计划、分批执行与原目标激活；可选标量是其特例 | As built；`migration_review.go`、`migration_execute.go` |
| **重命名** | 显式迁移，旧名保留只读别名 | As built |
| **必填 + 默认值** | 显式 Expr 默认值与批次写入 | As built |
| **引用/选择/金额** | 声明转换与引用映射，经原目标类型/约束校验 | As built |
| **删除/归档字段** | 物理删除拒绝；退役保留读取，禁止新写 | As built |
| **类型变更/一般转换** | 封存 Expr 转换，显式失败策略；被引用的类型转换必须隔离 | As built |
| **动作退役** | 分批拒绝或显式转交原审批，原流程按固定版本续接 | As built |
| **K7 动态演进** | 原 SchemaRegistry 已接发布期 family 与提交内容身份；兼容范围见 As built | `platform/ledger.go`；`submission_schema.go` |

**根因**：升级被当作"结构兼容性检查"，而不是**一次有计划的、可审阅的数据与定义迁移**。因为不承认要动数据，所以只能允许"不动数据"的改动。

## 2. 决定

### D1 升级 = 计划 + 数据迁移 + 定义激活，一次接受

引入**迁移计划**（`MigrationPlan`，构建器资产 + 宿主执行）：

```go
type MigrationPlan struct {
    From   ReleaseRef   // 源定义版本（封存）
    To     ReleaseRef   // 目标定义版本（封存）
    Steps  []MigrateStep
    Scope  string       // 目标记录范围（类型 + 可选过滤）
}

type MigrateStep struct {
    Kind   string   // add | default | rename | split | merge | retype | extract | retire-action | rebind
    Types  []string
    Fields []FieldChange
    Expr   *Expr    // 转换值（ADR-0040）
    Batch  int      // 分批大小（见 D3）
}
```

要点：

- **计划绑定两个封存版本**（源与目标），不是"当前"与"目标"——这样计划在审阅期间不会漂移。
- **转换用 ADR-0040 的表达式**：`split`（一个字段按表达式分到两个）、`merge`、`retype`（含显式转换与失败处理）、`extract`（从行到新对象）都是表达式 + 步骤类型，不是脚本。
- **不支持的转换必须显式拒绝**（有步骤类型清单，清单外拒绝），不静默跳过。清单外的复杂转换走 ADR-0013 的受控代码（Go/TinyGo Wasm）作为**显式选声明的步骤类型**。

### D2 每一类变更的确切语义

| 变更 | 语义 | 历史影响 |
|---|---|---|
| `add` + `default` | 新字段以表达式求值填既有记录 | 历史记录被**写入新事实**（一次真实迁移决策），不是改写旧决策 |
| `rename` | 字段名变更；**旧名保留为只读别名**，历史记录与旧发布继续按旧名解析 | 无（读时映射） |
| `split`/`merge` | 值按表达式重分布；源字段进入只读退役态 | 历史可读 |
| `retype` | 显式转换；转换失败的行**隔离并报告**，不静默置空、不丢行 | 历史可读 |
| `retire-action` | 动作停止出现在目录里；**已产生的历史决策继续重放**，在途等待审批按声明的处理（拒绝/重定向） | 无 |
| `rebind` | 引用的目标类型变更；必须提供目标的身份映射或拒绝 | 需显式映射 |
| **字段删除** | 不允许物理删除；只允许 `retire`（保留读取、不参与新写入） | 必须保留 |

**历史永远可读是硬线。** 今天"历史日志必须永远能重放"（ADR-0010、ADR-0037）是最高优先；删除字段会破坏它，所以只提供退役。

### D3 迁移是分批的真实决策，不是原地改写

- 每一步按 `Batch` 分批执行，**每批是一个业务事务**（ADR-0039）：部分完成是显式可见的中间状态，可重入、可续接。
- 迁移决策的主体是**执行迁移的管理主体**，不是"系统假装那条记录当初就是这样"。审计上能区分"这条记录的字段是被迁移填的"与"它本来就有"。
- 迁移可中断、可恢复、可重跑（同键幂等）。失败批留下明确的进度与原因。
- **恢复不重跑迁移**（沿 ADR-0010、ADR-0037）。

### D4 在途工作跨版本的语义

| 在途物 | 语义 |
|---|---|
| 已启动的 Flow 实例 | 保留启动版本与依赖，继续按旧语义跑到结束（已有，`flow_binding.go:22-58`，不变） |
| 等待中的审批 | 按声明的处理：默认**拒绝**并要求重新发起（因为审批针对的是旧定义的动作语义）；可声明重定向到新动作 |
| 未派发的外部效果意图 | 按**固定执行描述符**继续（已有语义，ADR-0037 §7"接受后六类集成执行配置取原固定 descriptor"） |
| 单据上的业务版本固定 | 不变（ADR-0042）：迁移**不改变**已固定的业务版本，除非计划显式声明 |
| 定时作业 | 下次执行用新版本（它们是反复发生的，不是在途） |

### D5 K7 版本协商落地

宿主沿原 K7 `SchemaRef.Version` 表示兼容族，内容身份由定义 owner 在发布时声明；不改内核或 Protobuf。本 ADR 的版本演进要求：

- 定义发布带 **schema 版本**（内容哈希，沿 `revision.go` 的内容 ID）；
- 提交时声明它所依据的 schema 版本；宿主接受**同一 family 内**的版本（兼容声明由发布期校验给出）；
- 跨 family 的提交明确拒绝并要求客户端刷新定义。

**不做**内核 K7 的全部动态学习语义（那是"权威/鉴权从何而来"的问题，超出本 ADR）；做的是让平台**能说出自己用的哪一版**，并拒绝说不清的提交。

### D6 客户扩展的保留

ADR-0011 末句的"客户扩展保留仍未完成"是本 ADR 的核心交付之一：

- 客户在工作台给**共享类型**（`core.*`）追加的字段/动作（ADR-0020 的扩展记录）在基础包升级后**必须保留**；
- 保留的实现方式：扩展按**来源包版本**记录，基础包升级时逐条重放扩展声明并验证（字段还在、类型还兼容），不兼容的扩展**明确报告并暂停**，不静默丢弃；
- 扩展的冲突（基础包新增了同名字段）在升级计划里显式解决，不自动覆盖。

## 3. 不做

- **不做原地改写的存储迁移**：所有数据变更走决策。
- **不做零停机在线迁移的承诺**：分批执行 + 中间状态可见 + 可续接；具体停机窗口由环境决定，不在 ADR 里承诺（Platform §10.6 的容量与 RTO/RPO 承诺仍待验收）。
- **不做自动推断的迁移**：每一步都要构建者声明。
- **不做跨应用迁移的原子性**：跨应用沿 ADR-0051 的协同与对账。
- **不做历史清洗**：退役字段的历史值永远保留。

## 4. 后果

- ADR-0011 的"可选标量扩展"从**上限**变成**迁移计划的一个特例**（`add` + `default` 为空的退化情形）。
- 记录迁移从 Host Console 的受权入口扩展为有计划的、构建者可见的资产（前端归 ADR-0047）。
- 迁移会**改变数据**，因此必须在环境演练、备份、恢复路径上被覆盖；`make rehearse` 的两行业演练要加入一次真实迁移。
- 风险：迁移是可破坏的。控制手段是 §D3 的分批 + 可重入 + 幂等 + 显式拒绝清单，以及"计划绑定两个封存版本"。

## 5. 验收

1. 六类变更各一例：新增带默认值的必填字段、重命名（旧名只读别名）、拆分、改引用目标（带映射）、退役动作、退役字段。每例证明：历史仍可读、在途 Flow 仍按旧版本跑、迁移分批可续接。
2. 迁移中途中断：进度与原因可见，重启后从断点继续，已完成批次不重复。
3. 幂等：同计划重跑不产生第二次变更。
4. 客户扩展：给 `core.material` 加两个字段，升级基础包后扩展保留；制造一个冲突（基础包新增同名字段）并证明升级计划显式报告而不是覆盖。
5. 版本协商：用旧 schema 版本提交被接受（同 family）；跨 family 被拒绝并要求刷新。
6. 反例：清单外的步骤类型、把字段物理删除、对被引用的字段做不兼容 `retype` 而无隔离策略 → 计划创建期拒绝。

测试归发布 owner、build owner 与宿主包；`make rehearse` 加入一次真实迁移；`docs/Testing.md` 增"数据与定义演进"手测行。

## As built

**§5 的实现与有界验收已完成。** 证据包括六类逐例的文件/PostgreSQL 日志、两行业真实二进制的 OIDC/PostgreSQL/RustFS 迁移与恢复，以及原工作台浏览器路线；下文明确各自范围。 应用 API 已有 `MigrationPlan` 的封存来源/目标、明确步骤、范围谓词、批次大小、引用映射与失败策略。计划和步骤拒绝未知属性、脚本/物理删除及缺少映射/隔离策略的转换；源码字段退役或重命名须在目标形状中保留为可读的只读字段。

`CompileMigrationPlan` 按源/目标形状绑定字段，复用 ADR-0040 编译器；`MigrationProgram.Transform` 产生独立映像，保留原始字段与输入字节，转换失败不返回部分结果。当前反例覆盖默认值保留显式 false、重命名别名、拆分、显式 decimal 转换、引用映射、退役、未知步骤与原字节保留。这是转换核心证据，不能作为持久迁移、恢复或在途兼容的完成证明。

`POST /v1/releases/migrations/review` 在原发布 owner 的私有安装视图里解析两个已保存版本的形状；来源须为当前封存激活版本。审阅前沿 ADR-0044 检查管理主体与来源行/字段，返回形状、记录量与逐行转换问题。审阅标识绑定计划、形状、来源映像、主体与求值时间；开始执行重新核对当前权限与来源，求值沿审阅时捕获的主体/时间。审阅不激活目标、不修改业务记录；目标必须已有 owner 草稿；提取的新对象可只有封存草稿，不要求先直接发布。

`build.migration` 保存不可变计划与实际进度；builder 通过原提交入口的 `start`、`advance`、`cancel` 操作它，权限、账本、1 MiB 接受预算及恢复继续由原 owner 承接。当前执行限于 build 自有对象；每批把数据映像、实际操作者历史和游标保存到同一个 `record-batch`，同键返回原答复，重放不运行转换。`reject` 转换失败只保存阻塞原因，不写该批先前成功的行；`quarantine` 保存成功行和逐行失败，有未解决失败不能激活。取消按批写补偿事实恢复源值、保留历史，再解除冻结；取消未完成时仍可续接。

迁移期间来源对象可读，普通写入及直接改存储定义被拒绝。每行接受结果与快照保留绑定源发布/字段形状的读取映像，目标事实独立保存；字段形状相同也按发布身份选择读取映像。完成后原发布 owner 验证目标值、引用和约束并激活已封存目标；没有第二套激活器，也不改旧日志或发布字节。可选标量升级保留为不动既有记录的特例，其他变更沿显式迁移与原激活门禁。

自动证据归 `migration_review_test.go`、`migration_execute_test.go` 与应用 API `migration_test.go`：包括三行两批、同键重试、来源冻结、失败整批边界、隔离/取消、快照、实际日志文件关闭重开续接、激活恢复、未选中必填值拒绝及相同字段形状的发布选择。日志后端测试复用原 kit；配置 `PLATFORM_TEST_DATABASE` 时同路线运行 PostgreSQL，未配置时文件日志通过不能代替 PostgreSQL 证据。

原发布工作台已有数据迁移面板：固定源/目标封存版本，编辑受控步骤与范围表达式，保存/发布计划，再审阅、开始、分批执行/取消、读取保存的进度及失败，再走原目标激活。操作复用 K5 outbox；回复丢失后重试原决定，编辑中的计划与尚未确认的决定阻止切换候选。步骤在原迁移面板用类型、批次、源/目标字段、引用映射和原 ExpressionEditor 编辑，支持重排、对象提取、动作退役与范围筛选；高级定义仍可查看和编辑原 JSON，二者共用同一计划，不增加迁移执行器。`migration.spec.ts` 在浏览器覆盖重命名两批、接受后丢失回复/同键重试、刷新续接、激活及新字段编辑；桌面与窄视口有截图证据。

构建器字段声明支持 `readOnly` 与单层 `aliasOf`；重命名计划须在封存目标里声明原名的只读别名。字段归属方统一投影其值，标准写入拒绝旧名；读取、筛选/排序、派生与集合不能借别名扩大目标字段权限。字段退役保留原字段、值与历史，禁止新写；现有 `migration_alias_test.go` 覆盖迁移、后续编辑、权限反例与重放，退役一例证明旧值不改、新建不填写退役字段。在途 Flow 的独立证据见下文。

`retire-action` 已接入真实迁移批次：审阅核对源候选含有该动作、目标候选撤下它，拒绝针对单行的定义退役。每批至多处置声明数量的待审批请求；Work 以自己的账本记录拒绝、关闭任务，原业务归属方执行旧定义的拒绝状态转换。父账本释放后才调用这些归属方，所有接收结果沿既有 child-decision 批次保存；每个决策仍只写自己的权威。拒绝记录保留原提交字节并记实际管理主体。追加失败不暴露审批、业务状态、任务或进度，同键不重复；恢复只应用保存结果。源对象的普通写入仍冻结，获声明的审批拒绝返回可完成。

对象安装替换该对象的完整动作目录与定义集合，历史 schema 学习记录保留；联合候选按重建对象的完整动作集收口，不再从已安装集合补回已撤下的生成动作。激活继续要求完成的迁移声明，不能把单纯从草稿删除动作当成可直接激活的退役。`migration_retirement_test.go` 覆盖两条审批/两批、拒绝状态与任务、追加失败、同键、提前激活/伪造内部处置拒绝、实际退役与重放。已经记账的审批拒绝是新事实；取消后续迁移不会把已拒绝请求改回待审批。

封存启动版本的 Flow 已沿原执行链选择历史对象/动作声明，不再靠“只新增可选字段”的摘要兼容特例。Build 在私有执行上下文用原编译器编译封存对象，账本身份、规则求值、授权与接受结果管线不变；当前成员、策略与能力撤销仍生效。旧字段读取沿显式别名或其发布的保存映像；旧动作写入合并到当前记录，别名写到新字段，保留迁移新增的值并重新检查当前写权限、引用与约束。未封存依赖的开发流程继续阻止不兼容变更；没有历史执行 owner 的代码依赖发生字节变化时明确拒绝。联合候选的定义预览与实际存储准入分别检查：可以先封存待迁移目标，激活仍要求已接受且完成的迁移。对象完整安装才替换动作集合，页面单独安装不再误删对象动作。

每行保留多次迁移的源映像；普通新写入与补偿取消更新共同记录头、保留更早的源值，恢复拒绝重复发布身份或不一致的映像。转换结果复用 `ExprGoValue` 边缘转换写入宿主类型，避免把规则内部 decimal 文本当成浮点字段字节。`migration_flow_test.go` 验证等待→重命名/必填默认值→改动或退役原动作→激活→快照及全日志恢复→旧实例完成、新实例使用新动作；旧实例仍可写旧字段名，经只读别名映射到新字段。`migration_projection_test.go` 验证类型转换后的新写入、第二次迁移/取消与旧源映像恢复。浏览器 `migration.spec.ts` 覆盖原发布工作台迁移后，从收件箱继续旧任务并核对旧/新动作与字段结果；六类逐例的持久恢复与在途证据归下述联合路线。

持有的审批与旧 Flow 新开的审批均按原封存动作，通过与 Flow 共用的历史执行上下文、同一账本和 Work owner 完成；私有 probe 保留上下文并丢弃其写入。`migration_flow_test.go` 验证升级/动作退役后由旧 Flow 发起并完成原审批。显式 `retire-action.redirect` 要求目标是同一对象/权威的封存审批动作；退役批次关闭原任务、返回原业务状态，保留原请求/提交字节并登记目标发布。目标激活后，Work 原作业机制以稳定身份重新授权原请求人、验证目标动作并创建新审批，原/新请求显式关联。当前策略拒绝时保存原因，不创建新请求；重复作业不重复交接。取消迁移不复活原审批，目标未激活的交接不派发。`migration_retirement_test.go` 覆盖默认拒绝、激活前后重定向、策略拒绝、任务关闭、原字节与恢复；浏览器覆盖原迁移工作台→新审批任务→目标动作完成。

拆分/合并后的旧写入复用原转换，将差量写到显式目标字段；只读源字段保留历史值，旧执行上下文的源映像保存本次旧输入。新版本直接写退役字段仍拒绝；纯 `retire` 不获得拆分/合并的写入权限。连续转换沿完成且无失败的封存计划追踪，歧义或缺少转换拒绝，不另设兼容解释器。

`migration_inflight_test.go:TestMigrationSixChangesResumeWaitingFlows` 覆盖 §5(1) 六类变更及合并：每例三行两批，中间实际关闭/重开文件日志、重试原键、续接与激活，再完成三个固定源版本的 Flow；核对原历史字节、成员读取、退役字段写入拒绝和全日志恢复。动作退役使用三条真实待审批请求；拆分再接一次重命名，在第二次迁移中从快照恢复，最早版本的流程继续完成。`TestMigrationRedirectsMultilevelDelegatedApproval` 覆盖源请求停在第二级、目标两级委托审批、逐级实际主体、级间全日志恢复、末级接受失败不露出业务/任务变化与同键重试。浏览器同时验证重命名和拆分的原工作台→收件箱→旧动作完成、新实例用新动作。上述路线已在文件日志及真实 PostgreSQL 上运行，两行业部署范围见下文。

迁移计划已注册为 Build 的 `migration` 资产（能力登记见 ADR-0056 As built）：`build.migration-plan` 保存草稿与最多 64 个不可变版本，发布只保存声明，不执行迁移；原 `AssetRegistry` 管封存、版本解析、私有草稿 bootstrap 与安装。描述体固定 `From`/`To` 两个既有封存闭包，因内容身份循环不能装进自身目标候选；普通 `Requires` 不复制两个发布的可变当前形状。执行固定 `{ref, sourceVersion}`，每次开始仍重新核对原审阅、当前管理权限与来源。旧 API 的内联 `plan` 输入在同一 start 决策中通过同一计划归属方封存，不保留第二执行器；历史 run/发布字节继续读取。`TestMigrationPlanAssetsRetainVersionsAndUseTheOriginalExecutor` 验证草稿/发布、原候选与注册表安装、两版保留、普通成员拒绝、旧版执行、拒绝偷换计划及全日志恢复。工作台在同一面板保存、发布、重载计划并开始固定版本；编辑未发布内容会关闭开始入口，操作仍走原 outbox。

`extract` 已沿原 `MigrationProgram` 执行：声明同一权威的 `target`、`identity`（text 或 reference Expr，`id` 为源记录 reference）与目标业务字段 Expr。每行身份必须非空且不可覆盖既有行，审阅报告重复身份；实际执行按 `reject` 整批阻塞或 `quarantine` 留下逐行失败，未解决失败禁止激活。目标首次声明采用封存 owner 安装映像；start 的 `record-batch` 格式 6 同批保存新对象声明与迁移进度，后续批次保存目标行、源映像及不可变提取来源，1 MiB 接受预算不变。新类型沿原 owner 编译/账本声明注册，恢复只检查版本、前驱和保存来源并应用映像，不运行表达式或重授权。迁移期间目标和来源普通写入均冻结；取消按批归档本迁移创建的目标行、恢复源值，保留新类型声明、历史及提取来源。

旧 Flow 后续写入复用同一提取表达式、实际决策主体/时间与固定目标身份，合并目标差量并检查当前权限/约束；拒绝改身份或覆盖另一来源。源退役字段保留历史值，原版本投影保存新输入，后继旧条件从其固定投影读取。`TestMigrationExtractsDeclaredObjectsAndResumes` 覆盖新对象封存/声明、三行两批、start/批次追加失败不露出变化、冻结、实际文件关闭重开/原键重试、重复身份阻塞/隔离、取消补偿、快照恢复后旧 Flow 完成以及全日志恢复。浏览器迁移路线已含保存/发布计划与对象提取→激活→收件箱继续旧 Flow，并核对目标记录；持久后端已同时验证文件及 PostgreSQL，两行业部署范围见下文。

客户扩展继续沿 ADR-0020 的独立对象/记录归属。发布及联合候选在原对象 owner 捕获只读 `extensionSource`：基础对象的真实归属、包版本与原字段形状；已有扩展的来源不会因基础包升级而改写，旧发布中未记录的来源保持未记录，下一次显式发布才捕获。扩展可有自己的状态与动作，它们只操作扩展方记录，不能取得基础类型的写入权威；编辑器选择基础类型不再删除这些声明。`platform.CheckExtension` 在原发布、普通扩展写入和升级准入复用：核对必填的 base 引用、来源形状及同名字段。基础字段不兼容或新字段与客户字段冲突时报告对象/字段、暂停升级与该扩展的新写入，历史仍可读取与恢复。保留只读别名的显式重命名迁移可解决同名冲突；原迁移的批次、恢复、幂等和激活门槛继续适用。

每次目标准入检查租户全部已安装扩展，包含目标应用闭包外的扩展；不通过升级偷偷重发扩展声明或替换客户记录。原发布审阅的“Customer extensions / 客户扩展”显示原包版本、目标包版本、保留字段与冲突。已接受安装的恢复只核对原受控安装映像与封存字节，原生包前提按旧候选字节参与此核对，不要求等于今天的包；这不安装旧原生代码。新激活仍要求目标原生资产与运行时完全一致，旧 Flow 的原生代码依赖准入不放宽。基础字段形状保存在仅构建者可读的对象元数据中，不通过普通业务类型发现暴露它。

`release_extensions_test.go` 用真实 Core 声明及后续原生包模型验证 §5(4)：`core.material` 的两个客户字段、三个记录与扩展动作在基础包升级后保留，实际文件关闭重开后全日志恢复与快照一致，升级追加失败不改变指针或记录；升级闭包外的扩展也受检查。同名字段反例暂停升级，原重命名迁移三行两批、级间重放后解决冲突；基础字段类型不兼容、伪造只读来源、发布时遮蔽基础字段均拒绝。浏览器沿工作台证明可选字段升级保留扩展、冲突拒绝、联合目标与显式重命名迁移、刷新续接、基础/客户字段独立写入及扩展动作继续执行。该 Core 升级/恢复路线已同时运行文件及 PostgreSQL；两行业部署不替代它对原生包声明升级的专门验证。

发布期 schema 协商已接原对象 owner、候选/激活与账本：只读 `schemaVersions` 按顺序保留至多 64 项 `{version, family}`，内容身份为 `schema.sha256.*`，原 K7 数字版本表示 family。对象记录/发布状态及版本历史自身不参与内容哈希。同一对象保留既有字段契约、权限、约束和动作语义，仅改展示或新增非必填标量时维持 family；其他变更进入下一族。回到早期内容不回退 family，展示内容往返仍允许发布。旧发布没有此元数据时按其原字节导出第 1 族身份，后继发布保留它，不改写历史。

同一族的已保留内容版本沿当前 owner 规则接受；未知内容或不同族返回 `UNKNOWN_SCHEMA` 与英中刷新原因，不写业务记录。拒绝仍由原结果管线保存，改用当前定义须新键。内容声明进入原请求摘要、紧凑结果/批次/拒绝与快照，同键更换或删掉声明即冲突。已有收据即使跨族或动作退役也原样返回；信号死信的锁外准备入口同样绑定声明。恢复只校验保存身份、收据及映像，不重新做兼容判定。审批的原请求身份与 Work 子收据分别核对。
