# ADR-0098 集成记录进入候选封存与晋级：边界、环境绑定与制品生命周期

**状态：** 已接受（2026-10-10）。承接 [SRS/SOW v1.0](../Platform-Refactoring-SOW.md) AR-06、AR-10、AR-12、AR-15 与 F2/F7；交付物 D-04。实现进入 [WorkQueue](../WorkQueue.md) 第 3 块（S-01/S-02 的必要依赖），本文只固定设计、迁移路径与拒绝条件。在实现落地前，现行边界“集成记录不在候选封存/晋级范围”（[ADR-0047](0047-platform-composition-and-workspaces.md) §14）继续成立，不得据本文宣称集成依赖已可整体交付。

## 1. 问题（F2 的具体形态）

页面、对象、Flow、查询、函数、代码与共享属性可进入联合候选、封存与晋级（[ADR-0039](0039-minimal-definition-release.md) 的 9 种资产种类，[platform/definition.go](../../capabilities/server/platform/definition.go)）。集成织物的记录——`build.connection`、`build.source`、`build.dataset`（含版本）、`build.pipeline`、`build.writeback`、`build.match`——是普通租户记录，**不在封存与晋级范围**；`build.table`（决策表，[ADR-0062](0062-decision-tables.md)）同样不在候选闭包内。后果：一个应用的页面与流程可以整体迁移，而它的来源、管道与回写要人工在新环境重建，且没有一致性检查——这正是 S-01/S-02 必须收口的缺口。

## 2. 决定 A：集成记录进入候选，但只封存“定义”，不封存“状态”

| 资产种类（新增） | 依赖边（闭包要求） | 明确排除的记录字段 | 理由 |
|---|---|---|---|
| `connection` | 无 | `state`、`requested`、`last`（检查结果） | 可达性是环境的，不是定义的 |
| `source` | `connection`（可选）、`dataset`（可选）、目标 `object`（可选） | `cursor`、`last`（拉取结果）、`puller` | 游标是消费位置：晋级到新环境必须从该环境自己的位置开始 |
| `dataset` | 无 | `version`、`last`、以及 `build.datasetversion` 的**全部记录** | 行数据是环境业务数据，不是交付物 |
| `pipeline` | `input`/`outputDataset`/步骤引用的 `dataset`、`outputObject`、步骤 `match` | `last`、`state` | 运行历史留在原环境 |
| `writeback` | `connection`、`object`、`on`（动作） | `sent`/`rejected`/`failed`/`answers` | 投递结果与答案属运行证据 |
| `match` | `object` | — | 规则本身是可交付定义 |
| `table`（决策表） | 所引用的对象/字段 | — | 与 F2 同类：能力存在但不在项目资源与候选闭包中 |

闭包规则与既有种类一致：候选声明的依赖必须在同一候选内或解析到目标环境已激活版本；`source`/`pipeline`/`writeback` 引用的对象、动作与查询按 `SourceVersion` 冻结到声明时的版本；解析不到时在**封存前**拒绝并指出缺失引用（不变量：发布自闭合性）。

`dataset` 的 schema 随定义走，`datasetversion` 数据不走；管道在目标环境首次运行会按该环境的数据重新产生版本。因此“数据集有最新版本”不是晋级条件，“schema 与定义一致”是。

## 3. 决定 B：环境绑定按名字解析，凭据不进候选

`connection` 的 `address`、`secret`（凭据名）、`allowPrivate` 以及 `source` 里的裸 `url`/`header` 是**环境绑定**，不随候选搬运：

- 候选携带连接的**逻辑名、kind 与 marking**；目标环境必须在晋级/激活时提供同名连接的绑定（地址与凭据名）。
- 绑定按环境由管理员维护，凭据本体仍只在部署环境的密钥存储中（Platform §2.3）。
- 缺少绑定、绑定名称不一致或 kind 不一致时，激活**在操作前拒绝**并给出具体缺口（哪个连接、缺什么），不做静默回退，也不把地址复制进候选字节。
- 支持的绑定变更是“同名同 kind 换地址/凭据”。需要改 kind 或不兼容地址形态时，必须新建连接并在候选里更换引用——这是显式变更，不是环境差异。

这条与 ADR-0039 的环境解耦一致：候选是定义的字节，环境差异以绑定表达。

## 4. 决定 C：升级、退役与失败处置

- **升级**：集成定义随联合候选的新版本激活替换；已激活的旧版本仍在历史读取中可解析（既有 `release-result` 语义）。游标、窗口与已接受批次不受影响；替换定义不重放、不回填历史数据。
- **在途工作**：正在执行的拉取/管道运行按启动时绑定的定义版本完成；新版本在其之后的下一次运行生效。版本冲突或定义失效时该次运行失败并保留游标，不报告成功。
- **退役**：`build.connection` 有 `retire` 动作（停止来源使用、定义保留）。退役与排空的结果是：不再产生新的拉取，已接受的结果与制品保持可读；删除定义需要显式迁移引用（有 `source` 引用时拒绝删除），不保留永久双轨。
- **失败处置**：失败定位要能回答“哪个来源、哪个版本、哪个连接绑定、哪个游标位置”，这是 S-02 的验收内容。

## 5. 决定 D：封存制品的生命周期所有权

F7 的制品（封存的持续 Flow 批次、大输入引用、计算输出）需要一个明确 owner 与规则，而不是散在各自路径里：

| 制品 | Owner | 保留与清理规则 |
|---|---|---|
| `build.datasetversion` 行数据 | 平台应用 `build`（数据集 owner） | 按数据集 `keep`（默认 3 个版本）滚动；被管道引用时不得清到引用版本丢失 |
| 持续 Flow 批次封存与大输入引用（`files` 字节） | 平台应用 `flow`（批次 owner）+ `files`（字节 owner） | 与引用它的已接受结果/快照同寿命；提交结果不明确时保留字节；已确认未被使用或已幂等命中的预备文件立即回收 |
| 计算调用产物（封存输入/输出） | 平台应用 `build`（`compute` owner） | 随调用历史保留；历史压缩策略未定时不自动删除 |
| 附件与导入字节 | 平台应用 `files` | 记录删除后可回收；孤儿扫描按 `files` 现有清理路径 |

规则：清理只允许删除**没有任何已接受结果、快照或在途工作引用**的制品；清理不得破坏仍需履行的历史读取与恢复义务（SOW §5.3）。孤儿扫描与历史压缩的具体节奏属实现设计，但其拒绝条件（有引用即不删）属本 ADR 决定。

## 6. 拒绝条件（实现时必须先于操作显示）

1. 候选引用的集成记录缺失、版本不匹配或不在封存范围；
2. 目标环境缺少同名连接绑定，或绑定 kind 与定义不符；
3. 数据集 schema 与候选定义不一致（升级方向不做隐式迁移）；
4. 删除仍被 `source`/`pipeline` 引用的连接、数据集或动作；
5. 把凭据、地址或行数据写入候选字节（封存校验拒绝）。

## 7. 迁移与实施路径（第 3 块）

1. `platform/definition.go` 与 `platform/revision.go`：新增资产种类与依赖校验，实现 §6 的拒绝条件；
2. `apps/build`：把集成记录纳入 `joint_release.go` 的闭包与 `revision.go` 的资产描述；`connection`/`source`/`dataset`/`pipeline`/`writeback`/`match` 已存在实体，改为参与候选的“定义”投影；
3. 宿主安装/投影路径（`definitions.go`）与 `environment_lifecycle_test.go`/`environment_http_test.go`：晋级、迁移与升级的既有测试扩展为覆盖连接绑定与 schema 检查；
4. `web/packages/build` 的 `resources.ts` 与发布界面：把集成记录与决策表纳入项目资源与候选选择（当前两者都缺）；
5. [Subtraction](../Subtraction.md) 新增条目的前置条件：只有在上述迁移完成后，才允许删除“手工重建集成记录”的操作说明。旧边界文字（ADR-0047 §14）在实现落地后一并修正。

## 8. 后果

- 校验闭包、升级与失败处置的原则不变，只把集成记录纳入既有机制；不新建第二套发布、迁移或绑定机制。
- 记录状态字段必须有精确的排除清单（§2 表），否则晋级会以“看起来成功”的方式搬运环境状态。
- 实现前，S-01/S-02 的集成依赖交付仍是本项目的必做缺口，WorkQueue 第 3 块承接；实现后可独立核对“页面发布成功 ≠ 应用全部依赖已交付”这条区分。
