# ADR-0124 — 平台整体收敛：现行决策、职责、实现与使用体验

状态：方向已接受（2026-10-15，负责人指令）；范围是整个项目，不限于 ADR-0098。A 的现行入口与核对中确认的文档冲突已整理（§7），其余范围按整块推进；施工顺序唯一归 [WorkQueue](../WorkQueue.md)。本文不把整体目标记为已经实现。

## 0. 问题与目标

项目经历了内核、原生应用、平台能力、可视化构建、Application Studio 和行业包等阶段。历史决定可以继续解释当时为什么这样做，但不能与现行决定一起指挥新开发。已完成的能力、尚在使用的原生实现、旧日志读取责任和未完成的交付，也不能笼统地归为“遗留”。

本工程保留成立的契约、业务能力、数据、权限和运行保证，删除无用实现、合并重复职责、理清产品结构，补齐真实交付必需的缺口。判断对象包括 `contract/`、Go 宿主、边缘实现、平台与行业应用、共享 Web 包、工作区、构建器、制品、部署和项目文档；不是只整理某一轮 ADR 的后续功能。自 2026-10-17 起，明确的减量目标与 XXL 分块由后继 [ADR-0125](0125-xxxl-radical-simplification.md) 接管；本 ADR 的产品边界、历史与保证仍然有效。

不把行数当作唯一结果；本工程也不再以“代码行数不是配额”拒绝量化。用统一口径衡量手写生产代码减量，并逐项证明功能等价与保证保留。一个名字相近的功能不一定拥有相同职责；一个文件更少的实现也不一定更简单。

### 1.1 冲突按主题和适用范围解决

1. 先看状态行与明确的取代范围；只有讨论**同一问题、同一适用范围**时，较新决定才替换较旧决定。编号较大不意味着整篇覆盖此前全部保证。
2. 局部取代时直接在旧正文的相关位置说明现行结论与后继 ADR；不能只在末尾补一个链接，让前面的旧命令继续生效。被取代的理由与重要否决结论保留为历史依据。
3. ADR 中的“先做某项”“下一阶段”只记录当时的实施安排，当前施工由 WorkQueue 决定。已完成的第一切片不得再次成为所有开发的前置任务。
4. “设计已接受”“工程已实现”“检查已通过”“真实使用已验证”分别陈述。不能从一种状态推导出另一种，也不要求给所有旧 ADR 套统一模板。
5. 已知文档与实现不同，回到原归属确认：是文档过期、实现偏离，还是尚未实施的设计。修正文档或实现后，在原 As built 写清支持范围；需要改变已接受的语义时先改对应决定。

## 2. 同一职责只有一个实现

能力归属按实际写入权威、权限、定义版本、生命周期与运行责任判断，不按菜单名称或目录名判断。共享实现留在原归属方，使用方只引用；统一导航不转移资产，统一依赖描述不增加第二个注册表。

能力目录、版本详情与调用结果读取复用原授权引擎，按当前有效角色和原 owner 的策略判定；不能在这些入口另用单个主角色字符串决定可见性。历史版本保留其确切声明，但读取资格仍取当前权限。能力描述直接投影原定义，不能重复解析另一份当前定义或让目录可见性替代执行时授权。

应用成员按完整 AssetRef 呈现，不能因编辑器没有本地记录种类而从资产树消失。添加已有资产同时提供可读草稿与已发布的非导航资源；共享引用沿原应用成员修改和候选发布，不转移 owner、复制定义或增加权限。没有本地草稿的成员进入同一只读定义详情，显示名称、原版本、声明能力与依赖；正式编辑仍由原编辑器承担。

| 内容 | 收敛原则 |
|---|---|
| 平台包 | 提供契约、宿主与通用构建/运行原语，不加入行业词汇 |
| 能力包 | 提供按需安装的技术能力，沿原包、依赖、配置与运行声明参与应用 |
| 行业包 | 保存对象骨架、规则、页面、样本与行业判断；不永久寄生在行业 Go/React 应用中 |
| 应用包 | 保存客户应用及其差异，复用平台和行业资产；交付仍走原候选、版本和环境绑定 |
| 定义、配置、运行数据 | 分别由定义 owner、环境绑定和运行 owner 管理；不能为了统一资源列表混成一种可任意编辑的资产 |
| 原生参考应用与历史读取 | 等价替代前保留有效能力；替代后停止普通新写入，仍履行旧日志、旧定义和在途实例的读取责任 |

已替代的普通执行分支与其重复配置同批删除。确实承担历史责任的代码注明输入格式和用途，不借“兼容”承接新业务。找不到真实调用者或责任的抽象直接删除，不先增加包装层或通用迁移框架。

每块功能整合都要说明原来的重复职责退出在哪里、现在由谁唯一承担，并用原任务检查能力保留。只补连接而保留两套普通实现，不算代码收敛完成；确因不同语义或历史责任保留的路径须有具体依据。代码行数不是机械配额，但新增功能、通过检查和 As built 篇幅不能代替实际删除、合并和简化。

## 3. 已有运行保证继续成立

结构整理不重新设计已经成立的后端。内核规范与向量、单一权威、单租户写入责任、权限判定、持久接受结果、不可变版本和恢复语义继续有效，依据包括 ADR-0026、0038、0039、0097、0098 §9 与各能力 ADR。

界面、API、自动化和 AI 使用相同归属方的规则与权限；跨应用不直接写另一权威。外部效果沿原持久意图、稳定身份、重试与对账；结果不明不能当成功，也不能自动重发危险写入。恢复应用已经保存的结果，不重新求值、授权或访问外部系统。

历史格式、在途版本和真实客户数据不因清理而改写。替换时说明旧写入如何停止、历史如何继续读、在途工作如何处理、失败后如何恢复。没有证据表明实现有问题的保证，不为“统一”另做一套执行器、账本、队列、授权系统或发布机制。

## 4. 按完整任务整理前端与构建过程

围绕应用和用户正在完成的任务组织入口。工作区、应用、资源、页面、记录和任务有各自的导航位置；应用上下文、未保存内容和返回位置随跳转保留。常用功能有正常可发现的入口，同一能力只有一个主要管理位置，可以从其他上下文跳入。

查看详情、选择引用、正式编辑、执行动作和管理配置使用可预测的交互。Inspector、预览、页签、分栏与弹出界面沿现有共享实现承担各自职责，不建立新的通用工作台。清理重复导航时保留复杂业务需要的编辑与操作能力。

发布后的变更仍可按应用集中发现、选择和审阅。是否存在已发布版本与草稿是否改变是两件事，不能用 `state=published` 推导草稿一致。变更读取由原 Build 定义归属方比较当前可编辑声明与保留的发布声明，包含应用本身及其原资产引用；前端清单和数量共用这个结果，不各自比较 JSON 或重新推断发布状态。无效草稿保留诊断，正式候选检查、版本固定与接受仍由原发布过程完成。

用一个连续任务判断构建体验：空白应用 → 对象/字段/关系 → 动作/事务/规则 → 页面 → 流程、集成或 AI → 试跑 → 发布 → 后续修改。遇到阻断就在真实归属方修复；不能靠行业专用前后端、隐藏 URL、手写底层定义或预先改生产状态绕过。

构建期选择统一读取可读的已保存对象草稿，优先于该对象的旧发布描述；对象引用、动作参数、事务、页面模板、页面规则与流程不要求中途先发布模型。流程与自动化的动作输入由原对象归属方描述，仅用于编辑，不伪造发布版本，也不替代执行授权；查询、AI 与计算仍保留其原发布版本。页面 create/edit 可用保存中的模型检查变量与规则，发布和联合候选继续只检查已安装或本次明确选择的模型。草稿描述不进入运行对象目录。关系与对象同批交付时使用原联合候选的对象描述检查，完整约束仍由原私有安装检查；未选中的草稿不能成为已存在的运行定义。应用试跑复用原私有运行器，明确推进测试时间后才观察后台流程，不触碰正式记录。

构建者的应用记录 ID 与已发布应用的运行身份各有用途，不能因共用 URL 参数而相互替代。编辑器保留原构建上下文，预览显式选择可读的已发布应用；共享值仍由原 ApplicationSession 按应用、版本与实例拥有，预览和正式运行隔离。页面跳转、返回及应用页头沿同一上下文传递，不在构建器另建共享变量存储，也不把应用草稿当成已发布应用运行。

AI 函数的构建配置与运行版本同样分开：输入选择可用保存中的对象和字段，仍遵守字段 `aiInput` 限制；发布、候选中的明确选择、实测评估和执行读取继续由原归属方检查。应用内直接新建的函数和智能体应加入原应用成员，保存完成不抢走已切换文档的焦点。智能体工具与函数执行不因构建配置可选而获得未发布版本或额外权限。

集成配置沿同一原则：对象与映射可选保存中的模型，源、管道、回写和匹配规则共同交付使用原联合候选，不要求先把新模型投入运行。连接可达性、凭据引用及目标环境绑定继续归原连接与环境配置，配置草稿不等于已就绪连接。直接新建的集成定义加入原应用成员，保存、共同发布、执行拉取/投递是分开的操作；不增加连接存储、读取器、调度或重试队列。

应用验证继续使用原样本集、TestPlan 与隔离运行器。新建样本和业务测试计划进入原专用编辑器，普通合成记录与动作输入复用已有类型化表单，复杂值和故意错误的输入保留高级 JSON；不从生产读取候选记录。样本保存和加入应用分开处理，重试不重复写已接受的定义，也不覆盖同时加入的其他成员。可移交计划的具名 roots、样本值与固定时间保持原语义，本地对照成员与模型绑定不进入制品。结果应能定位原模型、动作或流程，返回修改时保留应用与测试输入；通过试跑不替代候选审阅和激活。

应用运行中的排查沿原 Runs 投影和各运行归属方进行。筛选、实际运行状态、关联业务记录、启动版本和原回执应可直接查看；需要处理失败时明确打开原正式运行或记录详情，不把只读查看当成操作入口。构建应用与已发布应用的返回位置分开保留，不另建运行中心、状态账本或重试入口；结果不明仍先读回或人工处理，不能因为页面提供重试按钮而自动重发外部请求。

## 5. 范围与完成条件

下面是整个工程的结果要求，**不是第二份队列，也不是每次修改都要跑的检查表**。每块只处理当前有证据的问题；相邻领域已有正确实现时直接复用。

| 范围 | 要交付的结果 | 何时算这块完成 |
|---|---|---|
| A 架构决定与文档 | 现行来源、取代范围、历史理由和实现边界清楚 | 项目入口与相关正文没有相互冲突的现行指令；已知差异有准确结论 |
| B 能力与资产归属 | 明确现有能力由谁定义、编辑、引用、安装、发布、运行和退役 | 同一职责不再有竞争归属；开发者能判断复用、扩展还是缺少原语 |
| C 代码与旧实现 | 删除无调用职责的实现，合并确认重复的执行与 UI | 新工作只维护一套实际实现，历史责任和有效行业能力保留 |
| D 运行语义 | 修复具体入口间的权限、决定、失败、取消或恢复差异 | 受影响入口遵守原语义，旧版本与接受结果仍按原保证工作 |
| E 信息架构与交互 | 清楚的入口、导航与打开规则 | 用户能找到功能、预期操作结果，切换时保留工作内容与上下文 |
| F 完整应用构建 | 连续完成建模、行为、界面、装配、验证、发布和修改 | 实际完成一个业务任务；复杂规则与专业组件不以手写底层定义为正常前提 |
| G 生命周期与交付 | 四层包复用、客户差异、升级和退出责任一致 | 同一资产沿原机制交付与演进；有等价替代和历史安排后才能退出原生实现 |
| H 运营与证据 | 可定位问题，准确说明实现、验证、容量与保留范围 | 关键承诺有相应证据，真实设备、客户、容量和长期运行的未知不被写成通过 |

整体完成意味着这八类结果共同成立：产品一致、决策兼容、职责清楚、重复减少、操作和构建连续、生命周期保证保留、行业知识可复用，并有与声明范围一致的使用与运行证据。完成一块不能被写成整个工程已经完成。

## 6. 执行与验证

先整理 A，之后从当前代码与实际任务中选择下一整块，顺序只在 WorkQueue 更新。原供暖交付要求继续归 ADR-0122；MES 的第二验证、真实行业资产复用和原生应用退出条件均不被本工程撤销。客户现场尚未准备好，不阻止已能实施的平台整理；模拟结果也不替代真实交付。

每块开始由代理自行判断问题最可能在哪里、最直接的修改是什么，用最少的相关文件确认后动手；负责人不必逐块回答“直觉”，明确调整优先级时再遵循。整个 A–H 范围保留，不因当前切片遗漏其他目标。可独立的核对和实现交给子智能体，指定不同路径和产出，主代理统一决策与整合；不让多代理重复调查同一问题。

检查与实际变更相称。纯文档只检查链接和差异格式；代码先完成一个整块，再按 AGENTS/Testing 运行适用检查。权限、持久化、历史格式或公共接口发生变化时检查相应保证；不因整理目录而全面重测、不靠增加测试数量证明完成。ADR-0082 的精简原则保留，其固定八条浏览器路线的限制由此修订为按独立任务责任保留，不为数量删除必要检查。部署与现场结果只有实际执行后才记录。
