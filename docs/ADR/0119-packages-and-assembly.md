# ADR-0119 — 包的四层：平台包、能力包、行业包、应用包

状态：已接受（2026-10-12，负责人指令）· **消歧**：宿主既有 `Package`（`capabilities/server/packages.go`，Platform §2.5 的"能力包=可信代码或受控定义的分发单元"）是**分发机制**，本文定义它承载的**四类内容**；机制沿用，协议原生制品扩展见 ADR-0123，术语归属见 §1 · 与 ADR-0107（工件）、ADR-0114（退出）、ADR-0098 §9（边界）配套

协议能力包的可执行分发、独立网关与配置由 [ADR-0123](0123-pluggable-protocol-packages.md#11-as-built) 补充；原 Package 已支持可信原生制品的确切版本安装、封存与保留，不另建包管理器。

## 0. 意图

平台今天知道自己有"内核、宿主、构建器"，也知道 FDE 会做出"应用"。但**中间那两层没有正式形态**：

- 一个精通 IoT 的 FDE 和一个精通离散制造的 FDE，**共用的东西是什么**？
- 我们从第一个楼宇项目里学到的东西，**怎么变成第二个楼宇项目能直接拿来用的东西**？
- 大疆的 WMS 需要的"3D 库位实时预警"、"AGV/RCS 接入"，**是应用的一部分，还是别的东西**？

答案是后两者都不是"应用"，而是**能力包**与**行业包**。没有这两层，每一次交付都是从头再来——这正是"中国 FDE 没有武器库"的具体含义。

**判据**：第一个交付项目结束后，从中沉淀的东西**能被第二个项目在不改平台的前提下拿起来用**。

## 1. 术语消歧（先读这一段）

| 词 | 指什么 | 别混用成 |
|---|---|---|
| **`Package`**（既有机制） | 宿主包管理器：版本化分发单元，按声明预检、兼容安装、升级、排空、退役（`capabilities/server/packages.go`） | 不是内容分类 |
| **平台包** | 我们写的东西：内核、宿主、构建器、事务/规则/约束/集合/集成/AI 原语 | 不是"一个包" |
| **能力包** | 我们写的**面向一种技术**的扩展：数字孪生、3D 库位、GIS、时序视图、设备对接 | 不是既有的 `Package` 本身 |
| **行业包** | 我们写的**某个行业的特殊性**：对象骨架、规则模板、页面装配、样本、验收场景 | **客户不可见**（§2） |
| **应用包** | **FDE** 写的某个客户的应用，即 ADR-0107 的工件 | 不是 ADR-0102 的"客户扩展字段" |

**关系**：宿主 `Package` 是运输车，上面四类是货。**"能力包"一词今后只指能力包，不再泛指 `Package`**；既有 ADR 与代码里的 `Package` 保持原名不改。

## 2. 四层，谁写、谁可见

```text
应用包（FDE 写 · 客户可见可改）
   │ 依赖（单向）
行业包（我们写 · 客户不可见）
   │ 依赖
能力包（我们写 · 客户不可见）
   │ 依赖
平台包（我们写 · 客户不可见）
```

| 层 | 谁写 | 客户可见 | 内容 | 例子 |
|---|---|---|---|---|
| **平台包** | 平台开发 | 否 | 内核契约、宿主、构建器与工作台、事务/规则/约束/集合/生命周期/集成/AI 的原语与执行 | ADR-0100–0118 交付的东西 |
| **能力包** | 平台开发 | 否 | **面向一种技术**的可插拔扩展；依赖平台包；向行业包提供能力 | 数字孪生、3D 库位实时预警、GIS/地图、时序视图与统计、设备对接适配（外部库的封装）、报表/看板平台连接器 |
| **行业包** | 平台开发（可带 FDE 参与定义） | 否 | **某个行业的特殊性**：对象骨架、共享类型、规则模板、页面装配、样本数据、验收场景、构建步骤与工时记录 | 楼宇供暖、离散制造、大型化工、仓储与 AGV |
| **应用包** | **FDE** | **是** | 某个客户的应用：他的模型、规则、页面、集成、AI、权限，即 ADR-0107 的工件 | 某物业公司的供暖管理系统 |

**关键区分（负责人明确）**：行业包**不是**客户的东西，也不是 FDE 的草稿。它是我们对一个行业的理解，写出来供**同行业的所有应用**复用。客户改的是**应用包**；客户在应用包之外能改的，还有 ADR-0058 的**扩展字段/动作**（字段级），两者是不同粒度。

**为什么能力包与行业包分开**：能力是**技术**（数字孪生对供暖和仓储是同一件事），行业是**业务判断**。一个精通 IoT 的 FDE 和一个精通离散制造的 FDE 共享同一批能力包，行业包不同——这正是"武器库里有一半是通用的"。

## 3. 依赖与组合

1. **依赖单向**：任何包只依赖它下面那一层，或更低；**不得反向依赖**（行业包不得被平台包引用，应用包不得被行业包引用）。
2. **能力包可被应用包直接依赖**：跨行业的技术能力不要求先有行业包。
3. **一个应用包可以依赖多个行业包与能力包**；一个行业包可以依赖多个能力包。
4. **组合检查在安装期**（复用宿主既有的预检/兼容安装，`packages.go`）：缺依赖、版本不兼容、同名冲突都要**明确拒绝**。
5. **平台包不被任何包扩展**：一个能力包做不到的事，不能靠改平台包来表达（§6）。

## 4. 武器库 = 能力包 + 行业包

负责人原话："他们都要在自己的专业领域有一套武器库"。

- **能力包**是武器库里**技术的那一半**：精通 IoT 的 FDE 与精通制造的 FDE 共用；
- **行业包**是武器库里**业务判断的那一半**：只有同行业的人用得上。

**武器库的真实内容是"判断"，不是"组件"**：这类客户的设备怎么编、异常怎么分级、哪些指标老板真的看、哪些配置能让客户一眼认出来"这是我们行业的东西"。这些**今天没有载体**（在开发者脑子里、在 `apps/mes` 的 Go 代码里、在 `docs/Apps.md` 里，都不是武器库）。

**行业包必须从交付里长出来，不能事后整理**：见 ADR-0122 §3 把"产出一件可复用行业资产"写成交付的停止条件。

## 5. 版本、交付与退役

| 项 | 规则 |
|---|---|
| 版本 | 每个包有稳定 ID 与内容版本（沿 ADR-0107 的工件版本与 ADR-0039 的封存语义） |
| 安装与卸载 | 安装状态与内容版本分开：卸载后可以重装同一份包，也可以显式切回已保留的原版；只有内容改变才需新版本。同 ID、同版本的完整描述及其制品必须与原封存内容一致，不能因卸载而覆盖 |
| 交付 | 应用包的交付 = 工件 + 环境绑定 + 迁移计划（ADR-0107 §D4），不变 |
| 行业包/能力包升级 | 走 ADR-0106 的迁移计划；**依赖它们的应用包必须显式声明兼容范围**，"自动跟随升级"不做 |
| 退役 | 走 ADR-0114 的三条件（等价、验证、无残留依赖）；**能力包退役必须迁移或保留历史读取义务** |
| 客户扩展 | 客户对**应用包**的修改属于 FDE 的草稿/候选；对**行业包**无修改权；跨基础升级的扩展保留归 ADR-0106 §D6 |

部署目录与租户安装记录不是同一种状态：移走目录中的描述不会卸载包，也不能让安装/退役记录从管理入口消失；目录不再提供的版本仍可查看原声明与安装状态，但不能从目录重新安装。已安装的有效封存包按原权限继续使用。排空中的包仍是已安装包，保留名称占用且不接受新的依赖方；只能显式切换版本，不能通过再次安装绕过原版本检查。卸载复用排空与退役，不删除由包创建的应用、业务数据或历史。退役后重装原版或安装新版本均保留其他旧封存版本，供原绑定继续读取；当前版不同时出现在保留版本列表。退役不得留下其他未退役包声明的依赖，依赖按其已安装的封存描述判断，而非今天目录里的新描述。

## 6. 预留与扩展点（负责人指定）

负责人："在内核里面要给它做预留，否则我们改内核是很麻烦的。说到很边缘的地方了，就不用再搞预留了。"

**预留的规则**（这条防止两种极端：什么都不留 → 以后改内核；什么都留 → 空抽象）：

1. **预留的是机制，不是领域词汇。** `contract/` 不含领域词汇（AGENTS 硬规则 1、ADR-0098 §9.1）：不得为 AGV、库位、门禁之类预留字段或类型。预留发生在**平台层**（`platform` 与宿主的具名契约）。
2. **只为"已命名的下一次交付"预留**：当前是**仓储与 AGV**（WMS 立库 RCS、AGV WCS、黑盒下游指令，ADR-0121 §D7）。没有命名交付的地方**不留**——边缘情况不留。
3. **预留的形态**：一个具名的扩展点（接口/契约形状/资产种类），**只有声明没有实现**，且**不进入任何产品入口**。它不产生"半成品功能"，只保证形状可插入。
4. **预留不等于半实现**：不得留下空方法、`TODO` 分支或未接通的面板（AGENTS 硬规则 6）。预留的检查标准是"三天后能插进来"，不是"看起来像已经支持"。

**不做预留的地方**（避免蔓延）：第二种数据库、插件市场、跨租户联邦的深度、行业算法库——这些**没有命名的下一次交付**。协议包已由负责人指定为当前供暖接入的需要，范围按 [ADR-0123](0123-pluggable-protocol-packages.md) 的模拟与 S7-1200 子集推进，不因此预留其他历史协议。

## 7. 不做

- **不做插件市场/公共分发**（ADR-0008 §1 的既有边界：第三方生态待平台内部成熟后再考虑）。
- **不让客户改行业包**（负责人明确）。
- **不把能力包做成"组件库"**：能力包是**技术能力**（计算、呈现、对接），组件仍归 `@platform/ui`（ADR-0110）。
- **不让行业包携带执行代码**：行业包是**受控定义 + 样本 + 装配**，不是 Go/TinyGo；需要代码的算法走 ADR-0044 的受控代码，作为能力包的一部分包装。
- **不建第二套包管理**：复用宿主 `packages.go` 的机制。

## 8. 后果

- 平台第一次有了"**交付物可以沉淀**"的形态：一个项目结束，产出应用包（客户用）+ 行业包/能力包的增量（我们复用）。
- 需要一次**分类核对**：今天 `solutions/hospitality`、`solutions/manufacturing`、`apps/*`、`web/packages/*` 里的东西各属于哪一层。**核对结果不产生代码搬迁**，只产生归属判断；搬迁随 ADR-0114 的退出发生。
- `packages.go` 的既有安装/升级/退役机制可能不够表达四层的内容差异（尤其"行业包被同行业多个应用复用"），差异在哪、要不要扩展，在第一个行业包落地时确定——**本文不预先扩展机制**（§6 规则 4）。
- Catalog（ADR-0045）需要能索引能力包与行业包的**可复用资产**，而不只是组件与模式。

## 9. 验收

1. **分类核对**：给出一份清单，把 `solutions/*`、`apps/*`、`web/packages/*`、Catalog 现有资产逐项归入四层之一（平台包/能力包/行业包/应用包），并为"不属于任何一层"的项说明处置。**产出判断，不搬迁代码。**
2. **第一个行业包**：ADR-0122 的第一次交付结束后，产出一个楼宇供暖行业包，**第二个同行业场景能直接复用**（用一个复现场景证明：只配应用包、不改行业包与平台包）。
3. **第一个能力包**：至少一项技术能力（从时序视图、GIS 或设备对接里选一个）以能力包形态存在，且被**两个不同行业**的应用包依赖。
4. **依赖检查**：反向依赖、缺依赖、版本不兼容、同名冲突在安装期被明确拒绝。
5. **预留检查**：§6 规则 4 —— 检查是否有预留退化成半实现（空方法、未接通入口、假支持）；有则视为缺陷。
6. **反例**：把行业包做成客户可见、让行业包携带 Go 代码、为一个边缘情况预留形状、把能力包当组件库 → 分别拒绝。

测试归宿主 packages owner 与 Catalog 生成；`docs/Testing.md` 增"包分层与复用"手测行；`docs/Apps.md` 增可执行用法。

## As built

原 `PackageDescriptor.blueprint` 承载原 owner 的受控定义、应用根与构建说明，确切版本安装并封存，不自动跟随目录变化。行业包卡只对构建者提供 **Create application drafts**：另一个 Build 决定复用原发布草稿准备及批量接受格式，读取已安装的封存包，检查各个原 `.create` 权限并创建原草稿；不发布、不授角色、不创建业务数据。同名冲突明确拒绝，相同请求保留原 ID。包列表同时保留当前目录与租户已有安装/退役记录，`source` 区分目录提供与原安装记录；目录中已移除的版本显示原封存声明和不能再安装的原因，不伪装成仍可提供的版本。退役检查其他未退役包的封存 `Requires`，排空中的依赖方仍受保护；早于封存机制的历史安装只能使用原确切版本描述，缺少声明时说明原因并拒绝猜测依赖。排空不能通过安装绕过版本切换；退役后重装原版或安装其他版本均保留原版本映射，原接受结果、重放和快照机制不变。

派生动作和默认页面由 Build 原逻辑生成，行业 JSON 不复制它们。逻辑连接可先作为无地址草稿建立，同批对象/集成引用使用原准备上下文；正式候选与激活仍检查真实环境、依赖和执行权限。未引入第二包管理器、导入语言或业务执行器。统一构建入口为 `make packages`，协议包与 `deploy/packages/*.json` 进入同一可信目录。

包生命周期检查沿 `TestPackagePrecheckInstallDrainRetire`、`TestProtocolPackageInstallRetainsVerifiedBinary` 与 `TestPackageBlueprintCreatesOnlyDraftsAndRecovers`：普通包、行业蓝图与协议包同版重装，拒绝当前/保留版本的内容变化；排空保留名称与依赖保护；反复切换后保留三版唯一解析，以及保存失败/原请求重试、日志重放与快照恢复。蓝图卸载重装不改变已有应用草稿。包卡片分别显示来源与当前安装状态，不再把同一版本已经安装显示为运行失败；实际原动作拒绝仍保留原因。界面将退役显示为卸载后的未安装状态，提供重新安装与切换版本；预检和实际安装使用同一内容检查，缺少依赖时不可安装。浏览器范围沿 `protocol-packages`，不外推为真实设备或客户退役验收。

首件配置为 `industry.heating` 的模拟版本，含模型、页面、观测、维修流程、测试计划、样本、只读 AI 与业务告警推送。行业业务行为只在定义中；实际客户上线、多城市接入与行业判断由 ADR-0122 的真实交付继续验证。
