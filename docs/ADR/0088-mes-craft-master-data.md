# ADR-0088 工艺主数据：可复用的工艺路线、工序号即身份、算出来的可用设备

状态：已落地（2026-10-09）；MES 作为流引擎的验证场景（负责人 2026-10-09 指定）。

## 背景

负责人 2026-10-09 的要求：搭一个完整场景证明流引擎封装到位——MES 工艺流程，把工序/产品/工艺流程/设备/工艺参数建模到能被流引擎画出来，并且在 SFC 加工时呈现出每个工步要求的加工参数与**哪些设备能加工它**。

先核对 `apps/mes/server` 的既有事实，四处都不够用：

- `Operation{Step, Name, WorkCenter}` —— 没有工艺参数，"这一步要把温度压到多少"无处可写。
- `Product{ID, Name, Routing string, Operations}` —— 工艺路线只是一个名字字符串，工序内嵌在产品里，两个产品要用同一条路线就得抄两遍，也没有版本。
- `WorkCenter{ID, Name, Line, Resources []string}` —— 资源只是裸 ID，没有能力，所以"哪些设备能加工这一步"**根本无法回答**，只能答"这个工作中心的资源"。
- `SFC.Step int` 是"产品工序数组的下标"，而 `Operation.Step` 是 10/20/30 —— **两套编号**；前端 `product.operations[sfc.step]` 把两者混用，处置对话框让操作工**手输一个数组下标**（`reworkStep`，上限 `sfc.step`）。

## 决定

### D1 工艺路线成为一等的、可复用的、带版本的东西

`Routing{ID, Name, Version, Operations}`，`MasterData.Routings` 每个版本一条，`(ID, Version)` 是键；`Product.Routing` 只留一个 ID。于是两个产品可以共用一条路线（种子里 P-100 与 P-150 共用 RT-100），一条路线可以有修订（RT-200 v2 在机加工后插了一道去毛刺）。

`SFC` 记下 `Routing` 与 `RoutingVersion`：**下达那一刻固定**。改工艺路线不会移动已经在车间里的批次——`released()` 读批次自己的版本，`routingFor()` 才读最新版本，两者是不同问题。

### D2 工序号既是身份也是次序，一套编号

`Operation.Number`（10、20、30）同时是身份与顺序，`Step` 消失。`SFC.Operation`、`NC.Operation` 都按工序号说话，返工的载荷从 `reworkStep` 改成 `reworkOperation`。

这一步修掉的是"操作工手输数组下标"：`reworkable()` 的规则是"该批次自己那条路线里声明过的工序，且不超前于它当前所在的工序"，于是处置对话框变成**一个可选的工序列表**，而不是一个要记住的数字。

### D3 工序带工艺参数

`Parameter{Name, Title, Type, Unit, Target, Min, Max}`，`Type` 说明这几个数字怎么读：`setpoint`（保持这个值）、`range`（留在 min–max 之间）、`limit`（不超过 max）、`note`（读并确认，没有数字）。前端按 `Type` 渲染，不自己解释数字。

### D4 资源带能力，"哪些设备能加工"是算出来的

`Resource{ID, Name, WorkCenter, Capabilities}` 取代 `WorkCenter.Resources []string`；`Operation.Requires` 是这道工序对设备的能力要求。

规则只有一条，写在 `canDo`：资源属于该工序的工作中心，**且**持有该工序要求的每一项能力。这条规则有两个用途——`Master()` 出门前把每道工序的 `capable` 算好一起服务，`start` 动作按同一条规则拒绝。**服务端算、服务端拒、前端只显示**，所以操作台看到的答案与服务端执行的答案不会各说各话。

种子里故意让这件事不平凡：装配工作中心有 ASM-1（`assembly` + `torque`）和 ASM-2（只有 `assembly`），而装配工序要求两项能力，于是可用设备只有 ASM-1——"哪些设备能加工"不等于"这个工作中心有哪些设备"。

### D5 主数据仍然是种子，不落库

`DemoMaster()` 依旧是一个内存种子，经 `GET /v1/master` 服务；这一版没有给主数据加持久化、变更台账或权限。`docs/WorkQueue.md` 的口径不变：MES 是受控装配探针，**本块不据此宣称平台已具备完整 ERP/MES 的行业语义**——它是流引擎的验证场景。

### D6 工艺页：工作中心就是泳道

新增 Craft 视图，把一条工艺路线按 ADR-0087 D4 的方式画出来：`FlowSteps` 接受 `lanes`，这里用**工序触及的工作中心**当泳道，于是一条路线是"横跨铸造、机加工、检验三个责任"的图，而不是一串孤立的方块。SFC 详情用同一个 `RoutingFlow`，只是多叠上批次当前所在位置、状态与各工序上的不合格品。

## 后果

- 工序/产品/工艺路线/设备/工艺参数五样都能被流引擎画出来；SFC 详情页直接呈现"这一步要保持什么参数"与"哪些设备能加工这一步"，开工的设备下拉就是服务端算出的 `capable`，选不到不能加工的设备。
- 一套编号，处置对话框不再要求操作工心算数组下标；批次固定在自己下达时的路线版本上。
- 能力匹配只有一条规则、一个实现，既用于服务也用于拒绝，前端不重新实现。
- 顺带删掉 MES 中文词典里 13 条早在本块之前就已成死条目的文案（i18n 扫描测试只查"用了没翻"，不查"翻了没用"）。
- 代价与验证口径：`apps/mes/server` 经离线 vendor 工装 `gofmt`/`build`/`vet`/`test` 全绿（含新增的三个测试：批次读自己的路线版本、可用设备是算出来的且 `start` 按同一规则拒绝、返工指名工序）；`packages/mes`/`ui`/`app`/`workspace`/`catalog` `tsc` 全绿；`pnpm -r run test` 全绿（含 i18n 扫描）；`scripts/escapes.sh` 无新增。**未在浏览器观察**——泳道化的工艺路线图、参数面板与设备下拉的实际外观需要一次真实走查。

## 未做

- **主数据落库与权限**：工艺路线、工序与设备现在是种子；要真正维护它们，得让主数据成为 `platform.Record` 并接上编辑权限与变更台账。
- **参数实测与工艺纪律**：`Parameter` 说明"要保持什么"，但没有任何东西记录"实际保持了多少"，也没有超差自动判不合格；那属于过程数据采集（网关已经在推设备状态，见 `equipment.go`），与本块分开。
- **能力分级与设备占用**：能力现在只是名字，没有等级；`capable` 也不看设备是否正在加工别的批次。要排产就得再加负载与日历，那是调度问题，不是主数据问题。
- **工序间的物料与工装**：一道工序除了设备还可能要求物料、刀具与程序号；本块只建了设备能力这一维，因为负责人的场景问的是"哪些设备能加工"。
