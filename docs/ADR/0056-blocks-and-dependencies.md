# ADR-0056 — 功能块衔接与依赖真理：一份描述，多处读

<a id="adr-0056"></a>

状态：已接受（2026-10-12，负责人指令，ADR-0038 §2/§3 的结构面，与依赖表配套）· 统一 ADR-0020 的 Interface 查询、ADR-0013 的能力目录投影、ADR-0031 的血缘与 ADR-0043 的集合：**它们是同一份依赖描述的不同读法**，不再各自维护 · 本文是 ADR-0039、ADR-0040、ADR-0041、ADR-0042、ADR-0043、ADR-0044、ADR-0045、ADR-0046、ADR-0047、ADR-0048、ADR-0049、ADR-0050、ADR-0051、ADR-0052、ADR-0053、ADR-0038、ADR-0054、ADR-0055 的**依赖真理**：任何新能力必须先说明它衔接进哪一块、通过哪种引用

## 0. 实施前的问题

ADR-0038 §2 的图中，统一业务平台有一条横线：业务模型 · 业务规则 · 业务执行 · 数据与集成 · 协同与 AI · 应用生命周期。**本 ADR 实施前，这些范围的依赖描述互相分离**：

| 块 | 对外说清自己"能给别人什么"的地方 | 引用它是靠什么 |
|---|---|---|
| 业务模型 | `Definition{Ref, Entity, PropertyType, LinkType}`（`platform/definition.go:381-400`） | `AssetRef{App, Kind, Name}` |
| 业务规则 | 编译进 `Entity.Lifecycle.Transitions`（`platform/entity.go:153-169`）与 `platform.Operation`（`operation.go:289`） | 动作名、操作名 |
| 业务执行 | `flow` / `work` 应用的实例 | 流程名、任务 |
| 数据与集成 | 六类集成 `Definition`（`AssetKind` 的 connection/source/dataset/pipeline/writeback/matching，`definition.go:32-37`） | `AssetRef` |
| 协同与 AI | 协议（`Protocol`）、AI 函数（`AIFunction`）、智能体 | 协议名、函数名 |
| 应用生命周期 | `ReleaseAsset` / `Candidate` / `Active`（`platform/revision.go`） | 候选闭包 |

**问题不是缺结构，是缺一份统一的说法。** 具体表现为四个各自为政：

1. **引用形状不统一**：有的走 `AssetRef`（对象、页面、查询、集成），有的走**名字字符串**（动作名、操作名、协议名、函数名），有的走**路径数组**（`condition.Field`、`Binding.Path`）。于是"这个页面用了哪些资产"要按类型分别算。
2. **依赖的写入点分散**：`Definition.Requires` 由**四处不同代码**填（页面 `definitions.go:1010`、应用 `:1130`、查询 `:518-525`、候选 `release_candidate.go:72-130`），没有单一权威说"这个资产的依赖是这些"。
3. **四种"看关系"的方式各算一遍**：候选闭包（`release_candidate.go:18-179`）、血缘显示（`Lineage.tsx`）、影响面（候选差异）、企业模型的 `UsedBy`（ADR-0031）——**同一个问题，四份实现**。
4. **能力目录不完整**：`platform.Operation` 是"可被流程/页面/能力 API/AI 调用的操作"的目录，但**动作、查询、函数、协议、集成不在同一个目录里**，所以"这个块能给别人什么"没有单一答案，只能翻代码。

**判据**：对任意一个已安装资产，能一次回答三个问题，且答案来自同一份描述：**它依赖谁**、**谁依赖它**、**它向别人提供什么能力**。

## 1. 决定

### D1 一份依赖描述：所有跨块引用都是 `AssetRef` 或它的具名特化

```go
// 唯一依赖描述。每个已安装资产恰好一份。
type Dependencies struct {
    Ref      AssetRef      // 我是谁
    Requires []AssetRef    // 我依赖谁（跨块统一）
    Provides []Capability  // 我向别人提供什么（见 D2）
    Version  string        // 我的内容版本
}

// Capability 是"能被别处引用"的东西：动作、查询、函数、操作、协议操作、接口。
type Capability struct {
    Kind    string       // action | query | function | operation | protocol | interface
    Name    string       // 稳定名（命名空间内唯一）
    Inputs  ValueSchema  // 输入形状（或引用到声明）
    Outputs ValueSchema  // 输出形状
    Roles   []string     // 谁能用它（授权仍由 ADR-0044 判定）
    Side    string       // pure | effect | authoritative（见 D3）
}
```

要点：

- **引用一律解析到 `AssetRef` 或 `Capability`**：字段名/路径在**解析时**绑定到具体资产（如 `supplier.country` 解析为"对象 A 的字段 supplier → 对象 B 的字段 country"），因此依赖可以被机器算出，不靠人工声明。
- **`Provides` 是块之间的连接面**：业务规则块通过 `Capability{action}` 提供动作；业务模型块通过 `Entity`+`Capability{interface}` 提供结构；协同块通过 `Capability{protocol}` 提供跨系统操作；AI 块通过 `Capability{function}` 提供类型化推断。
- **`Side` 区分三类**（这是 ADR-0038 §2 反复强调的"业务规则成为正式定义"的落点）：
  - `pure`：无副作用（查询、计算、决策表、计算字段）；
  - `effect`：只声明意图（外部效果、通知、AI 调用）；
  - `authoritative`：改变权威状态（动作、事务）。

  **一个 `Capability` 的 `Side` 决定了它能被什么使用面调用**：`pure` 可用于条件、约束、页面绑定、AI 上下文；`effect` 与 `authoritative` 只能由受权提交路径调用。

### D2 一份依赖描述，四种读法

`Dependencies` 是**唯一写入点**，四种读法都是它的投影：

| 读法 | 用途 | 现在的实现 | 变成 |
|---|---|---|---|
| **闭包** | 候选要带哪些资产（自闭合） | `release_candidate.go:18-179` | 读 `Requires` 的传递闭包；悬空引用发布期拒绝 |
| **血缘** | "这个数据/字段从哪来" | `Lineage.tsx` + `Definition.requires`；集成血缘读定义本身（ADR-0031 已说明"证明的是声明不是观测"） | 同一份 `Requires` 的图；**运行时证据并排显示，不混入声明图** |
| **影响面** | "改这个会波及什么" | 候选差异（`previewCandidateLocked`，`:179`） | `Requires` 的反向图；与血缘是同一份数据的两个方向 |
| **能力发现** | "这里能引用什么" | `Operation` 目录 + `/v1/apps` 的声明 + 动作目录 | `Provides` 的合并视图；**角色过滤在读取时施加**（ADR-0044），不是另一份目录 |

**"谁是主人"不再需要单独回答**：`Requires` 里指向别的应用的边就是跨应用依赖，它同时是权限边界（ADR-0006 的协议）、发布闭包（ADR-0011）、影响面（ADR-0047）的依据。

### D3 块之间的调用资格由 `Side` 与授权共同决定

这是本 ADR 最有约束力的一条：**块与块之间能不能调用，由 `Side` 加授权决定，不由"谁写代码"决定**。

| 从 → 到 | pure | effect | authoritative |
|---|---|---|---|
| 条件 / 约束 / 计算字段 | ✅ | ❌ | ❌ |
| 页面绑定 / 显示 | ✅ | ❌（显示只读结果） | ❌ |
| 事务步骤（ADR-0039） | ✅ | ✅（只声明意图） | ✅（必须显式声明，且过授权） |
| 流程步骤 | ✅ | ✅ | ✅（每一步是新提交） |
| AI 上下文 / 工具 | ✅ | ❌ | ❌（AI 只能提议，采纳是人或受权主体的提交，ADR-0054 §D2） |
| 协议（跨应用） | 通过 `Probe`（只读，ADR-0006 §设计 1） | ❌ | 必须走 `Request`（独立决策） |

**这张表把今天散落在各处的"不允许"集中到一处。** 例如"AUI 在规则体内不能改别的应用"、"AI 工具只能调用已声明动作"、"页面不能写数据"，都是这张表的实例。

### D4 应用生命周期块是"依赖真理"的持有者

ADR-0050 的 `sample-set` 归 Build：有稳定名称、保留版本和合成记录的声明资产；依赖其样本所指的对象模型，应用通过原 `Resources` 引用，随原应用候选封存。样本不携带生产记录来源、凭据或执行权；试跑与原 `build.testplan` 共用这些输入，不新增测试执行器。它属于现有 D7 验证能力，规则、约束、动作与授权仍归原 owner。

- `ReleaseAsset` / `Candidate` / `Active` 是唯一封存依赖描述的地方（`platform/revision.go:16-45`）；
- **候选形成时必须校验整个闭包**，包括相互依赖（沿 ADR-0037 §4 的既有要求："计划必须验证整个集合及相互依赖"）；
- **激活后的依赖关系可查**（ADR-0046 §D3 的诊断面直接读它）；
- 依赖发生变化（升级、退役、重命名）走 ADR-0045 的迁移计划，不在别处补丁。

### D5 六块之间的衔接逐对说清

| 从 → 到 | 衔接方式 | 状态 |
|---|---|---|
| 业务模型 → 业务规则 | 规则引用字段与引用路径（解析为 `AssetRef`+字段） | ADR-0040 已统一原表达式与引用 |
| 业务规则 → 业务执行 | 动作/事务编译为 `Transition` 与 `Operation` | ADR-0039 已提供同权威跨对象事务 |
| 业务执行 → 业务模型 | 运行物携带应用与定义版本标签 | ADR-0046 已建立，运行仍归原 owner |
| 数据与集成 → 业务模型 | Pipeline 目标/Backing（ADR-0024） | 已有 |
| 业务模型 → 数据与集成 | 对象的来源声明、写回声明 | ADR-0051 已补显式确认与对账 |
| 协同与 AI → 业务规则 | AI 提议经采纳动作进入事务 | ADR-0054 已提供 |
| 协同与 AI → 数据与集成 | 集成的原始数据可成为 AI 上下文 | ADR-0046 §D3 / ADR-0054 §D5 已提供 |
| 应用生命周期 → 全部 | 候选闭包、激活、迁移计划 | ADR-0045 已提供显式分批迁移 |
| 全部 → 应用生命周期 | 每块声明自己的 `Provides` 与版本 | 由本 ADR 的同一描述提供 |

## 2. 不做

- **不建通用依赖注入/插件框架**：`AssetRef` 已经够用，缺的是**统一**，不是新机制。
- **不在运行时解析依赖**：依赖解析是**发布期**的事（这与 ADR-0010、ADR-0037 的"运行不重新解析"一致）。
- **不做第二份血缘**：一份描述，多种呈现。
- **不把 `Provides` 变成权限声明**：`Roles` 只说明能力面向谁提供；真实授权由 ADR-0044 判定。

## 3. 后果

- `Definition.Requires` 的四个人工填充点（`definitions.go:1010,1130`、`:518-525`、`release_candidate.go:72-130`）收敛为**一处计算**：从定义体里的引用解析出来。
- `AssetRef.Check()` 校验原受控资产种类；事务、约束和记录集属于对象/动作正文，不另建独立资产种类或执行器。
- 血缘与影响面从两套代码变为一份数据的两个方向；`Lineage.tsx` 与候选差异继续存在但读同一份。
- 前端"能引用什么"的候选列表由 `Provides` 生成，**按角色过滤**（ADR-0044），因此构建者看到的选择器与业务人员不同，但都不是前端自己判断。
- **对后续 ADR 的约束**：ADR-0039、ADR-0040、ADR-0041、ADR-0042、ADR-0043、ADR-0044、ADR-0045、ADR-0046、ADR-0047、ADR-0048、ADR-0049、ADR-0050、ADR-0051、ADR-0052、ADR-0053、ADR-0038、ADR-0054、ADR-0055 的每一项新能力都必须说明它提供哪种 `Capability`（`Kind` + `Side`）、它依赖什么 `AssetRef`。**没有说明的能力不算设计完成**——这是 ADR-0038 自举约束在依赖面的对应物。

## 4. 验收

1. 对任意一个已安装资产，`Requires`（正向）、反向图、`Provides` 三个查询返回一致的结果；三者由同一份描述算出（用一条测试锁住：手工改描述，三处同时变）。
2. 一个页面的依赖（对象、查询、动作、它使用的集成）**由引用解析自动产生**，不需要人工维护；改页面引用后依赖自动更新。
3. 悬空引用、跨应用未声明依赖、循环依赖在**发布期**拒绝并指出位置（循环依赖今天已有部分检查，`release_candidate.go:169`，扩展为通用）。
4. `Side` 约束：条件里引用 `effect`/`authoritative` 能力、页面里绑定可写动作、AI 工具里调用未声明动作 → 分别被拒绝。
5. 血缘与影响面：改一个字段，能列出受影响的页面/规则/集成；运行时证据与声明图并排且可区分（不混淆）。
6. 能力发现：构建者与业务人员在同一位置看到不同的可选能力（来自同一份 `Provides` + 角色过滤），前端不自行判断。
7. 反例：新增一种资产类型却没有 `AssetRef` kind、新增一个 `Capability` 却没有 `Side`、为某一块单独维护依赖列表 → 分别拒绝。

测试归宿主 platform 包与 build owner 包；`docs/Testing.md` 增"依赖与能力发现"手测行。

## As built

统一描述由 `platform.DescribeAsset` 从原 owner 的完整描述体生成，`WithDependencies` 是新资产 `Requires` / `Provides` 的唯一写入入口。已覆盖对象、动作、页面、应用、查询、函数、计算、流程、智能体、评测集、样本、迁移、六类集成、观测源（ADR-0058）与告警。新增 `protocol` / `interface` 承载既有协议与共享结构，`alert` 承载原告警配置；后者依赖其对象，没有可供直接调用的能力，`Provides=[]`，投递仍归原通知 owner。决策表复用原 `compute` 的 `operation/pure` 能力，不新增资产种类或求值器。事务、约束和记录集仍属于对象/动作，不另建独立执行资产。字段引用、规则读取、事务步骤、拒绝记录/route、AI 采纳、确认传输、设备派发与状态回读（ADR-0059）均解析到原 `AssetRef`。派发的命令、目标、反向请求和来源绑定固定在原启动动作，专用 Writeback 不产生虚构业务动作依赖。原生类型名与 owner 不一致时，完整体保存具名 `objectBindings`；协议、智能体工具和匹配来源同样保存明确绑定，不维护第二份依赖列表。

`DependencyGraph` 由这些描述产生正向、反向、候选集合和安装顺序。候选拒绝缺失引用、非法结构循环、描述体与独立修改的依赖/能力不一致；错误包含原资产与目标。对象数据引用、页面导航、原对象与自身动作、AI 提议来源与采纳关系允许已声明的语义循环，执行 route 循环继续由事务 owner 拒绝。跨应用动作必须带原提供方协议及其确切动作绑定；这不授予执行权，也不建立跨权威事务。条件/约束沿原规则语法只读，页面数据绑定只接 `pure`，显式动作、受控模型请求和流程提交保持原接受路径。智能体仍只可使用已声明工具，真正调用继续经过原授权。

应用的 `Resources` 成员边仅表达装配关系，不执行其中的动作；应用可以引用其他 owner 的原动作并沿同一候选封存。候选继续检查所引用动作和流程自身的执行依赖，因此把一个未绑定协议的跨应用调用放进应用成员，仍会被拒绝。应用引用不转移权威、增加权限或建立跨权威事务；显式页面/观测动作继续作为各自受权提交处理。

`GET /v1/dependencies` 返回成员可见的同一份描述，以及选定资产的传递依赖/反向影响；`GET /v1/provides` 返回同一描述的可用能力，可按 `kind` / `side` 选择。原 `Definitions`、Flow 能力面板和保留版本类型读取从同一数据投影，`Roles` 只作收窄。成员、行、字段、来源与动作权限仍由 ADR-0044 的原 owner 判定；隐藏资产和协议动作绑定不出现在图中。查询输出形状由原受权对象字段投影，不能借能力发现读取被隐藏字段。

构建器的共享资产历史处理归 `definition_history.go`：属性、关系、查询与函数共用制品构造、安装版本检查与发布流程；样本集与迁移计划共用当前资产列举、固定版本读取和安装历史验证，删除各自的重复循环。类型专属校验与安装仍在原处，原内容、契约版本、64 版本上限和历史保留；归档资产的固定版本仍可读，样本/迁移的旧版本安装准备不切换当前发布，安装映像保留原字节。宿主共享资产共用 `Tenant.storeDefinition` 更新发现目录；属性、关系与查询共用 `retainedDefinitionVersions`，删除重复 map 处理与 `sameQuery`。新版本赋值与代码归属保护仍在原安装函数，关系约束成功后才更新目录；函数继续刷新代码动作，对象/动作/页面批量安装只排序一次。页面、声明集合和关系遍历共用 `querySourceDefinition`；调用者分别提供完整或成员可见目录，完整引用与版本必须同时命中，不回退当前版本。

构建器与业务人员共用 Shell 的 Lineage：声明图、Uses/Used by、能力类型、调用方式和输入/输出形状。应用设计台、模型使用处与对象/数据集图复用 `@platform/app.DependencyGraph`；页面的查询/动作/计算/函数选择器读取后端 `Provides`，已保存的旧版本绑定仍保留。原客户端递归、项目反向扫描、集成独立图和 Build 安装排序的第二份解析已删除。集成映射、运行数据和诊断入口并列显示，运行证据不进入声明边。

新候选封存明确的 `Provides`（空集合也保存），删除该字段不能绕过新候选校验。历史候选由原格式读取，原字节、内容身份和已保存依赖不重写。流程、审批与函数从已封存候选选取原闭包，保留旧依赖身份。旧匹配定义参加新候选时只从原体和固定引用补出绑定，不查询当前草稿；原 Published / Versions 保留。若历史写回仍引用已取消的 `.confirmation` 虚拟动作，新候选明确要求先发布下一写回版本，旧内容仍沿原读取/执行路径保留，不在同一版本下删除旧边。原生代码资产仅允许新增引用元数据的投影差异；原版本、角色、字段、生命周期和执行声明必须一致。恢复仍应用已接受结果，不重新求值、授权或发外部请求。私有构建者试跑复用同一依赖图，原平台记录由新建的原 owner 提供，不被误编译成业务对象。
