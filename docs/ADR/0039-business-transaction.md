# ADR-0039 — 业务事务：单一权威内的多对象原子变更

<a id="adr-0039"></a>

状态：已接受（2026-10-12，负责人指令，ADR-0038 A 块第一份）· 修订 ADR-0006 的执行面口径（不改变其"跨权威不原子"结论）、扩展 ADR-0044、ADR-0047 的动作能力 · 合并 ADR-0039 的余额身份、精确过账与下限决定；旧 `Action.Posts` 已被事务步骤替换 · 当前顺序归 WorkQueue

## 0. 意图

一次“工序完工”需要结束当前工序、更新批次、记录不合格品、结束父工单并向下一工序派工。构建者通过一个事务表达属于同一权威的这些变更，不再拼装只改主体、创建子记录和余额过账的独立动作路径。

这份 ADR 把"一次业务操作可以原子地改多个对象、多条记录"变成平台的正式能力。

**判据**：构建者能在工作台里定义一个单据（头 + 行 + 编号 + 过账 + 状态流转），一次动作产生一个接受结果，里面含多个对象类型、多条记录；任何一条失败则**一条都不落盘**；重启恢复后逐字重现同一个结果。

## 1. 单次接受与权威边界

`acceptedBatch` 已能在一个接受结果内保存多对象记录、子决策、序列及所属方私有状态，统一受 1 MiB 结果预算约束。`BusinessTxn` 复用这一实现提供构建者声明，不增加提交引擎。

内核提交仍只有一个目标与一个权威；目标是本次业务操作的审计主体，不是记录写入数量限制。另一个权威的请求与回执继续是独立决定，不能用多对象事务跨越它。

## 1.5 档位：替换，不是增量（负责人决定，2026-10-12）

**本 ADR 及 ADR-0040、ADR-0041、ADR-0042、ADR-0043、ADR-0044、ADR-0045、ADR-0046、ADR-0047、ADR-0048、ADR-0049、ADR-0050、ADR-0051、ADR-0052、ADR-0053、ADR-0038、ADR-0054、ADR-0055、ADR-0056 一律按"替换"实施。系统不允许两个真相或两套规则。**

这一条决定了本程序的工作量级、迁移路线与风险面，必须写在最前面：

| | 被保留（**一个**执行底座） | 被替换（**退出**，不是共存） |
|---|---|---|
| 业务模型 | 对象类型、字段、生命周期、`platform.Lifecycle.Transition`、`platform.Operation`（流程/页面/AI 共用的操作目录） | 构建器动作的现状表达（`Sets` + `Creates` + `Posts` + `Journal` 的并列形态）→ 成为 `BusinessTxn` 的步骤 |
| 规则 | 决策表与计算字段的**发布、执行、版本**机制 | 四套条件/表达式语法（`Condition` 三元组、公式串、表格单元格、页面算子图）→ 全部退出，只留 ADR-0040 的一门语言 |
| 权威写入 | 接受结果、纯应用、恢复（ADR-0010、ADR-0037） | 任何绕过接受结果的直接修改路径（今天已基本消除，**不得因本次改造重新引入**） |

**三条硬约束**（违反即视为实现错误，不是风格问题）：

1. **不得长期保留两套表达。** 新增 `BusinessTxn` 的同时，旧的构建器动作表达**冻结**：可以继续被读取与重放，**不再接受新能力**；其定义在迁移到事务后**删除**（AGENTS 硬规则 6：不保留永久重复路径或临时垫片，替代旧路径时删除旧路径）。
2. **迁移是替换的一部分，不是后续任务。** 每个能力块落地时，它取代的旧表达要在同批冻结并登记退出（[Subtraction](../Subtraction.md)）。"先做新的，旧的以后再说"会直接产出两套规则——这正是本次要消灭的状态。
3. **一个语义只有一个实现。** 规则求值、约束检查、授权判定、依赖解析各自**恰好一份**实现（分别是 ADR-0040、ADR-0041、ADR-0044、ADR-0056）。任何"为了兼容旧路径而保留的第二份实现"都要在它服务的旧路径退出时一并删除，且**在 ADR 的 As built 里写明哪一份已删**。

**因此本程序的中间态是"迁移中的单轨"**：旧路径逐步冻结与退出，新路径接管，不存在"新旧并行的稳定形态"。中间态允许难看（旧定义不能编辑新事务），但不允许有两个真相。

## 2. 决定

### D1 权威的粒度是应用，不是对象类型

应用（`platform.App`）是权威单位；它拥有的**全部对象类型**共享同一本账本、同一个提交边界。一次业务事务可以同时写它拥有的任意对象类型、任意条记录。

对象类型不等于应用权威。现有参考应用的拆分不能反过来限制受控业务系统的表达；原生实现须按 ADR-0053 的等价替代与历史责任条件退出。

### D2 业务事务是唯一的多对象变更表达

新增定义契约 `BusinessTxn`（构建器资产，编译到宿主）：

```go
// 一次业务事务：同一应用、同一账本、同一接受结果内的全部变更。
type BusinessTxn struct {
    Subject   string       // 事务主体：单据、工单、批次…（事务的名称与审计对象）
    Steps     []TxnStep    // 有序；同一步骤内的记录以稳定键排序，保证重放确定
    Guard     []Condition  // 全部成立才继续；沿用 0040 的条件语言
    Idempotent string      // 幂等键的来源字段
}

type TxnStep struct {
    Kind    string   // create | update | archive | link | unlink | sequence | post | journal | effect | work
    Target  TxnRef   // {Type, ID, Via}：固定 ID、本事务内新建记录、或沿声明的引用路径
    Changes []Set    // update 时的字段赋值（沿用 0040 的赋值语言）
    When    []Condition
    // effect/work 步骤携带端点与载荷；sequence 携带命名序列
}
```

要点：

- **`Target.Via` 是关键**：行的父指向、子记录的归属、关联记录的定位都沿**已声明的引用路径**解析（复用 `platform/record_path.go`），所以构建者不需要写 ID，平台也不需要猜。
- **步骤是类型化的，不是 JSON 脚本**。每一种 `Kind` 由对应 owner 实现：`post`/`journal` 归 ADR-0039、ADR-0026 的既有实现，`effect` 归出站效果 owner，`work` 归 work 应用，`link` 归 links owner。新增 Kind 须扩展其规范主人，不在事务引擎里加特例。
- **`effect` 与 `work` 步骤只声明意图**，在事务被接受后由既有出箱/受属工作机制执行——它们**不在**原子范围内。事务原子的是状态；外部效果仍是至少一次（沿 ADR-0004、ADR-0041 §4）。

**每一种 Kind 的确切语义**（新增 Kind 须在此表登记，不在引擎里加特例）：

| Kind | 语义 | 在原子范围内 | 归属 |
|---|---|---|---|
| `create` | 新建一条记录；ID 由平台生成或按编号规则 | 是 | 记录 owner |
| `update` | 改一条**已存在**记录的字段；`Target` 必须解析到确定记录 | 是 | 记录 owner |
| `archive` | 归档（非删除；沿 `ledger.go:412-413` 的既有语义） | 是 | 记录 owner |
| `link` / `unlink` | 建/断一条**声明过的**关系；基数与删除策略由 ADR-0041 在事务级检查 | 是 | **ADR-0043 §D3**：同应用关系归该应用账本 |
| `sequence` | 取一个命名序列的下一个值（ADR-0026 的既有实现）；**拒绝不占号** | 是（与记录同批） | 宿主序列 owner |
| `post` | 向余额字段加减（ADR-0039 的既有实现） | 是 | 台账 owner |
| `journal` | 保存发往原账簿的凭证意图（ADR-0026）；Core 在自己的权威内独立决定入账 | 意图是；Core 入账否 | Build 意图 / core 账簿 owner |
| `effect` | 声明一条外部效果意图，接受后由出箱执行 | **否**（只声明意图） | 出站效果 owner |
| `work` | 声明一个受属工作/任务/审批 | **否** | work 应用 |
| `call` | 调用一个 `Side=pure` 的能力（ADR-0056 的 `Capability`），结果可赋给后续步骤 | 是（只读） | 能力主人 |

`journal` 的原子范围受 [ADR-0038 §9.1](0038-build-the-capability-to-build.md#91-内核与契约) 约束：Build 与 Core 是两个权威，不能因新增事务步骤而把两边的业务状态合成一次决定。原子保存的是原账簿可处理的凭证意图；实际入账、拒绝和对账继续归 Core，不能把“意图已接受”显示成“凭证已入账”。

**步骤之间的顺序规则**：

1. **同一记录在同一次事务中只能被一个实际执行的步骤写**。发布期拒绝已经确定的无条件重复目标；条件步骤及引用/输入目标由原私有执行器解析。若两个实际写入指向同一记录，整件拒绝，之前的行修改、编号与效果意图全部丢弃。不能因为发布时尚不知道两个动态 ID 是否相同，就拒绝整个可复用定义；也不另建条件互斥分析器。
2. **`link` 的目标必须已经存在或在本事务的**更早**步骤创建**（`create` 先于 `link`）。反之（先 link 后 create）发布期拒绝。
3. **`call` 只能读**：它读到的值是**事务开始时的快照**还是**此前步骤的结果**，必须由声明决定。默认读快照（确定性强）；显式要求读前序步骤结果时，该步骤的依赖必须可静态排序。
4. **`ForEach`（ADR-0043 的集合迭代）内部不得再嵌套 `ForEach`**：一层迭代，深度固定。嵌套会破坏"结果可静态排序"这个前提。
5. **`Guard` 在全部步骤之前求值一次**；`When`（步骤级）在该步骤执行前求值。步骤级条件不成立＝**跳过该步骤**（不是拒绝事务）——这是显式的：需要"不成立就拒绝"时用 `Guard`。
6. **分级拒绝（ADR-0055）在顺序中求值**：`route` 改变后续步骤的路径，因此 `route` 之后不得再有写同一记录的步骤（发布期检查）。

**主体的接受记录与步骤赋值分开**：主体是事务的审计对象，不要求定义里有一次无条件字段写入。主体步骤的 `When` 不成立时跳过其赋值；若本次没有任何步骤写主体，沿原动作授权、计算与校验保存主体的接受元数据，保留命令版本和历史。它仍属于同一个接受结果，不增加内核决定，也不伪造业务字段赋值。

### D2.1 余额过账是普通记录写入

余额对象以匹配字段的值确定稳定身份：`BalanceID` 用对象类型与有序匹配值生成 `bal-` 开头的记录 ID。同一物料与库位、订单行或预算维度的过账因此命中同一条余额记录，首次过账创建该记录。

`post` 只接受 integer、decimal 或 money 余额字段；匹配值与金额使用同一 Expr 读取输入、主体或已声明来源。运算遵守精确数值与整数范围，money 以最小货币单位计算并固定首次币种，后续不同币种拒绝。`floor` 在私有事务内拒绝负余额，主体、余额、编号和其他意图一同生效或一同丢弃。

撤销是相反符号的过账，不删除原记录。一次事务对同一余额记录的实际写入仍只能一次，冲突由同一目标检查拒绝；这不是另设账本、分录实体或过账引擎。需要正式账簿时使用 `journal`，其 Core 入账范围见上表。旧 `Action.Posts` 及其专用编辑入口已被 Transaction 取代，旧输入日志的恢复责任见 §6。

### D3 原子性的确切含义

一次业务事务的保证是**全有或全无**，范围是**该应用账本加全部 owner 私有状态**：

1. 全部步骤在私有上下文上验证并试应用（fork）；任何一步被拒绝 → 整个事务拒绝，**不留部分状态、不占编号、不产生效果意图**；
2. 全部通过后形成**一个**接受结果，一次落盘；
3. 恢复时**逐字节应用已保存的映像**，绝不重跑规则、模型或外部调用（沿 ADR-0010、ADR-0037）；
4. 同键同内容重试返回原答复；同键异内容冲突（K4 幂等性）。

**不保证**：跨应用的原子性（见 §3）、外部系统的 exactly-once、事务内的读一致性跨越已提交的其他决策。

### D3.5 授权：逐步骤、按顺序、作用在事务自己产生的状态上

事务的授权**不是一次判定**，也不是只看初始记录。规则（由 ADR-0044 的单一决定点执行，本 ADR 定语义）：

1. **发起权**：调用者必须有权发起这个事务本身（对应它的主体类型或动作）。
2. **逐步骤判定，顺序执行**：每一步在执行前判定。判定看到的是**该步骤执行时的状态**——包括**本事务更早步骤创建或修改的记录**，而不是事务开始前的快照。
   - 因此"创建头 → 用新头的 ID 创建行"是合法的：创建行时判定读的是**已经存在于事务上下文中的**头。
   - 这种记录**仍然要过完整判定**（行范围、字段、约束、事务级约束），不能因为"它是本事务刚建的"而跳过——否则事务会成为一个授权绕过口。
3. **任一步拒绝 → 整个事务拒绝**（与约束失败同一条路径，ADR-0055 的分级拒绝在此之上）。**不允许"跳过无权的那一步继续"**：那会产生业务上不完整但已落盘的单据。
4. **判定在私有上下文完成**（沿 ADR-0037 §3.2 的"审批预检使用只读声明及私有 fork/savepoint，不写共享状态"），因此判定失败不留任何痕迹。
5. **主体是申请人的身份**：审批放行后执行整个事务时，主体仍是申请人的身份并**按放行时的当前权限重查**（沿 ADR-0044、ADR-0037 的既有语义），不因为"已经批过"而跳过权限。

**代价与选择**：逐步骤判定意味着一个事务可能因为中间某一步无权而整体失败，虽然前几步本来是有权的。这是有意的——**原子性优先于部分可用性**；如果业务上确实允许"部分完成"，那应当被表达为**两个事务**（由 ADR-0055 的 `route` 或流程步骤串联），而不是一个事务跳过步骤。

### D4 预算与拒绝

接受结果保留现有 **1 MiB** 预算；完整单据的实际结果仍在此范围内，没有提高预算的依据。**预算耗尽时必须显式拒绝并说明超出的内容**，绝不静默截断——静默截断会让"部分成功"从后门回来。未来确有单据超限时，再按实际结果修订预算与编解码器。

超过单次事务合理规模的操作（大批量导入、全量重算）不走事务，走受属工作分批执行；**每批是一个事务**，批次间的部分可见是显式声明的结果，不是缺陷。

### D5 事务不是流程

- 长流程（等待、重试、跨系统）归 Flow/Work；**每个流程步骤内部可以是一个事务**，流程本身不是事务。
- 审批：事务在审批**之前**完整构造（暂留），放行后以申请人身份执行整个事务。审批放行不拆散事务。

### D6 契约与语言边界

内核 `K4` 不变：一项决策仍只改**单一权威**。本 ADR 不引入跨权威原子组（ADR-0006 的否决继续有效），只是在单一权威内部把"能改什么"从"一条记录"扩到"一个应用的全部类型"。

`contract/` 不变更语义；`BusinessTxn` 是 `platform` 层的定义契约（沿 ADR-0037 §2 的 owner 划分）。

## 3. 不变的那些边界

- **跨权威不原子**。两个应用的业务确认仍是：请求 → 提供方独立裁决 → 回执 → 调用方独立裁决（ADR-0006 §设计 2）。本 ADR 的合并路线是让**一个业务系统是一个应用**，从而让绝大多数"跨权威"在事实上消失；真正的跨系统协同归 ADR-0051。
- **不引入租户代码**、不引入表达式语言（条件与赋值见 ADR-0040）、不允许事务提交任意 journal 字节（ADR-0037 §3.1）。
- **不做补偿式回滚**（ADR-0006 D1(c) 已否决）。事务失败不留痕迹，不需要补偿。

## 4. 后果

- 构建器第一次能表达"一个业务操作改了五张表"；MES 的完工、ERP 的过账、WMS 的收发货全部落在一条事务里。
- `apps/mes/erp.go`、`apps/erp` 里"为了跨应用一致性而存在的拆分"失去理由，进入 ADR-0053 的退出路线。这正是 ADR-0032 §未做 里"主数据落库"的前置条件。
- 参考应用里手写的 Go 业务规则被声明式事务取代；被取代的 Go 代码按 ADR-0053 退出。
- 风险：事务成为新的"什么都往里塞"。约束是 §D4 的预算与"长流程不是事务"；评审时看的是**单据语义**，不是行数。

## 5. 验收

1. `capabilities/server` 新增宿主测试：构建器定义"收货单据"（头 + 2 行 + 编号 + 过账 + 状态），一个事务动作产生 `record-batch`，含 3 个对象类型、≥4 行、1 个序列、1 个过账，且全部行指向同一子决策。
2. 同测试内注入第 3 步失败：单据仍是草稿、编号未占、无分录行、无效果意图、输入未被消耗；重试同键返回原答复。
3. 同测试内注入追加失败与进程崩溃：重新打开后按前驱恢复，逐字节重现同一结果。
4. 幂等：同键同内容返回原答复，同键异内容返回冲突。
5. 反例：跨应用的两个对象类型出现在一个事务里 → 组合期或提交期明确拒绝，不得静默降级为两个决策。

`docs/Testing.md` 增加"业务事务"小节记录该场景的手测行；ADR 更新只在本文的 As built 段落，不新建报告文件。

## 6. As built — 完整业务事务

`platform.BusinessTxn` 由对象动作及 `Object.CreateTransaction` 保存、发布和执行。create/update/archive、声明的 link/unlink、单层 for-each、sequence、post、journal、effect、work 与 call 使用同一事务执行器；Guard、When、字段赋值、步骤参数和查询结果复用 ADR-0040 的 Expr。步骤目标、前序结果、重复写入、来源权限和版本均在原 owner 检查，不引入内核语义或第二个资产类型。

全部记录、序列与 owner 私有意图在原私有决定中构造，一次接受后纯应用；逐步骤复用原 Catalog、行范围、字段权限、计算与约束。审批等待不取号、不发送外部请求；放行后仍按申请人当前权限执行整笔事务。任何步骤或追加失败都不留下部分业务状态。恢复只应用保存的映像、前驱和原答复，不重新运行规则、查询或外部调用；接受结果保留 **1048576 字节**预算，超限明确拒绝。

post 的十进制、整数与金额运算复用原精确表达式引擎，币种、整数范围和非负余额要求沿同一实现判定。journal 只原子保存凭证意图，实际入账继续由 Core 独立决定；借贷平衡不代表目标账簿已接受。effect 只选择 `On=transaction` 的已发布 Writeback，保存原连接、映射与载荷，普通动作订阅跳过它；逻辑名称沿既有集成交付机制在目标环境绑定本地连接。work 保存原工作 owner 的任务意图。call 只允许原同步纯查询，固定保留版本和标量结果；默认使用事务开始的记录快照，`current` 明确读取前序步骤产生的私有状态，异步任务不伪装为纯查询。

条件主体写入与同类型动态目标已替换原过严的发布限制：已确定的无条件重复仍在发布时拒绝，其余按实际执行目标检查；移除单独的静态条件互斥特判。没有主体字段步骤执行时，原记录动作保存接受元数据，命令历史与版本继续一致；创建动作已有主体记录，不再追加一次更新。原 TransactionEditor 的逐步骤条件、关系目标和输入目标直接使用同一声明。文件日志场景检查创建与跳过赋值、两目标转移、实际目标重合/条件重叠时整件拒绝、步骤授权、编号撤销、关闭重开与同键原答复；范围归 `TestBusinessTxnConditionalSubjectAndDynamicTargets`，不外推为跨权威事务。

**旧表达替换**：新保存与读取供编辑的定义由 Build 的 `CanonicalObject` / `migrateObjectTransactions` 将 Sets、Creates、Posts、Journal、Reverses、Conditions、Reads、To/ToInput 转为事务并移除原字段；旧编号转为创建事务中的命名序列。旧不可变发布字节不改，当前执行时在内存编译为同一事务。旧 take/stored/create/post/numberingOf 仅供历史 raw-input 日志的 `LegacyReplay` 恢复，入口拒绝普通调用；已接受结果的恢复不经过它们。旧编号首次取号按原字段与格式读取已有最大值，接受时才保存起点，后续不再计数记录。退出登记见 [Subtraction §4](../Subtraction.md#4-构建器旧动作表达adr-0039已替换)。

构建者的 Action types → Transaction 和 Creation transaction 复用同一个类型化步骤编辑器，可配置 Guard/When、字段与前序结果、状态、关系、迭代、过账、出站、任务及纯查询。旧的 Rules、赋值、关联创建、过账、账簿和记录计数编号编辑器已删除，状态图读写事务中的状态赋值；当前与冻结对象描述也从同一事务投影直接状态常量及必填选择参数，供看板保留原动作目标，不恢复旧执行字段。条件、循环或多次状态写入不推断唯一目标。复杂定义仍可在折叠的 Transaction source 编辑同一份事务，非法 JSON 保留在输入控件中。

检查：`make check`、Build/platform owner 测试、宿主事务/审批/记账/原动作/旧草稿读取与保存/迁移/确认/派发的对应场景及语言/API 类型检查通过；新增 `coalesce` 的 Go owner 与同一 Go/Wasm 共享向量通过。完整单据接受结果 **14396 / 1048576 字节**；真实子进程在 fsync 后、应用前退出，重开后 **14362 字节**结果一致，不重跑规则、授权或外部调用。旧输入恢复后再执行原动作只产生一个凭证意图，撤销使用原凭证金额，不使用后来修改的记录金额。旧单号只授予创建权限且字段必填，仍连续编号。

`business-transaction` 浏览器路线完成类型化编辑、候选激活、操作员输入、审批放行、单号/状态/余额、一次带稳定键的外部请求与原收件箱任务；查看了桌面与窄屏界面，并修正 Object Explorer 窄屏侧栏挤压记录的问题。HTTP 接收方是本地模拟端点；实际设备、生产容量和独立构建者体验仍按各自 ADR 验证。
