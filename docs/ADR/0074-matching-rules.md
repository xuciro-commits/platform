# ADR-0074 — 主数据对齐：匹配规则与黄金记录（ADR-0069 Ⅰ-G）

状态：接受并实施 · 2026-10-06 · 承接 ADR-0070（Source）、ADR-0071（Dataset/Pipeline）、ADR-0069（第二程 Ⅰ 集成织物）

## 决定

### 1. 不做通用 MDM：一条规则说清"何时是同一个"和"谁说了算"

SAP 的物料、MES 的零件、WMS 的货品是同一种东西，各有各的 id。平台不另建"主数据中心"，而是给对象一条 **匹配规则** `build.match`：

- `object`：作用的对象类型（先覆盖 `core.party` / `core.material` / `core.site`，但对任意已安装对象都可用）；
- `keys[]`：每个键是若干字段 + 归一化方式（`exact` / `folded` 忽略大小写与空白 / `digits` 只留去前导零的数字）。**任一**键与已有记录一致，这一行就是那条记录；
- `prefer[]`：字段 → 以哪个**生产者**（管道名或数据源名）的值为准；其他生产者只在该字段为空时填入。这就是字段级的黄金记录，没有第二张"黄金表"。

每个对象同一时刻只有一条已发布规则（发布时拒绝第二条），避免两条规则互相打架。决策表打分（ADR-0069 表中提到）暂不做：键的"任一一致"已经覆盖三类主数据的真实情况，打分留给出现需求的那一天。

### 2. 规则在"行落入对象"的唯一入口生效

数据源的拉取与管道的对象输出都经过主机的 `applyRows`，所以匹配规则就在那里应用一次（`build.Resolver`）：

- 行 id 不是已有记录 → 按键查索引 → 命中则改写为命中记录的 id（于是 create 冲突后走 edit），幂等键追加 `:as:<id>`；
- 同一批里两行是同一个 → 后者并入前者；
- 命中记录已有 `prefer` 给别的生产者的字段值 → 从载荷中去掉该字段；
- 运行结果计 `merged`（SourcePull / Pipeline.Run），管道页最近一次运行显示"n 行由匹配规则合并"。

记录本身不多一个字段：合并进来的行只是对既有记录的一次编辑，审计里能看到是哪条管道、哪个 change 改的（ADR-0072 的血缘照常可追）。

### 3. 没做的

- 不做模糊/概率匹配、不做人工合并队列；规则不命中就是两条记录，构建者改键后下一次落地自然收敛。
- 不回溯重算：发布规则只影响之后落入的行；已经分裂的记录由下一次全量同步合并。
