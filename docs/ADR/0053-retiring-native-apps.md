# ADR-0053 — 原生参考应用的退出：等价、验证、再删

<a id="adr-0053"></a>

状态：已接受（2026-10-12，负责人指令，ADR-0038 §1 的退出面，F 块第二份）· 修订 [Subtraction](../Subtraction.md) 的执行口径：从"由人执行的一次性清单"变为**有判定条件的退出路线** · 与 ADR-0052（基准）、ADR-0038（自举）配套

## 0. 意图

ADR-0038 §0 定了：`apps/*` 里的原生应用是参考应用，不是产品形态，**当 FDE 能在工作台里构建出等价物时，它们应当逐步退出**。

但"逐步退出"如果没有判定条件，就会变成两种错误之一：

- **早退**：等价的构建产物还没验证就删代码，能力凭空消失；
- **不退**：因为"还有用"永远不退，行业代码持续增长，平台永远长不成产品。

**判据**：每一次退出都有**一个等价的构建产物 + 一次验证 + 一个删除清单**，三者齐全才执行。

## 1. 现状：退出清单的起点

[Subtraction](../Subtraction.md) 记录各旧路径的替代者与退出依赖，已完成项不再是待执行任务。原生参考应用位于 `apps/`：`crm`、`csm`、`erp`、`hcm`、`mes`、`pms`；它们仍承担有效业务与历史责任，不能按清单数量或目录名称直接删除。

按 ADR-0038 的口径，这些应用内部的代码分三类，处置方式完全不同：

| 类别 | 例子 | 处置 |
|---|---|---|
| **平台能力** | 生命周期、审批、编号、过账、集成、AI 的执行实现 | **不是退出对象**，它是平台的一部分（`apps/*` 里如果有这类代码，先迁到正确 owner） |
| **行业业务规则** | `apps/mes` 的 `canDo`/`reworkable`/`released`、`apps/erp` 的过账链 | **退出对象**：应能由构建者声明；退出条件是该声明存在并被验证 |
| **行业界面** | `RoutingFlow`（`web/packages/mes/src/index.tsx:226`）、各原生表单 | **退出对象**：应能由通用组件 + 配置产生（ADR-0049） |

**关键**：第一类今天混在 `apps/*` 里。**退出路线必须先分类，再退出**——把"平台能力"当成行业代码删掉会造成真实的能力损失。

## 2. 决定

### D1 退出单位是"能力"，不是"应用"

不删"`apps/mes` 这个应用"，而是逐能力退出：

```text
能力单元 = 一条行业业务规则 / 一个行业界面 / 一组行业主数据
          ↓
条件：等价的构建产物存在 + 已验证 + 不影响任何仍依赖它的东西
          ↓
动作：删除该实现 + 移除引用 + 迁移历史读取义务（如有存储）
```

应用整体退出是**结果**，不是手段：当它的全部能力单元都退出后，它自然变成空壳，那时删除模块、`go.work` 条目、前端包、lockfile、Catalog 产物（沿 [Subtraction §1](../Subtraction.md) 的 `erpadapter` 删除清单模板，那份清单是本仓库现有的最佳实践样例）。

### D2 退出的三个条件（缺一不可）

| 条件 | 含义 | 证据 |
|---|---|---|
| **等价** | 构建产物在同一业务场景下语义等价（同样的输入得到同样的接受/拒绝、同样的记录变化） | 对照测试：同一场景跑原生实现与构建产物，结果一致 |
| **验证** | 有人用构建产物走过该业务任务（不是只跑了测试） | 走查记录（负责人或 FDE），归 ADR-0052 的验收 |
| **无残留依赖** | 没有其他应用、协议、solution、部署或测试仍依赖它 | `git grep` + `scripts/boundaries.sh` + 组合检查 |

**"等价"必须是语义等价，不是界面等价。** 原生 MES 的设备下拉与构建产物的设备选择器不必长得一样，但"选不到不能加工的设备"这条规则必须同样成立（ADR-0032 D4 的教训）。

### D3 退出顺序：从最简单到最复杂

依据"依赖面小、语义最清晰"排序，**不按应用整体**：

| 批次 | 对象 | 理由 |
|---|---|---|
| 1 | 行业**主数据**种子（`apps/mes` 的 `DemoMaster`） | 依赖 ADR-0042 落库；语义最清晰；无协议依赖 |
| 2 | 行业**业务规则**（`canDo`、`reworkable`、`released`） | 依赖 ADR-0040、ADR-0043；有清晰的对错判定 |
| 3 | 行业**界面**（`RoutingFlow`、原生详情页） | 依赖 ADR-0049；需要视觉走查（耗时最长，但可与前两批并行开始配置） |
| 4 | **协同逻辑**（`apps/mes/erp.go`、协议桥接） | 依赖 ADR-0051；牵涉外部系统替身与演练 |
| 5 | 剩余**业务链**（`apps/erp` 采购链、`apps/pms` 的预订链等） | 依赖前四批；`Subtraction §2` 已标注"现在不删" |
| 6 | **模块整体** | 全部能力单元退出后的清壳 |

`apps/crm`、`apps/csm`、`apps/hcm` 的位置由各自能力单元落在哪一批决定，不在应用层面排序。

本轮首个界面接管单位为 MES 的工单列表与释放表单。`industry.mes-workspace` 提供 `mesworkspace` / `mesorders` 的原 Build 草稿，依赖 `mes.order` 与原动作，发布后的 `orders` 入口由通用扩展映射接替。产品、计划和位置选择通过原动作声明与共享表单表达，不复制 MES 对象或开工规则。当前保留手写 `ShopOrders` 及其注册；负责人确认新任务等价后再删除，不能将草稿包或自动检查通过写为原生界面已经退出。

当前自动证据包括两条浏览器路线的五项任务：原生应用查看与扩展创建、原工作区草稿保留、发布、MES 独立与关联计划工单、数量拆分、重复与无权操作拒绝、失败输入保留、旧链接，以及中英文和窄屏表单；已查看桌面与窄屏截图。这些证据不代替负责人对业务任务的等价确认。MES 模块原有 `TestDowntimeTellsSupervisors` 仍因派生停机来源不是可读记录而得到隐藏通知标题，未将该测试计为通过；本轮工单与共享表单任务通过。

### D4 历史与数据的责任不随退出消失

删除代码**不等于**删除读取义务：

- 已产生的历史决策、旧格式的日志条目、旧的存储形状，**继续按其原解码语义读取**（沿 ADR-0037 §3.5、ADR-0010 的既有义务）；
- 如果某个原生应用拥有**必须保留读取**的存储（例如 `apps/mes` 的 `SFC` 状态如果落过盘），删除前必须**迁移读取义务到接收者**（通常是构建产物对应的应用，或平台的历史读取路径），并留下测试；
- **不删开发期日志基线与既有能力**（Platform §10.3 D 的既有许可）；真实客户数据永远不删。

### D5 退出的停止条件由人判定

ADR-0038 阶段四要求"未参与底层开发的 FDE … 验证成功后，逐步退出"。因此：

- **触发退出的判定人是负责人**，依据是 ADR-0052 的走查证据（不是自动脚本）；
- 每次退出在 [Subtraction](../Subtraction.md) 里留下**已完成条目**（保持该文档"由人执行"的既有形态），**不另建退出日志**；
- 退出**不批量进行**：一个能力单元一次，随其所属批次交付。

## 3. 不做

- **不做"先删再看"**（D2 三条件）。
- **不做代码层面的通用化改写**：不是把 `apps/mes` 的 Go 改造成"更通用的 Go"，而是让构建者配出来。
- **不删仍有读取义务的历史路径**（D4）。
- **不把退出与基准混为一谈**：ADR-0052 证明"能建出来"，本 ADR 决定"何时删掉旧的"。两者可以不同时完成。
- **不退出平台能力**（§1 的第一类）：那类代码要么迁到正确 owner，要么留在原处，不因"它在 `apps/` 下"而被删。

## 4. 后果

- 退出是**渐进的、可审阅的、可中止的**；一次退出失败（发现等价不成立）就回退到"暂不删"，不产生静默的能力损失。
- `apps/mes` 的 `DemoMaster` 与三个 Go 规则函数是第一批真实退出对象，它们也是 ADR-0042、ADR-0040、ADR-0043 的**第一个验收用例**——这形成良性闭环：能力被建出来是为了退出旧实现，而不是为了"功能更多"。
- `scripts/boundaries.sh` 与 `scripts/escapes.sh` 的"已知逃逸只减不增"（AGENTS 硬规则 3）在退出过程中继续生效，因此删除会真实地减少逃逸计数，作为进度的一种可观测形式。
- 前端包（`web/packages/mes` 等）随界面能力退出而收缩；工作区包表（`workspace/src/host/packages.ts`）随之更新。

## 5. 验收

1. 分类：对 `apps/mes`（首批）逐文件分类为平台能力/行业规则/行业界面/行业主数据，产出清单并核对（第一类不得被列入退出对象）。
2. 第一批退出：`DemoMaster` 的等价构建产物存在、验证通过、无残留依赖，然后删除；用对照测试证明主数据语义等价。
3. 第二批退出：`canDo` 的等价表达式存在，在页面候选、服务端拒绝、AI 工具三处共用；对照测试证明接受/拒绝结果与原生实现一致。
4. 历史：退出后，此前产生的记录与日志仍可读取（专门的历史读取测试）。
5. 残留依赖：边界脚本与组合检查在删除后通过，且逃逸计数**下降**。
6. 反例：等价不成立的场景（语义不等价的规则）→ 退出中止，实现保留，缺口记入 WorkQueue。

测试：对照测试归宿主与对应应用包；`make check` + `scripts/verify.sh composition`；`docs/Subtraction.md` 按既有形态登记完成条目。
