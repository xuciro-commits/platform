# ADR-0108 — 应用设计台：围绕一个应用构建

状态：已接受（2026-10-12，负责人指令，ADR-0098 D 块第一份，对应前端第 1 项）；工程已实现（2026-10-14），体验待验收· 修订 ADR-0054（IDE 式工作空间的组织）、ADR-0053（构建者体验）与 ADR-0052（门户与投影）在**构建者侧**的口径：编辑器仍是原来的编辑器，但装配它们的骨架从"按资产类型"改为"按应用" · 工作区/门户的其余部分不变

## 0. 意图

今天构建者打开工作台，看到的是一排**按资产类型划分的入口**：Ontology / Workshop / Automate / AI Functions / Code / Projects / Releases。要做一件业务上的事（"工单完工要能派下一道工序"），他得自己翻译成平台概念并跨 4–6 个工具跳：

- 对象与字段在 Ontology；
- 状态与动作在对象编辑器里（ADR-0037 §设计 7）；
- 页面在 Workshop；
- 自动化在 Automate；
- 函数在 AI Functions/Code；
- 发布在 Releases。

ADR-0098 第一阶段六步流程（理解业务 → 设计应用 → 配置规则 → 构建界面 → 验证发布）**不是设计要求**，是设计起点。本 ADR 只定一件事：**装配骨架按应用组织，而不是按资产类型**；六步是否唯一路径要真实用户验证，所以**不把六步做成强制向导**。

**判据**：构建者围绕一个应用连续工作，不需要知道平台有哪些编辑器、更不需要知道它们之间怎么连接；切换资产时上下文与未保存状态不丢（这是 ADR-0046/0096 已有的行为，必须在新骨架下保留）。

## 1. 决定

### D1 一个设计台，五个工作区，共享一个应用上下文

```text
Application Studio（当前应用 = ADR-0107 的工件）
├─ Model    业务模型   对象、字段、关系、共享类型、主数据（ADR-0103 的版本）、约束（ADR-0102）
├─ Behavior 业务行为   状态、事务（ADR-0100）、规则（ADR-0101）、决策表、审批、异常与返工
├─ Interface 业务界面  页面、模块、应用外壳、专业组件（ADR-0109/0110）
├─ Assemble 装配       数据来源与集成、自动化与流程、AI 函数与智能体（ADR-0112）
└─ Verify   验证与发布  样本试跑、角色检查、候选、迁移计划、交付（ADR-0106/0107/0111）
```

- 每个工作区**复用现有编辑器**，不重写：`ModelWorkbench`（对象/属性/链接）、对象编辑器（状态/动作）、页面编辑器（`EditorWorkbench` 三栏）、流程画布（`FlowCanvas`/`BlockCanvas`）、函数与智能体编辑器、集成编辑器、Releases 工作台。
- **变化的是骨架与导航**：左栏是上述五个工作区 + 应用的资产树（按**业务概念**分组，不按资产类型平铺），右栏是当前资产的 Inspector，中间是编辑器。沿用 ADR-0054 的 Shell 页签模型（Dock）。
- **应用上下文**贯穿五个工作区：当前应用、当前资产、未保存草稿、历史。切换工作区不丢上下文（复用 `DraftSession`/AutoSave 的既有机制，ADR-0096 §9）。
- **导航范围明确分开**：应用工作区与业务资产树服务当前应用；全部应用、全部可读规则、租户交付与资产库服务跨应用查找，两者在同一侧栏中标明范围，不把全部可读规则称作“共享规则”。跨应用入口不暗带当前应用筛选；应用内返回和资产选择共用同一原引用及路由识别。Home、门户、命令菜单可以提供快捷入口，但不增加资产目录、授权或第二份归属信息。保留入口不等于已证明可发现性，仍须按实际任务检查。

### D2 按业务概念分组，不按资产类型平铺

今天的资产树是"对象 / 关系 / 属性 / 页面 / 查询 / 流程 / 函数 / 代码"（ADR-0052 §1 的诊断表原话："菜单是能力清单，不是任务路径"）。

新的资产树按**应用自己的领域词汇**分组，分组由构建者命名（默认按对象类型的命名空间前缀）：

```text
<应用>
├─ 主数据        物料、设备、工作中心、工序、工艺路线
├─ 单据与记录    工单、批次、派工单、报工
├─ 异常与质量    不合格品、返工、检验
├─ 规则          完工判定、返工限制、可加工设备
├─ 界面          工作站、工艺路线图、工单详情、看板
├─ 自动化        到期提醒、质量升级
└─ AI            工艺问答、异常分类
```

**分组不是授权、不是发布单位、不是依赖边界**——它只是导航。资产的真实归属（应用、版本、依赖）仍在定义里。构建者可以重命名、移动分组而不影响任何语义。

### D3 跨编辑器跳转保留上下文（沿 ADR-0052 §3.4 的 "Open in"，扩展到构建侧）

从任意位置一键到相关位置，且**带着当前选中的资产与草稿状态**：

- 对象 → 它的动作/状态/约束/引用它的页面/使用它的规则/它的记录样本；
- 规则 → 它引用的字段与关系、被哪些动作/页面使用；
- 页面 → 它绑定的对象与动作、它使用的查询；
- 运行物 → 产生它的定义版本与决策（ADR-0107 的诊断面）。

**"使用处/被使用处"必须由声明依赖推导**（`Definition.requires`），不靠扫描。

### D4 应用存在感：一个应用从创建到交付的完整轨迹

设计台要能回答"这个应用现在处于什么状态"，而不只是提供编辑入口：

- **新建**：从空白、从模板（ADR-0065 的模块模板）、从已有资产引用（ADR-0058 §2 的"添加已有"）；
- **进度**：模型是否完整、规则是否有未决错误、页面是否绑定有效、是否有未发布的变更（**由定义与候选状态推导，不维护第二份进度**）；
- **交付**：当前活跃版本、待发布候选、上一版本、迁移计划（ADR-0106）；
- **运行**：该应用的运行概览（ADR-0107 D3 的投影）。

### D5 六步流程是可选引导，不是强制路径

- 提供"从业务意图开始"的可选引导（描述业务 → 建议模型骨架 → 建议规则 → 建议页面），走**同一套定义与候选**（沿 ADR-0077 的 Builder Assist 边界：生成草稿，人类审查，同一发布门禁）；
- 引导**可跳过**、可退出、可从中途进入；
- 引导产生的草稿与手工产生的草稿没有区别（**这是硬要求**：否则会形成两套构建路径，ADR-0115 的自举约束会立刻失败）。

### D6 构建者工作台与业务操作台的分工不变

- 构建者在**设计台**（Build 投影）工作；
- 业务人员在**操作台**（Operations 投影）工作；
- 同一份定义，两个投影，权限不同（ADR-0052 §3.1 不变）。

## 2. 不做

- **不做新的一套页面/表单/流程编辑器**：全部复用（ADR-0098 §3 的硬要求之一）。
- **不做"零代码"的强制**：需要代码的地方（ADR-0044 的受控代码）在设计台里有同一入口，不隐藏在别处。
- **不做资产树的分组权限**：分组只导航。
- **不做六步强制向导**（见 D5）。
- **不把设计台做成一个新的平台应用**：它是 Build 投影下应用的组织方式，仍由 `@pkg/build` 贡献（ADR-0052 §3.2 的分类不变）。

## 3. 后果

- `@pkg/build` 的导航从资产类型平铺改为应用上下文（ADR-0052 §1 诊断表里指出的问题的正面修复；ADR-0054 D2 已把七个门户应用收回为一个 Builder，本 ADR 在其内部继续重组）。
- 需要一次真实用户验证：构建者围绕业务意图连续工作是否成立、五工作区划分是否与真实任务匹配、六步引导是否必要。**未验证前不得宣称体验重构完成**（这是 ADR-0098 第三阶段的判据）。
- 资产树的分组由构建者命名，因此需要持久化（属于应用的元数据，随工件版本走）。
- 反向工作：现有 e2e 路线（`web/e2e`）需要随导航变化更新；按 ADR-0082 只保留有证据价值的路线。

## 4. 验收

1. 构建者在一个应用里完成"加一个对象 + 一个状态动作 + 一个页面 + 发布"，全程不离开应用上下文，未保存草稿在切换工作区时不丢。
2. 从对象一键跳到引用它的页面、使用它的规则、产生它的记录样本；从规则跳到它引用的字段与关系。
3. 资产树按业务概念分组，分组可重命名与移动且不影响任何语义（用测试证明：移动分组后定义字节不变）。
4. 应用状态可见：模型完整性、未决错误、当前版本与候选、迁移计划。
5. 可选引导产生的草稿与手工草稿在定义层**完全一致**（同一份字节），走同一候选与发布。
6. 真实用户验证：至少一次由非平台开发者完成的走查，记录任务、断点与结论；未完成前本 ADR 标记为"体验待验收"。

测试：`make check-web` + 一条 e2e 路线（`make e2e SPEC=...`）；视觉与手感由负责人走查，不写像素断言（沿 ADR-0082）。

## 5. As built

资源发现按真实记录类型只建立一次库存观察与分页订阅；流程/自动化、测试计划/评测集不再各自注册同一类型的刷新回调。分类记录和完整资产引用只计算一次，资产树、成员匹配与“添加已有”共用索引，不再为每个成员反复扫描库存。原分类优先级、共享资产归属、完整读取限制、权限和不可用/缺失状态保留；不同页面的可见读取仍各自管理，不宣称 HTTP 或 SSE 连接数量按比例下降。

工程实现落在 `@pkg/build`，应用仍是原 `build.app` / `platform.Application` 工件。真实非平台开发者走查尚未完成，**体验待验收**；下面只声明实现与自动证据的边界。无可见业务页面的已发布应用归入交付与运维类别，主页说明用途，再由明确按钮进入原运行诊断；有业务页面的应用仍直接进入业务页；没有共享变量的单一应用页面不显示实例管理控件，原页面上下文和深链接保留。对象字段引用、动作引用参数、关系和页面模板共用可读的已保存对象描述，草稿优先于旧发布字段；事务当前对象仍使用未保存的编辑内容。模板可绑定草稿动作，引导直接进入应用内模板，页面与模型一起经原候选发布，不要求先单独发布对象。构建期描述不替换运行目录或执行授权；字段别名、公式和固定版本的只读属性保留，状态转换复用原事务投影。关系同批交付使用原联合对象描述和私有安装检查，单独交付仍须有原对象。对象详情打开动作正式编辑器前先保存当前草稿，拒绝时不离开原输入。告警和决策表新建完成时，只在原文档仍是当前文档时跳到已保存资源；用户已选择另一文档则不抢回焦点，原新建标签按原确认规则关闭。页面能保存绑定新增草稿字段，但预览仍读取原发布数据；未发布字段明确提示模型与页面一起发布，不把设计可选性当成运行可用性。

应用角色矩阵通过原 `build.object.edit` 仅提交变更的 access 与当前修订，不再把整条对象记录及只读/派生字段作为编辑输入。对象权限与应用矩阵因此沿用同一部分修改语义，原草稿和其他对象设置保留。

应用内页面预览通过原应用 AssetRef 选择已发布会话，不再把构建 `build.app` 记录 ID 当成运行应用名称。预览的应用/实例参数与构建参数分开，页头和页面调用继续进入同一预览实例，返回原编辑器时保留构建上下文；新实例和关闭实例仍归原 ApplicationSession，不改变仍打开的正式页面共享值。原 ComposedPage 统一阻止预览中的业务写入，展示值、导航和返回仍可交互；已保存但未发布的应用不会因此获得运行定义。`application-context` 已检查这些操作、原定义与业务记录不变，并观察桌面/390px 页头；跨应用切换销毁最后页面时仍清理临时会话，不增加持久状态。

流程与自动化的对象选择同样读取保存中的模型；动作块的参数来自原对象归属方的 `EntityActions`，不再要求先发布动作。已保存草稿替换该对象旧发布动作的编辑选项，其他查询、AI 与计算块保留原来源与固定版本。独立的构建期读取只向 Builder 提供描述，不进入正式能力目录或授予执行资格。来源触发、手动和定时流程的 Validate 使用可读保存对象调用原检查器，发布和候选仍以已安装或本次选定的对象为准。来源记录 ID 按原记录读取授权解析，不误当普通业务字段拒绝；其他路径保留字段检查。页面变量的字段选择与 create/edit 的属性和路径规则也按保存模型检查；单独发布不能借用未选中的模型修改。

项目总览的已保存变更数量与 Changes 共用原 Build 的变更读取，包含应用自身及其成员，不再用 `state=published` 推断草稿一致。清单显示字段、修改人和时间，选定后才读取原值/草稿值，普通记录元数据与版本序号不算定义改动；可移交接入、告警、测试、样本和迁移计划沿原归属方的描述比较，无效声明保留诊断。环境绑定和运行数据不当作可移交定义变更。数据读取不发布、不改变保留声明；批量选择仍进入原 ReleaseReview。Publisher 从 Release history 审阅已封存候选，不再给它一个没有读取权限的草稿变更入口。迁移计划按已有封存资产单独审阅，不因此执行迁移。原 `table` 编辑器在发布请求中映射回同一 `compute` 身份；选择解码、依赖追加与封存共用该身份去重，不把同一决策表同时选为两份草稿。Automation 继续是原 `flow`。

- **应用骨架**：Builder 从应用列表进入一个应用，由同一侧栏切换 Model / Behavior / Interface / Assemble / Verify，并按业务概念选择完整应用成员；工作区是任务视角，不再通过资源种类把同一概念的对象、规则和页面隐藏到不同区。已删除应用导航、ProjectHome 和编辑器上下文条中重复的五区入口；ProjectHome 不再复制主资产树，业务概念编辑面保留自己的选择控件。未选应用时仅主区域列应用。同一应用的导航只更新一个总览页签，资产编辑器各保留自己的页签与输入；旧布局中的重复总览由原布局读取合并。Shell 保留当前应用标题，Model 的对象总览按应用成员收窄。
- **业务概念**：`Application.concepts` 是随应用定义和封存候选保存的导航元数据，每组稳定 ID、标题和原 `AssetRef`，最多 100 组、1000 个分组引用。可命名、重命名、排序、移动资产；未分组资产按业务命名空间归组。分组不进入 `Application.Dependencies`，不增加权限，不改资源定义。移除成员后可保留历史分组引用，当前树只显示实际成员；删除分组返回默认归组。
- **上下文与跳转**：原编辑器页签切换保留局部草稿；共享定义与页面预览也由原 Build 上下文包裹。资产树与编辑器返回栏共用 `studioContext` 识别原资产、引用与工作区，已删除两份独立识别；记录 ID 同时按原编辑器类型判断，页面预览及动作引用保持一致。应用内工作区跳转携带应用与选中资产，跨应用的“全部可读规则 / 租户交付”明确不带应用筛选，原 Verify 内的应用筛选不变。对象可到动作/状态/约束/集合/样本；跨资产的“使用 / 使用处”只读取已发布 `Definition.requires`。未发布草稿的依赖与规则/页面诊断继续由原发布 owner 在候选审阅时计算，浏览器不扫描定义拼第二份依赖图。字段与关系的选择仍由原模型/行为 Inspector 提供。
- **应用轨迹**：空白应用、新建资产、添加已有/共享资产和页面模板继续使用原创建/成员编辑动作。已有资源同时提供可读草稿与已发布的非导航资源，不再限于外部对象；完整 `AssetRef` 的成员不会因没有本地编辑器而消失。无草稿的动作、函数、流程等进入同一只读详情，显示原名称、归属、版本、声明能力与依赖，返回和依赖跳转保留应用上下文；不可读或失效的引用明确提示，不提供无法创建该种类的伪编辑入口。Overview 的成员、缺失与未发布数量来自原记录/定义；Verify 嵌入原 ReleaseReview、迁移工作台与 ADR-0107 的版本/运行/恢复投影，只有共享资源的应用也按应用根创建联合候选。引用不复制定义、不转移归属、不增加权限。候选按应用根从封存字节筛选，筛选在分页前执行；`activeId` 保留原租户激活指针语义。引导、模板与发布面首次打开后保持挂载，隐藏时停止其可见读取。资产种类较多时，原实时读取客户端按服务器登记的条数与字节限制分组订阅，避免发布面增加一种资产便令整个工作区读取失败。
- **可选引导**：业务意图写入原应用 description；模型建议用原 `useNewRecord` / GeneratedForm 的初始值打开原表单，行为建议和页面建议跳到原编辑器/模板。所有步骤可自由进入或跳过。没有新生成定义格式、独立引导进度或发布路径；空项目首先呈现该业务任务入口，可直接跳过；可选择已有业务对象继续状态/操作设计，并进入原数据装配、页面和验证。当前是确定性的构建引导，不宣称已实现开放式 AI 模型/规则生成。
- **替代与棕地**：Build 原 Ontology / Integration / Interface / Logic / Functions / Releases 的类型菜单及 `resourceGroups` 导航实现已退出，编辑器 URL 和资产 identity 保留。Integrator 仍使用原集成入口，Publisher 仍使用原发布入口；原生行业应用不改写。旧应用没有 concepts 时按默认业务命名空间显示，缺省字段省略，不重写旧发布字节或日志；两宿主更新保留原数据卷。
- **入口与打开方式**：Builder 可进入原 Decision table、Automation、Alert、Integration health 与 Release history。Automation 创建/添加到应用时仍是同一 `flow` 引用，按原记录的 `kind` 打开对应编辑器，不新建 AssetKind。Decision table 作为原 `compute` 资产，Alert 作为 `alert` 资产进入应用成员与同一发布候选；保存草稿不会替换运行版本，复制、升级和回退携带完整规则。普通 `useOpenRecord` 使用原 Sheet 与获权 RecordPage 只读查看；审批、工作任务、流程及智能体运行进入原处理页签，显式快速查看仍可使用；收件箱处理与“打开记录”进入原正式页签，`beside` 保留为显式比较。侧栏不增加 Dock 页签、不改变原任务 URL；关闭后原输入保留。异步菜单首次就绪可见，手动折叠在同应用刷新后保留，手机沿原抽屉操作。
- **对象编辑**：删除重复的字段/状态/动作/角色结构树，主区域列表与流程图负责选择，原 Inspector 负责编辑；概览中的四项数量可直接进入对应任务。配置页签统一复用原 ContentTabs，保留已访问面板，支持方向键/Home/End，窄屏换行。对象属性表、权限表与应用角色矩阵统一使用公共 DataTable，选择/行内控件仍写原对象草稿，删除三处手写表格及两项文件豁免。字段创建、状态定义、动作与权限等原入口保留，生命周期面补明确的新增状态按钮；原 URL、草稿 owner、保存和发布方式不变。
- **门户**：普通成员的控制面板保留账户入口，开发者资产库工作区入口仅向构建者与管理员显示；公开参考内容不改变。租户构建应用的 description 进入原应用卡片与搜索。Operations / Build / Admin 现在实际筛选门户类别；仅重排类别的 Rail `Workspaces` 控件、公共参数和示例已删除，旧门户 URL 继续解析。此处取代 ADR-0052 §3.1 的三种工作区投影，不产生三套 Shell 或新的权限模式。
- **验证方法**：Go 定义检查沿 `make check`、`make test-go PKG='./platform ./apps/build'` 及根包 `TestApplicationStudio|TestLanguages|TestAPIContract|TestJointDraft`。公共交互修正通过 `make check-web`、`Workspace.test.tsx` 的文档切换、输入保留与迟到保存导航检查，以及 `workspaces` / `application-studio` 两条浏览器路线：引导创建与手工定义等价、对象状态动作、五区切换保留草稿且只有一个应用总览页签、业务分组与联合候选激活、普通成员只读查看→正式记录。`application-authoring` 另从空白应用完成两对象、引用字段、动作参数、草稿模板和一次联合发布，保存后续新字段、页面绑定与属性变量并核对原发布字节不变；`business-transaction` 保留原事务、审批与外部请求行为。关系首次联合交付、错误引用与约束由 `TestJointDraftsDeliverNewObjectsAndRelationship` 检查。草稿动作描述、普通成员拒绝、手动/定时/状态触发流程、未选择草稿拒绝及页面规则联合发布由 `build_authoring_test.go` 与 `TestPageDraftRulesUseSavedModelsWithoutPublishingThem` 检查；原流程版本恢复、查询固定版本和应用试跑测试继续通过。桌面与窄屏已观察；不外推为真实构建者体验或楼宇供暖客户交付通过。
