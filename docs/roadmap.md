# 路线图

这份文档回答：当前阶段的每一行还剩哪几项，改哪里，怎样验收。
行与“做完你能看到”在 [plan](plan.md)；阶段 4 的灵魂与门槛剧本也在那里，每一项都对着它验收。

## 规矩

- 工程验收遵循[三档验收](README.md#三档验收)，不额外设日常全量门禁。
- 一项一次提交。先写能跑的验收（内核不变量或 trunk 的一步），再动手；做完把这一项删掉，一行的项删完就删掉 plan 里的那一行。
- 一项做完，它定下的规则同一提交写进归属的文档（类型与对象进 [domain](domain.md)，界面进 [ux](ux.md)，分层进 [architecture](architecture.md)），这里只留没做的。
- 路上发现的新项加在本阶段末尾，不另起清单。
- “trunk”指 `frontend/e2e/<模块>.spec.ts` 里的一步；共用的登录与取值在 `e2e/support.ts`。`make trunk SPEC=<模块>` 定点跑，`make trunk-changed` 按改动映射跑。
- 这里写的设计是负责人 11-27 定的；照写的做。
- 这一轮各波都不停下来问（负责人 11-28 定）：哪里挡住改哪里，全部做完才停。对不上代码或做不到时，按 plan 阶段 5 的三句灵魂与下面“承重的要求”自己定，
  理由写进提交的“检查”一节、规则写进归属的文档，接着做下一项。仍要人的只有法律意见、真实付费与对外发布。
- 缺口登记在 `inner-box/`（不入库）。开工把那一条的 `status` 改成 `implementing`，做完改 `verified` 并写上提交号；条目只记证据，设计以本文为准。

## 并行的规矩

- 四波：**开通**（分支 `wave/onboarding`）、**运营**（`wave/operations`）、**硬化**（`wave/hardening`）、**性能**（`wave/performance`），都在平台仓库，各用自己的 worktree；由负责人分派。
- 性能波拥有 `kernel/records`、`kernel/constraints.go`、`host/optimistic_decision.go`、`host/read_image.go` 与 `scripts/check-load.mjs`；5.5a 的测量用它的结果，修复归它。
- 每项做完 `git rebase origin/main`，定点验收通过后快进推送 main；包库同理推它自己的 main。
- 先改自己拥有的路径。被挡住时可以改别人的路径，改到最小；rebase 冲突以对方已推送的为准，在它上面重做自己的那一小块。
- 共享文件只追加或只改自己的小节：`frontend/src/i18n/`、`docs/glossary.md`、本文与 plan（只删自己做完的项）。
- 生成文件（`contract/`、`frontend/src/host/gen/`）谁改宿主类型谁跑 `make contract`；rebase 冲突时重新生成，不手合。
- 各自通过不等于合起来通过：host 行数棘轮、文件改名、新增的类型取值都会在合并后才撞上。rebase 后在合起来的 main 上跑 `make check` 与相关不变量。
- 审查不等人：改 `kernel/`、接受路径、授权或包协议的提交，推送前开一个不带上下文的子 Agent，只给它代码差异。
  它答三句：改的函数还有谁在用；接外部程序的有没有真实运行记录；同类问题别处还有没有。三句的答案写进提交信息的“检查”一节。

## 开通

拥有：`services/security/control` 的租户、身份、邀请与接入申请，`services/security/idp`，宿主的建租户路径，前端的落地页、注册、开通向导与工作区设置，trunk `signup.spec.ts`、`workspace.spec.ts` 里成员与搬家的步骤。
顺序：5.1a → 5.1b → 5.1c → 5.2a → 5.2b → 5.2c。

### 5.1a 注册与验证

- 落地页与注册页是公开路由，从 Astryx 官方模板改造；邮箱加一次性验证码，10 分钟过期、只用一次。
- 邮件走已有的投递通道；本地开发用宿主捕获的邮箱，trunk 从那里读验证码。每个邮箱、每个来源地址有速率限制。
- 账号落在本地身份提供方；同一邮箱再注册是登录，不是第二个账号。

### 5.1b 建工作区

- 名字、语言、时区，选起步应用（市场里的应用包，预选 CRM）。建租户、装包、给创建人管理员，是一条带幂等键的控制面动作链：失败重试不留半个租户。
- 起步应用走市场的同一条安装与审阅路径，不另写一条。

### 5.1c 邀请

- 按邮箱或链接邀请，带角色，可撤回，有到期；被邀请的陌生人走同一个注册页，接受即成员。
- 验收：trunk `signup.spec.ts`，新宿主从落地页到两位同事看到 CRM，十分钟内走完，用时写进提交。

### 5.2a 成员自管

- 工作区设置里管成员、角色与邀请；最后一个管理员不能移除自己或降级。

### 5.2b 导出与导入

- 导出包是该租户的已接受日志、引用的包制品与一份带 SHA256 的清单；不含凭据，导入后连接要重新授权。
- 导入到另一台宿主的新租户：逐条应用已接受映像，不重算、不改格式纪元；完成后比对记录、历史与余额的摘要。
- 验收：内核不变量（导出再导入逐字节一致；篡改清单被拒）加 trunk 一步。

### 5.2c 删除与恢复

- 删除进入 30 天宽限：不能登录、不能写，数据保留；期内管理员或宿主运营可恢复。物理清除仍在 plan“条件触发”，这里不做。

## 运营

拥有：`services/resources/monitoring`（解冻）、用量投影与配额、接受路径入口的配额拒绝、前端 `src/apps/host` 与设置里的用量页、`scripts/check-load*.mjs`、`deploy/` 的备份与恢复。
顺序：5.3a → 5.3b → 5.3c → 5.4a → 5.4b → 5.5a → 5.5b。

### 5.3a 用量投影

- 每租户的记录数、存储字节、按天的写入次数、AI 用量与费用（网关已有结算）、已装包数；由接受结果与网关结算算出，是可丢的读投影，不进接受结果。

### 5.3b 配额是数据

- 套餐是一组配额，由宿主运营给租户。软上限：给管理员的收件箱发一个提问，每类每天至多一次。
  硬上限：新写入在接受路径入口被拒，带可翻译的原因；读、导出、删除与登录不受限。拒绝只有这一处。
- 验收：内核不变量（硬上限只拒新写入；已有数据与读不受影响；提问不重复）。

### 5.3c 用量页

- 工作区设置里每项用量一条进度与本月趋势；点开看到组成它的来源（每个数字都有出处）。

### 5.4a 宿主控制台

- 全部租户的健康、用量、车道占用、错误率与最近一次备份，可筛选排序；暂停与恢复租户（暂停即拒绝登录与写入，数据保留）。
- 运营的每个操作都是控制面的动作，进审计。验收：trunk 一步，暂停一个租户时另一个租户的延迟不变。

### 5.4b 告警

- 车道持有超过 10 ms、错误率、备份失败、磁盘余量；告警规则是数据，在控制台与通知里出现，恢复后自动关闭。

### 5.5a 容量

- 按 plan“之后的阶段”的阶段 5 指标跑三档，每档三轮取中位；数字写进提交与 plan“现在在哪”。
- 达不到第一档的先剖析再修；性能修复按内核的规矩单独提交，用不变量守住复杂度。

### 5.5b 备份恢复演练

- PostgreSQL 全量加日志，恢复到指定时间点，恢复后重放逐字节一致；记录恢复用时与丢失窗口。

## 硬化

拥有：安全评审涉及的修复（跨路径，改到最小）、`make test-security-pg` 的用例、租户 `sim`、`frontend/e2e/erp-marketplace.spec.ts` 的演示、`services/actions/txn_propagate.go`。
顺序：5.6a → 3.x → 4.x → 债。

### 5.6a 安全评审

规则写进 [architecture](architecture.md) 的“安全”一节；每条一个不变量或 trunk 步骤，`make test-security-pg` 覆盖新入口。

- 密钥：全仓没有写死的签名密钥，也没有 `"development-only"` 这类回退（`services/security/control/control_tenants.go` 的令牌密钥）；没有密钥就拒绝。
- 身份：请求头、查询参数、负载都不能设置宿主认定的租户、成员、调用者、批准人与跳数；逐个入口列出并验收。
- 租户隔离：跨租户猜记录号、令牌、上传与导出地址都被拒。
- 外连：连接器、包下载、投递地址拒绝内网与本机地址，除非运营显式允许。
- 上传与渲染：核对类型、大小上限，PDF 与图片渲染隔离。
- 会话：过期、撤销、退出全部设备；写入的跨站请求防护。
- 日志：不打印凭据、令牌、验证码与导出地址。
- 依赖：`govulncheck` 与 `pnpm audit` 进 CI，高危清零。

### 4.x 阶段 4 门槛演示（第 1–6 步）

## 性能

基线（11-25，M3 Pro，隔离 PostgreSQL，`.build/load/gpt-kernel-throughput-20261125/`）：同租户写入 1 并发 77 次/秒、P50 7 ms，64 并发反降到 34 次/秒、
P50 1.4 s，乐观决定 96% 回退到车道里重做；5000 人在线列表 P50/P95/P99 8.5/166/370 ms；成员 33→5000 人时 `member.add` 从 39 ms 涨到 225 ms。
按测得的损失排序，一项做到 plan 阶段 5 指标的第一档就停，下一项。

顺序：P1 → P2 → P3 → P4 → P5 → P6。

### P1 并发写入按读写集判冲突

- 现在乐观决定只要映像之后有任何提交就作废（`host/optimistic_decision.go` 比对全租户纪元、代与位置），无关记录的写入也互相打掉。
- 决定记下读到的记录与按类型的扫描；提交时只核对这份读集合之后有没有被写，没被写就接受，否则重试；回退到车道的次数按原因计数。
- 先给 `scripts/check-load.mjs` 加同租户 1、4、16、64 并发饱和写入 30 秒的一档（5.5a 共用）。
- 验收：新不变量证明并发写入的结果与某个串行顺序逐字节一致、互不相干的写入不回退；K13 竞态通过。
  16 并发 ≥ 300 次/秒且 P95 ≤ 150 ms，64 并发的吞吐不低于 1 并发。

### P2 读的尾延迟

- 5000 人在线时剖析（宿主在本机回环上开着 `/debug/pprof/`）：CPU、互斥与阻塞各一份，修最大的一项再测。
- 嫌疑按代码：每次读都分叉全部应用（`forkReadState` → `ForkApps`，组织状态整份 JSON 编码再解码），列表与编辑争车道。
- 验收：列表 P50/P99 ≤ 12/150 ms，单条读取 P50/P95 ≤ 15/35 ms（第一档）。

### P3 控制面写入随成员数线性变慢

- 成员、资料、令牌、角色存成一整份已接受状态，改一个成员就克隆、编码、校验整份（`services/security/control`）。
- 在当前格式纪元内改成只算改动的那部分；要改存储格式就登记 `inner-box/` 并跳过，不改纪元。
- 验收：5000 成员时 `member.add` P50 ≤ 60 ms，与 33 成员时同一数量级。

### P4 列表的排序与筛选下推

- 只有按编号排序、无筛选、全员可见时才走 PostgreSQL 窗口（`kernel/records/record_queries.go` 的 `FindPlan`）；按日期排序、带筛选或行权限就整表读回内存。
- 先下推单字段排序、等值与区间筛选、行权限；对象集聚合的计数与分组同理。
- 验收：1 万行按日期排序且带行权限的列表 P50 ≤ 12 ms；复杂度不变量证明读取行数与页大小成正比，不随存量增长。

### P5 顺手的小项

- 各项只在剖析或计数证实它在热路径上才做，同一个“内核”提交可以带几项：`Rows.Len` 改成计数查询；`versionPins` 与 `ownedRelations`
  先看写入是否碰到再扫；`/mcp` 目录一次读出全部动作的停用状态；授权里类型摘要按定义纪元预算一次；约束表达式一次提交里只编译一次。

### P6 包的读在并发下慢

- 按定义纪元缓存包视图，审阅与准备只算被问的那个包（从硬化移来）。

## 承重的要求

- 规则只在宿主求值一次：编号、默认值、带出、余额、状态转换、授权都在接受路径里算；界面只读类型描述，不复算、不猜。
- 一项能力一个实现：发号只经 `Caller.Next`（`platform.Sequence`），表达式只经 Expr 求值，授权只经唯一的决定点，汇总只经对象集聚合；不新写第二套。
- 不写行业特化代码：平台里没有库存、采购、会计、CRM 这些词；能力声明在类型、动作、角色上，所有类型同时得到。
- 重放得到同样的字节：宿主算出的号、默认值、带出值写进接受结果，重放读回，不重算。
- 投影可以丢：余额这类由事实算出的东西不进接受结果，格式变了就从事实重建，不写迁移；K47 守着它与事实一致。
- 每项一次提交：先写 trunk 步骤或内核不变量，再实现；改宿主类型后 `make contract`；相关 `make test RUN=K…`、
  改到的 trunk 用例通过才提交。完整静态与构建检查由 CI 执行，发版前才用 `make verify`；没有改动不重跑。
- 每条命令计时，控制在一分钟内；超过的写明命令交负责人在外面跑。

## 后端

后端边界由 `make check` 守住：`platform` 不超过 8000 行且只保留应用 SDK，依赖例外、包名与目录名不一致、能力探测均为零。
宿主为上面某一项补字段或接口时，保持租户数据、凭据引用、授权、当前格式纪元内的历史字节与已接受结果；定点验收，
涉及并发、分叉或恢复时跑 K13 竞态检查或 `make verify-sql`（[architecture](architecture.md)）。
