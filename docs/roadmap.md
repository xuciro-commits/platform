# 路线图

这份文档回答：当前阶段的每一行拆成哪几项，每项改哪里、怎样验收。
行与“做完你能看到”在 [plan](plan.md)；三个核心的规则在 [frontend](frontend.md)“运行时的核心”。

## 规矩

- 一项一次提交。先写能跑的验收，再动手；做完把这一项删掉，一行的项删完就删掉 plan 里的那一行。
- 路上发现的新项加在本行末尾，不另起清单。
- 验收里的“trunk”指在 `frontend/e2e/trunk.spec.ts` 加一步并让 `make trunk` 通过；“夹具”指 `scripts/frontend-seed.json`。
- 每一行做完，负责人按 [design](design.md)“负责人怎样看”的六步看一遍。
- 这里写到的文件、读取与动作都已对过宿主（夹具宿主 18511）；照写的做，对不上先停下问，不自己改设计。

## 接手怎样用模板

模板与组件是设计好的成品，它们的说明就是设计。照下面的顺序用，不跳步。

1. **先找自己的。** `src/pages/` 已有的表现能接住，就只写入口声明，不碰界面代码。
2. **再落官方的。** `pnpm --dir frontend astryx template <id> src/templates/<id>`；先把文件顶部的说明块整段读完。
   说明里的“Extending this template”逐条是约束：哪条保留、哪条因契约不同要改，写在下面各项里；没写到的一律保留。
3. **组件先读后用。** 每个用到的组件跑一次 `astryx component <Name>`，按它给的属性与示例写；文档说“别这样用”的不用。
4. **改造只做三件事：** 示例数据换成契约；补模板缺的表现；改完删掉 `src/templates/<id>`。框架、间距、交互、键盘与无障碍属性不动。
5. **说明不进代码。** 我们不写注释：模板说明里讲的道理，留在这里或 [frontend](frontend.md)，代码里删掉注释。
6. **一个表现服务所有入口。** 新表现做成 `src/pages/` 里的一个声明函数（像 `recordList`、`listPage`），入口只写一句声明。

- 业务对照只读 `study/from-frappe-crm/matrix.md`；`study/**/captures/` 与 `study/**/evidence/` 只为核对某个具体细节时定向看一张。

顺序：2.1.1 → 2.1.2 → 2.1.3 → 2.1.4 → 2.2.1 → 2.2.2 → 2.2.3。

## 承重的要求（2.1 与 2.2 都守）

- 规则只在宿主求值一次：编号、默认值、带出、状态转换、授权都在接受路径里算；界面只读类型描述，不复算、不猜。
- 一项能力一个实现：发号只经 `Caller.Next`（`platform.Sequence`），表达式只经 Expr 求值，授权只经唯一的决定点；不新写第二套。
- 不写 CRM 特化代码：能力声明在类型、动作、角色上，CRM 包只用声明；所有类型同时得到。
- 重放得到同样的字节：宿主算出的号、默认值、带出值写进接受结果，重放读回，不重算。
- 每项一次提交：先写 trunk 步骤或内核不变量，再实现；改宿主类型后 `make contract`；`make check`、`make check-frontend`、相关 `make test RUN=K…`、全量 `make trunk` 通过才提交。

## 2.1 类型语义

目标：线索与商机自动编号，负责人默认是自己，商机选了组织就带出行业与地区，状态走平台状态机。

### 2.1.1 编号

- 灵魂：编号就是记录标识，由宿主在接受时发，唯一且连续；地址里不再有 UUID 或 `chg-…-organization`。
- 类型声明 `naming`（`build.object` 定义，与 `display` 同级），模式沿用序列占位符 `{year}`、`{n:5}`，如 `CRM-LEAD-{year}-{n:5}`。
  编译成一条 `platform.Sequence`（名字取类型名），与事务序列一起登记（`ontology/transaction_sequences.go` 的收集处）。
- 内核：`kernel/protocol/change.go` 的提交校验只对“目标类型有 naming 的 `.create`”放开空标识；
  接受时由该类型的权威调用 `Caller.Next` 取号作标识，号写进接受结果；重放与幂等重试拿到同一个号。
- 事务：`services/actions/business_transactions.go` 新建步骤的标识现为 `receipt.GetChangeId()+"-"+step.Name`；目标类型有 naming 时改为取号。
- 界面：`ActionDialog` 对有 naming 的类型不生成 `crypto.randomUUID()` 标识，提交后用接受结果里的标识跳转；记录页头显示编号。
- CRM：线索 `CRM-LEAD-{year}-{n:5}`、商机 `CRM-DEAL-{year}-{n:5}`、组织与联系人各一条；夹具种子里写死标识的记录保留原标识。
- 验收：内核不变量——并发新建同一类型与重放后编号唯一且连续（并入 K13 竞态）；
  trunk——新建两条商机，编号相连；线索转换出来的组织、联系人、商机地址都是编号。

### 2.1.2 默认值

- 灵魂：新建时没填的字段由宿主按声明补齐；界面预填同一个值，人可以改；手填的值永远优先。
- 字段声明 `default`：字面值，或 `today`、`now`、`member`（提交人）、`setting:<名>`（租户设置，如币种）。
  与已有的 `from` 同处求值（`ontology/compile.go` 里 `f.From` 那段）；`from` 与 `default` 都有时 `from` 优先。
- 类型描述带出 `default`；`ActionDialog` 已从 `field.default` 取初值，把 `member`、`today` 在界面解析成当前成员与今天的显示值。
- CRM：线索与商机的负责人 `default: member`，商机币种 `setting:currency`。
- 验收：trunk——新建线索不碰负责人，保存后负责人是自己；改成别人后保存，仍是别人。

### 2.1.3 引用带出

- 灵魂：选了引用，跟随字段跟着变；人手改过的跟随字段不再被覆盖，直到引用再次变化。
- `from` 已有（[domain](domain.md)“字段可声明 from”），先核对它在编辑时的重算规则是否已满足上面一句，缺什么补什么。
- CRM：商机的行业、地区 `from` 组织；记录页在跟随字段旁用说明文字标出来源（“随组织”），走类型描述，不写死。
- 验收：trunk——商机改组织，行业与地区跟着变；手改行业后再改别的字段，行业不变。

### 2.1.4 状态走平台状态机

- 灵魂：状态只经声明的转换改变；进行中阶段之间自由移动，结束只经动作，回来只经“重新打开”。
- 商机：资格确认…待成交之间自由转换；“赢单”“输单”是动作，输单原因是输单动作的必填参数；结束后只有“重新打开”。线索同理（转化、不合格、无效）。
- 状态仍是字典（参考记录），转换声明在生命周期上；看板拖到结束列走对应动作，需要参数时先开对话框（`BoardView` 已支持）。
- 验收：trunk——拖到输单列弹出输单原因，填了才成；重新打开后回到进行中；结束的商机不能直接改状态字段。

## 2.2 角色与范围

目标：销售只看自己与团队的线索和商机，经理看全部；指派即授权；入口与动作按角色显隐。

### 2.2.1 团队范围

- 灵魂：能看哪些记录由唯一的授权决定点按声明算，读、列表、看板、搜索、聚合、引用解析处处一致，没有第二处过滤。
- 已有：项目角色 `salesrep` 只看负责人是自己的，`salesmanager` 看全部（`6d211a2b2`）。补“团队”：成员所在组织单元（`services/security/organization`）里的同事负责的记录也可见。
- 声明在角色的读取范围上（负责人是自己 / 是同团队成员 / 全部），不在 CRM 里写条件。
- 验收：内核不变量——同一记录在单条读、列表、聚合计数、引用标签里的可见性一致；trunk——两个销售同团队互见，跨团队不可见，经理全见。

### 2.2.2 指派即授权

- 灵魂：把记录指派给人（改负责人）后，对方立刻能读能办，原负责人按范围失去或保留；不需要另授权限。
- 负责人字段（`member`）参与范围求值，指派是一次普通编辑；授权缓存随接受结果失效。
- 验收：trunk——经理把线索指派给销售甲，甲刷新后在列表里看到它并能推进；销售乙看不到。

### 2.2.3 入口与动作按角色显隐

- 灵魂：看不到的入口不显示，做不了的动作不显示或说明原因；判断来自宿主（`/v1/applications` 菜单、记录读取的 `actions`），界面不按角色名写分支。
- CRM 应用菜单按角色裁：销售看不到设置类入口；无权的动作在“更多”里不出现。
- 验收：trunk——以销售登录，菜单只有业务入口，记录页没有管理动作；以经理登录多出报表入口。

## 之后的行

- 界面微件第二批落在各行：每个做成 `src/pages/` 里的一个表现，所有类型同时得到；一个一次提交，trunk 加一步用到它。
  - 2.3 `ImportWizard`：上传 CSV 或 Excel → 字段映射 → 宿主试算 → 逐行报错、原位改错重试。Excel 由宿主解析，前端不引表格库。语言与词汇的整批导入导出也走它与列表导出。
  - 2.4 `ChartBlock`、`MetricCard`：引入 `echarts`；指标卡、漏斗、柱图、折线、环形图，点任一块带着筛选进列表。
  - 2.6 `CalendarView`：`ListPage` 在表格、看板之后的第三种布局，按日期字段排，拖动改日期；从 Astryx `Calendar` 起步。

## 后端

后端边界由 `make check` 守住：`platform` 不超过 8000 行且只保留应用 SDK，依赖例外、包名与目录名不一致、能力探测均为零。
宿主为上面某一项补字段或接口时，保持租户数据、凭据引用、授权、当前格式纪元内的历史字节与已接受结果；用 `make verify` 验收，
涉及并发、分叉或恢复时跑 K13 竞态检查或 `make verify-sql`（[architecture](architecture.md)）。
