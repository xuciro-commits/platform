# 宿主运行 Specification

## Purpose

规定多租户宿主如何协调应用权威、私有决定、持久接受、结果应用、后台工作与租户故障，保证同一业务通过不同入口进入时仍遵守同一写入边界。本模块不定义行业规则、外部系统事务或进程级资源隔离；存储和恢复格式归[存储规范](../storage/spec.md)，当前身份与权限归[访问控制规范](../access-control/spec.md)。

来源：从 Git 历史中的接受结果、宿主职责和架构边界决定提炼，已对照 `docs/Architecture.md`、`capabilities/server/doc.go`、`capabilities/server/host.go`、`capabilities/server/staged_decision.go`、`capabilities/server/accepted_store.go`、`capabilities/server/accepted_plan.go`、`capabilities/server/operations.go`、`capabilities/server/quarantine.go` 和 `capabilities/server/deploy_recovery.go`。这是当前行为约定的文档化，不新增运行路径，也不把历史施工计划视为已实现能力。

## Requirements

### Requirement: 单个业务决定保留唯一权威

宿主 MUST 将业务决定路由到声明该动作与数据类别的原权威，不因多个应用共用宿主或 SQL 事务而扩大该决定的写入权。跨应用诉求 SHALL 使用原协议请求、应答与补偿；本规范不另行定义 K1–K9 语义。

#### Scenario: 应用请求另一个应用完成业务

- **GIVEN** 两个应用拥有不同业务记录，并已声明跨应用协议
- **WHEN** 第一个应用的决定需要第二个应用处理业务
- **THEN** 第二个应用通过自己的协议处理与权威作出决定，调用方不能直接替换其记录或借共用数据库获得跨权威原子性

### Requirement: 新写入先私有决定再持久接受

宿主 SHALL 在私有上下文收集记录、账本收据、编号、定义安装、归属方状态、通知和外部意图，校验全部参与变化后持久接受，仅应用存储实际返回的已接受字节，再公布变化。明确未提交时 MUST 丢弃私有变化；不得静默转入直接写入路径。

#### Scenario: 持久化前失败

- **GIVEN** 一个动作已经在私有上下文产生记录、编号和外部意图
- **WHEN** 接受存储明确返回未提交
- **THEN** 正式记录、编号及运行状态不推进，订阅者和外部目的地看不到这些意图，调用者得到失败

#### Scenario: 发现结果中存在不支持的副作用

- **GIVEN** 决定使用了不能完整封存的写入或外部操作
- **WHEN** 宿主准备接受结果
- **THEN** 宿主拒绝这项决定，不以先修改正式状态或直接发送请求补足缺失内容

### Requirement: 嵌套决定和后续输入各守接受边界

同一顶级输入中的嵌套决定 SHALL 贡献给原私有结果，不能提前独立确认部分状态。异步协议应答、效果结果、工作分发、智能体步骤和用量观察 SHALL 作为后续输入保存各自完整结果，不重新打开先前已接受的决定。

#### Scenario: 外层决定拒绝嵌套变更

- **GIVEN** 嵌套决定已经产生私有记录和通知
- **WHEN** 外层决定校验失败
- **THEN** 这些私有变更一起丢弃，不留下独立成功答复或可发送通知

#### Scenario: 已发送请求收到延迟应答

- **GIVEN** 原请求意图已被持久接受
- **WHEN** 外部应答到达
- **THEN** 宿主按原归属方回调语义接受新的结果，保留原请求与本次应答的身份及关联

### Requirement: 重试复用原请求的持久答复

宿主 SHALL 用具作用域的操作身份和内容摘要区分原操作重试与不同操作。相同身份、相同内容复用原接受或拒绝答复；同身份不同内容 MUST 拒绝冲突，不能因当前规则、定义或业务状态变化重新决定原操作。

#### Scenario: 提交成功后调用者丢失答复

- **GIVEN** 原结果已保存，但调用者没有收到响应
- **WHEN** 调用者以原身份和原内容重试
- **THEN** 宿主找回原答复并完成必要的原结果应用，不重复分配编号、追加业务变更或重新调用外部系统

### Requirement: 每租户写入和应用顺序唯一

同一租户的决定、已安装定义和接受结果应用 MUST 在单写者协调范围内按顺序推进；嵌套调用复用原上下文。宿主 SHALL 在结果完整应用后才允许建立下一次业务读取视图；读取位置的具体一致性要求引用[存储规范](../storage/spec.md)。

#### Scenario: 数据库已提交而内存尚未应用

- **GIVEN** 一项结果已经提交，宿主尚未完成全部参与状态的应用
- **WHEN** 另一个业务请求试图读取或决定
- **THEN** 请求不能观察到新 SQL 数据与旧定义或旧运行状态的混合状态，应用失败则停止该租户并进入恢复处理

### Requirement: 锁外工作必须复核原准备条件

网络、模型、制品和外部计算 I/O SHALL 在租户决定锁外执行。宿主 MUST 在准备时固定操作身份、定义、主体、来源和相关世代，接受返回结果前复核其仍有效；取消、替换或撤权不能被迟到结果越过。

#### Scenario: 模型或计算返回时工作已取消

- **GIVEN** 原工作在锁外等待结果
- **WHEN** 该工作被取消或其世代被替换后收到结果
- **THEN** 迟到结果不能继续执行原工具、写入业务记录或完成新世代，已产生的实际用量仍按原归属方结果语义处理

### Requirement: 提交不明和应用失败停止目标租户

提交状态无法确定、保存结果损坏或接受后应用失败时，宿主 MUST 停止目标租户的新业务与后台执行，保留健康和授权恢复入口。恢复替代实例完成检查前不得重新服务；其他正常租户 SHALL 继续运行，但不据此承诺共享进程、资源或数据库的物理隔离。

#### Scenario: 一个租户不能确定接受状态

- **GIVEN** 同一宿主服务两个租户
- **WHEN** 一个租户的接受提交无法确认是否成功
- **THEN** 该租户停止决定和后台发送，另一个健康租户仍可处理业务；恢复不能仅清除故障标记后继续使用可能部分应用的实例

### Requirement: 后台工作保持结果身份与公平调度

宿主 SHALL 保留工作世代、取消、重试与每应用配额的原语义，并在租户与应用间轮转就绪工作。成功但没有业务、状态、通知、意图或控制变化的定时轮询 MUST 只更新本地下次轮询时间，不追加接受结果或推进 K9 世代。

#### Scenario: 定时任务反复检查但没有结果

- **GIVEN** 一个定时任务的到期检查没有产生任何持久变化
- **WHEN** 宿主完成本次检查
- **THEN** 日志、持久任务前驱和接受世代不变，不广播业务变化，下次按原间隔检查；后续真实结果仍从原持久前驱接受

### Requirement: 宿主角色不替代业务归属方

接入应用 SHALL 通过公共应用 API 或按实际消费需要提供的内部角色获取宿主服务，业务决定仍由原归属方承担。共享结果编码与变化机制 MUST 保留输入、工作、效果和发布的专属语义，不形成能访问整个租户的第二套运行时。

#### Scenario: 新归属方接入现有持久化能力

- **GIVEN** 一个应用需要持久化私有状态并产生工作或外部意图
- **WHEN** 应用通过原宿主角色参与接受结果
- **THEN** 应用声明并校验自身状态，宿主协调持久接受和应用，不为该应用另设提交入口、调度器或业务状态裁决者
