# 运行存储与恢复 Specification

## Purpose

规定正式运行状态、原始接受结果、历史、读取位置、格式兼容与恢复比较的共同约定，使 PostgreSQL 与保留的内存、文件模式不产生不同业务语义。本模块不拥有业务裁决、跨应用事务或新的数据库平台；接受顺序归[宿主规范](../host/spec.md)，读取可见性归[访问控制规范](../access-control/spec.md)。

来源：从 Git 历史中的正式 PostgreSQL 状态、历史成本、映像演进和恢复决定提炼，已对照 `docs/Architecture.md`、`capabilities/server/runtime_state.go`、`capabilities/server/runtime_snapshot.go`、`capabilities/server/records_current.go`、`capabilities/server/record_read_scope.go`、`capabilities/server/snapshot.go`、`capabilities/server/replay.go`、`capabilities/server/internal/records/` 与 `capabilities/server/journal/`。这里记录已核对的存储约定，不承诺固定恢复时限、固定总内存或未经实际负载验证的生产容量。

## Requirements

### Requirement: 正式状态与接受结果同事务保存

PostgreSQL 正式路径 MUST 在原接受事务中保存日志、操作身份与原答复、租户位置、当前记录、历史增量、收据、唯一键及归属方封存的状态变化。存储 SHALL 保存已验证变化，不从查询 JSON 重新推断业务含义，也不以异步投影代替正式状态。

#### Scenario: 接受事务中途失败

- **GIVEN** 一项结果同时包含记录、历史、工作和原答复
- **WHEN** 保存其中一部分失败且事务确定未提交
- **THEN** 整个接受事务回滚，日志位置及全部正式状态保持前驱，不出现已确认答复对应缺失记录的状态

### Requirement: 当前读取使用固定且已应用的位置

同一次协调读取或决定 SHALL 使用一致的数据库事务视图与对应定义，数据库位置 MUST 等于宿主完整应用的位置。已开始的读取保留其原视图；位置不一致时拒绝服务，不能过滤较新行或键来伪造旧视图。取消或读取失败 MUST 释放事务与所持记录锁。

#### Scenario: 旧读取与后续提交并存

- **GIVEN** 一次读取已经固定在位置 S，随后有结果提交到位置 S+1
- **WHEN** 原读取继续查看记录、历史、答复或唯一键
- **THEN** 原读取保持 S 的一致内容，不混入 S+1，也不因过滤新行而漏掉 S 中应存在的旧记录

#### Scenario: 请求取消或数据库读取失败

- **GIVEN** 一次请求持有读取事务和记录访问锁
- **WHEN** 请求被取消或读取出错
- **THEN** 资源被释放，错误不能解释为记录不存在；普通临时错误不使后续正常请求永久等待

### Requirement: SQL 记录按需读取并叠加私有变化

正式 SQL 路径 SHALL 按当前任务读取记录，使用私有覆盖表达本次变更，不常驻完整当前记录、完整唯一键集合或跨请求全局行缓存。查询 MUST 将 SQL 候选与本次私有写集一起交给原条件、派生和权限规则；精确总数、复杂查询、明确的大结果仍可能读取全部候选。

#### Scenario: 查询包含未提交的本次变更

- **GIVEN** 私有决定新增、修改或删除了记录，但尚未接受
- **WHEN** 同一决定再次查询相同集合
- **THEN** 结果包含其私有新增与修改，屏蔽其删除，其他请求看不到这些变化；丢弃决定不影响正式记录

### Requirement: 普通写入只接续本次历史后缀

支持增量历史的新结果 SHALL 保存当前映像与格式、前缀数量、前驱链头、本次后缀和新链头，普通编辑不为封存或应用复制完整历史。各结果族 MUST 验证数量、前驱和确定编码；首次建立旧链、显式历史读取及依赖历史的业务规则仍保留完整读取责任。

#### Scenario: 新后缀声称错误的历史前驱

- **GIVEN** 记录已有已接受的历史前缀
- **WHEN** 待应用结果的历史数量或链头与前驱不一致
- **THEN** 结果被拒绝，不跳过检查、不截断原历史，也不通过提高结果大小限制保存另一份完整历史来掩盖错误

### Requirement: 派生唯一键沿业务原规则维护

唯一键 SHALL 由记录归属方按原空值、零值、复合字段、scope 与归档规则生成，随记录替换删除旧键并加入新键。SQL 检查 MUST 结合固定读取视图与私有覆盖；不可见冲突仍成立，数据库索引不成为第二套业务规则。

#### Scenario: 私有变更违反唯一约束

- **GIVEN** 已有记录占用某个业务唯一键，即使调用者看不到该记录
- **WHEN** 本次决定产生冲突键或随后因其他条件被拒绝
- **THEN** 原约束拒绝冲突且不泄漏隐藏记录，未接受的旧键删除或新键加入不会遗留到正式索引

### Requirement: 格式演进不改写原字节

接受封套、快照、定义版本与业务映像格式 MUST 分别识别。旧结果先按原规则验证原字节，再由映像归属方显式转换；未知格式、尾随内容和未声明的形态变化 SHALL 拒绝。转换不得改变记录身份、修订或创建修改印记，存储不得自行猜测字段改名。

#### Scenario: 旧映像需要转换或格式未知

- **GIVEN** 旧日志包含与当前模型形态不同的业务映像
- **WHEN** 归属方提供合法的旧格式转换，或完全无法识别该格式
- **THEN** 前者在保留原字节和历史身份后生成工作映像，后者明确拒绝；两者都不关闭严格解码或重写原结果摘要

### Requirement: 检查点恢复固定归档并比较正式末态

SQL 检查点 SHALL 保存归属方状态、日志位置、记录摘要和该位置的 SQL 读取归档，恢复只应用原接受结果后缀，再比较当前记录、历史、键、状态值与收据。任一差异 MUST 阻止切换，不得覆盖正式差异数据；可移植完整快照与旧日志恢复保留各自读取路径。

#### Scenario: 检查点之后新增定义并恢复

- **GIVEN** 固定检查点之后的日志新增了流程或其他记录
- **WHEN** 宿主从检查点与后缀恢复
- **THEN** 查询候选同时包含归档与后缀中的记录，恢复不先装载全部当前记录，也不因只枚举归档而漏掉新增定义

#### Scenario: 已有正式 SQL 状态与恢复结果不符

- **GIVEN** 日志与快照能够读出，但正式 SQL 当前值或历史发生不匹配
- **WHEN** 恢复进行固定位置比较
- **THEN** 该租户停止切换并保留差异，不将重放结果覆盖数据库后声称恢复成功

### Requirement: 封存结果恢复与旧输入读取分别负责

新接受结果恢复 MUST 只应用已保存映像和原答复，不重新执行业务规则、授权、模型或外部请求。已存在的旧提交和输入日志 SHALL 保留通过原归属方代码重建的读取责任，不接受新普通写入；此兼容路径不享有封存结果跨规则变化纯应用的承诺，也不是恢复时重发外部请求的许可。

#### Scenario: 同一日志包含旧输入与新结果

- **GIVEN** 租户历史同时包含旧输入格式和已封存的新结果
- **WHEN** 恢复依次读取两种记录
- **THEN** 各走对应版本的兼容路径，新结果直接应用原映像，旧格式不因普通实现已替换而被丢弃，恢复不向外部重发请求

#### Scenario: 旧输入与现有归属方代码不再兼容

- **GIVEN** 日志保留的是旧提交或输入，没有完整的封存结果映像
- **WHEN** 原归属方缺失、输入无法解码或原兼容重建返回拒绝
- **THEN** 恢复停止并报告不兼容，不跳过旧输入、不改写历史，也不把重新调用归属方代码称为不执行业务逻辑的纯应用

### Requirement: 恢复资格只由目标租户决定

恢复 SHALL 检查目标租户固定启动组合、归属方格式和快照格式；其他租户增删或注册顺序不参与资格判断。明确声明格式时构建摘要仅作诊断；未声明格式和旧快照 MUST 保留原二进制限制。新结果格式不自动赋予旧二进制回退资格。

#### Scenario: 同宿主其他租户发生变化

- **GIVEN** 目标租户的启动组合和恢复格式保持兼容
- **WHEN** 其他租户被增加、删除或调整注册顺序
- **THEN** 目标租户仍按自己的资格恢复；目标组合或格式不兼容时仍拒绝，不能用其他租户未变化替代兼容检查

### Requirement: 首次转换和旧写者恢复必须验证来源

存储转换 SHALL 在租户暂停写入、日志位置固定时回填并比较原数据；只有已识别的旧格式遗漏与原接受结果的前驱和后继完全对应时才能更新派生元数据。无法解释的差异 MUST 回滚，不修改原日志、原答复、收据或历史。

#### Scenario: 旧写者没有同步完整 SQL 后缀

- **GIVEN** 原 SQL 位置之后仍有连续的原接受结果
- **WHEN** 兼容恢复补足该后缀
- **THEN** 先独立比较原 SQL 位置，再按原顺序补状态并比较末态；原位置损坏、后缀不合法或期间日志变化均拒绝，不能只推进位置

### Requirement: 可重建投影与外部字节责任分开

只读 SQL 投影和知识向量 SHALL 与正式状态区分，正常启动保留投影并按变化更新。知识检索先按租户、模型及来源筛选，再执行当前读取权限；不足时继续读取候选。完整备份 MUST 包含所需对象字节和部署配置，日志摘要不能替代文件或密钥。

#### Scenario: 检索候选或备份缺少必要内容

- **GIVEN** 向量候选包含无权读取的来源，或备份只保存日志而遗漏被引用的对象字节
- **WHEN** 用户检索知识或尝试恢复相关内容
- **THEN** 无权来源不出现在结果中，候选不足不能绕过权限补足；缺失字节不能被宣称为完整恢复，向量索引可重建也不等于原文件可恢复

### Requirement: 接受结果和外部制品保持有界

接受结果 MUST 保留当前 1 MiB 大小限制，不能以扩大封套容纳整段历史或大型制品。使用外部字节时 SHALL 保存受控引用并验证摘要、归属和可用性；内存、文件和 PostgreSQL 模式使用相同决定与结果规则，不引入永久双写的第二正式状态。

#### Scenario: 决定包含超限内容

- **GIVEN** 决定试图直接封存超出接受结果预算的历史或制品
- **WHEN** 校验结果大小及引用
- **THEN** 不合法结果被拒绝；可以使用的制品沿既有受控引用保存，不通过截断、压缩字段含义或切换直接写入路径取得成功
