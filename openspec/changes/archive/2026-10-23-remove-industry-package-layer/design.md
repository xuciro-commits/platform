# Design

## Context

见 proposal.md。PackageDescriptor 没有行业分类，Blueprint 保存原 owner 的声明闭包，Runtime 描述可信驱动；界面已统一使用 Application blueprint。五个分发包只是以 industry 为前缀的具体应用集合。安装状态、封存内容和初始化请求身份独立于分发目录。

## Goals / Non-Goals

统一产品职责与实际实现，撤下旧分发名称，保留完整资产及历史。此次不增加包类型枚举、行业标签系统、导出工作台、迁移执行器或平台层业务测试；不调整平台现有模块目录及原应用的发布内容。

## Decisions

1. 平台、能力、应用是职责维度，不是三套安装状态机。沿用既有描述符的原语义，不将分类字段变成强制枚举；可复用业务定义仍归应用，技术扩展不能夹带行业固定业务规则。
2. 五份部署描述符仅将 ID、namespace 改为 application 前缀，供暖 guide 中的旧称同步更正。因为新 ID 是新包身份，版本仍为各自首次发布的 0.1.0；不在旧 ID、旧版本下修改封存内容，不做新旧名称映射。
3. 原包退出目录不会删除租户安装。PackageViews 原有 installed 回退读取封存描述，草稿创建继续查安装版本；不修改这些通用路径。新的目录只提供应用包，现有运行无需重新创建草稿、安装或初始化。
4. 初始化请求身份包含包 ID、版本和计划，旧未完成任务必须使用原封存描述符，不可改用新包重试。部署指南明确这一点；本次不执行任何业务初始化。
5. 生成的本地包镜像中旧的五份目录项移到索引外归档，保留文件原字节；不在构建脚本中加入行业前缀清理分支。Git 归档规范保留原决策，当前规范和文档不再依赖该概念。

## Risks / Trade-offs

- 新标识被误作原初始化重试 → 明确禁止自动重建、自动初始化，保留原封存描述符及运行键。
- 名称清理被当成完整 FDE 包制作能力 → 仅交付现有机制的一致职责和分发，独立 FDE 构建及完整界面导出证据不因此补齐。
- 目录撤下后旧安装不可读取 → 使用原有安装脱离目录、制品封存及恢复测试核对，不添加特例。

## Migration Plan

更新当前文档、描述符与注释，验证新目录及原包机制，提交并沿原更新入口更新两台宿主。保留数据卷、租户配置、密钥、已发布资产及旧安装。回退只恢复分发文件和代码版本，不重写业务数据或卸载应用。
