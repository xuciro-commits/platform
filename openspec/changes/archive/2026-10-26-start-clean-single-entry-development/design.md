# Design

## Context

现同一API18495背后启动8495/8490两份Vite；Docker将两口映射同一容器。旧Rauthy配置仍包含行业用户、固定口令及多个回调。浏览器会自动恢复未确认请求，因此全新环境必须改变身份范围。

## Goals / Non-Goals

**Goals:** 一个平台产品入口、同源登录、可重复启动的空白开发基线及真实账号权限验收。

**Non-Goals:** 不重写业务运行、内核或授权引擎；不清理其他项目；不把普通启动改成自动重置。

## Decisions

- 复用原Deployment HTTP服务，在显式配置的身份上游启用/auth固定反向代理；Vite将该路径与API交同一个本地宿主。沿原OIDC提供方验证，不新增网关服务或第二认证实现。
- Docker默认只发布8495。原生热更新保留API18495与PG/IdP/S3回环连接，单一Vite对用户提供8495。移除行业/compat变量、双入口循环及对应检查。
- 一个本地bootstrap生成器持有实际部署配置，写入忽略的.env和.build/local私有目录；生成的Rauthy文件、租户配置和账号说明均0600。普通调用只验证和复用；本轮明确销毁旧状态后初次生成新密钥及随机租户范围。
- 新基线仅admin、builder、user三个中立账号；host管理员独立配置，构建者有构建/集成资格，普通用户没有业务角色。账号与PKCE客户端不导入旧行业配置。
- OIDC会话和PKCE上下文绑定issuer/client；不匹配的旧缓存不参与新登录。租户身份及IdP密钥轮换阻断旧令牌和离线请求；不常规擦除合法发件箱。
- 删除前按Compose项目标签、配置文件和实际挂载核实容器/卷归属。此次删除本仓库全部旧.build状态、旧.env及本项目历史卷/备份；源码、安装包、依赖缓存与其他项目资源保留。新的私有配置在清理后生成。

## Risks / Trade-offs

- 同源代理错误可能使登录不可用 → 测试固定上游路径、回调与真实PKCE登录，并验证旧账号和旧令牌拒绝。
- 普通用户被引导为管理员 → 经原成员目录检查三类账号的实际权限与空白业务状态。
- 重置可能误删其他项目 → 使用核实的精确资源列表，禁止全局prune。
- 已初始化环境被随机覆盖 → bootstrap幂等验证，不提供隐式重生兜底。

## Migration Plan

完成单入口、私有引导和认证缓存修改并检查；停止本项目宿主与容器，清除明确归属的旧卷和本地状态，再生成新配置。按提交版本启动Docker基线，实际验证唯一入口、同源登录、三账号权限、旧身份失效、无旧业务数据及重启保留。同步规范、归档并更新文档，账号说明通过本地私有文件交付。
