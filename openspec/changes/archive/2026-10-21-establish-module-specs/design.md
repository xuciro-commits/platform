# Design

## Context

动机与范围见 [proposal](proposal.md)。仓库保留产品、结构、任务、内核契约和就地操作文档，旧长篇设计已从工作树删除。现行架构边界需要模块化的稳定归属，不能重新散落为逐功能决策文件。

## Goals / Non-Goals

**Goals:** 为现有约定建立四层十二模块的 OpenSpec 基线，让变更沿主责模块更新；保留所有公开入口、历史兼容和未验证限制。

**Non-Goals:** 不改变运行行为、内核语义、SQL 结构或数据，不推进其他队列工作，不把源文件目录机械映射为规范目录。

## Decisions

### 四层导航，完整职责为模块

采用 `kernel / runtime / platform / experience` 层级，各模块聚合相关需求和场景。按小功能平铺会重新形成碎片；只用一份总规范又会混淆归属。层级是文档导航，不是新的微服务或代码依赖要求。

### 当前规范、变更差量和项目顺序分工

现行约定在 `openspec/specs`，变化的设计与局部任务在 `openspec/changes`，优先级仍只归 WorkQueue。Architecture 保留真实结构，详细不变量移到模块；内核精确语义继续唯一归 `contract/spec` 和向量，OpenSpec 不复制正文。

### 使用官方集成，固定工具版本

通过官方 CLI 生成 Codex 的六个核心 Skill，入口统一纳入根 Makefile 并固定版本。与全局安装或另造文档框架相比，贡献者可在仓库内重现命令，项目规则留在 AGENTS 和 config，不修改上游生成的 Skill。

### 提炼历史，按代码核对

旧文档只从 Git 读取；每个模块标明源码定位。只迁入仍成立的约定及有明确承接的历史责任；施工状态、未来设想和旧环境测试结果不搬入规范。本次 ADDED 表示首次记录现有约定，不表示运行时新增功能。

## Risks / Trade-offs

- 把历史提案当成事实 → 核对当前 owner 与调用方，未观察的客户、性能与体验结果不写成保证。
- 跨模块重复定义 → 主责模块保存要求，其余模块链接；AGENTS 只保留简短护栏。
- 变更目录变成第二队列 → 局部任务只服务本次变化；完成后同步归档，项目顺序保留单一入口。
- 格式通过被当成系统通过 → 本次只检查 OpenSpec、链接和差异，不报告业务测试或生产验证。

## Migration Plan

一次性整理这十二个模块的增量规范，按官方 sync 流程形成现行规范，更新入口后集中检查并归档本次文档基线。旧文档保留在 Git 历史；没有业务数据或存储迁移，也不需要部署宿主。
