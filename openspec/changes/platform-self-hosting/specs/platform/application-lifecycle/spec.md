## ADDED Requirements

### Requirement: 系统变更复用原草稿、候选与发布

系统作用域的元对象修改 SHALL 使用与其他应用相同的草稿、候选、依赖检查、发布与安装机制，不新建第二套发布路径。包含源码文件的系统变更 MUST 在批准后由同一发布记录携带文件清单与构建证据；定义类发布与代码类发布共用变更、审批与激活记录。

#### Scenario: 系统对象的联合草稿

- **WHEN** 一次系统发布包含对象、页面与动作的互相引用
- **THEN** 在候选安装视图中完成跨对象引用检查后才发布
- **AND** 不要求先发布临时对象，也不复制应用发布的检查逻辑

#### Scenario: 定义类与代码类混合变更

- **WHEN** 同一个系统变更既改页面又改 TypeScript 组件
- **THEN** 批准后先构建，构建成功才安装定义并激活
- **AND** 构建失败时两类修改都不生效

## REMOVED Requirements

### Requirement: 原生参考能力只有完成替代后才退出

**Reason**: 负责人明确撤回行业参考应用与探针，仓库不再维护需要"完整替代验收"才能退出的原生业务能力；保留的通用机制由平台机制测试与自举验收覆盖。

**Migration**: 删除 `deploy/packages` 中的行业包与对应宿主配置；不生成同名替代应用，不保留隐藏执行入口。平台通用机制的历史兼容责任仍按原规范执行。

### Requirement: 完整替代验收覆盖保留的协同任务

**Reason**: 该要求以 CRM/PMS/MES/ERP 跨应用任务与 `platform/integrations` 为前提；两者随本次变更退出，协同验收不再有对象。

**Migration**: 删除对应业务资产与测试；版本化协议、请求答复与补偿的通用语义仍由协议与宿主规范定义，供后续应用使用。
