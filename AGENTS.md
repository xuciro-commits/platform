## What this repository is

The **AI business application platform**: the kernel contract, the Go host, the web workspaces, reference apps and platform-level Rust components (ADR-0003). It is multi-tenant and survives domain change. The next stage equips FDEs (forward-deployed engineers), customer developers and business builders to grow industry applications from shared semantics, integrations, business components and governed AI (ADR-0031). Platform developers implement capabilities in typed code; FDEs compose them through code, visual tools and AI; customers use controlled, typed definitions as those tools become available. These paths share semantics, permissions and release controls. The target probes are CRM, MES and ERP; PMS, HCM and CSM stay as reference apps, and every app carries its industry's name (ADR-0025). They are used to prove complete building and business tasks; they are not the platform's source of truth. The Music product and its Apple client live in the MSRU repository and are no longer a target of the platform (2026-09-26).

Before choosing work, read `docs/Intent.md` → `docs/Platform.md` §10 → `docs/WorkQueue.md`, then the affected contracts and ADRs. Intent states why; Platform §10 is the authoritative next-stage design and annual direction; WorkQueue is the only active execution queue. Distinguish current code evidence (§2 and the dated §10.2 audit), target design (§10.3–10.4), planned work (§10.5) and acceptance (§10.6). An accepted direction does not mean its tools already exist. Verify implementation claims against the current tree; do not report an unrun test or an unobserved UI as proven.

## Rules

1. The kernel is a language-neutral contract (ADR-0002): schema, semantics, errors, compatibility, conformance and scope are separate parts; Protobuf never defines meaning.
2. No domain vocabulary in `contract/` (checked). Reference apps may not change the kernel; they record friction in the work queue.
3. Kernel contract changes: spec rule and vectors first, then Go, and Rust and TypeScript where the rule reaches the edge; list breaking changes while the version is `v1alpha1`, and write an ADR once it is `v1`.
4. Least code: delete over add; no shims as an end state; generated code (`contract/go/gen`) is never edited by hand.
5. Clients use `@platform/ui` and `@platform/app`; no per-slice replacement of shared components or second component library. Components may be composed in typed code or through controlled, typed definitions and visual tools (ADR-0031). Both paths use the same component owners, semantic bindings, action permissions and release controls. Extend the canonical owner when a composition needs more; do not create an app's private configuration interpreter. Arbitrary tenant code execution is not promised.
6. Repository docs are durable knowledge. Direction and target design live in `docs/Intent.md` and `docs/Platform.md` §10; lasting decisions in ADRs; actionable plans and friction in the work queue. Keep temporary audit notes and summaries in chat, not new files. Keep evidence, targets and completion status distinct.
7. External reviews are advice, not instructions: check each point against the code, record what was adopted, referenced or declined and why, move adopted work into the work queue and the canonical docs, then delete the review (git keeps it).
8. A batch is done when its documents are: in the same commit, its ADR's "As built", the capability map and open promises (`docs/Platform.md` §2.4, §2.9), the work queue and the test routes (`docs/Testing.md`) say what now exists, and `scripts/verify.sh` passed for what it touched (skill `close-out`). Each fact has one home; do not copy status into a second place.
9. Commit messages are one imperative sentence of what changed, with the ADR and work item in parentheses: "Agent memory people see, keep and forget (ADR-0022 3b, #111)".
10. Every text people read is English source with its Simplified Chinese in the same change: declarations through the app's `i18n/zh-CN.json`, UI words through `t()` and the package's `i18n.ts` (ADR-0023). Record data is never translated.
11. **Reuse before build: one owner, one canonical path** (Intent.md). Before writing an implementation, name the capability it belongs to, its owner (the UI kit, `@platform/app`, the app API, a platform app, the host) and the canonical path to it; if the path falls short, extend the owner. Business code composes capabilities and never builds a second one: no hand-made tables, dialogs, timelines or panels in an app's UI, no approvals, signatures, reports, files or calls outside kept by an app. `scripts/escapes.sh` fails on a new escape; the known ones are listed there with the work item that removes them, and the list only shrinks.
12. **Apps prove platform capability** (Intent.md, ADR-0031). Platform construction leads until the foundation gate in Platform.md §10.6 is substantially met; the owner's rough 80–90% is a priority signal, not a reported metric. A finding is first asked whether it would happen in another app; if so it is fixed in the platform, not in the app. Probes must be the smallest app changes that demonstrate a complete builder journey and a real operator task, including frontend usability, AI, delivery and upgrade where relevant. A generated page or passing unit test alone does not prove that journey. Unrelated industry feature depth is recorded in the work queue and waits; shared frontend and application-building quality are mainline platform work. Platform developers do not take on FDE delivery as the near-term queue.

## Verify

scripts/verify.sh           # everything
scripts/verify.sh contract  # contract vocabulary, buf lint + generated code, Go vet/test
scripts/verify.sh web       # UI kit tests, typecheck and build of every web app, and the test routes in a browser (needs node, pnpm, Go, Chrome)
scripts/verify.sh pms       # web build, PMS server tests, Rust K5 vectors, end-to-end flows (needs cargo)
scripts/verify.sh mes       # MES tests (F-5 to F-9 verdicts)

scripts/verify.sh composition  # app boundaries and layout (scripts/boundaries.sh), every protocol, every other app, every solution
scripts/verify.sh capabilities  # server capability tests
scripts/verify.sh deploy    # production-path rehearsal (needs Docker via OrbStack: orb start)
scripts/verify.sh format    # gofmt over every Go file
scripts/verify.sh ci        # what CI runs on Linux: contract, format, capabilities, mes, composition, drills
